# Web Source Diagnosis

把重点放在“内容在哪里”，而不是“还能试哪个工具”。本方法是判断指南，不是固定路由；依据当前证据自行偏离。

## 开始前先回答

1. 用户真正需要的是页面正文、文件、接口数据、页面交互后的状态，还是只需公开事实？
2. 当前观察到底是什么：目标内容、JS shell、登录页、反爬页、错误页、redirect、文件下载，还是空响应？
3. transport success 是否真的带来了 semantic content success？HTTP 200、工具 SUCCESS、页面可打开都不能单独证明已取得目标内容。
4. 已有结果是否足以回答任务？若足够，停止抓取并进入分析。

## 默认判断顺序

1. 对明确 URL，先使用当前环境中最直接且受保护的专用抓取能力一次。
2. 检查返回内容本身，而不只检查状态码或工具状态。
3. 若已取得目标正文/数据，直接分析；不要为“确认一下”再次抓同一来源。
4. 若失败，先给失败分类，再选择一个真正不同的信息来源或 representation。
5. 新动作必须能解释“这次与上次有什么不同”；若 source、参数、表示层和假设都未变化，不重跑。

## 按证据改变 source hypothesis

- **真实正文已到** → 停止获取阶段，进入分析。
- **JS shell / 首屏无正文** → 考虑浏览器渲染、页面运行时或后端数据接口，而不是继续调 HTTP UA。
- **页面内容来自结构化接口** → 优先读取权威接口数据；不要为了保持“网页抓取”形式而解析渲染后的噪声 DOM。
- **明确 HTTP 404 / 已删除** → 停止源站重试；有标题或关键词时再找转载/归档。
- **登录/权限墙** → 不绕过授权边界；使用用户已授权的访问方式或要求必要输入。
- **反爬/网络失败** → 选择一个不同恢复通道；不要只循环改 header、UA、timeout。
- **PDF/文件下载** → 转入对应文件处理能力，不把二进制或下载页当 HTML 正文继续解析。
- **搜索结果已经提供足够公开事实** → 若任务不是必须取得原文，可直接基于可验证来源完成。

## 升级工具的条件

只有当当前证据说明“现有 representation 不能承载目标内容”时才升级工具层。

例如：

- HTTP 返回确定为 JS 壳 → 浏览器是合理升级；
- 原站明确删除 → 搜索转载/归档是合理升级；
- 普通静态 HTML 已有完整正文 → 升级浏览器通常没有新增信息。

不要把“第一次没成功”自动等价成“使用更重的工具”。

## 停止条件

出现任一条件即可停止继续获取：

- 已取得回答用户目标所需的正文/数据；
- 源站明确不存在，且缺少可定位的转载/归档线索；
- 安全、权限或用户授权边界阻止继续；
- 新候选动作不会改变 source hypothesis，也不会带来新的可验证信息。

## 验证

完成获取后至少确认：

- 内容主题与用户给出的 URL/标题/目标一致；
- 不是错误页、登录页、导航壳或搜索摘要冒充原文；
- 若声称“全文”，当前内容覆盖确实足以支持该说法；
- 若用了转载/接口/归档，清楚区分它与原始页面的来源关系。

## 反模式

- 同 URL、同参数、同工具重复调用而没有新证据；
- HTTP 200 就宣称已抓到正文；
- 没有 source hypothesis 时随机在 fetch / browser / shell / search 间切换；
- 用 shell/curl 绕过受保护网络工具的安全边界；
- 已取得正文后再抓一次“验证”；
- 原站已经明确 404 后继续换 UA 或猜隐藏端点；
- 把抓取问题升级成长篇推理，却不先检查真实返回内容。

## 方法边界

不要让本方法变成“网页永远先浏览器”或“永远先 web_fetch”的固定路由。首选动作由当前工具面和可观察事实决定，关键约束只有两个：先识别 representation，失败后改变假设而不是盲试。

## 可沉淀内容

任务结束后，只在出现可迁移的新模式时沉淀 Experience/Method，例如某类 representation 的可靠识别信号。站点固定接口、解析字段、重定向细节等确定性机制应进入专用工具或站点 Skill，而不是要求模型长期记忆。
