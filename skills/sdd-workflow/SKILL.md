# SDD 工作流编排（sdd-workflow）

将 SDD 四阶段工作流（需求规格 → 技术设计 → 任务规划 → 编码实现）固化为编排规则：规划先行、逐关审批、文档传递。本 skill 只负责"何时调用哪个子 agent、传什么、产物放哪、何时放行"，不替代子 agent 内部职责，不代替用户裁决。

## 常量区（全文单点声明）

- `SPEC_ROOT` = `.codeartsdoer/specs/` —— 三件套统一存储根目录
- `SKILL_DIR` = `skills/sdd-workflow/` —— 本 skill 目录
- `DOC_FILES` = `spec.md` / `design.md` / `tasks.md` —— 三件套，文件名固定
- 全文编排规则一律引用上述常量符号；后续章节禁止出现路径字面量，路径调整仅改本区
- 写路径白名单：阶段 1-3 编排期间仅允许写 `{SPEC_ROOT}` 与 `skills/` 下的路径，禁止写 `src/`、`tests/` 等源代码

## 附属参考文件（按需加载，不内联复制）

- `references/stage-prompts.md`（R1）：四阶段 Task 调用 prompt 模板、降级角色化代产模板与占位符定义。发起任何阶段 Task 调用或经授权降级代产时加载。
- `references/doc-conventions.md`（R2）：三件套元信息头格式、审阅状态流转、断点续跑决策表、变更传播回退规则。产物落盘校验（含降级代产溯源标注写入）、断点判定、审批状态回写时加载。

## 一、触发条件

1. **显式触发**：用户表达"走 SDD / 规格驱动 / 四阶段流程开发某需求" → 触发本 skill 并进入初始化。
2. **隐式触发**：用户描述的开发需求同时满足以下三项时，建议走本流程并征求用户同意：
   - 属新功能或增强（非缺陷修复、非一次性问答）；
   - `{SPEC_ROOT}/` 下尚无该需求的既有 spec 目录；
   - 用户未指定其他开发流程。
3. **防误触发**：用户明确要求"直接改代码 / 跳过规划 / 不要写文档"时不触发，按用户指令执行。
4. **触发后动作链**：环境校验（二）→ feature_name 生成与查重（三）→ 断点判定（四）→ 呈现流程计划等待用户确认；确认环节用户补充的澄清、成功标准与边界表述按三A记入澄清记录（clarification log）。

## 二、环境校验

1. **校验项**（进入阶段 1 前逐项确认）：① Task 工具可用；② `spec-requirement-agent` 存在；③ `spec-design-agent` 存在；④ `spec-task-agent` 存在。
2. **失败处置**：任一项缺失即终止初始化，逐项列出缺失能力（如"缺少 spec-design-agent，无法启动 SDD"）；零副作用——不创建任何目录与文档。
3. **禁止项**：环境校验失败（启动前）时不得以主 Agent 身份模拟子 agent 产出文档，只如实告知缺失项。该禁止项仅约束启动前校验场景；运行期阶段 1-3 规划子代理通道失败且按第八章允许的自动重试耗尽后的代产，须经用户显式授权，两类情形不得混同。阶段 4 执行通道失败走 8.4 独立处理。

## 三、feature_name 生成与查重

1. **提炼约束**：从用户需求中提炼，≤20 字符、仅 [a-z0-9_]、可辨识对应业务功能（例：需求"SDD 工作流 skill" → `sdd_workflow_skill`）。
2. **查重规则**：与 `{SPEC_ROOT}/` 下既有目录仅做目录名比对（存量目录只读兼容，不读取内容）；同名冲突追加数字后缀（`_2`、`_3`…）并告知用户冲突消解结果。
3. **无法提炼**：需求宽泛或语义模糊时，给出 2-3 个候选名供用户选择，不擅自定名。
4. **目录创建失败**：如实报具体路径与失败原因（附检查权限/磁盘建议），不静默降级到其他目录。
5. **禁止项**：用户确认 feature_name 前不得发起任何 Task 调用。

## 三A、澄清记录（clarification log）

1. **定义**：用户在需求提出、流程启动确认、feature_name 确认各环节给出的澄清、成功标准与边界表述的逐字记录。
2. **采集纪律**：只记用户原话；编排层转述须经用户复述确认后方可记入；用户更正时以较新表述覆盖旧记录。
3. **传递**：作为阶段 1 输入要素⑤传入（R1 §二差异表）；无澄清时显式传"无澄清记录"标记，不得省略该要素。
4. **生命周期**：不新建独立状态文件；当前流程会话内保留用户原话。若流程中断，续跑时优先从运行环境可访问的现有会话/EventLog/最近用户表述恢复可证明的澄清；spec.md 已生成后以已落盘 spec 为 durable 语义权威。若关键澄清无法恢复且会导致不同执行路径，须向用户重新确认，禁止猜测或静默丢失。

## 四、初始化与断点续跑

1. **探测**：环境校验通过后探测 `{SPEC_ROOT}/{FEATURE_NAME}/` 下三件套存在性与元信息头审阅状态。
2. **断点判定**：按 `references/doc-conventions.md` 断点续跑决策表（首行命中即止）确定续跑起点；决策表以 R2 为单一真相源，此处不内联复制。续跑语义以已落盘产物为主，并按三A第 4 条恢复可证明的用户澄清；无法恢复且会改变执行路径时再向用户确认。
3. **呈现与确认**：全新流程呈现"feature_name + 四阶段流程计划"待用户确认；恢复流程报告"续跑起点 + 判定证据（各文件存在性与状态）"待用户确认。
4. **禁止重复生成已批准产物**：已"已确认"的文档不重新生成，从其后续阶段或审批关卡续跑。
5. **状态仲裁**：头部为"已确认"但用户当次否认曾批准时，以用户当次声明为准——回退该状态并重新进入对应审批关卡，提示可能的历史会话歧义。
6. **一致性自检**：续跑前按 R2 比较审阅状态、内容摘要/可用指纹与可证明 provenance；若内容相对已知版本变化且来源无法证明，则暂停并请用户确认版本有效性。不得仅凭日期或内容变化猜测是何工具/人员造成。

## 五、四阶段编排规则（含文档路径约定）

### 5.0 统一编排模式

每阶段固定执行：前置状态检查 → 按 `references/stage-prompts.md` 对应模板组装 prompt（引用不内联）→ 发起 Task 调用 → 校验回执与产物落盘（预期文件存在且非空、头部含元信息块）。

### 5.1 阶段 1 · 需求规格（spec-requirement-agent）

- 前置：用户已确认启动流程与 feature_name。
- prompt 五要素齐备（按 R1 阶段 1 模板组装）：用户需求原文（逐字）、项目描述（README/工程上下文摘要）、steering context 路径（如有）、feature_name、澄清记录（按三A，无则传"无澄清记录"标记）；禁止仅传需求原文。
- 产物：`{SPEC_ROOT}/{FEATURE_NAME}/spec.md`。

### 5.2 阶段 2 · 技术设计（spec-design-agent）

- 前置：spec.md 存在且审阅状态"已确认"。
- prompt 必含 spec.md 绝对路径与"先读取再设计"指令（按 R1 阶段 2 模板）；修订回路时附修改意见原文与用户版本差异说明。
- 产物：`{SPEC_ROOT}/{FEATURE_NAME}/design.md`。

### 5.3 阶段 3 · 任务规划（spec-task-agent）

- 前置：design.md 存在且审阅状态"已确认"。
- prompt 必含 design.md 绝对路径与"先读取再规划"指令（按 R1 阶段 3 模板）。
- 产物 tasks.md：每任务标注 executor（coder / bug-fix-agent）、priority、涉及文件、验证方式。

### 5.4 阶段 4 · 编码执行（分流）

- 唯一放行前置：三件套全部存在且审阅状态均为"已确认"；任一未获批即调用执行 agent 视为违规。
- 分流：nature=defect → bug-fix-agent；nature=enhancement → coder。
- 并行策略：涉及文件不重叠的任务并行分组；同文件任务强制串行。
- 每任务完成须过项目验证（ruff + pytest）；全部回执（成功/失败/阻塞）汇总呈报用户。
- 失败任务处置：阶段 4 不自动重试失败的执行任务；失败任务及其依赖/文件冲突链保留现场等待用户指令。已由获批 `tasks.md` 授权且与失败链机械独立的任务继续执行并汇总，不因无关失败全局冻结。

### 5.5 顺序刚性与调用纪律

1. 四阶段严格顺序推进：禁止跳阶段（无 spec 直接 design）、禁止合并阶段（一次调用同产 spec+design）。
2. 任意时刻阶段 N 调用发生，则阶段 N-1 产物必已获批。
3. 修订回路：重调当前阶段子 agent 时 prompt 附"基于现文件修订 + 修改意见原文"。
4. 编排 prompt 中不得复制子 agent 内部模板正文，只传路径与上下文。

### 5.6 文档路径约定

1. 三件套仅存于 `{SPEC_ROOT}/{FEATURE_NAME}/`，文件名固定为 `DOC_FILES`，禁止散落 `docs/` 等他处，禁止多余副本。
2. 阶段间传递只经文档文件路径引用（子 agent 先读取再产出），禁止以对话转述摘要替代文档作为阶段输入。
3. 禁止删除、移动、重命名已生成文档；修订仅允许原文件内容更新。
4. 用户手工编辑过的文档为权威版本；后续修订必须基于用户版本并先呈现差异说明。
5. 元信息头格式与审阅状态流转一律按 `references/doc-conventions.md` 执行。

## 六、审批关卡规则

### 6.1 强制关卡

1. 阶段 1/2/3 产物各自构成强制审批关卡；通过条件仅为用户明确肯定（确认 / OK / 通过 / 没问题）。
2. 沉默或转移话题不得视为批准；未明确确认不发生下一阶段调用。
3. 用户长时间中断后返回：重新呈现待审批产物预览与断点位置，等待指令。

### 6.2 预览三要素（产物生成当轮即呈现）

① 产物文件绝对路径；② 要点摘要 3-5 条、300 字内；③ 明确审批询问语。审批询问轮次内容单一聚焦，禁止与其他任务指令混排。

### 6.3 四分支裁决语义

| 裁决 | 表述特征 | 处理 |
|------|---------|------|
| approve | 明确肯定词（确认/OK/通过/没问题） | 状态回写"已确认"，解锁下一阶段 |
| revise | 含修改意见 | 当前阶段修订回路：重调子 agent 修订 → 重新预览 → 再次询问，循环至明确批准 |
| rollback | "回到阶段 m"类表述 | 变更传播提示（列出 m 之后全部已生成产物及失效影响）→ 用户确认回退范围 → 受影响产物状态回写"待用户确认"，文件不删除 |
| cancel | 中止表述 | 保留全部产物终止；断点天然存在于目录状态，同名再触发可续跑 |
| 模糊（先这样吧/再看看） | 无法判定批准或修改 | 按未批准处理；发起一次二选一式澄清询问；澄清后直接执行，不重复展示选项 |

### 6.4 状态回写纪律

1. 回写权仅归编排层：仅改头部审阅状态字段，禁止整文件重写（防破坏用户手工编辑）。
2. 子 agent 无权写"已确认"；产物生成时头部一律"待用户确认"。
3. 回退传播：回退阶段 m 获批后，m 之后所有已存在产物状态强制回写"待用户确认"（内容未变也回退，因上游约束已失效），文件不删除。

## 七、异常处置

| 场景 | 系统行为 | 用户感知 |
|------|---------|---------|
| 阶段 1-3 子 agent 调用失败/超时 | 如实报告失败阶段与原因；保留已完成部分产物；允许自动重试至多 1 次；重试耗尽后当轮按第八章发起降级授权询问（失败详情 + 范围选项），零副作用暂停。此自动重试规则不适用于阶段 4 执行任务。 | 失败阶段、原因、已保留产物路径、降级授权询问（拒绝时可再选重试/中止） |
| 产物校验失败（回执成功但文件缺失/为空） | 判本阶段失败，不进入审批环节；报"阶段 N 产物缺失：{路径}"并重新调用 1 次；重调仍失败后当轮按第八章发起降级授权询问 | 缺失路径与重调询问 |
| 产物与前置冲突（如 design 与已批准 spec 相悖） | 预览时标注冲突点，提请用户注意；只标注不裁决，由用户决定驳回修订或放行 | 预览含冲突提示清单 |
| 阶段 4 执行任务失败 | 不自动重试该失败任务；保留失败现场并暂停其依赖/文件冲突链。已由获批 `tasks.md` 授权且机械独立的任务继续执行并汇总；用户仅裁决失败链后续（重试/修订 tasks.md/中止该链）。 | 失败任务及依赖链清单、验证输出、独立任务完成情况与失败链后续选项 |
| 目录创建失败 | 报具体路径与失败原因（检查权限/磁盘建议），不静默降级 | 错误提示含路径与建议 |
| 外部改动/状态不一致 | 暂停流程，请用户确认版本有效性后方可继续 | 版本确认询问 |

## 八、无子代理降级模式

### 8.0 定位与总则

1. 降级是阶段 1-3 规划子代理编排的异常分支：规划子代理通道可用时必须优先 Task 调用，降级仅为规划子代理通道失败且允许的自动重试耗尽后的补救路径。阶段 4 执行通道失败不适用本总则，按 8.4 独立处理。
2. 不提供默认绕过子代理的常驻选项，禁止为省事主动降级。
3. 降级只是"谁执笔"的变化：流程骨架、阶段顺序、审批关卡与状态回写语义一分不变。

### 8.1 降级触发判定

1. 失败信号识别（三类）：①调用失败/超时/轮数耗尽（Task 调用报错、子代理达对话轮数上限未产出产物）；②通道异常跑偏（进程行为与预期会话不符、任务记录丢失致回执不可查）；③回执成功但产物未落盘（预期文件缺失、为空或头部缺失元信息块）。失败形态无法归类时按"调用失败"兜底并如实记录原始错误信息。
2. 重试前置：本条仅适用于阶段 1-3 规划子 agent。判定降级前允许自动重试至多 1 次（沿用第七章异常处置）；重试成功则按正常模式继续，不进入降级询问。阶段 4 执行失败按 5.4/第七章 failed-task hold 处理，不套用本条。
3. 产物校验为准：失败判定以预期产物文件存在且非空且头部含元信息块的落盘校验为准，子代理回执文本不得替代校验（与 5.0 统一编排模式同一口径）。
4. 零副作用暂停：进入降级授权询问前流程必须处于暂停态——不产生新的目录与文档写入，不发起下一阶段任何调用。
5. 禁止项：未重试先问、跳过授权直接代产均禁止。

### 8.2 降级授权与范围

1. 授权询问四要素当轮呈现：①失败阶段与类型及原始错误摘要；②已重试情况（1 次自动重试已执行）；③降级方案说明（主 Agent 角色化代产 + 产物带溯源标注 + 审批关卡与正常模式完全一致）；④授权范围选项。
2. 范围三选项：仅当前失败阶段 / 本流程剩余全部规划阶段（阶段 1-3）/ 拒绝降级；用户自定义范围表述时，复述确认一次后按其表述执行。
3. 授权显式性：仅用户明确肯定表述生效；沉默、模糊表述（"先这样吧/再看看"）按拒绝处理，发起一次二选一澄清（与 6.3 裁决表"模糊"行同口径）。
4. 范围明示与记录：授权生效当轮回复明示"已获授权的降级范围"，作为后续代产对照依据；授权仅当前流程会话内有效，不落盘为独立状态文件。
5. 拒绝处置：询问用户后续指令（再次重试 / 中止保留断点），不强行代产也不自动中止。
6. 禁止项：禁止与阶段产物审批合并询问（一次对话只解决一个决策）；禁止预设"推荐降级"倾向性引导。

### 8.3 角色化代产

1. 角色化：获授权后按 `references/stage-prompts.md` 第五节模板以对应阶段角色自产（引用不复制模板正文），产物格式与子代理产物无差异（spec 九章结构 / EARS 格式 / 任务标注）。
2. 输入一致性：先实际读取前置已获批产物与失败阶段既有中间产物，禁止凭对话记忆转述替代读取文档；前置产物缺失时暂停，按断点续跑决策表回退判定，不凭空编造。
3. 落盘一致性：落盘至 `{SPEC_ROOT}/{FEATURE_NAME}/` 对应文件名；头部元信息块合规并按 `references/doc-conventions.md` 1A 写入溯源标注，审阅状态一律"待用户确认"。
4. 审批复用与双身份：预览三要素、四分支裁决、状态回写纪律复用第六章，语义零修改；代产时身份为"代产者"（头部只写"待用户确认"），用户批准后切换回编排层身份执行状态回写。
5. 既有产物衔接：在原文件内容更新或新建缺失文件，禁止删除重建；已获批前置产物只读取不修改。
6. 禁止项：头部不得写"已确认"；不得省略先读取步骤；不得越授权范围代产。

### 8.4 红线守护

1. 混合模式：同一流程允许部分阶段子代理产出、部分阶段授权代产；每产物按其自身溯源标注记录，混合不影响审批与续跑判定。
2. 环境恢复与切回：降级期间通道恢复，默认续用已授权范围完成剩余规划阶段；用户可主动要求切回子代理模式，自指令当轮生效，已代产产物溯源标注不回改。
3. 阶段 4 独立处理：降级授权默认不覆盖执行阶段；三件套全部获批后执行通道仍不可用时单独询问——选项：主 Agent 直接执行 enhancement 编码任务（defect 类需用户逐项明确授权或转人工）/ 等待环境恢复 / 中止。
4. 降级状态呈报：每次代产预览注明代产与溯源标注；交付汇报汇总"本流程主 Agent 代产产物清单"。
5. 续跑授权不跨会话：断点续跑按 `references/doc-conventions.md` 断点续跑决策表判定（零改动）；涉及代产点且通道仍失败时，重新发起降级授权询问。
6. 禁止项：禁止以降级为名合并阶段、跳过审批、绕过状态回写。

## 运行边界

1. 不替代子 agent 内部职责（文档撰写、格式校验、模板遵循由子 agent 自治完成）；唯一例外为经用户显式授权的第八章降级代产，授权与审批红线不变。
2. 不负责 SDD 流程之外的工程质量活动（代码评审、CI/CD、发布管理、经验沉淀）。
3. 不迁移、不治理 `{SPEC_ROOT}/` 存量 feature 目录（只读兼容，仅目录名比对查重）。
4. 任何情况下不绕过用户审批推进阶段，禁止"一口气跑完四阶段"的自动直通模式。
