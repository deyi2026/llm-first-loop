# SDD 三件套文档数据契约（doc-conventions.md）

> 用途：三件套（spec.md / design.md / tasks.md）的元信息头格式、审阅状态流转、断点续跑判定与变更传播回退规则。编排层在产物落盘校验、断点续跑判定、审批状态回写时按本契约执行。

## 一、三件套元信息头格式（精确样例）

三件套头部必须含引用块（`>` 前缀）元信息，四项必备：类型、日期、范围（所属 feature 目录）、审阅状态。精确格式如下：

**spec.md 头部：**

```markdown
> 类型: 需求规格 | 日期: {YYYY-MM-DD} | 范围: {SPEC_ROOT}/{FEATURE_NAME}/
> 审阅状态: 待用户确认
```

**design.md 头部（类型为"技术设计"，增"对应规格"回指）：**

```markdown
> 类型: 技术设计 | 日期: {YYYY-MM-DD} | 范围: {SPEC_ROOT}/{FEATURE_NAME}/
> 对应规格: spec.md（同目录） | 审阅状态: 待用户确认
```

**tasks.md 头部（类型为"编码任务规划"，增"对应规格 + 对应设计"回指）：**

```markdown
> 类型: 编码任务规划 | 日期: {YYYY-MM-DD} | 范围: {SPEC_ROOT}/{FEATURE_NAME}/
> 对应规格: spec.md | 对应设计: design.md | 审阅状态: 待用户确认
```

说明：

1. `{YYYY-MM-DD}` 为产物生成日期；审阅状态仅两值：`待用户确认` / `已确认`，随审批流转更新。
2. 范围字段为产物所属 feature 目录路径；design/tasks 的回指字段固定指向同目录上游文档。

### 1A 溯源标注增量字段（可选）

1. 字段契约：可选字段`产出方式`，追加于三件套头部引用块内且与审阅状态同块；取值仅两枚举——`子代理产出`（默认值，允许省略）与`主 Agent 代产（降级模式）`（代产产物必填）；禁止删改代产标注、禁止给子代理产物反向添加代产标注。
2. 完整头部示例（代产产物）：

```markdown
> 类型: 需求规格 | 日期: {YYYY-MM-DD} | 范围: {SPEC_ROOT}/{FEATURE_NAME}/
> 产出方式: 主 Agent 代产（降级模式） | 审阅状态: 待用户确认
```

3. 不变量与落点：本字段为可选增量，不破坏既有四项必备字段解析；不参与断点续跑判定（§三决策表判定输入保持"存在性 × 审阅状态"两维不变）；状态流转表（§二）对溯源字段零感知（回写仍仅改审阅状态字段）。本小节为第一节增量子小节，置于 §一说明之后、§二之前；§一既有三个精确样例正文不重写。

### 1B 日期字段更新规则

1. 更新时机：仅产物生成、重新生成、修订回路落盘时把日期字段更新为本轮生成日期；审阅状态回写（含回退传播）、用户手工编辑一律不更新日期。
2. 与一致性自检联动：日期仅是展示型元信息，不用于推断改动来源。§三一致性自检可比较审阅状态、内容摘要/摘要指纹与可用 provenance；发现内容变化时只报告"内容已变化/来源未知或可证明来源"，不得用"日期未变"归因为外部工具。
3. 不变量：本小节不改变四项必备字段与 1A 溯源字段的解析，不参与断点续跑判定；为第一节增量子小节，置于 1A 之后、§二之前。

## 二、审阅状态流转表（两态）

状态机仅两态：`待用户确认 ⇄ 已确认`。

| 事件 | 状态变化 | 执行者 | 约束 |
|------|---------|--------|------|
| 子 agent 生成/修订产物 | （写入）待用户确认 | 子 agent | 头部一律写"待用户确认"，无权写"已确认" |
| 用户明确批准（approve） | 待用户确认 → 已确认 | 编排层 | 仅批准当轮执行；仅改头部状态字段，禁止整文件重写（防破坏用户手工编辑） |
| 回退传播（rollback 获批） | 已确认 → 待用户确认 | 编排层 | 回退阶段 m 之后所有已存在产物强制回写（规则见第四节） |
| 状态与用户声明冲突 | 已确认 → 待用户确认 | 编排层 | 用户当次否认曾批准时，以用户当次声明为准，回退状态重新进入对应审批关卡 |

## 三、断点续跑判定决策表

判定输入 = 三件套各文件存在性 × 元信息头审阅状态。按优先级自上而下匹配，**首行命中即止**：

| # | spec.md | design.md | tasks.md | 判定续跑起点 | 依据/说明 |
|---|---------|-----------|----------|-------------|-----------|
| 1 | 无 | 任意 | 任意 | 阶段 1（全新生成） | 无规格则一切从头 |
| 2 | 有·已确认 | 无/未确认 | 任意 | 阶段 2（生成或重生成 design） | spec 已获批即约束成立 |
| 3 | 有·已确认 | 有·已确认 | 无/未确认 | 阶段 3 | design 约束成立 |
| 4 | 全部有且已确认 | — | — | 阶段 4（执行分流） | 三关卡全过 |
| 5 | 有·待用户确认 | 任意 | 任意 | 阶段 1 审批关卡（不重生成，直接重呈预览） | 产物在、审批悬置 |
| 6 | 有·已确认 | 有·待用户确认 | 任意 | 阶段 2 审批关卡 | 同上类推 |
| 7 | 有·已确认 | 有·已确认 | 有·待用户确认 | 阶段 3 审批关卡 | 同上类推 |

**仲裁规则**：文件头部状态为"已确认"但用户当次否认曾批准时，以用户当次声明为准——回退该状态并重新进入对应审批关卡，同时提示可能的历史会话歧义。

**一致性自检**：续跑前对比审阅状态、文档内容摘要/可用指纹与可证明 provenance。发现内容相对已知版本变化但来源无法证明时，暂停并向用户确认版本有效性后方可继续；日期字段不得作为改动来源判定依据。

## 四、变更传播回退规则

1. **触发**：用户要求回退到阶段 m（m < 当前阶段），经变更传播提示（列出 m 之后全部已生成产物及失效影响）且用户确认回退范围后生效。
2. **状态回写**：m 之后所有已存在产物的元信息头审阅状态强制回写为"待用户确认"——即使内容未变（上游约束已失效）。
3. **文件保全**：失效产物一律不删除、不移动、不重命名；后续经重新生成（原文件内容更新）或用户确认沿用。
4. **回写纪律**：仅改头部状态字段，执行者为编排层，禁止整文件重写。
