# 网页抓取快速收敛（web-fetch-fast）

用户发来网页/文章链接要求分析、摘要、总结、展开全文时，目标是**一次抓取优先、失败快速分流**。不要让模型把推理能力消耗在 UA、curl、redirect 和站点字段试错上。

## 核心原则

1. **先调用一次 `web_fetch(url)`**。不要先搜索标题，也不要先手写 curl。
2. **成功即分析**。正文已到后不要二次抓取验证。
3. **失败只按真实回执分流一次**。参数、URL、恢复通道都没变化时，不重复同一动作。
4. **网络安全边界属于程序层**。不要用 `execute_command` + curl 绕过 `web_fetch` 的 SSRF、redirect 和 DNS-rebinding 防护。
5. **源站确认不存在就止损**。转转载/归档/用户补充，而不是继续换 UA 或端点硬试。

## 标准流程

### Step 1：一次 `web_fetch`

直接把用户提供的完整 URL 交给 `web_fetch`。

头条 `article/<ID>`、`i<ID>`、`?group_id=<ID>` 会由 `web_fetch` 内部机械提取文章 ID，优先尝试固定 `m.toutiao.com/i<ID>/info/v2/` 快路径。该快路径复用受保护 curl 通道：逐跳校验重定向、校验私网/保留地址，并用 `--resolve` 钉住已验证 DNS 结果。

快路径失败时，工具会自动回落到通用 httpx + 受保护 curl 正文提取链。模型不需要自己拼 UA、URL 或 HTML/JSON 解析器。

### Step 2：按回执分流

| 回执 | 下一步 |
|---|---|
| `SUCCESS` | 直接分析正文，不重复抓 |
| 明确 HTTP 404 / 已删 / 不存在 | 停止源站重试；有标题/关键词则搜转载或归档，无线索则向用户索取标题、截图或正文 |
| `BLOCKED`（安全边界） | 不绕过；说明边界，或改用用户提供内容 |
| 超时 / 反爬 / JS 壳 / parse failed | 只选一个真正不同的恢复通道：搜索镜像/转载，或使用可用浏览器读取页面 |
| URL 本身错误 | 修正 URL 后最多重试一次 |

### Step 3：恢复仍失败就结束抓取阶段

明确告诉用户当前可确认的是“源站不可获取 / 未找到镜像 / 缺少定位信息”，并说明最小所需补充信息。不要继续换 UA、换 curl 参数、重复同一 URL。

## 头条经验（已程序化）

- `info/v2` 是已验证的高成功率正文源，现在由 `web_fetch` 内部调用。
- `data.title` / `data.content` 的解析和 HTML 清洗由程序处理。
- 快路径失败自动回落通用抓取链。
- 这些是确定性执行细节，不再要求模型记忆或重写。

## 死链 / 已删文章

确认源站 404/已删后，要区分“抓取失败”和“文章不存在”。有标题/关键词时可搜索转载或归档；没有足够线索时直接向用户索取，不继续硬试。

建议顺序：
1. 明确死链结论；
2. 已知标题/关键词 → `web_search` 找转载/镜像；
3. 有明确原 URL 且确有必要 → 查归档；
4. 仍无结果 → 向用户索取截图/标题/正文并结束当前抓取尝试。

## 批量链接

逐个调用 `web_fetch` 获得真实正文，再统一比较/总结。不要把多个用户 URL 拼进 shell 并行 curl；安全边界必须继续由工具层执行。

## 反模式

- ❌ 绕过 `web_fetch` 手写 curl：重复实现 UA/redirect/解析，也绕开统一安全边界。
- ❌ 无目标 `web_search`：拿文章 ID 直接搜，结果容易跑偏。
- ❌ 同 URL 同参数反复 `web_fetch`：没有新信息时结果仍然有效。
- ❌ 抓到正文后二次抓取验证：浪费轮次和 token。
- ❌ 源站确认 404 后继续换 UA/端点硬试：不存在的内容抓取技巧无法恢复。
- ❌ 把网页抓取失败升级成模型长推理：先信任工具真实回执，再决定唯一下一步。

## 目标

| 路径 | Agent 工具调用 | 预期行为 |
|---|---:|---|
| `web_fetch` 内置快路径成功 | **1 次** | 直接得到正文 |
| 一次抓取 + 一个真正不同的恢复通道 | **≤2 次** | 快速收敛 |
| 盲试反例 | 5-10 次 | 同参重试 / 手写 curl / 无目标搜索 |
