# 规则与程序审查：阻碍模型发挥的因素清单（只分析，不动代码）

> 日期: 2026-08-31 | 审查对象: docs/ai_rules.lite.md v7 + 本会话程序行为（第一手证据）
> 方法: 以本次"上下文健康检查"会话的完整故障链为样本，逐层归因。所有现象均有会话记录佐证。

## 0. 本会话故障链复盘（审查的直接动因）

用户要一次健康检查，实际发生了：
1. 模型四连切换（27b-cog → qwen-27b → qwythos-9b-q4 → qwen3.8-27b-mlx），每次切换缓存全量 miss；
2. 中间落到 9B 4-bit 量化模型后，连续 6+ 次以**完全相同参数**调用 read_file 读 evidence:// URI，程序发了 2 次停滞提醒仍未阻止；
3. read_file 本身不支持 evidence:// 协议，但失败回执里却提示 "recover=read_evidence"——一个不存在的工具，直接误导弱模型继续死循环；
4. 多轮 "[程序终止边界·无模型回答]"，LLM HTTP 500；
5. 注入的"AI 最近进度"是被截断的元状态片段（"当前 29,951/30,000 字符 (9"）——不完整信息比没有更糟；
6. read_file 首次读 ai_rules.lite.md 时返回 evidence 复用元数据而非正文，force_refresh 才取回——静默吞内容。

**结论：这次健康检查的失败不是模型"不想做好"，是程序环境把中等能力的模型逼进了死胡同。**

## 1. L1 程序缺陷（最优先，改程序比改规则收益大一个量级）

### P1-1 evidence:// 引用与 read_file 不兼容 ★★★★★
- 现象: 压缩恢复清单、工具回执尾部大量 evidence://v1/... 引用；read_file 无法解析该协议（路径登记为不存在）；回执提示 "recover=read_evidence" 但工具清单中无此工具。
- 危害: 弱模型照提示重试 → 死循环 → 空耗轮数预算 → 任务失败（本会话实证）。
- 建议: 二选一。 对 evidence:// URI 做透明解析（read_file 收到该协议自动转投底层存储）； 失败回执里**禁止出现不可执行的工具名**，提示语改为"该引用为程序内部索引，请改用 search_files 定位实际文件"。

### P1-2 read_file 证据复用模式静默吞正文 ★★★★★
- 现象: 读 docs/ai_rules.lite.md 首次返回 coverage/freshness/transport 元数据 JSON，无正文；需 force_refresh=true 才拿到内容。evidence_reuse 判定 "current_evidence_covers_request" 但没有把内容投影进回执。
- 危害: 违反"信息不丢失"核心承诺。模型拿到一个自认"成功"的回执却没有可用内容，极易把元数据当正文引用或反复重读。
- 建议: evidence_reuse 命中时**必须内联正文**；无法内联时状态标 failure 而非 success。这是典型的"静默降级"，协议里明确禁止，程序自己在违犯。

### P1-3 停滞提醒是软约束，对弱模型无效 ★★★★
- 现象: 程序连续 2 次发"[停滞提醒]"后，模型仍继续第 3~6 次相同调用。
- 危害: 提醒只消耗上下文不改变行为；每轮通知本身还在挤占 30K 预算。
- 建议: 升级为硬熔断——相同工具+相同参数第 2 次即拒绝执行，回执只返回一行提示+已登记的失败原因，不产生新的 evidence 块（每次失败回执还附 8 行 evidence 元数据，纯噪音）。

### P1-4 模型 failover 链无能力下限 ★★★★
- 现象: cognilocal-27b → qwen-27b → **qwythos-9b-q4_k_m** → qwen3.8-27b-mlx。健康检查这类轻量任务被切到 9B 量化模型，指令遵循直接崩溃。
- 危害: 换模型不解决问题反而制造问题（死循环元凶）；每切一次缓存全 miss，成本叠加。
- 建议: failover 链按"能力下限"排序而非可用性排序；低于下限（如 <14B 或量化 <q6）的模型不进自动链，只能显式指定。切换前若任务已有进行中产物，优先重试同模型 2 次再降级。

### P1-5 通知里推荐不存在的工具 ★★★★
- 现象: 程序附录反复出现 "可调用 search_archive(query=...)" "经 declare_context 工具（若已注册）"——两者均不在工具清单中。
- 危害: 与 P1-1 同类：把模型引向不存在的工具，弱模型会真的去调。
- 建议: 程序生成提示语前先对注册工具表做存在性校验；"若已注册"这类含糊措辞不如不提。

### P1-6 截断的元状态注入比不注入更糟 ★★★
- 现象: "AI 最近进度"字段塞入被腰斩的报告片段（"29,951/30,000 字符 (9"）。
- 危害: 模型会试图续写/引用一个不完整的数字；规则 22 自己已实证"元状态语料会把弱模型带偏答非所问"（68fed5f5）。
- 建议: 注入前做完整性检查；不完整的进度摘要只保留一句"上轮报告因预算截断，全文见 data/audit/..."，给路径不给半截话。

### P1-7 程序已知的信息诱导模型再查一遍 ★★★
- 现象: 健康检查的核心答案（预算用量、压缩次数、模型切换次数、错误计数）全部在程序手里，但环境引导模型去查 architecture_status / evidence 索引。
- 危害: 模型查不查都一样——数字是程序算的；查了反而烧轮数（本会话实证）。
- 建议: 这类"程序自答型任务"直接在通知里注入指标表，把模型的角色定位为**解读与建议**，不是数据采集。

## 2. L2 规则层：v7 中该删/该瘦/该降级的部分

### P2-1 规则 18 内嵌 Web 面板操作手册 ★★★
- 现象: 一条规则塞了 URL、左侧栏位置、按钮清单、CLI 备用通道、飞书通道、措辞示例。
- 分析: 这是**运维文档**不是**行为规则**。模型只需要知道"审批引导用户去 Web 面板，不要引导 CLI"；按钮怎么点是用户的事。
- 建议: 压缩为一句话 + 详细步骤移到 SoP 文档（规则开头已声明有 SoT 超集，正好归位）。

### P2-2 规则 24（截断补救 SOP）与程序能力重复 ★★★
- 现象: 三分支截断分类、每分支落盘路径、search_archive 用短关键词等细节全写进模型规则。
- 分析: 工具回执**已经**自带落盘路径提示（本会话 execute_command 回执可见）；程序做了的事规则再背一遍 = 双保险变双负担。这条还是全文件最长的一条，占注意力头部位置。
- 建议: 保留"截断→先读工具回执里的落盘路径提示"一句，其余细则下沉到程序回执模板。

### P2-3 规则 33 一条塞三个主题 ★★
- 现象: 中断恢复真相源 + 工作区归属 + 路径失败即停，三个独立关注点挤在一条。
- 分析: "路径失败即停"是工具使用纪律，"工作区归属"是路径解析——后者本就该由 workspace_base() 程序函数兜底，让模型背路径规则是让大脑干小脑的活。
- 建议: 拆三条；工作区解析逻辑下沉程序，模型侧只留"相对路径基于当前工作区根"一句。

### P2-4 规则内嵌大量历史实证 ID ★★
- 现象: 68fed5f5、d1192d8c、EVO-20260824-3cd4d74b 等考古编号散布正文。
- 分析: 对执行零价值（模型不会也不能去查这些 ID），纯占上下文；每轮注入时都在为已结案的历史付缓存成本。
- 建议: 正文删除，脚注一行"历史实证索引见 docs/ai_rules.md"。

### P2-5 "必读指令"与缓存守卫职责重叠 ★
- 现象: 系统提示要求"任务开始必读 ai_rules.lite.md"，同时 architecture_status.rules_version 可查版本、变化才重读。
- 分析: 版本未变时重读 38 行规则 = 纯预算消耗；但"规则存疑时读"这个分支是有价值的（防规则漂移）。
- 建议: 必读条件收敛为"rules_version 变化 或 规则存疑"两个触发器，去掉"任务开始"无条件触发。

### P2-6 应保留的规则（明确不动，防矫枉过正）★
- **规则 21（程序反馈语义）**: 本会话 "[程序终止边界·无模型回答]" 频发，此规则是防止把程序注入当模型结论的唯一防线——**必须保留**。
- **规则 20（任务有界推进）**: 防"永不结束对话"，正是本次审查要求的反面，保留。
- **方法层 ①~⑤**: 状态追踪/前置自问/假设先行/增量推理/结论固化，是防死循环的认知层根药，保留。
- **灾难性安全硬约束**: 不动。
- 方法层 ⑥"工具轮三句限制"：对多步调查任务略紧，但属弱约束且对弱模型有保护作用——**降为建议**即可，不必删。

## 3. L3 架构层

### P3-1 上下文预算 30,000 字符过小 ★★★★
- 现象: 上一轮健康检查报告写了一半就到 29,951/30,000。
- 分析: 规则 v7 正文就 ~2,400 字符，加上系统提示、evidence 块（每次工具回执 8 行起步）、程序通知，真正留给"思考+回答"的余量极小。预算越小 → 压缩越频繁 → 每次压缩丢信息 + 缓存 miss + 注入更多恢复清单 → 恶性循环。
- 建议: 预算至少 3~5 倍提升；或按任务类型分档（健康检查类只读任务给小预算可以，但写报告类必须放宽）。同时恢复清单做总量上限（本会话清单里 architecture_status 引用重复出现，一条都读不回来还占着位置）。

### P3-2 每次工具回执尾附 evidence 块 ★★
- 现象: 每个 execute_command/read_file 成功回执尾部都有 8 行 [evidence] 元数据（ref/source/coverage/projection/recover）。
- 分析: 单次看无害，但它们不可读（P1-1）、不可用（无对应工具）、只进不出（占据预算尾部）。对一个不能被消费的机制，注入本身就是负资产。
- 建议: evidence 元数据默认不注入模型上下文，落盘审计即可；需要恢复时由 search_archive 按需取出。
