# 审查等待与结果读取

审查启动回执只代表已启动。完成通知只代表子代理已结束；准入资格仍由
`review_admission(action="status")` 核验候选、真实结果和审查结论后签发。

## 当前 run 内等待

```json
{"action":"status","child_id":"启动回执中的 child_id","wait_seconds":30}
```

- 先读取 Host 持有的真实句柄；仍运行时最多等待 30 秒，完成即提前返回。
- 每次返回重新读取结果；`pending` 才继续等待，终态按结果处理。
- 多个审查在同一轮分别调用 `status`。纯 status 批次且 child_id 各不相同
  时并行等待，回执仍按声明顺序返回。混合 start/status 和同 child 重复查询
  保持串行，不重排有依赖的操作。
- 不带目标的 `wait(seconds=...)` 只等墙钟；如果使用它，返回后立即查询
  status，不连续只等墙钟，也不把 `elapsed` 当作“子代理仍运行”。
- 用户停止等待可提前返回；该操作不取消审查子代理。

## 完成后唤醒

需要结束当前 run 后续跑时，沿用已授权的单次唤醒机制，绑定
`event_predicate="review_terminal"` 和对应审查 child_id，并设置超时兜底。
只有当前真人 run 可签发既有唤醒授权；此修复不扩大授权范围。

谓词读取当前 Host 内存中的直属、隔离审查句柄和真实完成事件，不依赖
事先查询 status 才更新的准入缓存，也不消费中途报告。已失败、取消的
审查也应唤醒父会话读取原因；丢失句柄、重启后的旧磁盘记录不能冒充当前
真实完成。内部重派后跟随稳定审查引用当前绑定的 live child。

唤醒本身不签发 PASS，也不执行测试、push 或发布；醒来后先查询 status。
