## 0. 读法与边界

0.1 本计划只回答三个问题：现在在哪（§1）、下一步做什么（§3–§7）、谁做/何时/怎样算完成（§8–§12）。

0.2 每项工作带资源标记：

- `[可自执行]`：软件、文档、测试脚本，AI 可在工作区完成并留下回执；
- `[需裁决]`：工作组或用户决定，AI 只准备决策材料，不代替签字；
- `[需外部]`：计量实验室、产线、法务、第二实现，AI 不能替代。

0.3 数值与时间口径：本计划不填任何 `[TBD]`；门槛数字保持 SPEC v0.9.2 原样；排期用相对周（`Wn` 起始日 = W0 + 7n 天），日历只作换算示例，不是承诺。

0.4 完成口径：任务完成 = 产物 + 回执 + 可复现命令，三者缺一不算完成；`simulated` 不得写成"实测"；未过探针不得标记阶段完成。

0.5 本计划不覆盖（与 SPEC 1.2 对齐）：读码器内部检测算法、上层 EKF/融合、靶标施工工艺、传感器时基同步、安全决策逻辑。

## 15. 执行编排（分工与并行协作）

### 15.1 五条编排原则

1. **单写者**：任一文件同一时刻只有一个写者；并行靠"写区划分"，不靠加锁。

理由：契约先落地；B6 的**布局 JSON 与清单哈希**可先于 B3 完成（B3 需要"已知真值的合成图"作输入），但 PDF 打印校验与 B3 实拍是同一闭环，二者**并行而非串行**（与 §4.2"B5、B6 与 B3 并行"一致）；合并顺序按依赖与 rebase 成本排：B1→B2→B6→B3→B4→B5→B7→B8；B5 与读取链无数据依赖，但与 B1 共用序列化，故排在读取之后以免反复 rebase。

文档轨道（T1）独立合并，但 **A3 追溯矩阵必须引用 B1 已冻结的字段名**，否则矩阵返工——这条是 A3 不得早于 B1 冻结的唯一硬约束。

契约一旦合并，任何字段增删改都必须走变更单（记录进 §16 变更历史），并在 `schema_version` 升位；实现方只改实现，不迁就契约。

### 15.6 冲突、阻塞与状态口径

- **契约冲突**：以 `ctp/schema/observation.schema.json` 为准；实现改实现，契约改动走变更单并升版本。
- **同文件双写**：禁止。发现即回退后写者，重排时序（不回退先写者，避免丢工作）。
- **证据三件套**：产物文件 + 可复现命令 + 输出摘要/回执；缺一按"未验证"，不按"完成"。
- **进度真值**：durable task 的 `pending/in_progress/blocked/done` 是唯一进度真值；§15.4 时序表只是排期意图，不构成进度。
- **阻塞登记**：需要签字或外部资源的，把 task 置 `blocked` 并在 `blocked_reason` 写明"等谁给什么"，不用"继续推进"替代。
