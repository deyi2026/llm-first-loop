# 借鉴需求实现设计：子会话并行治理三机制 + 一条保真原则

- 类型：design（v0.3，经 grill 第一层拷问 + 第二层自检修订，已收敛）
- 来源：外部实践文章（Claude Code subagents / worktree / 审查分档相关）与我方经验库差距分析
- 日期：2026-10-22
- 状态：拷问评审收敛（第 1 层 25 问 + 第 2 层自检，记录见 §9）

## 1. 背景与范围

对照来源文章的机制与我方现状，结论分三类：

1. 已有对应物，不重复实现（见 §6 排除项）；
2. 真正值得借鉴的三条（本设计主体）；
3. 一条反向原则（破坏性清理的保真前置）。

本设计只覆盖第 2、3 类，目标是把"文章的做法"翻译成**我方可执行、可验收的行为定义**。

## 2. 术语

- **写集**：一个子任务预计创建或修改的文件路径集合（含新建文件的预期路径）。允许目录级粗粒度声明；目录级命中产生的假阳性只会导致保守串行，不导致事故。
- **读集**：任务需要读取的、且**由本并行组内其他任务产出**的路径（外部既有文件不计入，它们不构成组内依赖）。
- **预检**：派发并行子任务组之前完成的检查，失败即改变派发方式（转串行或加依赖），不取消任务本身。
- **双闸**：事前预检（模型纪律）+ 结算核验（结算产物清单以磁盘事实为准）。

## 3. 机制一：并行前写集交集预检（事前闸门）

### 3.1 问题

现有沉淀全部是事后补救：EXPERIENCE-20260924（并行写者共享工作树导致 edit 基线失配，教训是开工先留基线）、EXPERIENCE-20261018（多条件评测共享任务目录导致条件污染与答案泄漏）。缺少事前闸门。

### 3.2 需求陈述

派发任何并行子任务组（spawn_subagent 多个，或 workflow_run 并行模式）之前，必须完成两项判定：

1. **写写冲突**：每个子任务列写集，两两求交集，交集非空 ⇒ 串行化或 depends_on 排序；
2. **读写依赖**：任务 B 的读集 ∩ 任务 A 的写集 ≠ ∅ ⇒ B 必须排在 A 之后（A 的产出是 B 的输入时，二者本来就该有依赖边，预检兜底防漏）。

两项都通过才允许并行派发。**写集为空集 = 纯只读任务，天然可并行**（但其读集仍须过第 2 项判定）。

### 3.3 流程

```
列出各子任务 {写集, 读集}
  → 判定1：两两写集交集
  → 判定2：跨任务 读集 ∩ 对端写集
  → 均为空？──是──> 并行派发（判定结果记入 task_state）
  └─任一非空──> 串行化 / depends_on 排序，记录排序原因
```

### 3.4 规模与成本

- 两两判定为 O(n²)，n < 20 无瓶颈；DAG 分层派发时只在同层并行组内判定，跨层由依赖边保证。
- 子任务很多（>10）时，task_state 记**判定结果摘要**（谁与谁冲突、如何排序），不记全量清单。
- 权衡声明：预检成本（列表+求交）≪ 并发冲突事故成本（已有两条教训实证），宁假阳性保守串行，不冒险并行。

### 3.5 失败处置（拷问新增）

- **组内单点失败**：已完成子任务的产物保留，不回滚整组；失败项单独重试或收回主任务处理。
- **重试写集**：重试沿用原写集声明；重试方案改变产物路径 ⇒ 视为新任务重新预检。
- **冲突已发生**（预检漏检或越界写）：按 EXPERIENCE-20260924 教训，以 git 基线/备份区分各写者版本、逐版本判存，**不自动合并**，冲突内容交裁决。
- **依赖失败传导**（第 2 层自检新增）：因判定 2 产生的依赖链中，上游任务失败 ⇒ 下游任务标记 blocked（输入缺失），不允许带着空输入继续执行。

### 3.6 事后兜底：结算双闸（拷问新增）

预检是模型纪律，存在"忘做即静默失效"的固有弱点。兜底锚点：子任务结算时产物清单是必经路径且以**磁盘事实**为准（非子任务自报），收尾对比"实际产物 vs 声明写集"：路径重复 ⇒ 冲突漏检，进入 §3.5 冲突处置；出现声明外新产物 ⇒ 越界写，记入教训并修正该类任务的写集估计方法。事前纪律 + 事后结算 = 双闸。对比范围以主工作区（含已合并产物）为准；fs_isolation 任务按 §3.7 合并后才纳入对比，隔离区内同名路径不构成冲突。

### 3.7 隔离任务的合并时序（拷问新增）

fs_isolation 子任务的写发生在隔离区，不直接冲突主工作区，但其产物**合并回主区**时可能冲突。规则：合并阶段本身串行执行；每个合并前将该子任务写集与主区当前状态（含已合并任务的写集）再判定一次。

### 3.8 落地载体

程序不强制，落为模型运行纪律：沉淀为 method（已沉淀：`method:parallel-subtask-writeset-precheck-ec9994c9f0bc`，candidate），与已有事后教训经验配套使用。

## 4. 机制二：审查三档强度

### 4.1 现状

RULE-AI-28 为单一门槛（全量测试 / git push / 文稿发表前独立审查），RULE-AI-35 对护栏类变更加实测拦截要求。本质是"标准 + 护栏加严"两档，缺少轻量档。

### 4.2 需求陈述

| 档位 | 适用 | 内容 |
|---|---|---|
| Quick | 文档/低风险改动 | 自查 + stop_slop 类机械检查；验收锚点：机械检查须留工具回执，无回执视同未审 |
| Standard | 代码变更 | 现行 RULE-AI-28 独立审查门槛 |
| Deep | 护栏/拦截判据/阻断清单/正则/阈值/安全边界 | Standard + RULE-AI-35 实测拦截（构造应拦输入实测） |

约束：**档位由变更性质决定，不允许被审方自选降档**。判定按变更内容的事实特征（是否触及拦截判据、是否代码、是否纯文档），有争议取高档。**混合变更按其所含最高风险部分定档。** 保守代价如实声明：“大量文档 + 少量阈值改动”的变更会整单走 Deep，此为有意保守（与 RULE-AI-35 现行语义一致），不设比例豁免。

### 4.3 落地载体与回退

RULE-AI-28 属于规则真值源（docs/ai_rules.md），规则修改不可自行生效。本设计以演进提案（submit_evolution）提交；**审批通过前，现行规则按原样执行（维持现行门槛，不因提案存在而放宽）**；提案被拒 ⇒ 维持两档现状，不自行降档，差异记入教训。

## 5. 机制三：拆分理由透明化 + 待裁决项聚合

### 5.1 需求陈述

1. spawn 子任务时，除已有必填 acceptance 外，强制写明 **why**：为什么这个子任务值得单独拆出（预期收益一句话，须能回答"不拆的代价是什么"）。
2. 子任务产出中"值不值得做只有用户知道"的开放项，聚合为**待裁决队列**，在回复中以固定段落集中呈现，不散落在各子任务汇报里。

### 5.2 质量约束

- why 写不出"不拆的代价" ⇒ 视为拆分理由不成立，默认不拆（并入主任务执行）。
- 待裁决项必须附带选项与默认行为（不裁决时我方按什么继续），不允许只抛问题。
- 裁决后队列项标记已裁决并回填结果，不重复请示（无新事实不复议）。

### 5.3 派发说明固定格式（拷问新增）

并行派发时向用户呈现统一表格：**任务 | why | 权限声明(requires) | 写集/读集摘要 | 判定结果（并行/串行原因）**。写集为空的纯读任务优先声明 fs_isolation 或最小 fs 权限（权限最小化，防并行任务默认全 fs 写权限）。（机制三已沉淀：`method:subtask-split-why-pending-decisions-1d61c11a3f04`，candidate）

## 7. 反向原则：破坏性清理的保真前置

来源文章记录了 2.1.304 修复的 bug：detached HEAD 下退出时静默删除工作树和分支。吸取的规则：

- 任何删除/清理工作产物的操作（工作树、分支、实验目录、备份），**前置条件是产物已保存/已合并/已归档的证据回执**，而不是"流程结束/退出"这个事件。
- 无保存证据 ⇒ 不清理；只有回执（文件存在性、合并记录、归档路径）可作为放行依据。
- 与 RULE-AI-24"先保真、再优化"同源：清理是优化动作，保真是前置。

## 8. 验收标准

- [ ] 机制一：下一次多子任务派发前，派发说明含各任务写集/读集与两项判定记录；结果记入 task_state。
- [ ] 机制一兜底：下一次多子任务结算时，实际产物 vs 声明写集对比已执行并留痕。
- [x] 机制二：演进提案已提交（EVO-20261022-53724ede，pending_review；审批前现行规则照旧执行），档位矩阵覆盖三类变更并含混合变更定档规则。
- [ ] 机制三：子任务派发含 why 与权限声明；待裁决项以固定段落聚合呈现且带默认行为。
- [ ] 反向原则：清理操作记录中可追溯"保存证据回执 → 清理"的先后关系。
