这份设计面向 LFL 的任务收尾与知识调用。目标是让每次有实质工作量的任务都能留下可统计的使用反馈，并让下一次模型在检索时看到相关反馈、适用条件和版本状态。最小实现应复用已有账本、检索工具和事件流，把反馈接回选择过程。

# 从大模型调用角度组织流程

模型需要知道四件事：现在有哪些相关知识、为什么值得读、过去在相近场景表现怎样、如何用最少调用完成回记。

1. 任务开始时沿用 Rule31 的有界检索。先返回少量候选短卡，保留稳定引用与继续获取入口；同一连续任务内避免反复检索。

2. 短卡呈现用途、适用前提、重要反例、来源版本、可用状态和分项反馈。规则额外呈现义务与触发条件，避免把强制要求压缩成普通建议。

3. 模型需要采用或核实某张卡时，按稳定引用读取完整内容。全文读取返回实际版本；若与先前候选不同，标明变化，让模型重新判断。

4. 执行过程中由程序记录可观察的检索、读取、工具结果和版本事实。采用、帮助、误导等语义由模型明确声明，不能由调用顺序猜测。

5. 当前任务收尾时汇总“本任务已读取、已采用、待反馈”的对象，模型一次提交简短结算；任务中已发现错误的卡片立即反馈和处置。

6. 后续检索读取结算后的统计与证据入口。修改建议进入既有修订或演进流程，复审完成后新版本重新参与检索。

用户可见答复只需简短列出主要帮助、问题和改进建议；详细记录持久化。不能让用户每次填表，也不能为了凑反馈再读一遍整个知识库。

# 使用事实与收益评价分开记录

使用声明回答“我怎样处理它”，评价回答“本任务中观察到什么”。两者可以在一次工具调用中提交，但应保留不同字段和来源。

| 维度 | 最小记录 | 解释 |
| - | - | - |
| 对象身份 | kind、稳定 ref、实际读取版本 | 区分规则、Method、经验；绑定本次真正读到的版本 |
| 任务归属 | task 或明确工作单元、run、episode、session、模型 | 宿主绑定真实身份；不能用同会话的旧记录代替新任务 |
| 使用决定 | applied、adapted、not_applicable、rejected | 兼容已有四态；未采用的普通候选另记选择原因，不计为使用失败 |
| 本次帮助 | helped、neutral、hindered、unknown、mixed | 模型自评；不得直接写入独立资格结论 |
| 评价依据 | 简短观察、evidence_refs、evidence_level | 可分 model_declared、observation_linked、independently_evaluated |
| 任务结果 | 验收项与其事实引用 | “任务完成”与“知识导致收益”分别记录 |
| 改进建议 | 建议内容、问题类型、关联修订或演进引用 | 说明需补前提、更新来源、修步骤还是处理规则冲突 |
| 幂等与更正 | slot_id、submission_hash、revision、supersedes | 重试返回同一回执；决定、评价、证据或建议任一改变即按 supersedes 追加修订，父记录经程序校验 |

保留现有 `task_benefit=not_evaluated` 的独立评估含义，新增模型自评字段，而不是为了统计好看把旧 42 条回执追填为“有效”。历史缺项标为 unknown，不当成失败或零收益。

新旧记录的可比性由 schema 版本显式承担：v2 起每条记录带 schema 标记与任务绑定、版本绑定、自评字段；投影按 schema 分桶，v1 及无 schema 的旧记录归入“legacy 未分层”桶。legacy 桶按“字段是否齐全”参与统计：某项统计需要哪些字段，legacy 条目齐全即参与、缺任一即排除——仅需 ref 与决定的总次数可计入，需要版本、任务绑定或模型自评的分母不计入。P2 的分层验证以 v2 起的样本为限，短卡呈现 legacy 统计时必须标注其可参与的口径与不可分层部分。不追填、不外推，是这条口径的两个不变量。

“少了几次重试”“避免了错误路径”等描述应指向实际观察。没有对照时，不能把模型估计的节约时间当作实测增益，也不能把任务成功归因到每张采用的卡片。

不适用、错误引导和证据不足必须分开。“我用不上”不能直接降低卡片的事实可信度；读过但未采用、只检索到、未送达模型、没有机会应用，也不能合并成负反馈。

# 待结算清单的生成机制

清单不是新账本，而是“工作单元窗口内可观测的读取事实 − 已回记事实”的差集投影。生成规则全部机械、fail-open：

- 读取事实来自单一打点：统一检索工具的精确水合成功路径（`search_records(kind=method, query="method:…")`、`kind=experience|lesson, query="experience:…"`、`kind=rule, query="RULE-AI-…"`）追加一条 `knowledge_read` 事件，携带 kind、稳定 ref、返回版本或投影哈希、session、run。版本哈希取自构成本次回执的同一份内存内容快照，打点时不重新读盘——两次读取之间文件可能已变，重读会伪造“读取时刻版本”。事件语义收窄为“精确内容已返回调用方”：它不证明回执已送达下一次模型输入，更不证明模型已看到或采用。“已送达模型输入”仅在消息流层可证时单独记录，否则保持 unknown；“模型声明采用”只来自结算声明。三层事实分开记录，送达未知不冒充已读。工具迹行确实不含回执内容，但事件流另有 `message.appended` 携带回执正文——该通道 fail-open、正文可被附加段改写、无结构化版本字段，不能当作读取版本凭据；打点仍须放在检索工具层，这是本设计唯一的新增埋点，且只发生在精确水合路径，泛查询不打点。
- 已回记事实以持久化结算回执为权威：Method/经验的 usage ledger 回执与规则侧 EventStore 回执，按（工作单元、对象、读取版本）三元组匹配读取事实——跨 run 补交的回执同样进入匹配集，批量部分成功只抵扣已落账条目。`scan_method_use_ledger` 的工具迹扫描模式保留为降级线索：`knowledge_read` 事件缺失时清单退回工具迹扫描并标注“仅 ref、版本 unknown、非权威”，仍可结算，不阻塞；工具迹只认 ref 不辨版本，其抵扣结果不用于版本级统计。
- 窗口枚举以 task/goal 图事件为锚：自该 task 上次成功结算回执（无则自 in_progress 事件）以来的事件范围。task 图缺失或归属不明时回退 session 窗口，清单标注 attribution=degraded(session)，不静默扩大范围。降级窗口产出的结算回执标 attribution=unresolved：不抵扣任何确定任务的待结算项、不进入任何任务级覆盖率分母，仅进入会话级观察；后续带证据补交归属后，条目移入该任务的回执集并开始参与其分母。

清单回执必须自带覆盖边界声明：不覆盖 `read_file` 直读知识文件、附件内嵌摘录、泛查询命中。清单是“事件源可观测范围”，不是全部知识接触。模型可补充自报条目，程序校验 ref 存在性后落账并标 self_reported；校验失败该条回执 failed 并给原因，不静默丢弃。因此结算 none 拆成两列分别呈现：事件源无接触、模型自报无接触——清单漏检不能被折叠成“无接触”，反之模型自报也不能冒充事件源观察。

# 幂等键与重复结算

身份分两层，均由程序派生，模型不自选。slot_id = sha256(工作单元 id, kind, 稳定 ref, 读取版本标识)——回答“哪个工作单元对哪个对象的哪个版本作出过评价”；submission_hash = sha256(提交条目全字段的规范序列化：使用决定、本次帮助、评价依据、证据引用、建议)——回答“这次提交的内容是什么”。模型只提交字段值，两层键的计算和判定都是程序职责，“相同提交”由此获得机械定义：submission_hash 相同即相同提交。

落账采用先扫后写：submission_hash 已存在则跳过追加，把既有条目作为回执返回——传输层重试与重复提交同一内容由此折叠为一条。这复用 `record_migrated_entry` 的 `dedupe_key` 先例并扩展到两侧 live record_use 路径；MethodStore 与 ExperienceStore 均已有跨进程 flock 单写锁，扫描与追加在锁内天然串行化，无需新增锁协议。

同一 slot 的不同提交是修订而非重复：决定、评价、证据或建议任一改变即 submission_hash 不同，追加新条目并经 supersedes 链回原条目，不改写历史行。v2 把“使用决定”放进幂等键，导致“同决定、评价从 unknown 改 hindered”得到相同键、更正被旧条目吞掉——这是 v3 拆分两层身份的直接反例。supersedes 落账前程序校验父记录：父必须存在、属同一 slot、位于既有链上（父追加序早于本条），校验失败该条回执 failed 并给原因，不产生断链或环。统计以 slot 为单位取链头：一个工作单元对同一对象、同一版本至多计一条现行评价，修订不重复计数；读取版本不同（卡片已修订）是不同 slot，旧反馈保留原版本归属。回执携带 slot_id、submission_hash、revision 与账本水位；写入结果未知时模型按 submission_hash 查原结算，不重复追加。ts 不参与两层键、也不作为排序权威——账本顺序以追加序（单调水位）为准，本地时钟回拨不破坏去重。

# 三类知识共用入口但保留不同权威

| 对象 | 收尾反馈重点 | 后续动作 |
| - | - | - |
| 经验 | 原场景与本次场景差异、解法是否仍可执行、来源是否过期 | 追加使用声明；按证据修正、补前提或进入已有失效流程 |
| Method | Trigger 和 Discriminator 是否匹配、短路径是否减少返工、Stop 和 Verification 是否足够 | 自评进入检索视图；独立 qualification 仍走原流程 |
| 规则 | 是否触发、是否遵守、执行证据、冲突或操作负担、建议修订 | 记录执行与反馈；修改走规则事实源和既有审查流程 |

规则的有效性来自已批准的权威来源，不由人气分或模型满意度决定。低收益评价不能自动跳过 Rule28 审查，也不能自动降低规则优先级。确有冲突时留下冲突依据并按现有指令层级处理。

规则的使用不必逐条强迫模型填写所有已加载规则。优先结算本次明确触发、影响行为或存在问题的规则；程序能证明的审查、授权和拦截回执直接关联，模型补充语义评价。

实现上优先扩展现有生命周期入口并提供批量结算适配层。Method 与经验使用声明仍分别写入既有 usage ledger；规则执行反馈可复用 canonical EventStore 并提供可恢复查询。跨库统一视图是可重建投影，不能成为第二份“是否使用”的真相源。

规则反馈的读取回流明确属于 P1 改动清单，不再留白：`search_records(kind=rule)` 的返回增加规则反馈注释通道——程序可证的执行回执次数、最近问题一句话摘要、未决冲突，数据取自 EventStore 投影并携带反馈水位与 pending_count。`_annotate_usage` 的 per-side 注释模式（method、experience 两侧已在用）是现成扩展点；rule 侧从事件投影取数而非 usage ledger，且注释不改规则排序、不改规则权威。缺少这一步，P1 验收“任务 B 首次相关查询能读到该反馈”对规则不成立。

# 索引更新的三个时钟

“实时更新”应拆成三个可验证承诺，不能用一个更新时间覆盖所有阶段。

| 数据层 | 目标语义 | 提供给模型的事实 |
| - | - | - |
| 正文与生命周期 | 成功提交后，下一次精确读取及词法发现可见当前版本 | source_version、source_root 或 release identity、状态、更新时间 |
| 使用反馈与统计 | 成功结算返回持久回执；下一次查询可看到该反馈或明确的投影落后状态 | feedback_watermark、indexed_watermark、pending_count |
| 语义向量 | 异步更新并绑定内容版本；旧向量不能冒充新内容 | vector_version、语义可用状态、落后范围或降级原因 |

索引表应从事实源自动派生，适合模型查询，也可供管理页浏览。不要让模型每次手工维护一张全库总表。

写入结果三分：明确已提交（fsync 与落盘回执成功）、明确未提交（写入路径返回错误，绝不返回“已记录”）、结果未知（进程中断、超时或回应丢失）。未知不是失败：恢复时先按 submission_hash 扫描账本——命中且全字段一致视为已提交并返回既有回执；未命中才允许重发，键去重使重发安全。批量结算返回逐条 receipt 和 committed、pending、failed 状态，跨库部分成功不能宣称整批原子完成。

修改卡片正文后，旧反馈保留原版本归属，并可通过 parent/supersedes 查看历史。反馈更新通常只改变统计投影，不应为每条反馈重新嵌入完整正文。生命周期变化、删除和替代关系要先影响当前候选集合，不能等待向量更新后才隐藏旧状态。

被新部署固定的规则文件与运行时共享卡库具有不同更新边界。热更新缓存只保证“配置源改变后可刷新”，不意味着修改主仓库后所有发布实例会立刻采用。模型应能看到自己实际查询的来源身份。

# 让反馈真正影响下一次选择

第一阶段先把历史反馈清楚地呈现给模型，保留现有排序。短卡至少提供：

- 最近相近场景的采用与不适用次数，分别列出误导记录。

- 当前版本与历史版本的分项数据、有效样本数和未知数。

- 模型类别或模型能力条件、任务类型、工具与环境版本。

- 最近问题的一句话摘要、证据引用，以及修订是否仍待处理。

- 一步读取完整卡片与相关反馈的入口。

同一查询中仍需保留词法与语义发现通道，允许模型继续查找。常用卡不能只因使用次数高就挤掉新卡；从未曝光的卡不能按低采用率处罚。

只有在上述数据可靠后，才考虑有界的反馈辅助排序实验。评价应按任务和模型分层；样本不足时不输出看似精确的成功率。不得把“经常被选”当成“更有效”，也不能让自评循环强化自己的排序。

呈现本身就是干预：第一阶段即使只展示反馈、不动排序，模型的选择分布也会随之改变，幸存者偏差从呈现层即开始作用。因此第一阶段的任何对照以“呈现与否”为轴设计，而不是等到排序实验才开始计量；反馈注释必须同时披露未曝光与未知分母，防止“看得见的卡”在呈现层就挤占“没被看见的卡”。

统计漏斗区分候选返回、模型可见、精确读取、声明采用、完成反馈和独立评估。无法确认 provider 送达或当前任务应用机会时，相关分母明确为未知。前端可以展示可观测范围内的覆盖率，不能外推为全库有效率。

# 收尾可靠性与操作成本

每个有实质工作量的工作单元应有一次结算。无知识接触时如实记 none；接触过但没有足够依据时允许 unknown。简单问答、闲聊和纯复述不增加专门工具流程。

以 task 或明确工作单元为主、run 和 episode 为执行追踪。同一任务可能跨多个 run，不能把每轮模型调用当成一个任务；同一 session 也可能包含多个任务。身份映射不确定时应报告归属缺失，不能静默匹配旧记录。

成功、失败、取消、中断均保留已观察事实。来不及生成评价的任务标记 incomplete，待后续恢复；不能自动生成“有帮助”。业务交付完成与反馈是否完整分别展示，反馈失败如实报告和补交，不触发为了凑评价而无限追加模型回合。

批量结算只负责校验引用、版本、身份与持久化，不替模型评分。默认每个工作单元一次简短结算；任务内发现明确问题时即时补记。沿用现有负反馈处置要求，不能以“已经记录”代替必须的修正或审查。

结算的操作成本自 P0 起进入回执，不推迟到 P2：每张结算回执记录本工作单元的结算调用次数与结算占用回合数。理由是行为风险的时间不对称——P0/P1 上线即产生持续 token 与回合开销，若要等 whole-run 报告才发现开销过大，模型可能早已演化出跳过结算的行为退化；单工作单元粒度的计数在 P0 就足以暴露这一趋势。P2 保留 whole-run tokens、延迟与分层对比。

这份设计不新增普遍的硬阻断门。新增的机械约束应服务于真实记录和去重；语义判断、是否采用以及进一步调查仍由模型决定。

# 边界与失败模式决策表

| 边界情形 | 决策 | 依据 |
| - | - | - |
| 条目缺 ref、决定非法、ref 不存在 | 该条回执 failed 并给原因，整批其余条目继续 | 现有 FileNotFoundError/ValueError 行为保留，纳入批量回执而非静默丢弃 |
| note 超长 | 沿用 2000 字符截断 | 两侧 store 现行为 |
| 本地时钟回拨/漂移 | ts 仅作展示；排序与去重权威是追加序与派生键 | 键不含 ts；账本单调水位已有 |
| 同内容并发提交 | flock 单写锁内先扫后写，收敛为一条，返回既有条目 | 两侧 store 均有跨进程 flock；dedupe_key 先例 |
| 磁盘满、fsync 失败、torn tail | 写入错误如实上抛（经验侧 ExperiencePersistError、Method 侧 OSError），批量回执逐条 failed，绝不返回“已记录”。行数水位区分不了“完整末行”与“截断半行”——半行无换行符时行数可不减，lost=0 仍可能损坏；v3 起每条记录自带行级完整性凭据（规范序列化字节的 sha256 后缀），恢复扫描只越过校验通过的记录，校验失败的尾部移入隔离旁文件并出具诊断报告（位置、字节范围、疑似原因），不静默跳过、不直接在坏行上追加 | EVO-20261010 账本损失教训；行数水位的半行盲区为外部审查反例 |
| 最坏场景：结算丢失 | 只损失反馈，不损失业务交付；反馈缺失经投影 pending_count 与 receipt 缺席对模型可见，可跨 run 补交 | incomplete 语义已有 |
| 降级路径 | `knowledge_read` 缺失 → 清单退回工具迹扫描（仅 ref、版本 unknown、非权威，不用于版本级抵扣）；归属不明 → attribution=unresolved，不抵扣确定任务；投影落后 → 显示落后水位而非旧数据冒充新 | fail-open 与三水位原则 |
| 失败检测 | 三水位 + 按 submission_hash 可查 receipt + 结算成本计数 | 全部为既有或本设计新增的可观测面 |
| 重试策略 | 结果未知先按 submission_hash 查原结算，命中即返回既有回执；确认未提交后同内容重发即可，本地文件系统无需退避；换 run 补交走 incomplete 恢复 | 键去重使重发安全；先查后发避免重复追加 |
| 用户可见错误 | 最终答复一句话如实说明结算失败与补交途径，不暴露内部堆栈 | 诚实优先于表面完成 |

闭环的最低合格标准是：任务 A 的真实使用反馈成功落账，任务 B 的模型能在相关检索中看到它，并自主选择采用、调整或跳过；索引延迟和记录缺失对模型可见。这能证明链路连通，实际任务收益仍需单独验证。
