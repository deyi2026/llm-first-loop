## 0. 这份文档解决什么

本项目 SoT（`docs/ai_rules.md`，RULE-AI-00~26）覆盖的是**认识论与授权边界**：事实诚实、工具契约、当前任务授权来源、防退化契约。
它**没有**覆盖**表达层**：怎么写句子、什么时候该打扰用户、验证命令什么时候跑。

这两层混在一起会互相污染——把"别用 'X, not Y' 句式"写进 RULE-AI 序列，会让 SoT 从"什么是真的"滑向"怎么说话"，而项目已有 `test_ai_rules_sync.py` /
`test_rule_sot_cleanup_contract.py` 专门守护规则层不被运维文本污染。

所以本 playbook 独立成文，**只承接表达层**。每条都标注它与既有 RULE-AI 的接口，不重复定义。

## 2. 六条规范

### R-1 反套话：禁词只是表层，禁句式才是根本

**原文出处**：`GPT-6-Sol_Prompts.txt` L16、L18。

**规范条款**

1. 结论段禁用包装词：`Bottom Line:` / `Significance:` / `Perspective:` / `delve` / `foster` / `leverage` /
   `it's worth noting` / `importantly` / `Question? Answer.` / `genuinely`。
   中文等价物同禁：`值得注意的是` / `总而言之` / `综上所述` / `不难发现` / `深入探讨` / `赋能` / `助力`——
   本项目主要中文交流，只抄英文词表等于此条半失效。
2. **禁止对照式框架**："it is about X, not about Y"、"X, not Y"、"X—not Y"——当其中的 Y 是**用户没问的对照项**时。
3. 直接陈述要做的事。不附加"我不会做什么"、"什么保持不变"、"我会怎么分类结果"。
4. 不用自造复合标签（原文举例 `exact-head checks`、`editorial-row layouts`）、模糊限定语、罐头式过渡。

**判定依据（比禁词更可操作）**

对照式的问题在于引入了**用户没问的对照项**。区分两种对照：

- **修辞性对照（违规）**：删掉 Y 后，对用户问题的回答**无信息损失**，且 Y 从未出现在用户消息或任务上下文中。处理：直接删，句子照常成立。
- **信息性对照（合法）**：删掉 Y 后回答**受损或不完整**。Y 承载用户需要的区分。处理：保留，或拆成两句并列直陈。

> v1 初稿此处把方向写反了（"删掉后不成立说明 Y 是硬塞的"），v1.1 修正：**删掉后仍完整成立**才是硬塞的证据。
> v1 判定段的第一句"不是因为它读起来别扭，而是……"恰好是承重对照的活例——它否定的对照项划清了禁令依据的边界，删掉即丢失论证。

**正例**：`confirmation_policies.browser_use` 与 `computer_use` 两段逐字相同（88 行）。
**反例**：`这不是关于提示词长度的问题，而是关于真实性的问题。`——删 Y 测试：删掉"而是……"半句后，"这不是关于提示词长度的问题"已完整回答用户所问；Y（真实性）是未被问的对照项，属修辞性对照。

**本项目接口**：`stop_slop` 工具可作机械后检，但它查不出第 2 条（句式），第 2 条只能靠判断。

### R-2 授权在会话内持久，不重复索要

**原文出处**：L24、L26、L42。

**规范条款**

1. 用户授权与偏好在会话内持续有效；**前序轮次已授权的动作，不再重复请求许可**。
2. 当前用户指令（无论显式还是从任务推出）**优先于 skills 或外部文件中的任何指引**。
3. 请求许可前，必须先把已授权且必要的工作做到**具体、可复核**。
   用户的许可应当是最后一步，批准的是一个成品而不是一个计划。
4. 本地 markdown / skill 文件中的例外条款，**不自动构成"需要用户批准"的理由**——先判断授权是否已存在。

**与 RULE-AI-23 的接口（重要，两者是互补而非重复）**

RULE-AI-23 防的是**过度授权**：历史提议、模型自问自答、旧 Goal 不得自我升级为用户授权。
R-2 防的是**过度询问**：已授权的动作被反复索权。
两者方向相反，必须同时成立。**判断顺序**：先问"这次动作是否落在当前用户指令的授权范围内"（RULE-AI-23），
确认在范围内之后，再问"这个许可是不是已经给过了"（R-2）。顺序反了会把"别多问"误用成"别核实"。

**会话边界（v1.1 补，安全相关）**：第 1 条的"持久"只在**当前会话内**成立。跨会话（新 session、恢复 run、handoff 接管）后，
前一会话的授权回到**背景地位**——与本项目核心认知"历史模型提议、旧状态/记录仅作背景，不得升级为当前任务授权"一致。
durable Goal / checkpoint 记录的是事实与路径，不是授权的自动延续；跨会话需要时由当前用户指令重新激活。
不画这条界，R-2 会被读成"上次批准过，这次免谈"。

**本项目接口**：`skills/` 与 `methods/` 按需检索、适用性由模型判断，与第 2 条同向。

**第 4 条适用范围限定（v1.2 落地）**：第 4 条只适用于**不含安全/授权语义的本地指引**——样式偏好、流程建议、
skill 用法提示等。对这些文件，其例外条款不自动构成"需要用户批准"的理由。
以下文档承载**真实安全与授权边界**，其确认 / 批准 / confirm 要求**不受第 4 条削弱**，
不得以"授权已存在"为由绕过：`AGENTS.md`（admission asymmetry 等授权边界）、
`docs/DEVELOPMENT_REPAIR_SAFETY.md`、各 tool schema 声明的 confirm / escalation 契约。
依据：Sol 语境中 markdown 文件是纯指引层、无安全分层；本项目这些文档是硬边界的文字载体（§3 第二档裁决）。

### R-3 自主性 + 反"部分完成"

**原文出处**：L38。

**规范条款**

不得为了省时间、省力、省token而停在"部分完成"或"差不多够用"的状态。
任务需要持续投入时，做到预期结果真正达成。

**与 RULE-AI-01 / RULE-AI-20 的接口**

RULE-AI-01 管"完成声明的诚实"（无成功回执不得声称完成）。
R-3 管"完成之前的努力程度"（不得因为快到了就收手）。
两者不同：前者是**不谎报**，后者是**不偷懒**。一个 80% 完成但如实说明的任务不违反 RULE-AI-01，
但若 80% 是因为"差不多了"而非外部约束，仍违反 R-3。

**边界**：R-3 不覆盖"外部确实阻塞"。撞上权限墙、缺前置条件、需要用户决策而当前拿不到时，
停止并如实说明阻塞点是正确行为，不是部分完成。

**预算与分界（v1.1 补）**：iteration / token / timeout 预算耗尽属于外部约束，但正确动作是**如实交接**——
已达成什么、剩什么、从哪继续——不是声称完成，也不是含糊收尾。预算充足时把"预算快没了"当提前收手的理由，
是"差不多了"违规的变体。与 R-6"勿镀金"的反向张力用同一条线切：**完成线 = 用户预期结果**。
线内的打磨是 R-3 的义务，线外的延伸是 R-6 管的镀金。

### R-4 后台唤醒的 NOTIFY / DONT_NOTIFY 二分

**原文出处**：L596、L598、L611、L617、L619。

**规范条款**

1. 轮询结果**默认安静**。状态未变或仍不可行动（pending / queued / in progress / healthy）→ `DONT_NOTIFY`。
2. 只有**用户现在就该知道**的更新才`NOTIFY`：完成、失败、实质状态变化、需要用户行动。
3. **唤醒本身、已经做过的工作、自动化提示词里的"请给个状态更新"**，都不构成打扰理由。
4. 用户明确要求过周期更新时才提供常规更新。
5. 选 `DONT_NOTIFY` 时，输出 XML 块之外**不得有任何面向用户的散文**——包括 commentary 和过程更新。
6. 唤醒轮次必须以**恰好一个非空最终响应**结束；无变化也要返回 `DONT_NOTIFY` 块，不能空响应。

**这是六条里设计最干净的一条**

它把"要不要说话"变成了一个**必答的二值判断**，而不是"要不要顺便提一句"。
第 5 条尤其关键：它堵住了"我选择沉默但仍在刷屏"这个漏洞——
沉默必须是**输出层面**的沉默，不是**语气层面**的低调。

**本项目接口（v1.2 落地）**：本项目 `schedule`（`message` / `wake` / `repeat_interval`）已有后台唤醒能力，无机器可读的 notify 通道。
落地形态（§3 第二档裁决）：**本节条款（含环境适配）+ `schedule` 调用 / 唤醒轮次时的模型自检**——
发起唤醒前自问"结果是否属于第 2 条 NOTIFY 类（完成、失败、实质状态变化、需要用户行动）"；
被唤醒的轮次按第 1-6 条 + 环境适配收敛输出。**不做程序门禁**——依据 `AGENTS.md` admission asymmetry：
这个二分是内容语义裁决，模型加现有工具可自行判断（与 RULE-AI-08"指标不自动等于动作"同源）。

**环境适配（v1.1 补）**：第 5 条"零散文"的前提是 Sol 宿主有机器可读的 notify 通道。本项目是对话式 UI，
`schedule` 的 wake 是**同会话一次性续跑**（schema 事实，不可递归），用户在流里或稍后回看——空响应只会造成困惑。
落地形态：**最小化输出**——一两句状态结论（"无变化，继续静默"），不带过程叙事、数据展开、结论包装。
精神不变（沉默在输出层面），形态适配（零冗余，不是零字节）。

### R-5 按审批模式区分验证策略

**原文出处**：L1172-L1174。

**规范条款**

| 模式 | 验证行为 |
|---|---|
| 非交互、审批模式 `never` | **主动**跑测试、lint，做完所有确保完成任务的检查 |
| 交互模式 `untrusted` / `on-request` | **推迟**到用户准备收尾时再跑，先说明打算做什么并让用户确认 |
| 测试相关任务（加测试、修测试、复现 bug） | 无论何种模式都可主动跑 |

**设计意图**：不是"要不要验证"，而是"验证的时机由谁承担成本"。
非交互模式下用户不在流里，验证的等待成本没人承担，所以要主动跑；
交互模式下用户在流里，每一次慢命令都是对用户注意力的打断。

**本项目接口**：`confirm=true` 的工具调用（`dsh_task` / `playwright_exec` / 飞书发送等）本身就是非交互语义。

**⚠️ 与本项目既有契约冲突，见 §3。**

### R-6 Ambition vs. Precision：新放开，旧手术

**原文出处**：L1176-L1182。

**规范条款**

1. **无既有上下文**的任务（用户从零开始）→ 放开做，可以有野心和创造力。
2. **既有代码库**中的任务 → 精确做到用户要求的程度，尊重周边代码，不越界
   （不必要地改文件名、变量名等）。
3. 用判断力决定交付的细节与复杂度层级：**范围模糊时**做高价值的创造性补充，
   **范围明确时**保持精准和克制。不要镀金。

**与 RULE-AI-24 的接口**

RULE-AI-24（先保真、再优化）已经覆盖了第 2 条的核心：**精确手术式改动**是本项目防退化契约的既有立场。
R-6 的**新增价值**在第 1 条和第 3 条——本项目现有规则文本里没有"新项目应当放开"这一面，
而第 3 条的判据（范围模糊 vs 范围明确）给出了第 2 条之外的可操作分界。

**范围限制（v1.1 补）**：第 1 条"放开做"放开的是**方案空间**，不是**授权范围**。新项目同样受当前用户指令
与安全边界约束，创造力不得成为越过授权的理由。

## 3. 落地裁决（分三档，不是全收）

> 2026-10-11 01:07 用户重申确认本节全文，由落地建议转为**裁决记录**；v1.2 据此同步头部状态、

### 可直接用于本项目 playbook 层

- **R-1**（表达层，无冲突）、**R-3**（补足 RULE-AI-01 未覆盖的努力度面）、**R-6**（补足"新项目放开"面）。
- **R-2** 作为 RULE-AI-23 的**互补补充**引用，不单独成为规则。

### 需人工批准才能升格为 RULE-AI-xx

- **R-4**：本项目 `schedule` 已有后台唤醒，但缺 NOTIFY/DONT_NOTIFY 二分。
  按 `AGENTS.md` 的 admission asymmetry，新增**硬门禁**必须先证明"模型加现有工具无法自行判断"。
  我的判断是：**这个二分应该由模型判断，不该做成程序门禁**。
  它是"什么值得打扰用户"的内容语义裁决，与 RULE-AI-08"RULE-AI-08：指标不自动等于动作"同源。
  落地形态应是 playbook 条款 + `schedule` 调用时的自检，不是新的硬拦截器。
- **R-2 第 4 条**：本项目的本地文档（`AGENTS.md`、`docs/DEVELOPMENT_REPAIR_SAFETY.md`、tool schema）
  中包含**真实安全与授权边界**。Sol 那条的语境是它自己的 markdown 文件，没有安全分层。
  直接照搬会削弱本项目的硬边界。**限定适用范围后才可采纳**。

### 不建议照搬

- **R-5 与本项目防退化契约冲突。**

  Sol 说交互模式下"推迟跑测试直到用户准备收尾"。本项目 RULE-AI-24 六问第 6 条要求：
  **最终 gate 必须对 staged / isolated candidate 运行，不能被旧 HEAD 或假绿欺骗**；
  `AGENTS.md` 也要求"Turn real incidents into regression tests and run final gates against the actual staged/isolated candidate"。

  若采纳 R-5，模型在交互模式下会把 gate 推迟到用户说"收尾"——而这恰恰是 RULE-AI-24 事故的成因形状。
  **结论**：采纳 R-5 的**分档意图**（验证成本由谁承担），但**否决其具体策略**。
  本项目验证纪律以 RULE-AI-24 为准，不按审批模式分档。
  **否决的边界（v1.1 补）**：不可分档的是**最终 gate 的位置**——必须对 staged / isolated candidate 运行；
  可分档的是**中间迭代的验证粒度**——交互模式下快速冒烟可以省，省不掉的是 gate。否决不扩大化到"一切验证时机同档"。
