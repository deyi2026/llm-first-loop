# P1 `lfl init` 首次使用向导：实现契约与 RED 验收（v0.1）

状态：**Stage B / 隔离实现验证中**。Stage A 已有真实 RED 8 项；当前隔离分支正在将其及安全案例转 GREEN。未经独立审查和 R9 通过前，不声明可以合并、发布或生产生效。

## 1. 权威事实及目的

- 安装版入口为 `llm_loop.cli.application_main`。当前支持 `chat` / `web` / `paths` / `check-install` / `doctor`，**没有 `init`**。
- `lfl doctor` 已有独立的离线只读检查：配置、模型必需键、包、数据路径、工作路径、资源路径；其返回值不代表 Provider 可用。
- `--config` 优先于进程 `LFL_ENV_FILE`，再到安装应用根（`LFL_HOME` 或平台默认）`.env`；源码模式沿用当前源码根默认 `.env`。进程变量优先于配置文件，已设置的空值不能被文件悄悄覆盖。
- `read_env_file_values()` 是与现有 CLI 相同的引号、注释和重复键解析契约；不得引入第二套 parser、安装状态或服务控制面。

目标：从安装成功到首次明确选择 `chat` / `web` 之前，让人知道应该配置什么、会在哪儿写入，以及什么仍未被验证。**向导只处理本地首次配置，不代替模型和服务的真实验收**。

## 2. 用户流程（MVP）

| 命令 | 约束和结果 |
|---|---|
| `lfl init --plan` | 完全离线、非交互、只读的人类预览；不创建配置或目录；状态不依赖终端是否 TTY |
| `lfl init --plan --json` | 稳定 `lfl.init.plan/v1` 结构化输出，仅包括配置来源、是否已有文件、需要哪些键、阻断原因、下一步，不回显秘密值或目标绝对路径 |
| `lfl init` | 仅在 TTY 下交互；逐项说明目标和配置来源，允许跳过 `LLM_MODEL`，必须二次明确确认才能写入 |
| `lfl --config /chosen/config.env init` | 只允许新建明确指定的文件；既有文件只读提示并转 `lfl doctor`，不自动修改或覆盖 |
| `lfl init --json`（无 `--plan`） | 错误码 2；禁止用 JSON/管道模式绕过互动确认 |
| 非 TTY 的 `lfl init` | 错误码 2，提示 `lfl init --plan`，不读密钥、不写盘 |

预览 JSON 应至少包含 `schema`, `status`, `read_only=true`, `write_performed=false`, `requires_confirmation=true`, `target.source`、`target.exists`、`target.can_create`、`required_keys`（`LLM_API_KEY`、`LLM_BASE_URL`）、`next_steps`。`LLM_MODEL` 是可选显式覆盖，不应硬编码 DeepSeek 作为用户必选服务。有效预览本身返回 0，即使状态是 `needs_setup`；危险目标/无法解析的配置文件返回 1，语法错误返回 2。

交互顺序：①读取既有 `doctor` 只读事实和 CLI 配置来源 → ②显示新建目标、将保留的进程覆盖项和预计创建文件 → ③收集 API URL、可选 Model（普通输入）、Key（`getpass` 隐藏输入）→ ④展示不含 Key 的摘要 → ⑤明确输入 `yes` 后提交新文件 → ⑥调用既有只读 `doctor` 本地重检并展示 `lfl chat` / `lfl web` 可选的下一步；绝不自动启动它们。用户拒绝、EOF、Ctrl+C 均不提交。

## 3. 安全与写入边界

1. `lfl init --plan` 全过程不得调用 `prepare_environment`、`load_env_file`、`Engine`、Provider、网络、service_control，也不得写入 `os.environ`、`LFL_HOME` 或 `.env`。用现有只读 `doctor`/配置快照实施，不能把进程中的 Key 编进返回结果。
2. 已存在的 `.env`（包括空文件）、目标文件符号链接、目录、不可写父目录均**不自动覆盖**。既有合法祖先路径中的符号链接可**仅在用户确认前**规范化为真实父目录，写入前必须显示规范化目标并明确确认；实际持久写入的目录遍历只使用已确认的路径和逐级 `O_NOFOLLOW` dirfd，**遍历时不能再次调用 realpath**，否则会把恶意替换的祖先符号链接隐藏在检查之前。不能借路径别名逃逸到只读安装包或替换已有目标。已有配置路径让用户通过 `lfl doctor` 或自行编辑处理；v0.1 不提供 `--force`。默认来源为源码根时，不得因 `cwd` 变化而误把其他目录的 `.env` 当作目标。
3. 不因 `LFL_HOME` 已存在就将安装包内只读资源、源码目录或任意父目录当作可写数据目录。仅显式确认后按原有应用根创建所需最小目录，权限优先 `0700`；凭证配置文件权限 `0600`，不可通过标准输出、错误日志、JSON、回执或异常消息泄漏 Key。
4. 安全提交需避免两个进程同时创建导致覆盖：在目标目录创建随机且 `O_CREAT|O_EXCL`、权限 `0600` 的临时文件，写入、`flush/fsync`，再用同目录无覆盖的原子发布策略。必须阻止目标 symlink、`..` 路径逃逸与文件名竞争。失败清理**只属于本次事务**的临时文件，不删除/修改任何已有配置或用户数据；必要时保护父目录创建操作。
5. 保留文件格式解析语义：重复键首项有效，引号内 `#` 不是注释；文件中值含换行、回车、控制字符或无法安全序列化必须明确拒绝（防 `.env` 注入）。`--json` 永不包含提供过的密钥、URL 查询参数或原始完整错误信息。HTTP 非本机连接只作安全提示，不在未获得用户选择时替用户更换 Provider。
6. 不自动发送测试请求、安装扩展、调整模型参数、启动/重启 Web / Feishu / Learning 或修改当前进程环境。首次设置成功不是 Provider 验证成功，更不是安装 Goal 完成。

## 4. 故障/竞争/回退验收矩阵

| Case | 预期 |
|---|---|
| 未配置、非 TTY 请求 `--plan --json` | 输出无秘密的 `needs_setup` 预览、返回 0，零写入零 Provider |
| 进程已有完整必要配置，无默认 `.env` | 预览报告环境来源，明确无需新建；不从文件替换空 shell 键 |
| 显式配置文件存在（含无法读取） | 不覆盖、不修改；存在提示使用 doctor，读取错误有界且脱敏 |
| 指向符号链接/目录或安装包内部目标 | 禁止写入，明确报阻断；即使 `--plan` 也无读 Secret 的路径跟随 |
| 用户取消、非 TTY、EOF/KeyboardInterrupt | 完全没有新文件/临时文件/状态目录，退出码稳定 |
| 提交确认前 Key 含换行、CR、控制字符 | 拒绝；配置或日志不泄漏原始输入 |
| 两进程争抢同一目标 | 恰好一个发布成功，另一个拒绝；已有目标不被替换 |
| `doctor` 在配置写入后返回警告 | 如实显示“不满足本地就绪”，保留成功创建的配置并给修复建议，不假装 Provider 可用 |

## 5. 验收顺序与明确禁止

**Stage A（已完成）：** 最新 `main` 隔离 worktree；本设计与针对未实现 `lfl init` 的8项真实 RED（因未识别命令落入有副作用 bootstrap，而非导入异常）。Stage A 不写实现，也不修改 `main`。

**Stage B（隔离实施中）：** 从 RED 用例到 GREEN，增加原子写与并发/恢复验证、安装 wheel 全新环境的真实首用测试；针对目标源码 + 精确 SHA 获取独立 GLM-5.3 Rule28 Host PASS（P0/P1=0）后，才运行原版完整 R9 和受管提交。确认没有偷写密钥、覆盖既有配置或网络调用。所有 Stage B 结论以测试日志/实际退出码而非本设计声明为准。

**Stage C（独立授权）：** 对最新 `main` 独立集成并通过 Rule34 专项审查；获得单独合并授权后才在安全条件下 `--ff-only` 合并。push / Release / 发布 / 重启另行授权。后续升级备份回滚与扩展管理不纳入本单元。
