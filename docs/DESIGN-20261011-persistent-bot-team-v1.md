## 1. 背景与问题

### 1.1 两类多智能体形态的分化

2025-2026 的开源生态中，多智能体已分化为两类：

1. **任务编排型**（AutoGen / CrewAI / LangGraph / LFL 的 spawn_subagent、workflow_run、dsh_task）：为任务拉团队，干完散伙。成熟、工程保障好。
2. **常驻成员型**（ds-bot、部分聊天产品）：bot 是跨对话可寻址的持久身份，有记忆、有私聊、有群聊。开源实现稀少，ds-bot 是少数真做 bot-to-bot 私信+群聊的。

### 1.2 LFL 现状差距

| 维度 | ds-bot（DIY 实现） | LFL spawn_subagent | 差距方向 |
|---|---|---|---|
| 生命周期 | 跨对话持久身份 | 进程结算制，completed 即散 | **LFL 缺** |
| 横向通信 | bot↔bot 私信 + 群聊轮次制 | 仅 parent↔child | **LFL 缺** |
| 会话隔离 | 自己设计「一人一份隐藏会话」 | child 天生独立会话 | **LFL 强** |
| 验收 | 无 | acceptance 自检协议 | **LFL 强** |
| 崩溃恢复 | 无（alpha 期） | 租约+拓扑磁盘真相 | **LFL 强** |
| 上下文治理 | 上下文管家（check 线二选一） | 有 building blocks，无自动决策 | **LFL 半缺** |
| 敏感信息 | 密钥三正则拒收 | 无专项防线 | **LFL 缺** |

### 1.3 问题定义

**在不动 LFL 程序边界的前提下，用现有工具拼装「伪常驻 bot 团队」：身份跨任务延续、成员可协作讨论、上下文不失控、敏感信息有防线。**

程序级演进（真常驻）作为后续建议，不在本设计实施范围内（见 §9）。

## 2. 目标与非目标

### 2.1 目标

- **G1 身份连续性**：同一个 bot 跨任务/跨父会话可识别、可复用；档案随每次结算更新（它做了什么、表现如何、下次注意什么）。
- **G2 横向协作**：≥2 个 bot 协作完成一个任务，支持「群聊」形态：有秩序（轮次）、有引用（@）、可弃权（[PASS]）。
- **G3 上下文治理**：child 上下文到压力线前主动决策（换段/压缩），不静默丢失用户原始要求；被压缩内容可检索回取。
- **G4 安全防线**：bot 输出中的凭据类敏感信息被识别并隔离，不进群聊、不进档案。
- **G5 可追溯**：每次往来有编号，事后能还原「谁在何时对谁说了什么、导致了什么」。

### 2.2 非目标

- ❌ 不修改 LFL 程序边界：阶段 0/1 全部用现有工具（experience、spawn_subagent、agent_message、handoff_now、source_synopsis 等）拼装。
- ❌ 不复刻 ds-bot 的「多用户聊天产品」形态（用户面、私聊入口）——我们只服务 LFL 父代理编排。
- ❌ 不做常驻进程。bot「存在」= 档案卡存在 + 可被再次唤起，不是进程活着。
- ❌ 不追求 ds-bot 的记忆后厨全量机制（MEMORY_LIMITS 四级结构）；档案压缩用「重写+archive」（v1.1 修订，见 FR-5：synopsis 绑定的是 source 确切 SHA，档案卡是可变的，绑卡会静默过期）。

## 3. 术语

| 术语 | 定义 |
|---|---|
| bot | 有持久档案的角色化子代理实例。spawn 一次 = 一次「 incarnation（化身）」 |
| 档案（dossier） | 一张 experience 卡：角色定义 + 使用记录 + 沉淀教训。bot 的持久身份载体 |
| 房间（room） | 群聊状态：成员表、消息日志（带 seq）、各成员 seen 游标、轮次计数。**v1.1：外置为工作区房间日志文件**（每 exchange 追加一行），父代理可据此重建，不再只存活于父代理内存（原设计在父代理 handoff 换段/中断时会整个丢失，见 R2/NFR-3） |
| 轮次（turn） | 房间中的发言权单位：一人发言 → 其余成员各获得一次响应机会 |
| 管家（steward） | 上下文压力决策流程：到线触发一次独立小决策（换段 or 压缩） |
| 往来编号（exchange id） | 一次「注入→响应」的配对标识，用于追溯 |

## 5. 总体设计：三层架构

```
┌─────────────────────────────────────────────────┐
│ 父代理（编排者 + 房间主持人 + 中继 + 聚合验收）      │
│                                                 │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│  │ bot A    │  │ bot B    │  │ bot C    │      │  每个是 spawn_subagent
│  │ (档案→   │  │          │  │          │      │  的独立会话 child
│  │  唤起→   │  │          │  │          │      │
│  │  回写)   │  │          │  │          │      │
│  └──────────┘  └──────────┘  └──────────┘      │
│      ↕agent_message（父中继私信；无横向直连）      │
└─────────────────────────────────────────────────┘
  身份层：experience 档案卡（FR-1）
  通信层：父中继 + 房间轮次协议（FR-2/3）
  管家层：上下文压力决策（FR-4/5）+ 凭据防线（FR-6）
```

设计原则：

1. **父代理是唯一的编排真值源**。房间状态、seq、验收聚合由父代理维护；bot 之间零直连（当前 LFL 也做不到直连）。房间日志外置为工作区文件（v1.1），父代理 handoff 换段后可重建房间，与 NFR-2 归档共用同一份文件。
2. **bot 是无状态的化身**。任何持久信息只在档案卡里；化身内上下文是易失的，重要结论必须随结算回写。
3. **协议抄成熟的**。房间轮次、管家阈值、凭据正则语义均照搬 ds-bot 已验证设计，只做 LFL 本地化。

## 6. 详细设计

### 6.1 档案卡 schema（FR-1）[设计]

每 bot 一张 experience 卡，标签含 `bot-dossier`，正文为受控 Markdown：

```markdown
# BOT：<名称>
## 角色定义
- 职责：（一句话）
- 指令：（唤起时注入的角色 prompt 原文，冻结区，改动需人工确认）
- 能力边界：（能做什么/不能做什么/需要什么权限）
## 使用记录（最近 3 次原文，更早 synopsis 化）
- [exch-<id> | <日期> | <任务名>] 结论摘要 / 表现评价 / 下次注意
## 教训
- （跨任务沉淀的 do/don't）
```

生命周期：

```
创建：save_experience(record_kind=experience, tags=[bot-dossier, <bot名>])；卡名固定「BOT:<名>」（唯一命名约定）
唤起：search_records(experience, "BOT:<名>") → 水合 → 拼进 spawn 的 task/context
      （spawn 显式 inherit=false：防父会话历史整体泄入 child，bot 只见档案+任务+房间所需上下文）
回写：结算后 refine_experience(record_use, note=本次表现+教训)
```

v1.1 新增防护：

- **防身份分叉**：唤起检索未命中时**不得静默新建档案**——并发两次「检索未中→各建一卡」会让同一 bot 分叉成两张身份卡。未命中必须报父代理裁决（确认是新 bot，还是换检索词重试）。
- **防档案静默漂移**：瘦身只走 FR-5 的「重写+archive」，不做原地 synopsis。

**[待验证] V1**：experience 卡正文长度上限是否足以容纳完整档案；record_use 的 note 512 字符上限 [LFL 事实] 是否够一次使用记录（不够则拆多卡或引 synopsis）。

**[待验证] V5（v1.1）**：search_records 是否支持按 tags 精确过滤 [LFL schema 未声明 tags 参数]；若不支持，只能靠「BOT:<名>」命名约定兜底——POC 需实测同名/近名词碰撞时的检索准确性（命中错卡=错误人格被唤起）。

### 6.2 父中继私信协议（FR-2）[设计]

消息格式（父代理注入 child context 时使用）：

```
[Message from <bot名> · exchange <id>]
<内容>
[end]
```

规则：

1. 父代理**必须裁决后才转发**：A 说的话不自动流给 B；父代理判断「B 需要知道吗」并可能改写（压缩/去除噪音），但保留来源标识。
2. exchange id 单调递增，格式 `exch-<房间或任务短名>-<序号>`；父代理在房间日志中登记。
3. child 收到消息后若需回复，输出以 `[Reply to <bot名> · exchange <id>]` 开头，父代理负责路由。
4. 仿 ds-bot：**bot 不应感知「上下文被换过」**——凡被管家压缩掉的内容，须已进 synopsis 或归档日志，可经父代理代查回取。

### 6.3 房间轮次协议（FR-3）

照搬 ds-bot groups.js 的已验证设计 [源码事实]，常量本地化：

| ds-bot 常量 | 值 [源码事实] | 本设计取值 | 理由 |
|---|---|---|---|
| ROOM_LOG_MAX | 60 | 60 | 单房间消息日志上限，超出滚出（滚出部分父代理归档） |
| FIRST_LOOK（新成员入房首看） | 12 | 12 | 控制首次注入量 |
| DELTA_MAX（增量单次上限） | 24 | 12 | LFL child 更贵，从严 |
| 每成员每轮发言上限 | 2（admin 4） | 2（父代理=主持人不受限） | 照搬 |
| 房间轮次上限 | — | 3（新增） | NFR-1 成本上限，ds-bot 无此限制是其「费用黑洞」成因之一 |

协议细节（全部 [源码事实] 照搬）：

1. **seq 游标**：房间日志每条消息带 seq；每成员维护 seen 游标，注入时只给 `seq > seen` 的**他人**消息。成员自己的发言不回显（其内容已在其自身会话中）。
2. **stripOwnName**：成员输出若以 `Name:` 回显自己的名字前缀，父代理剥离后再入日志（防日志自污染）。
3. **[PASS] 变体**：`[PASS]`、`【PASS】`、`[跳过]`、`【过】` 等中英括号变体均识别为弃权。
4. **@ 最长名优先**：`@Mx` 不误读为 `@M`；点名后由被点者接续下一发言权。
5. **发言权转移**：上一位发言/弃权后，其余成员依次获得响应机会；全部弃权或轮次耗尽则房间回合结束。

**[待验证] V2a（机制，先于一切算术，v1.1 拆出）**：向**运行中** child 发 agent_message，child 能否在自己的执行循环中途收到、以何种时序回应？关键在 spawn 的 task 形态：若 task 是「干完即结算」，child 很可能在父代理发起下一轮前就已 settled，房间无从谈起。**唯一可行路径**：spawn 时就给 child「房间成员循环」任务——收到消息→发言（或 [PASS]）→等待下一条，直到收到 `[ROOM-END]` 才结算。此机制不成立，房间协议整体不成立（此时直接走批处理回退形态）。

**[待验证] V2b（配额算术，v1.1 前置推演）**：若靠 agent_followup 续话已结算 child——父级限额 ≤4 次/15min [LFL 事实]，而 3 bot × 3 轮至少需 6 次续话，**算术上不可行**；且每 child ≤2 次刚好卡满 3 次发言（初始+2 续话）、零容错余量。**结论前置：followup 只能作个别追问，不能当房间主通道；主通道只能是 V2a 的长驻 child 消息循环。** 附带实测：长驻等待中的 child，其租约（subagent_lease expires_at）会否因「无进展」被 fleet 回收。

### 6.4 上下文管家（FR-4）[P1]

照搬 ds-bot steward.js 阈值 [源码事实]：

```
usable = window − reserve        （reserve 至少占一半窗口）
check  = 0.8 × usable            # 决策线：越线即触发管家
hard  = 0.95 × usable            # 硬线：绝不允许触及
管家调用预算 6,000 tokens；决策输出 ≤1,500 tokens
```

LFL 本地化映射：

| ds-bot 机制 | LFL 对应 |
|---|---|
| 检测上下文用量 | `architecture_status(dimensions=[context_usage])` [LFL 事实] |
| switch（活干完了） | `handoff_now()` + 开新段继续 |
| compact（活在进行） | `source_synopsis(save)` 就地压缩旧消息 |
| 被压缩内容可查回 | synopsis 本身 + 证据检索 |

管家决策提示词必须包含的前置核查 [源码事实，逐字保留语义]：

> 把用户要求的每一部分对照助手实际做的，找助手问了但用户没答的问题。

决策输出 = 二选一 + **六项 checkpoint**（换段时写入 handoff，压缩时写入段首）[源码事实]：

1. 逐项结果（带原始标识符，不许改写用户用语）
2. 决策与理由
3. 被拒绝的方案（防止下一段重提）
4. 用户约束（原话）
5. 未答请求（用用户原话标注「待答」）
6. 下一步顺序

**[待验证] V3**：child 会话内 context_usage 是否可被父代理查询；若不可查，管家降级为「child 自报 + 父代理按消息数粗估」，check 线按消息条数近似。

### 6.5 凭据防线（FR-6）[P1]

ds-bot 三正则的语义（正则原文未抄录，本设计按语义重写并补 LFL 场景）[源码事实→设计]：

| 检测 | 语义 | ds-bot 排除项（防误报，照搬） |
|---|---|---|
| 密码给出式 | 「密码是 X」「密码：X」 | 「密码管理器」「密码策略」「因为」「作为」等上下文 |
| 密码后置式 | 「用 X 当密码」「以 X 作为密码」 | 同上 |
| 证件号 | 护照/身份证/社保号模式 | — |
| 长数字 | ≥15 位连续数字 | — |

LFL 侧动作：父代理在**入档案前**和**入房间日志前**各跑一次检测；命中 → 拒收 + 内容移入隔离卡（独立 experience 卡，tags 含 `secret-quarantine`，正文脱敏只记「某 bot 在 exch-N 泄露凭据类型」）+ 向该 bot 回一条警告消息。

v1.1 补强（拷问发现的三个绕过/误伤面）：

1. **第三检查点**：结算回写前对 child 最终输出**及其写入工作区的文件**复查——bot 可能把凭据写进 artifact/代码文件，完全绕过消息面检测。
2. **误报豁免**：编码类 bot 常写长数字测试向量/时间戳/固件号，长数字检测需对代码块与测试夹具上下文豁免；豁免规则进 R6 样本集一起测（否则实现者类 bot 会被反复误伤拒收）。
3. **归档不扩散**：房间日志落盘归档前跑第二次全量扫描；未过扫描的房间只归档脱敏结构摘要（seq/发言者/动作），原文不落盘——防线是语义重写、漏检非零，归档会把漏检秘密持久化放大。

## 7. POC 方案（阶段 0）

**任务**：3 个 bot（如：调研员/实现者/评审员，均可复用上轮分析产物）协作完成一个小型多步任务（例：「给 X 方案挑刺并出修订建议」）。

**验收 gate（全部满足才进阶段 1）**：

1. ✅ 档案卡创建→唤起→回写全链路走通，第二次唤起能看到第一次的记录
2. ✅ 至少 2 轮房间轮次完成，日志含 seq、@、[PASS] 或等效弃权各至少一次
3. ✅ 一次父中继私信成功（A 结论影响了 B 的输出，可从 B 的输出引用追溯）
4. ✅ 聚合验收通过：3 个 bot 的 acceptance 各自结算 completed
5. ✅ V1–V5 五个待验证项有明确结论（**V2a 机制成立与否决定房间协议存废**；批处理形态是否替代逐个唤起）
6. ✅ 全程 token 成本有测量，能回答「这套玩法的单价」。测量手段本身是 [待验证] V4（v1.1）：当前无已知的按 child 用量回执工具 [LFL 事实：仅 model_catalog 档位 + architecture_status(context_usage)]；若无实测回执，降级为「档位 × 会话/轮次」结构化估算，结论中如实标注「估算」，不得冒充实测

**POC 前置（v1.1）**：adjust_strategy 提高父会话 max_iterations/timeout——房间多轮 = 大量串行工具往返，防父预算中途耗尽（见 R10）；实测 V2a 前不动真任务。

**POC 明确不做**：管家自动触发（手动模拟一次即可）、凭据正则自动化（人工核对）。

## 8. 风险与开放问题

| # | 风险/问题 | 影响 | 缓解 |
|---|---|---|---|
| R1 | agent_message 对运行中 child 的中途送达/回应机制未验证（V2a）；followup 配额算术上撑不起 3×3 房间（V2b，≤4 次/15min < 需 6 次） | 房间协议不可行 | V2a 为 POC 第一实测项；不成立 → 批处理回退形态（§6.3）；长驻 child 租约回收需同测 |
| R2 | 父代理自身上下文被房间日志+多 bot 回执撑爆 | 编排质量下降 | 父代理先对自己跑管家（FR-4 也适用父）；换段后从外置房间日志文件重建房间（v1.1，原「滚出即归档」不解决换段续命） |
| R3 | 档案卡污染（bot 表现差仍回写，档案越来越差） | 坏 bot 反复被唤起 | 回写必须含「表现评价」**且绑定任务类型**（v1.1：跨任务类型差评不触发退役）；连续 2 次同类型差评 → archive 档案（bot 退役） |
| R4 | 子代理工具面继承假设不实（历史记录称子代理工具受限，与当前 schema 声明矛盾） | bot 能力设计与实际不符 | POC 第一步实测：spawn 后让 child 报告可用工具清单 |
| R5 | 多 bot 并发写同一文件/工作区 | 冲突损坏 | 房间协议天然串行（轮次制）+ 各 bot 输出目录隔离 + 父代理是唯一合并点 |
| R6 | 密钥防线是语义重写非原文正则 | 漏检/误检 | P1 落地前用脱敏样本集测一遍（自建 20 例，含 §6.5 豁免用例） |
| R7（v1.1） | bot 档案+隔离卡大量涌入 experience 域，污染 LFL 自身经验检索（停滞 discovery 命中无关 bot 记录，学习闭环质量退化） | 主学习闭环受损 | 「BOT:」命名前缀 + tags 约定 + 检索时显式排除；活动档案池上限（初值 ≤20，POC 后校准）+ 长期不用即 archive |
| R8（v1.1） | bot 拿到 spawn_subagent/workflow_run/service_control/send_feishu 等编排与外呼工具 → 递归舰队、越权重启、外发 | 成本爆炸+安全 | NFR-6 默认拒绝白名单；房间日志登记每次 requires；R4 实测兜底 |
| R9（v1.1） | 房间日志/归档文档把漏检凭据持久化扩散（防线漏检非零，落盘=放大） | 泄露放大 | §6.5 归档前二次扫描 + 未过只归档脱敏结构摘要 |
| R10（v1.1） | 父会话迭代/时间预算被房间多轮串行往返耗尽 | 任务中途停摆 | POC 前 adjust_strategy 提额；NFR-1 轮次/成员上限是主缓解 |

## 9. 演进路线（超出本设计实施范围，供 submit_evolution 参考）

- **阶段 0**：POC（本文档 §7）
- **阶段 1**：伪常驻完整版（FR-1~8 全量，档案池成体系）
- **阶段 2**：程序级演进建议（需人工审批）：
  1. **child↔child 消息原语**：父中继是 workaround，规模上去后父代理是瓶颈与单点
  2. **durable bot id**：spawn 声明引用持久 bot 档案，程序级绑定（spawn 时自动水合、结算自动回写），替代本文档的 prompt 级拼装
  3. **群聊原语**：多 child 共享房间 + 轮次调度下沉为运行时机制
