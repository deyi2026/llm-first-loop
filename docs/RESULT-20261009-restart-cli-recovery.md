# 重启配置查询与单次恢复修复

## 事故事实

2026-10-09 的受管 Web 回执显示两次不同失败：13:55 目标代码不支持已写入的预算配置；14:53 的 `svc-47a97795f5114231b7be6597d5f11fb9` 则发生在新增重启加固提交 `993f9c2f8` 上。后者的 resolver CLI 无条件进入 `--check-toml` 处理，把 `WEB_PORT` 当作文件路径，输出“runtime.toml 不存在，跳过 schema 校验: WEB_PORT”。脚本把这句提示当成端口，未找到实际旧 PID，并用错误的端点检查新服务。旧 Web 仍在 8903 监听，不能把该回执中的 `web_stopped` 等同于真实停机。

新加固中的自动回滚也存在可复现缺陷：desired 代次推进后复用原失败 action，既有部署身份检查正确拒绝了第二次物理执行。因此只有候选选择单测不足以证明回滚能力可用。

## 修复范围与行为

- resolver 分离 `WEB_PORT`/`WEB_HOST` 值查询与显式 `--check-toml`；查询使用 canonical runtime 配置，错误写 stderr，非法参数返回 2。
- Web/all 在任何 stop/start 之前验证端口范围 1..65535。异常输出落 `not_started` 回执，释放准入，不把诊断字符串传给进程探针。恢复脚本原有可执行权限。
- 单次自动恢复使用新的受管 action，精确绑定回滚部署 generation，接管原终态屏障，并走原有完整 worker 核验。原动作保留失败事实、原部署身份和恢复 action 引用。
- 回滚回执限定目标服务；并发 CAS 发布冲突尊重新操作者；恢复来源阻止二次回滚。无回执/陈旧回执不能证明停机，不自动制造新的物理操作。脚本 rc=0 但身份核验缺失时继续保留恢复屏障。
- 今日新增配置测试改用临时有效 TOML，不依赖被 Git 忽略的本机生产配置；触碰文件的既有 Ruff/Pyright 诊断以等价上下文管理和显式类型收口，不修改诊断基线。

## 验证与运行态边界

原候选上的首批回归为 7 failed；修复后重启、resolver、生命周期、准入、Web 排队及 shell 相邻集为 176 passed。新增回归还覆盖真实脚本遇到事故诊断字符串、端口 0/65536 时零物理操作；恢复失败单次封顶；预检失败释放准入；缺少恢复身份时不释放；错误服务回执不作为候选；并发发布胜出。

本变更在独立修复工作树准备，通过 R9 staged PROBE 完整门禁后提交，使用受管 CAS 发布和 Web-only 重启做运行态验收。Feishu、Learning 和预算批准均不在本修复的变更范围内；不进行真实模型调用来验证服务重启。生产上线结论必须以最终受管 action、live manifest、健康接口和准入屏障为据，不能从单测或脚本返回码推断。

最终部署候选以已运行的 `987f8642f` 为基线，只带重启修复，排除插件分支的未资格化类型错误。完整门禁还暴露了 `test_settings_llm_timeout_uses_float_parser` 对隐式 `LLM_BASE_URL` 的依赖；未修改的 `987f8642f` release 单点复现相同缺失配置异常。该测试补显式虚拟 URL，保留原小数解析断言，不修改生产配置或静态诊断基线。
