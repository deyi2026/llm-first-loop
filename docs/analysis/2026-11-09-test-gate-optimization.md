## 1. 核心判断

用户提出的方向成立：**测试应主动构造边界、故障和回归场景，尽早暴露真实问题；问题修复、适用检查完成后，就应进入已授权的 push 或部署。** 同一事实不应因为换会话、换动作名称或重复触发工作流而被反复证明。

目前的主要问题不是“测试太多”这一项，而是：

1. **执行口径分裂**：本地 R9、GitHub CI、Release 各写一套命令和准备步骤，测试集合、信号测试处理、WebUI 准备与失败处理不同。
2. **部分门禁阻碍发现问题**：全量测试先等独立审查，随后才发现依赖、路径、静态扫描等早可发现的问题，修订后又进入审查循环。
3. **证据复用受会话与短期资格限制**：已经有部分复用能力，但同一候选跨阶段、跨会话仍易重复；合并与 push 审查还可能重复通读代码。
4. **红灯处理同时存在过严和过松**：捆绑代码的风格债可能挡住整轮验证；并行失败却可能因一次串行通过而被直接放行。
5. **交付终点不够明确**：没有新增问题时，还可能继续加测试、追低优先级建议、重新冻结与重审。

建议目标是：**一套执行口径、一次必要的完整验证、一份可复用的审查证据；每个红灯有根因和出口，通过后停止追加流程。** 对变化后的候选补足受影响验证；对身份、依赖或平台不同的结果保持区分。

“没问题”应落实为“本次变更相关的必要检查已完成、没有未处置的交付阻断项”，不能把缺依赖、未运行、超时或缺失平台证据记成通过。

## 2. 本轮核实到的现状

### 2.1 三条执行链仍未统一

| 入口 | 当前实际执行 | 已确认的差异 |
|---|---|---|
| 本地 `scripts/ci_gate.sh` | Ruff、环境声明检查、Pyright、隔离 HOME、候选 WebUI 构建、tier0、xdist 全量、失败文件串行复跑、架构提示汇总 | 全量 pytest（`:139`）**未显式写 `-m`**，选择集来自 `pyproject.toml` addopts 的 `-m "not real_llm"`，故实际**不排除 `serial_signal`** |
| GitHub `ci.yml / test` | 冻结 Python 依赖、Ruff、Pyright、串行 pytest，明确排除 `real_llm / serial_signal`（`ci.yml:60`） | 未调用本地统一脚本；该 job 未显式执行 env-pin、WebUI 构建和本地的 HOME/浏览器准备步骤 |
| GitHub `release.yml / gate` | 冻结依赖、版本检查、Ruff、要求完整结果的 Pyright、串行 pytest | 只排除 `real_llm`（`release.yml:80`）；WebUI 在后续构建 job 才构建；也未调用本地统一脚本 |
| WebUI | `npm run build` 已包含 TypeScript 检查与 Vite 构建；另有 `npm test` 即 `vitest run`（实测 **57** 个 `*.test.*`/`*.spec.*` 文件） | 上述三条入口均未显式执行 Vitest；“构建通过”不能覆盖交互行为测试 |

**直接结论：目前不能把三个入口的绿灯当作等价证明。** 本地“唯一全量口径”的规则文字与工作流实现尚未完全对齐。相关入口的差异有源码依据，但本轮未重新执行 GitHub 工作流，不能据此断言它们当前一定失败。[S1–S4]

**这不只是“三套口径不统一”，而是一处规则自述冲突（P0-1）。** 现行 `docs/ai_rules.md` 同时写着两句互相矛盾的话：第 1 条要求“PASS 才全量测试”，第 5 条“全量口径”把 `ci_gate.sh` 定义为唯一口径并明文声明“其内 pytest … 排除 `real_llm`/`serial_signal`”；实测 `ci_gate.sh:139` 无 `-m`、`pyproject.toml` addopts 只排除 `real_llm`。因此**规则承诺的测试集合与脚本实跑的集合不是同一份**，绿灯语义无法仅凭规则文字判定。另有一处范围错位：第 1 条把 `src/、tests/、scripts/、tools/、webui/` 都列为代码闸覆盖范围，而静态检查器 `changed_python_paths()` 的前缀只有 `("src/", "tests/", "scripts/")`——`tools/` 下 14 个 `.py`、`webui/` 下的前端改动不在其 touched 判定内（见 §6.2）。[S1、S4、S8]

### 2.3 已有的优化应直接复用

当前已经具备以下能力，无需重新设计一套：

- 功能分支 push 已不再触发整套 CI，主要由 PR 触发；PR 旧运行可取消。
- Host 支持 patch 范围、`previous_child_id` 窄复审、`UNAVAILABLE` 分类。
- 同 parent、同内容、同目标的 PASS 已有 30 分钟、最多 3 次复用；另有严格 no-delta 的派生全量复跑资格。
- 本地 R9 已设置候选源码 `PYTHONPATH`、私有测试 HOME、WebUI 构建和默认 4 worker。
- push 审查启动前已增加未入库知识资产检查，能提前发现一类廉价阻断。
- Release 已有 draft 和 manifest 收口能力。

**本次应补剩余缺口，不再重复建设。**[S1–S3、S8]

## 3. 哪些门禁应保留，哪些应优化

| 项目 | 建议 | 理由与最小边界 |
|---|---|---|
| 真实事故回归、关键路径和边界测试 | 保留 | 直接验证错误行为是否消失，防止退化 |
| 权限、数据完整性、重复执行、敏感信息与工件身份检查 | 保留硬阻断 | 失败直接影响用户、数据或对外交付 |
| 独立代码审查 | 普通代码候选默认一次；修改后窄复审 | 审查解决代码风险，避免同一补丁在测试、合并、push 三处反复全文审 |
| “全量测试之前必须先 PASS” | 建议调整 | 测试是发现问题的工具；隔离、无生产副作用的测试应能先跑或与审查并行 |
| 合并与 push 检查 | 保留各自动作风险检查；代码审查事实可复用，但两个动作闸互不豁免 | 合并重点是主线集成；push 重点是范围、敏感信息与 remote/ref。按 RULE-AI-34(5)“互不豁免互不替代”：合并 PASS 不派生 push 资格，push PASS 也不派生合并资格 |
| tier0 后立刻再全量 | 按反馈价值使用 | 开发回路先快测有用；同快照刚通过 tier0，最终全量已覆盖它时不必机械重复 |
| 行数、函数数、文档形状等结构指标 | 区分风险与维护提示 | 职责倒置、循环依赖等保持阻断；纯数量和排版偏好优先提示，避免为数字而拆函数 |
| 第三方原样捆绑代码的风格规则 | 独立归属与扫描策略 | 第一方业务代码保持严格；上游代码保留安全、完整性和运行验证，避免无关格式改写 |
| 一次并行失败、一次串行通过 | 保留失败证据，定性后收口 | 串行通过只能证明执行条件影响结果，不能自动证明并行红是假的 |
| 非必要能力缺失导致 skip | 允许明确标记适用边界 | 对本次交付必需的能力则是验证未完成，应到具备能力的环境补跑 |
| 同工件上传失败、同版本重启 | 只恢复失败动作 | 未改源码、构建输入和工件时，不应重新审查代码和跑全量 |
| P2 建议、观察指标 | 默认非阻断 | 有具体高风险证据时再重新定级，不把“还能改进”变成无限等待 |

上表是**规则修订建议**。本文没有使现有门禁失效；尤其 RULE-AI-28 / 34 仍须按正式变更流程（EVO 提交 + 人工审批 + 生效验证）修订和验证。**修订生效前，普通代码候选的执行顺序仍是“代码审查 PASS → 全量测试（`bash scripts/ci_gate.sh`）”**；本条不是授权，任何历史提议或本文自身都不得被当作并行启动或跳过审查的依据。规则变更还须按 RULE-AI-35 实测“应拦输入”才能宣称生效。

## 4. 建议的最短交付流程

### 4.1 普通代码变更

1. **廉价预检**：确认候选、交付基线、解释器和依赖、路径、测试可写目录、目标平台；需要 push 时提前检查认证可用性和目标，不泄露凭据。
2. **开发验证**：先跑最小回归与邻接测试，尽早暴露问题。**注意**：现行 RULE-AI-28(1) 要求“PASS 才全量测试”，故此处可先跑的是定向/邻接测试；“尽早跑全量”属修订提案，修订生效前不适用。
3. **冻结候选**：代码和必要测试稳定后取得一次独立 GLM-5.3 审查。对 REVISE 只补修订点及新增影响面的窄复审。
4. **最终验证**：候选已具有同输入、同口径、同环境的完整验证则复用；否则只执行一次必要的权威全量验证。
5. **交付**：没有未处置阻断项时，执行已授权的 push、合并或受控部署。部署补工件及目标环境验收；完成后停止追加检查。

**关于“审查与全量测试并行”（须先有授权）**：本文建议的并行只在 EVO 修订 RULE-AI-28(1) 并验证生效后适用。修订生效前，普通代码候选的顺序固定为：冻结候选 → 审查 PASS → `bash scripts/ci_gate.sh`；不得以“并行更省时间”为由提前启动全量测试。修订通过后若采用并行，必须使用同一个冻结快照；审查带来代码变化，就验证新变化，不能拿旧快照的通过覆盖新候选。

**近期最保守、也最容易先落地的版本**：先保持“最终代码候选一次完整 R9”，优先去掉环境返工、三套口径与重复审查；不要一开始建设复杂的自动影响分析。

### 4.2 不同动作不必走同一条长链

| 动作 | 最小必要验证 | 正常情况下不追加 |
|---|---|---|
| 纯说明文案 | 内容、链接、隐私与必要文档契约检查 | Python 全量 R9、生产重启 |
| 规则文档、提示词、知识卡 | 相应同步、schema、检索或行为测试；按内容风险审查 | 不能按“后缀是 MD”直接免测，也不默认全仓重跑 |
| 普通 Python 修复 | 回归与邻接测试、一次最终完整 R9、一次代码审查 | 无变化的二次全文审查与二次完整 R9 |
| WebUI 改动 | 构建中的类型检查、相关 Vitest、对应 API/浏览器验收；按实际影响接入最终门禁 | 已包含的 TypeScript 检查再机械跑一次 |
| 数据迁移、权限、Peer、自动升级、重启逻辑 | 上述验证加受影响边界的负向、集成与目标平台测试 | 无关平台、服务与模型矩阵 |
| 功能分支备份 push | 范围、隐私、目标和必要快测；明确未获生产资格 | 默认要求先达到生产发布全套资格（此项须修改现行 push 策略后采用） |
| 合并 main / 部署新版本 | 对最终集成结果有效的测试、审查与动作检查 | 重复证明完全相同输入 |
| 已验收工件重传 / 已部署版本纯重启 | 工件摘要、版本身份、动作权限、健康与实际终态 | 代码未变时重新跑代码审查和 R9 |

## 5. 红灯必须有处理出口

### 5.1 一次失败后的决策表

| 红灯类型 | 典型表现 | 处理动作 | 可以交付的条件 |
|---|---|---|---|
| 产品缺陷 | 错误结果、权限绕过、重复副作用、数据损坏 | 最小复现、修复、增加回归，复验受影响范围 | 对交付有影响的阻断缺陷解决 |
| 测试缺陷 | 固定日期过期、固定 sleep、依赖前序状态、断言内部格式 | 改测试以验证真实契约；使用可控时钟、Event、独立 fixture | 新测试能识别原错误，修复版本通过 |
| 环境/执行问题 | 依赖缺失、错误 HOME、`/tmp` 链接、浏览器未安装、资源竞争 | 修复预检/准备或换适用执行环境；补足缺失验证 | 必需证据齐全；缺失证据不记为 PASS |
| 工具/审查不可用 | 超时、无裁断、输出截断 | 标 `UNAVAILABLE`，修复调用条件，最多一次有理由的自动恢复 | 取得必要裁断或已存在有效复用证据 |
| 检查策略不适配 | 捆绑上游风格债、纯行数指标、重复命令 | 一次性修订归属和策略，用正负例验证 | 政策变更有效，必要风险检查仍能挡错 |
| 低优先级已知债 | 与本次变更和交付风险无关、已有明确处置 | 记录原因、负责人和清理期限 | 未触及本次风险；不影响必需功能或安全 |

每个问题复用现有 issue、回执或 known-red 载体，只需要记录：**节点/症状、候选与环境、根因、影响、下一动作、负责人或期限**。不新建复杂的“红灯治理平台”。

未知失败先定位一次。相同失败不改输入地反复重跑、反复请求 Reviewer，没有信息收益。停止的是无效重试；仍可继续其他独立工作。

### 5.2 纠正当前“串行绿即假红”的判据

**代码事实（本轮实测）**：`ci_gate.sh:157` 在 xdist 失败后只重跑失败文件；`:159` 打印 `⚠️ serial 复核绿 = xdist 分布假红（不阻断；文件清单如下，登记观察）`，随后**不 exit**，流程继续走到 `:190` 的 `✅ ci_gate 全链路通过`。即：一次串行绿会把整轮结论改写成“全链路通过”。

**同时必须点明它证明不了什么**（v1 未说清，易被误用）：串行复核重跑的是 xdist 的失败文件，而这些文件来自已过滤的测试集合；被 `-m` 排除的 `serial_signal` 测试**不可能出现在这个文件列表里**。因此“串行复核会顺带验证信号路径”的推论不成立——它既不覆盖、也不排除被过滤的集合。真正的缺口是：`ci_gate.sh` 根本没有执行 `serial_signal`，而规则第 5 条却声称它排除了该标记（见 §2.1）。修改 `-m` 属 P0-1，须单独走代码闸，不能靠本节的判据调整替代。

建议改为：

- 串行通过**不改变总体结论**，输出独立状态（如 `status=parallel_only_failure`），失败文件清单与首次失败日志原样保留。
- 结论行不得再打印“全链路通过”；应打印“并行阶段 N 文件失败，串行未复现，未定性”，并在回执中标注本次验证**不含**被 `-m` 排除的集合。
- 自动进行一次失败节点或必要文件范围的诊断复验，保留首次失败。
- 串行通过时标记“并行条件相关，待归因”，区分 fixture 污染、资源冲突与真实并发缺陷。
- 能用独立目录、动态端口、明确同步、线程/子进程清理修好的，直接修。
- 确需独占资源的少量测试明确进入串行组；每个必要候选跑一次。50 次稳定性压力测试留给专门诊断或 nightly。
- 本次变更引入的、关键路径的、未定性的并发红仍阻断。已确认无交付影响的临时问题只能显式限期接受，不能靠一次绿静默清账。

pytest 官方也将并行偶发失败与未受控状态、顺序依赖和清理问题联系起来；“串行绿”不具有自动排除这些问题的证明力。[W1]

### 5.3 skip、xfail 与已知红不是清零按钮

当前登记表为空，应维持“发现新红先处置”的原则。现有环境条件 skip 已解决一部分通道误报，但还需区分：

- **不适用**：该平台天然不具有此能力，可标明原因。
- **本机不可测**：隔离通道不能验证，安排合适 runner；不能据此声明目标平台通过。
- **本应可测却未准备好**：部署必需依赖或测试能力缺失，应修复准备流程。
- **预期失败**：若采用 xfail，限定问题、异常与期限；避免泛化匹配。恢复后应显式清理。

收集数、执行数、skip、deselect 和失败数应同时记录。当前已有 `collect_ignore` 根据校准数据和依赖存在与否改变收集集合，所以测试数量变化也可能来自输入环境，而非测试减少或质量提升。[S4、S6、S9]

## 6. 优先处理的三个技术缺口

### 6.1 统一入口和结果口径

保留 `scripts/ci_gate.sh`，让本地、PR、main、Release 调用同一执行实现。允许少量明确模式，例如开发快测、完整验证、发行附加验证；共同步骤不复制到多份 YAML。

实施重点：

- 显式定义普通测试与信号串行测试集合；规则所称“排除 serial_signal”要与实际命令一致。
- 将解释器、lockfile、候选源码导入、物理路径、HOME、WebUI、浏览器能力检查集中准备；依赖缺失时在昂贵审查前暴露。
- 共享主工作树 venv 或 node_modules 时核验目标 lockfile 与已装依赖相容，不能仅凭“路径可用”认定一致。
- WebUI build 已执行 TypeScript 检查，不重复叠加；相关变更执行现有 Vitest。
- 发行沿用共通测试证据，再追加 tag/版本、签名、工件、安装和目标平台要求。
- 结果至少区分 `PASS / FAIL / INCOMPLETE / NOT_APPLICABLE`，并分别表达“测试通过”和“可以 push / 可以部署”。

当前 Pyright 超时可返回 exit 0 加 `status=unknown`；Release 已要求 `--require-complete`。应复用这一区分，避免只读退出码宣称全部通过。[S1–S4、S10]

### 6.2 修改文件范围覆盖整个交付，避免最后一笔提交改变判定

当前 `changed_python_paths()`（`scripts/check_static_diagnostics.py:193`）汇总的是：

- `HEAD^..HEAD`；
- 未提交改动；
- 未跟踪 Python 文件。

且它的路径前缀只有 `("src/", "tests/", "scripts/")`（`:68` 与 `:211` 两处为同一元组）。**这意味着 `tools/`（实测 14 个 `.py`）与 `webui/` 下的改动不在 touched 判定内**，而 `ai_rules.md` 第 1 条要求代码闸覆盖 `src/、tests/、scripts/、tools/、webui/`。只改 `tools/` 的交付会因此漏掉“被改文件诊断清零”这一项——这是 v1 未发现的第二处范围错位。

本轮 HEAD 最后一笔提交只含知识资产，`git diff HEAD^ HEAD -- '*.py'` 为空；但前面的待考察集成范围包含运行时代码变化。

因此，**“被改文件历史诊断也必须清零”这项要求，仅能覆盖最后一笔已提交改动，无法代表整个交付范围**。全树“新增诊断”仍有检查，这不是整个静态门禁失效。[S10]

建议按本次 PR base / 已验收基线到最终候选计算完整路径集。**base 必须在动作开始时固定为 `git merge-base <base_ref> HEAD` 的 SHA 并写入回执**——只记 ref 名（如 `origin/main`）不算固定，因为 ref 会移动；禁止 Agent 在判定时临时选择有利基线。缺 base 时明确失败或采取保守策略。前缀集合应补齐 `tools/`（必要时含 `webui/` 侧检查器），并与规则第 1 条的覆盖声明一致。

用三个有意义的反例验证即可：两笔代码提交后追加知识提交，前面的代码仍受检查；改变提交拆分方式，不改变相同交付内容的判定；只改 `tools/` 下 `.py` 的提交必须进入 touched 集合。无需新增一整套测试框架。

### 6.3 捆绑代码是分支遗留问题，不是 main 的当前阻断

**实测归属（本轮）**：`0cc2e932…` 是分支 `review/goal8ab7-deepin-0646-20261109` 的 tip，不在 main。该分支提交了 **409 个** `src/llm_loop/_bundled/**` 文件，main 当前为 **0 个**。`_bundled` 是 **`setup.py` 的构建期生成物**：`setup.py:15-19` 的 `DOCS` 白名单 + `:22` 的 `skills`/`methods`/`webui/dist`，由 `BuildApplication.run` 复制到 `build_lib/llm_loop/_bundled`（`:41`）；且 `.gitignore` 实测**不含**该路径（`git check-ignore` 判定不被忽略）。据此：

| 判定对象 | 结论 |
|---|---|
| main 的门禁 | **不是阻断**。main 的 Ruff ratchet 本轮实测通过（`new=0`、`status=complete`）。 |
| 该分支 | **是合并阻断**。它带着 409 个生成物副本，日志 Ruff 报 `new=1622`（未复跑分支 ratchet，属日志+算术推断）。 |
| 剩余问题 | 不是“查清来源”（来源已查清），而是**这个分支要不要合**：不合则关闭、保留诊断结论；要合则必须先移除生成物副本再复跑 ratchet。 |

**两条 v1 与二审均未覆盖的连带风险**：

1. **第二份规则文本**：`_bundled/docs/` 含 `ai_rules.md`、`ai_rules.lite.md`、`configuration.md`、`DEVELOPMENT_REPAIR_SAFETY.md`、`governance/card-lifecycle.md`（与 `setup.py:15-19` 同名单）。副本一旦入库，仓库内会同时存在两份规则文本，检索、阅读与引用都可能命中过期副本；而 `tests/unit/test_ai_rules_sync.py` 实测**不引用 `_bundled`**，不会捕获两者漂移。
2. **副本一致性无门禁**：生成物入库后，权威源与副本可各自演化，现有检查器不比对 `_bundled` 与 `docs/`、`skills/`、`methods/` 的一致性。

**最小处置（按优先级）**：

1. 先做**分支去留决策**——这是流程决定，不是技术修补。
2. 若倾向保留该分支成果：优先把 `_bundled` 从提交中移除（`git rm -r --cached`）并补 `.gitignore` 条目，维持“构建期生成”。这比加 lint 排除更小、更安全。
3. 若确需入库副本：用 Ruff 的路径配置（如 `extend-exclude`）限定 `_bundled`，实施时验证目录发现与显式传文件两种调用的效果 [W2]；同时**补一条副本一致性测试**（源码摘要 vs `manifest.json`），否则第二份规则文本与生成物漂移都没有门禁。
4. 无论走哪条：不要提高全仓 baseline、不要对整个 `_bundled` 加无条件忽略，也不要为通过 UP006、UP045 或空白检查大规模改写上游。

先处理会影响执行的错误，再决定原样上游代码是否适用本项目全部风格要求。

## 7. 如何复用审查与测试结果

### 7.1 复用依据是输入一致，不是“以前绿过”

复用既有回执至少核对：

- 被验证源码/测试/规则与相关知识资产的内容指纹；
- 依赖锁、测试配置、命令与门禁版本；
- OS、架构和必要能力；
- 可信 runner、完整终态、原始退出码；
- 覆盖范围，以及任务是否依赖 Git 历史、父提交或 tag。

默认完全相同输入才直接复用。对于内容有变化但确定不影响某项检查的情形，用少量明确路径映射并补相关定向测试；判不清就补验证，不先建设智能依赖推理引擎。

**特别注意**：仓库存在读取 Git 历史、文档或知识资产的测试。不能只比较 `src/` 就声称结果相同，也不能只凭 Tree SHA 相同忽略历史敏感检查。

### 7.2 各阶段只做它独有的检查

- **代码审查**：覆盖候选的正确性、安全和边界，默认一次；变更后窄复审。
- **合并检查**：核对基线变化、冲突、最终集成内容和测试覆盖。纯机械一致性可复用代码审查；实际集成变化再审受影响面。**但合并闸独立判定**：按 RULE-AI-34(5)，代码审查或 push 审查的 PASS 都不自动放行合并，反之亦然。
- **push 检查**：核对待推范围、隐私、目标和工作区状态。候选通过后发生认证/网络失败，恢复时先检查范围和目标是否变化。
- **部署检查**：核对所部署工件、目标环境、服务范围、回滚条件、健康和运行身份。

现有 30 分钟缓存可以保留为执行凭证窗口，但不应等同于“超过 30 分钟代码审查自动失真”。建议持久化审查事实，执行前轻量核对并派生动作资格；沿用现有回执存储，避免另造授权系统。

GitHub PR 默认测试的是合并分支；它与功能分支、最终 main 可能不同。因此不能直接删掉 main/Release 校验并复用 PR 头提交绿灯。只对已证实等价的输入复用；必要 required check 仍须在当前提交上给出可信结论。[W3、W4]

### 7.3 规则和旧知识同步收口

调整 RULE-AI-28 / 34 后，同步相关审查清单、英文/lite 规则、必要测试及实际命中的 Method/Experience。旧卡中的“每个动作再全文审查”“纯重启再 R9”等建议应就地修订。

当前 Rule 28 的 push 段仍写“双 remote：`lfl` 主仓 / `origin` legacy”，与实际配置不符——本轮实测：`origin` = `deyi2026/llm-first-loop`（正式）、`legacy` = `llm-first-loop-legacy` 且 pushurl 为 `no-push://legacy-archived`（推送显式禁用）、`gitee` = 镜像、**无 `lfl`**。执行时应读取实际 Git 配置，规则修订时一并消除旧例子，不继续把历史示例当当前事实。[S2、S8、S13]

## 8. 测试怎样更有价值，而不是继续堆数量

每个新增测试应说明：**拦住哪个已发生或可信的错误，为什么现有测试没覆盖。**

优先保留：

- 真实事故的最小回归：例如异常路径变量未赋值、Peer 参数被静默丢弃。
- 状态转换与副作用：重试只执行一次、取消真的停止、恢复不重复写、升级失败能回退。
- 用户可见行为：长会话切换、移动端输入、审批后返回、实际安装包能启动。
- 新门禁的两侧：一个应挡住的真实违规，一个此前误拦而应放行的合法场景。

应合并、改写或移出硬门禁：

- 多个测试重复断言同一个字面字符串、内部调用顺序或数据形状，不能揭示不同错误。
- 固定 sleep 和现实日期碰运气的时序测试。
- 只断言“调用了 mock”，没有验证行为与副作用。
- 用文档标题、行数、模板完整性替代正确性验证。
- 所有普通提交都跑的多 Provider、真实模型、跨主机全矩阵；这些应由相关变更和实际发布需求触发。

删除或降级测试前，先写清其保护的行为是否已被其他用例覆盖。对高风险变更的负向场景属于必要验证；不要求每个小改动都重做全矩阵。

## 10. 收口标准与轻量度量

先用现有任务回执记录五项指标，不新增专门采集系统：

|---|---|

## 11. 建议采纳的规则文本草案

> **测试与交付原则**：测试以发现和修复真实问题为目的。隔离、无生产副作用的诊断测试和全量测试不以独立代码审查通过为前置；必要的最终审查和验证必须覆盖实际交付候选。  
>
> 普通代码候选默认完成一次独立代码审查与一次必要的权威全量验证。修订后按变化补窄复审和受影响测试；输入未变且证据完整时复用已有结果。合并、push、部署只增加对应动作的风险检查。  
>
