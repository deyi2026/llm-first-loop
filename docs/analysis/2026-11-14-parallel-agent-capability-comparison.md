## 0 结论先行

1. **并行的瓶颈已经位移。** 厂商自己的文档承认任务状态会滞后、关停很慢、每会话只允许一个团队、lead 角色不可转移、禁止嵌套团队、agent 不擅长实时协调与委派〔引用 1/2/3〕。瓶颈不再是「能不能并发」，而是「并发出来的东西怎么合并、怎么验收」。
2. **主流的并行是进程内编排，不是跨会话协作。** Claude Code agent teams 的作用域是单会话内的队友；Cursor Cloud Agents、GitHub Copilot in the cloud 的作用域是云端执行器农场。跨会话、跨进程、跨机器共享同一份协调账本，主流实现未提供等价物。
3. **并行收益高度依赖任务结构，而不是并发数。** Anthropic 内部评测里 multi-agent 相对 single-agent 提升 90.2%，同一篇明确写多数编码任务真正可并行的部分比研究任务少得多〔引用 1〕。
4. **「多 agent 增益」有相当比例是「更多思考预算」的别名。** 同一评测中 token 用量解释了 BrowseComp 成绩方差的 80%〔引用 1〕；multi-agent 的 token 消耗约为单 chat 的 15 倍〔引用 1〕。不加约束地并行，成本放大与收益放大同量级。
5. **产物契约是并行的隐形基础设施。** 子 agent 把产物直接写进文件系统、只向协调者回传轻量引用，才能避免多阶段转述失真〔引用 1〕。
6. **本仓实测支持第 1 条。** 跨会话并行的 34 次合并队列失败中，`merge_conflict` 作为**主因**出现 **0 次**，失败集中在 base 新鲜度（17）与凭证齐备度（10）〔实测，见附录 C〕。真正耗人的是「基线过期」和「凭证不齐」，不是「代码冲突」。
7. **趋势判断**：下一阶段竞争点不在 agent 数量，而在三件事——可验证的完成判据、低成本的合并闸、可复现的环境隔离。
8. **应用方向**：强适用 5 类场景、弱适用 3 类反模式、1 套选型判据（§7）。

## 2 主流现状：四种并行形态

并行开发今天有四种形态，能力边界差异很大，混为一谈是多数误判的来源。

### 2.1 形态一：单会话内子代理（subagent）

父 agent 派发子 agent，各自独立上下文窗口，干完回报结果〔引用 2〕。关键设计有两条：

- **能力用工具白名单约束，不靠提示词约束。** 官方 `Explore` agent 只读，`Write`/`Edit` 工具被拒〔引用 2〕；文档给的原则是「通过限制子 agent 可用的工具来施加约束」〔引用 2〕。
- **成本用模型路由控制。** 子 agent 可指定比父 agent 更便宜的模型〔引用 2〕。

形态内的关键事实：**子 agent 不是独立进程，而是父会话的一次派生调用**。它的上下文、工具权限、失败处理都寄生在父会话的生命周期里。

### 2.2 形态二：单会话内团队（agent teams）

这是当前公开文档里最完整的并行编排实现〔引用 3〕，要素如下。

**组织结构**：每个队友是**一个完整、独立的 Claude Code 会话**，有自己的 context window，加载 CLAUDE.md、MCP server 与 skills；**父会话的对话历史不传递给队友**〔引用 3〕。队友可以先在 plan mode 出方案，由 lead 审批后再实现〔引用 3〕。

**共享任务列表**：任务三态 `pending` / `in progress` / `completed`，任务可依赖其他任务，未完成时在任务列表里显示 `blocked`；**依赖自动解阻**——某队友完成被依赖任务后，依赖任务自动解除阻塞，无需人工干预〔引用 3〕。队友不自我认领 blocked 任务，但 lead 可以直接指派〔引用 3〕。

**质量门**：`TeammateIdle` / `TaskCreated` / `TaskCompleted` 三个 hook，**退出码 2 表示阻止并回送反馈**——分别是「队友即将空闲时打回继续干」「任务创建时打回」「任务标记完成时打回」〔引用 3〕。这是把「完成」从 agent 的自我声明变成可被外部否决的事件。

**消息投递**：每个 agent 的收件箱是一个 JSON 文件（`~/.claude/teams/{team}/inboxes/{agent}.json`）；**只有写入成功才算「已发送」**，写失败时发送方收到错误、什么也没发出〔引用 3〕。配置目录随会话结束删除，任务列表目录保留、可配清理周期〔引用 3〕。

**权限与信任边界**（这一段是并行系统里最容易出事的地方）：

- in-process 队友运行在 lead 的实时 allow/deny 规则下；split-pane 队友只继承命令行 deny 规则与工具列表，`--allowedTools` **不传递给** split-pane 队友〔引用 3〕。
- **队友不能代答权限确认，也不能代为提供同意**；被拒绝的动作不能转交另一个队友去绕过检查〔引用 3〕。
- auto 模式下，分类器把「由另一个 agent 转达的批准声明」当作**不可信输入**而非用户确认；每条 agent 间消息在投递前都被审查，被拦截的消息不会送达收件人〔引用 3〕。

**明列的限制**：每会话仅一个团队；lead 角色固定、不可转移；不支持嵌套团队；in-process 队友不能再派生后台 subagent；任务状态可能滞后；关停可能缓慢〔引用 3〕。

**一个容易被忽略的行为**：文档写明 Claude 会自行命名普通 subagent 以便后续给它发消息，**团队可能在用户未要求时自行形成**〔引用 3〕。

### 2.3 形态三：云端并行执行器农场

这一形态把并行推到基础设施层，能力边界与前两者根本不同。

**Cursor Cloud Agents**〔引用 4〕：可以并行运行任意数量的 agent；每个 agent 跑在**隔离 VM** 中，拥有完整开发环境（clone 的仓库、依赖、密钥、网络访问）；支持**多仓库环境**同时容纳前端、后端、基础设施与共享库；入口覆盖 iOS app、Web、Desktop、Slack、GitHub/Bitbucket PR 评论、Linear 与 API；每个 agent 在**独立分支**上推送变更作为交接。该文档的一句话点破了并行系统的真实上限——**「agent 的能力上限就是它所处环境的能力上限」**〔引用 4〕。

**GitHub Copilot in the cloud**〔引用 5〕：付费计划自 2026-10-28 起启用新体验，概念分三层——Client（你交互的地方）/ Session（工作的容器，跨 app、IDE、移动端、CLI 延续）/ Environment（cloud sandbox、GitHub Actions runner 或自定义远程环境）；**聊天会话与被委派的 agent 任务是分离的 session**；支持自定义 agent、agent skills、repository 级 MCP server，以及 **Hooks 在 agent 工作时运行命令做校验或日志**；委派任务以开 PR 交付。

**Devin**〔引用 6〕：把并行用在 backlog 上——从 Linear/Jira ticket 到整个 feature、bug 修复、app 测试；文档给出两条硬要求——**「写明确的完成判据」**与**「让任务易于验证，例如检查 CI 是否通过」**〔引用 6〕。

### 2.4 形态四：跨会话手工并行

Claude Code 文档自己指出：Git worktree 让用户**自行**运行多个 Claude Code 会话，**不提供自动的团队协调**〔引用 3〕。

这条事实很重要：跨会话并行能力是现成的，但**协调被外包给了人**。这也正是形态二把范围限定在「单会话一个团队」的根本原因——跨会话协调需要的不是调度，是**协议**。

### 2.5 四形态能力边界汇总

| 维度 | 单会话子代理 | 单会话团队 | 云端执行器 | 跨会话手工 |
|---|---|---|---|---|
| 协调作用域 | 父会话内 | 单会话内的队友 | 平台内调度 | 人类 |
| 共享状态载体 | 父会话上下文 | 任务列表 + 收件箱文件 | 平台侧 session/environment | 无（靠人） |
| 规模 | 受父会话约束 | 文档列有明确规模上限 | 文档称「任意数量」 | 受本机资源限 |
| 嵌套 | 可 | **明确禁止** | 可 | 可 |
| 完成仲裁 | 父 agent 裁决 | hook 退出码 2 打回 | 环境校验 / PR | 人类 |
| 信任边界 | 工具白名单 | 转达批准视为不可信输入 | 平台隔离 | 人类 |

## 3 量化：收益、代价与适用边界

目前公开可定位到一手出处的量化结果，主要来自 Anthropic 的多 agent 研究系统工程博客〔引用 1〕。它同时给出了收益与代价，二者常被分开引用，导致结论失真。

### 3.1 收益

在 Anthropic 内部研究评测中，multi-agent 系统（Opus 4 编排 + Sonnet 4 子 agent）比 single-agent（Opus 4）表现高 **90.2%**〔引用 1〕。

同一篇指出 multi-agent 的适用条件是三项：可高度并行的查询、超出单个上下文窗口的信息量、大量复杂的工具接口〔引用 1〕。反之，需要共享同一上下文、agent 间强依赖的领域不适用〔引用 1〕。

### 3.2 代价

- token 消耗：单 agent 约为纯 chat 的 4 倍，multi-agent 约为 **15 倍**〔引用 1〕。
- 增益归因：BrowseComp 成绩差异中，**token 使用量单独解释了 80% 的方差**，三个因素合计解释 95%〔引用 1〕。

**这条最容易被忽略**：它意味着「多 agent 的增益」在很大程度上与「投入了更多思考预算」不可区分。工程上正确的问法不是「要不要多 agent」，而是**「每份 token 的并行是否划算」**〔判断〕。

### 3.3 失败模式

文档记录了早期 agent 的三类典型错误：给简单查询生成 50 个子 agent、无尽搜索不存在的来源、过度更新导致 agent 互相干扰〔引用 1〕。这三类的共同根因是**并行度没有与任务可分解性对齐**。

### 3.4 两个可直接迁移的工程做法

- **产物契约**：让子 agent 把产物直接写进文件系统，只向协调者回传轻量引用，避免多阶段「传话游戏」失真〔引用 1〕。
- **长上下文接力**：总结已完成的工作阶段 → 写入外部 memory → 起一个干净上下文的新子 agent，通过 handoff 保持连续性〔引用 1〕。

### 3.5 评估方法

文档建议把长研究任务拆成**离散 checkpoint** 来评估，而不是看最终产出〔引用 1〕。这与工程侧「完成判据」的要求是同一件事的不同表述。

## 4 本仓机制：跨会话账本制

### 4.1 构成（代码事实）

本仓的并行协调不走进程内调度，走**共享账本 + 显式合并队列 + 独立裁决**。相关实现：

| 组件 | 位置 | 作用 |
|---|---|---|
| `LaneStore` | `src/llm_loop/introspection/lane.py` | lane 生命周期；flock + CAS；`_assert_unique` 对 branch / worktree / goal 做 1:1 硬拒 |
| `MergeQueue` | `src/llm_loop/introspection/merge_queue.py` | 合并队列；4 道 preflight 机检；`requeue` 重投；`note_main_advanced` 标记过期 |
| `lane_gate_check` | 同上 | S1 十条机检（纯函数、只读、零副作用） |
| `review_admission` | 宿主准入层 | 独立只读 reviewer 签发一次性资格，覆盖全量测试 / push / 发表三类 |
| `claim_task` 系列 | 任务层 | fencing token，防并发写同一 durable Task |
| `task_create` / `task_update` | 任务层 | durable Task，支持 dependencies、blocked、`evidence_refs` |
| `coordination_status` | `src/llm_loop/introspection/goal_coordination.py` | 跨会话只读协调视图（goal / session / 队列 / 事件） |
| `help_inbox` / `help_request` | 协调层 | 跨会话收件箱，先落盘再投递；请求不携带授权 |

账本：`data/audit/lanes.jsonl`、`merge_queue.jsonl`、`verify_receipts.jsonl`（追加式，跨进程可见）。

### 4.3 与主流的能力边界对照

| 维度 | 主流（§2.1–2.4） | 本仓账本制 |
|---|---|---|
| 协调作用域 | 单会话内 / 平台内 | 跨会话、跨进程、跨机器（账本共享） |
| 规模 | 团队形态有明确上限；云端形态受平台配额 | 账本无硬上限〔实测 64 lane、40 goal 并存〕 |
| 嵌套 | 团队形态**明确禁止** | 允许派生 sub lane〔实测 32 条〕 |
| 领导权 | lead 固定、不可转移 | 归属可追（`owner_session_id`）+ 认领用 fencing token |
| 协调介质 | 会话内任务列表 + 收件箱文件 | durable Task 账本 + 合并队列 + 跨会话收件箱 |
| 完成仲裁 | hook 退出码 2 打回 | 独立 reviewer 一次性资格 + S1 十条机检 |
| 信任边界 | 转达的批准声明视为不可信输入 | 代理不得自我授权；跨会话请求不携带授权；写侧归属显式解析 |
| 合并安全 | 人工或 agent 自行处理 | 4 道 preflight + S1 十条 + 独立审查准入 |
| 失败诊断 | 任务状态可能滞后 | 失败按机检顺序定主因，34 项全部可分类〔实测〕 |

### 4.4 两套机制是不同层，不是替代关系〔判断〕

进程内团队解决的是**「一次任务内部的分工」**；账本制解决的是**「多个独立主体之间的交付协议」**。前者更快、更轻，但作用域止于单会话；后者更重，但能跨主体协作，且**可被审计、可被外部裁决**。把这二者混为一谈的典型错误，是拿单会话的并发数去论证跨仓库交付能力。

## 5 四个关键判断

### 判断一：并行的第一瓶颈是合并与验收，不是并发度

**证据**：主流文档自述的限制包括任务状态滞后、关停缓慢、禁止嵌套、lead 不可转移〔引用 3〕；Anthropic 记录的失败模式包含 agent 互相干扰〔引用 1〕；Devin 把「完成判据明确」与「CI 可通过」当作并行任务的前提〔引用 6〕。本仓侧，34 次合并队列失败中 `merge_conflict` 作为主因 **0 次**〔实测〕。

**推论**：衡量一个并行系统，不该数 agent 数量，该数**合并闸的吞吐量**——即单位时间内有多少条并行产出被安全地并入主线。

### 判断二：并行度应按「可验证判据密度」分配，而不是平均分配

**证据**：给简单查询生成 50 个子 agent 是被记录在案的失败模式〔引用 1〕；主流三种质量门（hook 退出码 2、CI 通过、外部 reviewer）都以「可机器验证」为前提〔引用 3/5/6〕。

**推论**：判据密度低的任务并行化只会放大噪声；这类任务应当串行、或干脆不做。**并行预算应当按判据密度分配，而不是按团队规模摊派。**

### 判断三：账本制的价值在「可审计、可外部裁决」，不在「合并更快」

**证据**：本仓 101 份独立审查归档、60 张验证凭证、34 项失败全部可按主因分类〔实测〕。对照：进程内团队的团队配置目录随会话结束删除，任务列表目录可配清理周期〔引用 3〕，不可作为长期审计依据。

**推论**：涉及**对外交付**（发布、push、跨仓改动）的并行协作，需要账本而非会话内编排；纯内部探索则相反，会话内编排更省事。

### 判断四：并行系统的下一个战场是「失败可诊断」，不是「更高并发」

**证据**：主流现状是队友不自我标记完成、任务状态滞后〔引用 3〕。本仓同期正在补的正是这一层：34 项失败按机检顺序定主因（`primary_check` / `primary_reason` / `failure_class`），并提供只读分诊视图。

**推论**：并发度每提高一档，失败组合数上升得更快。**没有失败分类的并行系统，规模越大越不可用。**

## 6 趋势判断（含可证伪观察点）

| # | 判断 | 依据 | 6–12 个月观察点 |
|---|---|---|---|
| T1 | 编排从会话内走向跨会话、跨主体 | 文档把跨会话并行明确交给 worktree + 人工协调〔引用 3〕；Copilot 已把 session/environment 拆成平台概念〔引用 5〕 | 是否出现以**共享协调账本**为卖点的成熟产品 |
| T2 | 环境隔离成为一等公民，并从容器升级为「可复现的环境定义」 | Cursor 独立 VM + 多仓环境〔引用 4〕；GitHub 三层 Environment〔引用 5〕 | 环境定义是否入版本库、与代码同源评审 |
| T3 | 完成判据从 agent 自我声明转为外部裁决 | hook 退出码 2〔引用 3〕、CI 判据〔引用 6〕、Hooks 在 agent 工作时执行〔引用 5〕 | 判据执行是否从「任务完成时」前移到「每次写入时」 |

## 7 应用方向

### 7.1 强适用场景（5 类）

1. **广度取证与审查**——任务天然可分解、产物是文件、判据是「条目齐全 + 引用可回溯」。对应 Anthropic 的宽搜策略〔引用 1〕与本仓的独立 reviewer 机制。
2. **异构模块并行**——前端 / 后端 / 测试各占一块，先定接口再放行。对应 Claude Code 的跨层协作用例〔引用 3〕。
3. **竞争性假设调试**——同一症状给出多个互斥假设并行验证，最后由一处收敛。对应 Claude Code 的 competing hypotheses 用例〔引用 3〕。
4. **大批量机械改造**——迁移、合规整改、版本升级；判据取 CI 是否通过〔引用 6〕。
5. **跨仓交付与发布**——需要账本、外部裁决与失败归档，不适合会话内编排（见判断三）。

### 7.2 弱适用场景与反模式（3 类）

1. **强串行依赖链**——后一步必须读前一步的输出。并行只会把等待放大到多处。
2. **需要一致语义判断的冲突**——同一个设计取舍的分歧。自动解冲突的产出是「绿但错」，必须保留单点决策（人或模型）。
3. **没有完成判据的任务**——并行度越高，验收越无据可依。

### 7.3 选型判据（4 问，按序）

1. 任务能否切成**互不依赖**的子任务？不能 → 串行。
2. 每个子任务是否有**可机器验证**的完成判据？没有 → 不并行，先补判据。
3. 产物是**文件**还是长对话？是长对话 → 先改产物契约（写文件、回引用），否则并行必然失真〔引用 1〕。
4. 合并成本是否低于重做成本？重做更便宜 → 放弃合并。

### 7.4 在本仓的落点（3 条）

- 并行预算优先投给**可判定完成的窄任务**（判据密度高），而非宽泛的探索。
- 跨会话交付继续走 lane + 合并队列 + 独立审查；会话内子代理只用于**单次任务内部的检索与初稿**。
- 新增并行任务前，先按 §7.3 四问自检，再决定要不要开 lane。

## 8 本仓当前的缺口（3 项）与由此产生的观察点

| # | 缺口 | 现状 | 影响 |
