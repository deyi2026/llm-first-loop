## 1. 问题与场景

在 LFL 中，一个任务经常被拆到多个会话里做（父会话派子代理、DSH 进程、后台 job、另一个 tab），或轮次中被打断后从新会话接续。当前工具集是**单会话假设**：

| 工具 | 设计假设 | 多会话时会怎样 |
|---|---|---|
| `create_goal` / `checkpoint_goal` / `update_goal` / `task_create` / `task_update` | 一个 goal 只属于一个会话 | 不知道别处已有同主题 goal，重复建 |
| `get_goal` / `task_frontier` | 默认解析"我的 goal" | 可能读到**别人的** active goal（`prefer_session_id` → 全局 active 回退） |
| `spawn_subagent` | 父等子，子拿一个 goal | 子会话的 goal 与父会话不连贯 |
| `dsh_task` | 一次性、结果只回最终文本 | 中断即丢，无法续接、无法看中间决策 |
| `schedule` | 能做定时/事件唤醒 | goal 完成**没有**可用事件源（见 §2.5） |
| `session_handoff` | 显式人读的交接文档 | 靠人转述，无工具级读取面 |

需求因此分成四类（v1 的两类表述不足以驱动设计）：
- **A（定位类）**：我要接手/查看某个已存在的任务，如何**确定**找到它，且不会误动别人的？
- **B（依赖类）**：我必须等 A 完成才能开工，怎么低成本地"知道它完成了"？
- **C（冲突类）**：A 和 B 并行写同一目标，如何不互相覆盖？
- **D（可见性类）**：不参与写的人（或轮次中断后回来的我）如何一眼看清"现在有哪些活、谁在干、卡在哪"？

## 2. 现状核实（v2：逐条给出代码位置；标注"已核"与"未实测"）

### 2.1 Goal 存储与会话字段
- 存储：`src/llm_loop/introspection/goal.py`，JSONL `goals.jsonl` + flock + 原子重写；`GoalStore.create()` 生成 `GOAL-<日期>-<8hex>`，写入 `session_id`（来自 `bound_session_id()`）。**已核**。
- 记录字段：`id / objective / status / generation / created_at / updated_at / session_id / checkpoints / completed_at / blocked_reason / spec_change_ref`。**无 version、无 owner 别名、无租约字段**。**已核**。
- `GoalStore.list(status, limit)` 存在 → 跨 Goal 列举**不需要**新建存储。**已核**。

### 2.2 读取端的会话隔离（v1 遗漏）
- `GoalStore.get(goal_id=None, prefer_session_id, strict_session)`：无 id 时的回退序 = `active_preferred` → `active` → `latest_preferred` → `latest`；`strict_session=True` 时才拒绝跨会话回退（找不到就返回 None）。**已核 `goal.py` `get()` 全文**。
- 已有 4 处调用方**显式**使用隔离读取：`tools_goal.py`（`run_get_goal`，`goal.py:301` 起）、`tools_task.py`（`task_frontier` 无参解析，`tools_task.py:241`）、`session_handoff.py:38`、`goal.py:105`（`active_identity`）。
- **结论修正**：隔离能力**已存在**，缺的是"写侧校验"和"默认策略统一"。这直接把工作量降低了约一半。

### 2.3 写入端未校验归属（v2 新增，A/C 类的真实危害面）
- 以下工具只要拿到 `goal_id` 就写，不比对 `session_id`：`checkpoint_goal`、`update_goal`、`task_create`、`task_update`；`task_frontier(goal_id=…)` 显式指定时同样不校验。
- 对比：`update_goal` 的收口门**有**结构性检查（open 任务拒绝 complete、`evidence_required` 未 verified → BLOCKED、零 done 任务需自报 `evidence_refs` 过 verifier）——**门很严，但门不认人**：任何会话只要知道 goal_id 就能推别人 goal 的状态。
- 附带证据：`GoalStore.update()` 不改写 `session_id`，因此 owner 判据**在数据层是稳定的**，可直接用作校验键。**已核**。

### 2.4 子代理 / DSH 的结果可见性（v2 补充）
- `job_output`：执行体首行取 `requester = current_session_id.get()`，再 `JobRegistry.instance().snapshot(job_id, session_id=requester)` → **跨会话读不到别人的 job**（返回"不存在或无权访问"）。**已核 `job_output.py:34-35`**。
- `subagent_result`：读取时校验 `parent_id + generation + result_id` 三元组（`subagent_result.py:131-141`）→ fleet 内部**已有归属校验范式**，可移植到 goal/task。**已核**。
- `subagent_lease` / `subagent_topology`：租约与拓扑有磁盘事实可读（`lease/settlement`、`expires_at`）→ "谁在跑"的可见性**已有半个基础**。
- `dsh_task`：不继承会话历史，结果只回收最终文本；中间过程需 `dsh_session_read` 回放。**成立**。

### 2.5 唤醒能力（v1 说过头，v2 修正）
- `schedule` 工具 schema 提供 `subject_refs` + `event_predicate ∈ {job_terminal, generation_reached, action_settled}`。
- 但生产装配**只登记了 `job_terminal` 求值器**；另两个谓词当前回退为纯超时唤醒（`scheduler.py:60`、`factory.py:212`）。**已核**。
- **设计含义**：不能假设"可以让 schedule 等 Goal 结束"。要做得先接求值器，或改用启动时 readiness 门（设计书选择后者为主、前者为可选增量）。

### 2.6 任务图依赖（v2 新增，推翻 v1 D3）
- `dependencies` 在 `task_create` 里只允许引用**同 Goal 已存在**的 task_id（`tools_task.py:159` 起）。
- frontier 求值：`deps = [d for d in t.dependencies if d in pending_ids]`、`all(d in done_ids for d in t.dependencies)`（`task_store.py:399`、`:432`）→ 若把 `goal:<gid>` 塞进 `dependencies`，它永远不在 `done_ids` 里，该任务**永久不可达**。**已核**。
- **结论**：跨 Goal 依赖必须是**独立字段**（如 `blocked_by_goals`），由专用求值器判定，不能复用 `dependencies`。

### 2.7 已有但被忽略的跨会话通道
- `event_stream(scope=workspace)`：workspace 级事件读取面已存在 → 可见性层的**现成数据源**，不需要新写审计。
- `session_handoff`：跨会话交接（人读）；`task_state`：模型自写状态，按会话存；历史 run 可读。
- **结论**：可见性层是"接线"问题，不是"造数据"问题。

### 2.8 未实测项（诚实边界）
- 无参 `get_goal` 在"当前会话无 goal 且 workspace 有他人 active goal"时的实际返回，本轮**只做了源码推演，未跑双会话实测**。
- 跨会话 `task_frontier(goal_id=…)` 的可读性同样只做源码推演。
- 这两条**作为设计书的判别实验**（设计书 §7 测试计划 T1/T2），验证前不得当作"已确认行为"对外陈述。

## 3. 问题定级（按 v2 事实重排）

| 类 | 具体缺陷 | 危害 | 定级 |
|---|---|---|---|
| A 定位 | 无 id 解析会跨会话回退（`get()` 回退序） | 读到别人的 goal 并继续推进 → **写错对象** | P0（已存在隔离开关，接线成本低） |
| C 冲突 | 写侧不校验归属（§2.3） | 任何会话可推任意 goal 状态；并行时无版本/租约 → 覆盖 | P0 |
| B 依赖 | 跨 Goal 依赖无合法表达（§2.6） | 任务要么被硬等（阻塞轮次烧资源），要么靠人转述 | P1 |
| D 可见性 | 无 workspace 级"在途任务总览" | 重复建同主题 goal、误判"没人做" | P1（数据源已有） |
| B 唤醒 | Goal 完成无可用事件（§2.5） | 只能轮询或阻塞 | P2（先给 readiness 门） |

## 4. 方案取舍（v2：每项都写明被否决的替代方案及否决理由）

### 4.1 分层，而不是"加一个跨会话 API"
四层各有独立机制，混在一起会导致"看起来能跨会话了，但会写坏"：
1. **L1 归属契约**：写侧校验 owner；读侧默认 strict，跨读需显式意图。
2. **L2 可见性**：`coordination` 只读视图（Goal + owner + 任务图 + 在跑 job/child + 最近事件）。
3. **L3 依赖**：跨 Goal 依赖用独立字段 + 求值器 + 环检测。
4. **L4 并发**：版本 CAS（首选）或租约（备选）。

### 4.2 被否决的替代方案
| 替代方案 | 否决理由 |
|---|---|
| 只做"跨会话读 API" | 治不了 C 类：读得到 ≠ 不该写。写侧仍可推别人的收口门 |
| `dependencies` 里塞 `goal:<gid>` | §2.6 已证伪：任务永久不可达 |
| 靠 `schedule` 事件等 Goal 完成 | §2.5：求值器未接线，写出来是"看起来能用、实际回退成超时" |
| 阻塞主会话轮次等子任务 | 轮次是稀缺资源；`wait` 已有 job 等待，但跨会话无 job 句柄 |
| 自动接管/续跑他人 goal | 违反授权边界（RULE-AI-23）；接管必须是显式动作 + 新 owner 记录 |
| 会话上下文跨会话继承 | `dsh_task` 明确不继承；继承=把别人的授权带进我的轮次 |
| 引入后台常驻协调服务 | 成本远超收益；现阶段 workspace 级事件流 + 启动门已足够 |

### 4.3 依赖协调的工作方式（B 类落点）
不靠"谁在等"，而靠**可判定的前置条件**：
- 消费方开工前跑一次 readiness：我依赖的 goal 是否 `complete`（且带 `completed_at` 与终局证据）？
- 若未完成：不阻塞，回执"阻塞在我不可控的外部 goal，建议（i）改为异步、或（ii）显式声明我这一侧可先行部分"。
- 可选增量：`schedule` 接 `goal_settled` 求值器后，支持"完成时唤醒我"——但要先做求值器，不是先做 API。

## 5. 与主线哲学的关系

- 这不是把 LFL 变成任务编排器；目标仍是"让不会协调的模型也能被正确使用"。
- 三类证据都要**模型主动去拿**，而不是靠模型默认知道。设计上要求：写侧拒绝时**给出可执行出口**（谁拥有、如何申请、如何显式跨会话），而不是只回一句 FAILURE。
- 不新增常驻组件、不引入外部依赖；全部落在现有 Goal/Task 存储 + workspace 事件流之上。

## 7. 建议的实施顺序（v2 调整：先把危害面关掉，再谈便利）

## 8. 拷问记录（v2 新增：对本文档与建议本身的 8 个反问）

> 目的：把"看起来合理"的建议压到"能被证伪"的程度。每条给出**问**、**答**、**留下的残余**。

**Q1：这套改造是不是"给不会协调的模型加复杂度"？会不会让它更容易乱建 goal？**
A：会，若不配套"发现优先"。所以 P1-a 的 `coordination` 视图必须是 `create_goal` 回执里的**指针**（"workspace 内已有 3 个 active goal，其中 1 个同主题"），而不是要模型自觉去查。残余：同主题判定是模糊匹配，只能提示不能阻断。

**Q2：写侧强校验会不会打断"父会话为子建 goal"的合法路径？**
A：合法路径是**父会话用自己的身份创建**（`create_goal` 已绑定 `bound_session_id`），再交给子；子只能写自己名下或显式受让的。若父要把已有 goal 交给子，走显式 `transfer`/`adopt`（含 reason + 双方 session 记录）。残余：子代理若被赋予"代表父"的语义，需要用同一 session 身份启动，而非宽松校验。

**Q3：A 类"误读别人 goal"是否只是理论风险？**
A：不是。`get()` 的回退序里 `active`（不限会话）在第二顺位；一旦当前会话没有 active goal，就必然回退到全局。而 `update_goal` 不校验归属，形成"读错→写错"的完整链路。残余：危害是否在真实会话中已发生，本轮未做历史审计（未实测，标注为开放项）。

**Q4：版本 CAS 与 append-only JSONL 冲突吗？**
A：不冲突。JSONL 是追加 + 原子重写（`_atomic_rewrite`），CAS 只需在记录里加 `version` 字段并在写入前比对该 goal 的最新行。冲突时失败并回执 `current_version` + 对方 `session_id` 与最近 checkpoint 摘要，让调用方能自行裁决。残余：整文件重写下，多 goal 并发写仍靠 flock（已有），性能在千级 goal 时需实测。

**Q5：跨 Goal 依赖会不会造出环，或制造"永远等不到"的死锁？**
A：会，所以必须：(a) 建立依赖时做可达性检查，拒绝成环；(b) 依赖目标 `blocked`/被 `cancelled` 时，下游不得"等"，必须转 blocked 并写明原因；(c) 设 `deadline_at`，到期后降级为"外部原因阻塞"。残余：跨 workspace 依赖不支持（也不应支持）。

**Q6：`coordination` 视图会不会变成新的"信息过载"？**
A：默认只投影**在途**（active/in_progress）与**最近 24h 内变更**，其余靠参数展开；且只读、不产生写副作用。残余：默认窗口是启发式，需在实践中调。

**Q7：把 `get()` 默认改成 strict 是不是更彻底？**
A：不改。默认 strict 会让"新会话接续旧任务"这个人最常用的场景每次都要显式传 id，退化体验。正确的是**写侧强校验 + 读侧默认带 provenance 标注**（回执里明示"该 goal 属于 session X，非当前会话"）。残余：标注依赖模型读懂，仍需 P0-b 的实测确认有效。

**Q8：这一整套做完，模型就会跨会话协调了吗？**
A：不会。工具只能保证"不会写错人"和"能看到全貌"，协调策略仍靠模型。真正的收益是把失败从"静默写错"变成"显式拒绝 + 明确出口"。残余：如果模型不使用 `coordination` 视图，P1 的收益接近 0 —— 所以视图必须挂到 `create_goal`/`task_frontier` 的默认回执里。

---

## 9. 结论（v2 定稿）

1. 数据层**已经够用**：`goal.session_id`、`GoalStore.list`、`event_stream(scope=workspace)`、`subagent_lease/topology` 都在，缺的是**契约与接线**。
2. 最危险的不是"看不到别人的 goal"，而是"**看得到并且能写**"（§2.3）。因此第一个动作是写侧归属校验，不是加新 API。
3. 跨 Goal 依赖**不能复用 `dependencies`**（§2.6 已证伪），必须独立字段 + 求值器 + 环检测。
4. 唤醒**不能假设 schedule 能等 Goal**（§2.5），本期用 readiness 门，事件求值器列为增量。
5. 任何"跨会话"能力都必须是**显式**动作（带 reason 与证据），默认路径永远是"只碰自己的"。
