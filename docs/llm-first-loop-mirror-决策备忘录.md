## Q1　棘轮历史债基线以谁为准？

**问题**
门禁在比对「历史遗留问题」时，需要一个参照提交来判断「哪些是老问题、哪些是新引入的」。现在这个参照被冻结在一个叫 `500ee8f3eff0` 的提交上——它既不是当前 HEAD，也不是当前远端。白话：**账本的第一页钉在了一个旧的日期上。**

**不决定的代价**
- 这个参照只影响**历史债数字的口径**，**不影响判定**：新引入的问题（`new`）和「被改动文件必须零诊断」两条红线，与参照是谁无关，所以不会漏放真正的新问题。
- 但**数字会莫名其妙地跳**：远端 ref 一刷新，`historical/current/resolved` 三个数可能整体变化，看门禁输出的人会误以为「突然新增了一堆债务」，然后可能做出错误决定（比如去放宽基线——而这是仓库明令禁止的）。

**选项**
1. **保持现状（钉在 `500ee8f3eff0`）** — 代价：无；收益：零动作。缺点：上面的「数字跳变」风险继续存在。
2. **改为钉在「最近一次远端 main」** — 代价：要改一次基线文件（必须走 `guard(r9):` 通道 + 独立复核）；收益：口径与团队直觉一致。风险：远端一推进，参照又会过期，需要机制来定期更新，否则回到现状。
3. **不改参照，只补「打印参照 + 抓取时间」** — 代价几行脚本改动（`chore(r9):`）；收益：任何人看输出都能立刻知道参照是谁、有多旧，不再靠猜。

**我的推荐：3**。理由：真正的痛点是「人看不懂数字为什么变」，而不是参照选谁；补一行可观测输出，比动基线（高风险、需防篡改通道）划算得多。若之后确认参照确实长期错位，再走选项 2。

**我需要你回答的一句话**：*棘轮基线先只加「参照+时间」的可观测输出（推荐），还是直接改参照？*

## R6　本地领先 16 个提交、未 push

**问题**
远端停在 2026-10-10，本地多了 16 个提交（含本轮 6 个）。白话：**本机是唯一有这些提交的地方；机器坏了就没了。**

**不决定的代价**
- **本机是单点**。这 16 个提交只存在于本地磁盘。远端 `origin`（legacy）**不包含**它们，当前上游 `lfl` 也**不包含**它们。
- 越往后拖，「一次 push 的量」越大，中途出问题（冲突/推送失败）的成本越高。

**选项**
1. **push 这 16 个到 `lfl`**（无需先 fetch：`lfl/main` 缓存 ref 与远端实测一致，且已实测无分叉、可 fast-forward） — 代价：一次网络操作，几分钟；收益：上游恢复为完整备份，且 Q1 的「新鲜参照」顺手就有了。
2. **只 fetch 刷新 ref、不 push** — 代价：零风险；收益：Q1 有最新参照数据（虽然当前已实测一致）。缺点：备份缺口仍在。
3. **什么都不做** — 代价：继续单点。收益：不动。

**我的推荐：1**。理由：已实测远端可达、无分叉、可 fast-forward，这是本轮**成本最低、消除风险最大**的一步；而且它顺带把 Q1 的数据基础变成新鲜的。

**我需要你回答的一句话**：*是否授权把这 16 个提交 push 到 `lfl`？（已实测无分叉、可 fast-forward）*

## Q2　是否复核 `external_red_registry.json` 的 90 条豁免？

**问题**
门禁遇到已有失败时，可查一张「豁免清单」放行。清单里有 **90 条**（涉及一批测试文件）。仓库自己的规则写着「**逐批销号、非永久遮罩**」，但没有规定谁来定期复核。
（白话：**这是一张「已知故障豁免表」，写明了要定期清理，但没人排期清理。**）

**不决定的代价**
- 清单会**只增不减**，门禁的「红」逐渐失去警戒意义——新故障和旧故障混在一起，看不出谁在恶化。
- 尤其注意：本轮首次在受限环境跑出的 24 个失败 + 13 个错误，涉及 **12 个测试文件，全部不在**这张清单里（它们是环境产物，见《收尾报告》F 节）。这说明**清单的覆盖面与真实失败面并不对齐**——要么该补登记，要么这些失败在正常环境本就不存在（已证明是后者）。

**选项**
1. **排一次专项复核**：逐条重跑 90 条豁免，判定「已修复 → 销号」或「仍然红 → 保留并注明原因」 — 代价：估计 **半天到一天**（90 条 × 定向重跑 + 归因）；收益：门禁恢复可信度。
2. **只做一次抽样**（抽 10-15 条）+ 建立「每条必须带到期日」的规则 — 代价：**1-2 小时**；收益：先止血，避免清单继续膨胀。
3. **不动** — 代价：清单继续积累，门禁噪音化。收益：省时间。

**我的推荐：2**。理由：全量复核一次性成本高、且其中不少条目可能因外部演进已自然转绿（清单本身说明过「外部演进合流后自然转绿」），抽样能快速判断「到底还剩多少真账」，再决定要不要投全量。

**我需要你回答的一句话**：*这张 90 条豁免清单，先抽样复核（推荐）还是排一次全量复核？*

## Q3　是否拆分 13 个超过 1500 行的文件？

**问题**
有 13 个 Python 文件超过 1500 行，最大的 `runtime/service_control.py` 4446 行。白话：**单个文件太大，读它、改它、审它都变慢，冲突概率变高。**
近 30 天改动最频繁的三个：`factory.py`（102 次）、`tools/registry.py`（65 次）、`web/routes.py`（57 次）。

**不决定的代价**
- 每次动这些文件都要通读上下文，改动风险随规模上升；同时多人在同一文件改动时**冲突概率高**。
- 但**现在硬拆也有实打实的代价**：这些正是最热的文件，仓库里还有多条在飞的开发线（本轮之外），大规模结构迁移会制造大量 rebase 冲突——**拆得越急，越可能把在飞的工作搞乱**。

**选项**
1. **先只拆一个「最内聚的段」**（建议 `factory.py` 里「provider/模型装配」这一类自成一体的部分） — 代价：**1 天左右**（含回归）；收益：验证拆分方法可行，且拿最热文件开刀收益最大。
2. **先不拆，只立「新代码不得再往这些文件里加」的红线**（等体积膨胀自然停止） — 代价：**1-2 小时**（加守卫规则）；收益：零冲突风险，先冻结增长。
3. **一次性拆多个** — 代价：数天 + 高冲突风险；**不推荐**。

**我的推荐：2 先做、1 随后**。理由：在飞开发线未知的情况下，先用红线**冻结增长**（便宜、无冲突），再挑最内聚的一段做试点；直接大拆会把当前最活跃的文件变成冲突源。

**我需要你回答的一句话**：*先立「冻结增长」红线（推荐），还是直接对 `factory.py` 做一次试点拆分？*

`src/llm_loop/assurance/` 约 **2948 行**，自述「未接入生产运行时」。实测：**整个 `src/` 里对它的引用数 = 0**（没有任何生产代码用它），但它的 **7 个测试文件每次全量测试都在跑**。
（白话：**一整套没人用的代码，还在花钱维护和测试。**）

**不决定的代价**
- 每次全量门禁都跑它的测试（本轮它还是首次环境跑红的一员），持续消耗时间与注意力。
- 更隐蔽：它给人「这块有测试保障」的错觉，但它保障的不是生产路径。

**选项**
1. **退役**：把 7 个测试迁走/移除，再把源码目录移出 `src/`（或删除） — 代价：**半天到一天**；收益：维护面直接减少近 3000 行。**注意顺序**：必须**先迁测试归属，再搬源码目录**——反过来会出现「源码没了、测试还在引用」的中间态，全量测试直接红，把一次干净退役搞成一次故障。

**我的推荐：先做「明确结论」而不是先写码**——即由了解背景的人一句话定「还要不要这个能力」；若要就选 2、不要就选 1。理由：这是**产品意图问题，不是工程问题**，工程侧只能执行。

**我需要你回答的一句话**：*`assurance/` 这套能力**还要不要**？（要 → 排接入；不要 → 按「先迁测试、后搬目录」退役）*
