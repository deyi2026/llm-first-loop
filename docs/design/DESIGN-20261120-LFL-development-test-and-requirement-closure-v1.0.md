# LFL 开发效率、质量与需求完整收口——需求与实现设计方案 v1.0

> **状态**：设计候选（已完成内部对抗性拷问与修订；**尚未实施、未修改 CI/Goal 门禁、未合并 main**）  
> **日期**：2026-11-20  
> **适用范围**：LFL 单 Goal、多 Agent / 多 Lane、Mac/Deepin 相关开发；兼容现有受管审查、R9、GitHub 分支保护和部署流程。  
> **原则**：先跑通、不过度工程化；AI 负责设计和判断，程序负责事实、证据和硬边界；不以“开发提速”为由放宽最终安全门禁。

## 0. 决策摘要

本方案采纳以下不可混淆的规则：

1. **设计与测试同生**：输出需求实现设计时，同时输出每条需求的增量测试、最终全量/真实验收设计及需求—测试—证据映射；没有可验证验收标准的需求不得开始实施。
2. **开发期只运行增量测试**：在隔离开发 Lane 内，每次修改只运行新增/修改测试、受影响旧测试、必要契约/安全测试与变更范围静态检查；不因每次开发提交重复运行完整 R9。
3. **全部必需需求实现、增量测试通过后，才冻结最终候选**；独立 Reviewer PASS（P0/P1=0）后运行原版完整 R9。最终门禁仍按精确候选树执行。
4. **分批交付允许，半成品收口禁止**：可按独立、完整的交付切片分批验收、合入和部署；整个 Goal 在其所有必需需求验收完毕前保持未完成。每个正式交付切片有自己的最终质量门禁。
5. **完成状态必须有证据**：需求、测试、Reviewer、R9、PR/CI、部署回执绑定 Goal、REQ ID、基线和候选 SHA/树身份；不能以模型自述、旧 SHA 回执或“测试曾通过”替代。
6. **质量不止于测试全绿**：评审必须检查重复代码、单一真相源、模块边界、过度 guard/兼容层、异常恢复、并发/副作用及旧代码清理。
7. **复用现有机制**：以现有 TaskStore/Goal、Lane、Host 资格、R9、受保护 PR/CI 为基础；不另造第二套可写的任务状态数据库，不重写全量测试框架。

### 0.1 端到端流程

```text
需求确认与影响面基线
  -> 同步产出：实现设计 + 增量测试设计 + 全量/真实测试设计 + REQ 验收矩阵
  -> Goal / TaskStore 建立 REQ 对应任务，分配 Lane
  -> [开发循环：实现一项 -> 增量测试 -> 修复 -> 证据落账] × N
  -> 必需 REQ 全覆盖、全部增量 PASS、无未授权遗漏 -> 冻结交付候选
  -> 独立 Reviewer PASS (P0/P1=0) -> 原版完整 R9 exit 0
  -> 受管 PR / 远端 CI / 分支保护 -> 合并 main -> 主 CI
  -> 统一受管部署、实际运行 SHA/服务健康/回滚验收
  -> 本交付切片 ACCEPTED；所有切片均 ACCEPTED 后 Goal COMPLETE
```

**重要边界**：“开发期不跑全量”仅适用于未进入正式集成的开发迭代；正式 PR、受保护 main、发行和部署门禁仍按现行安全策略执行。当前脚本尚不支持本方案的开发期提交路径，**不得直接绕过既有门禁**。

### 1.2 真实问题

- **测试成本错配**：每次小修改都跑全量，排队、资源争抢和反复验证拖慢开发；但只跑新增测试又会漏掉跨模块回归。
- **需求闭环不完整**：文档列出 10 项、任务只建 7 项，现有任务图即使全部 done，也不能证明原始 10 项均已交付。
- **并行开发产生陈旧证据**：其他 Lane 先合并导致 base 变化，旧测试或 Reviewer 回执不一定仍能代表新候选。
- **代码质量累积恶化**：通过增加判断、兼容层、状态副本和重复实现解决局部问题，最终形成难维护的“屎山”。
- **设计循环过长**：反复“拷问”文档却不进入实现，或者开发中途丢失未完成项。

### 1.3 目标、非目标与度量

**必须达成**：必需 REQ 映射覆盖率 100%；未授权遗漏 0；开发期提交不运行完整 R9；正式候选 Reviewer P0/P1=0、完整 R9 exit 0、受保护 CI 通过；部署树与验收树身份可对账；Goal 不得因取消/跳过必需项而假完成。

**衡量效率**：记录开发循环等待时间 P50/P95、每交付切片完整 R9 次数、增量选择测试数/耗时、因遗漏返工次数、合并冲突次数、最终回归缺陷数。先建立现状基线，再比较试点前后；**不预先宣称节省百分比**。

**非目标**：不重写 pytest/R9，不改变真实 LLM 测试的授权/成本控制，不降低安全扫描/签发器/分支保护，不自动授予 Reviewer PASS，不建立新数据库/复杂流程引擎，不要求每个小修复都写几十页设计。

## 2. 需求与测试同步设计规范

### 2.1 每份需求实现设计必须包含

1. **目标与范围**：用户行为、边界、不做什么、依赖、完成定义。
2. **实现设计**：涉及模块、接口/数据契约、状态 SoT、异常与恢复、兼容/迁移、回滚策略。
3. **增量测试设计**：每个 REQ 的正向、负向、边界和必要故障恢复用例；对应既有回归测试与影响面。
4. **最终测试设计**：原版完整 R9、相关真实/集成/性能/安全测试、部署健康验收；明确哪些不属于 R9。
5. **REQ 验收矩阵**：稳定 REQ ID、优先级、验收条件、Task ID、增量测试 ID、最终验收证据类型、交付切片。
6. **完成/变更规则**：需求新增、删除、延期、豁免、设计变更与证据失效的处理。

**开始开发的准入**：每条必需 REQ 都有可判定验收标准和至少一条可执行增量测试计划；如果属于纯文档/人工验收，则需说明可核验的证据类型和为何无自动化测试。测试计划不等于已经运行通过。

### 2.2 REQ 矩阵模板（设计时填写，运行状态从 TaskStore 派生）

| REQ ID | 交付切片 | 验收条件（行为/不变量） | 代码触点 | 增量测试 ID | 最终/真实验收 | Task ID |
|---|---|---|---|---|---|---|
| REQ-001 | D1 | 失败后可恢复且无重复副作用 | `src/...` | T-001/T-002 | R9 + 恢复演练 | TASK-001 |
| REQ-002 | D1 | 未授权写入被阻断并留证 | `src/...` | T-003/T-004 | R9 + 安全负例 | TASK-002 |
| REQ-003 | D2 | 并行更新不丢失 | `src/...` | T-005/T-006 | R9 + 并发真实验收 | TASK-003 |

上表为**示例而非本次真实实现清单**。REQ ID 创建后不可重用；验收条件不能因实现困难而静默删减。`TaskStore` 是任务状态的唯一真相源，设计文档是**获批准需求范围**的真相源，两者通过 REQ ID 校验一致；不在 MD 中维护第二套可写“完成状态”。

### 2.3 测试设计最小覆盖

- 正向：期望行为和输出；负向：错误输入、未授权、超时/失败；边界：空值、上限、兼容。
- 涉持久化/外部副作用：中断、重试、崩溃恢复、幂等、原子性与回滚。
- 涉多 Agent：并发写、锁竞争、陈旧 base、跨 Lane 接口调用、丢失更新。
- 涉模型：真实 Provider/模型身份、上下文/预算/缓存行为、失败回执；真实调用另设受控验收，不假装普通 R9 已覆盖。
- 涉 UI/部署：真实交互、健康检查、实际运行 SHA、配置与回滚条件。

## 3. 开发期：增量测试闭环

### 3.1 每次变更的最小执行顺序

```text
锁定 REQ / Task / Lane 与候选基线
  -> 修改最小代码（必要时先 RED 再 GREEN）
  -> 选取增量测试：新增/修改 + 受影响旧用例 + 契约/安全负例
  -> 修改范围 Ruff/Pyright/安全扫描
  -> 增量 PASS，记录选择集、未覆盖理由、测试结果和树身份
  -> TaskStore 更新进度与 evidence_refs
  -> 下一条 REQ；此时不运行完整 R9
```

### 3.2 增量测试选择规则

选择集 `S = N ∪ I ∪ C`：

- `N`：本次新增或修改的测试，覆盖当前 REQ 的验收条件。
- `I`：受影响旧测试；至少覆盖被改函数/模块的调用者、接口消费者、相关脚本、跨模块 monkeypatch 和数据契约。
- `C`：按风险补充的契约、安全、恢复、并发或迁移测试；高风险变更不能仅靠 happy-path 单测。

选择器输出**具体测试 node IDs/文件、选择原因、未覆盖面**。如果 `S` 为空、存在无法归属的变更文件、选择器报错或影响面无法界定，增量门禁必须 `BLOCKED`，先补映射/契约测试；不得输出假 PASS。必要时扩大到相关包或集成用例，仍不把“盲跑全量”当默认开发循环。

`--quick` 当前不是精确增量测试。拟新增 `scripts/dev_gate.sh` 作为薄入口，复用已有测试命令/静态检查；避免复制 R9 的全套实现。修改范围的类型分析若无法可靠限定，必须明确记录 `UNKNOWN/BLOCKED`，不能把未运行写成 PASS。

### 3.3 开发提交与正式提交分权

**拟新增** `bash scripts/r9_commit.sh --dev "<message>"`，而不是让开发 Agent 直接跳过安全脚本。该模式仅适用于隔离 worktree 的非保护开发分支，且必须保留：暂存白名单、提交锁、精确 PROBE 树、fixture/敏感信息扫描、已有 hooks、变更文件检查和证据记录。只把**测试选择集**改为增量；不得签发正式全量资格、不得推送受保护 `main`、不得标记发布候选合格。

`r9_commit.sh` 默认行为、`ci_gate.sh` 默认/`--release`、Host 签发器和受保护分支规则不变。**这属于策略与代码演进，实施前必须先完成负例验证并取得所需批准；在新模式正式上线前继续遵守现有全量提交门禁。**

### 3.4 增量回执最小字段

`goal_id`、`req_ids`、`task_ids`、`lane_id`、`base_sha`、`candidate_tree_sha`（及提交 SHA，如已存在）、`changed_paths`、`selected_tests`、`selection_reasons`、`results/exit_code`、`static/security_status`、`evidence_refs`、`started_at/finished_at`。所有字段由执行环境或 Host 记录；模型只可解释，不可自签 PASS。未提交脏工作树不能冒充已冻结候选树。

## 4. 需求完整性：防“做一半被遗忘”

### 4.1 两个真相源，职责不重叠

- **设计 MD 的 REQ 清单**：获批准的需求**范围**和验收契约；稳定 ID，不记录可随意改写的运行完成态。
- **现有 TaskStore**：任务状态、依赖、owner、验收证据的**运行事实**；不另建可写需求进度数据库。

新增只读 `check_goal_coverage` 核对两者：每个必需 REQ 恰好映射到一个有效 Task 或显式批准的交付拆分；每项 Task 的验收条件可回溯到 REQ；每个 REQ 具备增量测试与最终验收定义；Task 完成证据可验证。设计文件版本/摘要必须与检查时采用的版本一致。

### 4.2 完成状态与关闭条件

显示层可派生以下状态，**不必先改 TaskStore 状态枚举**：

| 派生状态 | 判据 |
|---|---|
| `PLANNED` | REQ 已批准且 Task pending |
| `IMPLEMENTING` | Task in_progress / blocked，或实现尚无有效测试证据 |
| `INC_PASS` | 实现已提交/冻结到开发树，关联增量测试全部 PASS 且证据绑定同一树 |
| `DELIVERY_ACCEPTED` | 该交付切片的最终 Reviewer、R9、PR/CI、必要真实/部署验收均通过 |
| `DEFERRED_APPROVED` | 明确授权的范围变更，注明新 Goal/Issue 与责任人；不算原范围已实现 |

**Goal COMPLETE 的硬条件**：获批准范围内全部必需 REQ 均 `DELIVERY_ACCEPTED`；任何未授权 `pending/in_progress/blocked/failed/cancelled`、缺测试、缺证据、旧 SHA 回执或未验收部署都拒绝收口。单独关闭 Task 不等于 REQ 验收通过；全部 Task done 也不自动证明 REQ 全覆盖。**开发交付 Goal** 若 `audit_dir` 缺失、账本不可读或设计清单无法解析，必须 fail-closed；普通非开发 Goal 不因本方案被误加部署义务。

### 4.3 取消、延期和需求变更

1. `cancelled`、`waive`、`not applicable` **不是**完成的同义词。仅用户明确批准、指明 REQ ID 和原因的范围变更，才可从“本次必需项”中移出；保存原条目、变更前后范围及审批证据。
2. 延期需求必须关联后续 Goal/Issue 和 owner；原 Goal 报告必须写明“范围变更/延期”，不得声称原需求全部实现。
3. 新增需求赋新 ID；改变验收条件需版本化，旧证据失效或重新证明；不能直接覆盖历史验收记录。
4. TaskStore 当前单 Goal 40 Task 上限应保持；超过时拆为可独立验收的交付 Goal，并在父 Goal 保存 REQ 覆盖与子 Goal 依赖，不通过合并/省略 REQ 逃避追踪。
5. 会话中断、模型切换、Lane 退出后，恢复时先读取 Goal/TaskStore、批准的 REQ 清单、最近回执和当前 main，而不是从聊天总结猜测完成状态。

### 4.4 阶段交付与整体收口

允许 D1（5 个独立 REQ）先完整验收并部署、D2（其余 REQ）继续开发，但必须满足：D1 是可独立运行的纵向功能切片，未完成代码不暴露为已交付能力；D1 自己通过 Reviewer/R9/CI/部署门禁；总 Goal 仍为 active/blocked，直到 D2 也完成。优先**多 Lane 开发、单批集成**，减少每条 Lane 单独触发完整 R9 的次数；只有确有业务价值时才分批发布。

## 5. 最终验收：只对正式候选运行全量

### 5.1 冻结前检查

- 全部本交付切片的必需 REQ 有实现、增量 PASS、无未归属文件/未审查副作用。
- 设计范围/TaskStore/测试映射一致，旧逻辑已清理，必要迁移和回滚设计已落实。
- 合并各开发 Lane 后形成**精确集成候选树**；不能拿单个 Lane 的增量 PASS 代表合并树 PASS。
- 记录 `candidate_commit_sha`、`candidate_tree_sha`、`base_sha` 和代码/测试/设计版本。

### 5.2 终验顺序

1. 独立 Reviewer 审查精确冻结候选（包括需求覆盖、架构质量、安全、测试充分性），要求真实 `PASS`、P0/P1=0；Reviewer 实际模型身份与 Host 申报身份必须一致，不得自称独立审查。
2. 执行**原版完整 R9**：`bash scripts/ci_gate.sh`，发行按现有 `--release` 策略；保留完整输出、真实 exit code、测试统计、环境/树身份。R9 包括仓库既有的 Ruff、环境声明、Pyright、WebUI、tier0、serial_signal、serial_perf、xdist 非 real_llm 套件，不得静默删选集。
3. 对 R9 不覆盖的真实 Provider、Host/Oracle、物理 UI、安装、跨平台、性能或部署能力，按该 REQ 的**独立真实验收计划**执行；不得用普通 R9 全绿替代。正式全量测试使用受管单槽/资源预算，避免多个会话同时争抢；若候选已由受限开发提交冻结，不应再为同一树无意义地调用一次完整提交包装器重复 R9。
4. 经受管推送、PR、远端 CI 和分支保护合入 `main`；核对主分支 push CI，确认部署候选树与验收树一致，或经过明确允许的等价性核验。
5. 统一受管部署，核验实际运行 SHA/generation、受影响服务健康、必要四服务检查、回滚条件和真实用户路径；写入最终回执后才更新交付状态。

### 5.3 何时需要重新运行全量

- **候选代码/测试/配置的语义或被测树改变**：原回执不能直接复用；先跑受影响增量，再对新冻结候选重新 R9 和必要审查。
- **纯 replay + base 前进**：仅在现有 Host/Lane 机械校验 `patch-id --verbatim` 序列相等、路径不交叉、凭证有效等条件**全部成立**时，才可按已批准的 carryover 机制免除重跑；任一条件未知/失败，走原全量路径。
- **R9 首轮红、重试后绿**：保留首次失败和重试原因；不能抹去并发/时序回归。发行门禁仍遵守现行不接受复跑放行的规则。
- **仅文档措辞变更**：是否影响资格由既有 Host 的精确树/材料策略裁决；模型不得自行宣称“非代码改动所以不用重验”。

## 6. 防屎山代码的架构质量门禁

每个实现批次 Reviewer 必须回答以下问题；答不清则标注风险并修复，不以“测试通过”覆盖：

1. **单一真相源**：是否新增与现有 TaskStore、Goal、Lane、运行状态重复的权威状态？若有，为什么不能派生？
2. **职责边界**：模型负责策略判断、程序负责事实/原子性/授权边界，是否把模型判断硬编码成不断增加的 `if/guard/filter`？
3. **复用与删除**：是否有现成组件可复用？新实现替换旧实现后是否删除死分支、冗余兼容层、无用开关和重复测试？
4. **最小接口**：是否为单个需求引入框架、通用抽象或跨模块依赖？是否可以用更小的契约完成？
5. **可验证性**：测试是否断言用户行为、不变量、失败恢复，而不是锁死某种代码写法或旧提示词文本？
6. **并发与副作用**：多 Agent 同仓开发是否可能脏读、重复提交、丢失更新、锁冲突、重复外部写？
7. **兼容/迁移**：修改旧状态或数据协议后，历史数据、恢复、回滚和版本升级是否仍成立？
8. **可维护性**：函数/模块职责是否清晰？异常路径是否可观察？是否新增没有所有者和退役条件的技术债？

优先使用仓库已有架构守卫和历史债棘轮；不为本方案再发明一套任意行数、文件数或复杂度阈值。确有技术债须登记 owner、原因、退出条件和对应 REQ，不允许“以后再说”式永久悬挂。

## 7. 多 Agent / 多 Lane 协调规则

- 主 Agent 负责需求分解、跨 Lane 接口约束、验收矩阵、最终集成和证据核对；同一问题族只允许一个写入负责人，不因 Agent 数量增加而多头改同一权威文件。
- 可并行开发**相互独立的问题族**；各自 worktree、基线、Task/REQ、改动路径和证据独立。只读审查/定位可以并行，但不冒充独立签发。
- 分 Lane 前检查**文件和依赖面**，包括私有函数引用、测试 monkeypatch、脚本/配置消费者；“路径不相交”不等于“功能不相互影响”。
- 开发期每 Lane 仅增量；进入交付切片时先集成、冻结，统一终验；合并面继续使用现有队列/锁/Host 凭证，避免多 Lane 各跑一次重复全量。
- 其他会话先推进 `main` 时，先核对 base/变更集合/证据有效性；不得 reset 覆盖其他 Lane 成果，亦不得把旧 SHA 回执贴到新候选。

## 8. 最小实现方案（拟改动点，不代表已完成）

| 改动项 | 最小实现 | 不允许的做法 |
|---|---|---|
| 设计模板 | 在 `docs/ai_rules.md` 维护流程规则 SoT，并同步 `docs/development_methodology.md` 的解释与链接；为小修复提供简版。 | 新建庞大文档审批平台，或让两个规则文档互相争夺权威。 |
| REQ 覆盖检查 | 增加小型只读 `scripts/check_goal_coverage.py`（名称建议）：从固定格式的设计 REQ 表读取 ID，与现有 TaskStore 的 acceptance、task/evidence 对账；解析失败即 BLOCKED。 | 再造可写进度数据库，或让模型自行报告 100%。 |
| 增量测试 | 增加薄入口 `scripts/dev_gate.sh`：明确输入 REQ/变更范围，选择 `N∪I∪C`，执行必要静态/安全检查，输出绑定树的回执。 | 以 `ci_gate.sh --quick` 冒充精确增量；空选择集当成功。 |
| 开发提交 | 在**授权及安全负例通过后**扩展现有 `r9_commit.sh --dev`，复用 PROBE、锁、暂存/扫描；仅替换测试选择，不签发正式资格。 | 直接 `git commit --no-verify` 或放宽 `main` 门禁。 |
| Goal 关闭 | 在现有 `goal_gates.complete_gate` 之前或内部增加 REQ 范围/取消审批/最终证据核验，保持 fail-closed。 | `cancelled`/`waive` 无明确范围变更就等于完成。 |
| 正式集成 | 原版 R9、独立 Reviewer、受保护 PR/CI、Host 签发和部署入口保持权威。 | 用开发期增量 PASS 替代正式集成。 |

**最小实现优先级**：先做模板/覆盖检查，再做开发期增量入口，最后经安全审查改开发提交路径与 Goal 终局门禁。若 TaskStore 已有字段足以承载，不新增字段；只有无法证明需求覆盖时才增加最小映射元数据。

### 8.1 拟议命令（当前仓库**尚未提供**，仅作实现契约）

```bash
# 开发 Lane：只测增量，产出绑定树的回执
bash scripts/dev_gate.sh --goal GOAL-... --req REQ-001 --base <base-sha> --receipt <path>

# 开发提交：只有受控开发分支允许（实施前须批准并验证）
bash scripts/r9_commit.sh --dev "feat: implement REQ-001"

# 最终收口：对账完整性，随后运行原版完整门禁
python scripts/check_goal_coverage.py --goal GOAL-... --design docs/design/xxx.md --candidate <sha>
bash scripts/ci_gate.sh --release
```

### 8.2 迁移与安全发布

1. 先测量当前开发期 R9 次数、耗时与现有 Goal 完成缺口；只读影子报告不改变现有行为。
2. 用隔离 worktree 实现并验证增量选择器和覆盖检查；不改 `main`/正式 PR 策略。
3. 对 `--dev`、Goal 门禁、分支保护/CI 路由做独立 Reviewer、完整 R9、远端 CI；**涉及 Host/受保护策略的变更需单独授权**。
4. 仅选择一个低风险真实 Goal 试点；核对未遗漏、提速、无回归后再推广。失败可关闭开发期增量模式，回到现有完整提交门禁；已写审计证据保留。

## 10. 实施阶段、依赖与完成定义

### 阶段 A：需求/测试模板与覆盖可视化（低风险）

- 先更新 `docs/ai_rules.md` 中的流程规则 SoT，再同步方法论文档；选一个既有 Goal，把设计 REQ 和 TaskStore 做只读映射；输出缺口报告。
- 实现 `check_goal_coverage` 的只读/影子模式；验证 T-07/T-08/T-09/T-11/T-12。
- **阶段完成**：能明确回答“原设计多少项、已实现多少项、遗漏哪些项、证据在哪里”；尚不改变完成门禁。

### 阶段 B：开发期增量门禁与受限提交（核心提速）

- 实现增量选择器/回执，覆盖 T-01～T-06/T-10；保留安全扫描、锁和树身份。
- 先影子对照，确认被选用例覆盖实际修改影响面；完成安全负例、独立 Reviewer 和完整 R9 后，再受控开启 `--dev`。
- **阶段完成**：开发 Lane 的每次迭代不运行完整 R9，且不能凭开发回执获取正式发布/合并资格。

### 阶段 C：正式收口联动与试点（保证质量）

- 将覆盖检查接入 Goal COMPLETE，联动 Reviewer/R9/PR/CI/部署最终证据；保持原门禁默认安全。
- 以一个真实多 REQ Goal 试点“设计—增量—冻结—全量—部署—销账”；核对 F-01～F-09。
- **阶段完成**：可重复证明所有必需 REQ 已完成；能清晰区分阶段交付与整体 Goal 收口；保留一键回退至原全量提交路径。

**整体 Definition of Done**：方案代码、测试、文档、负例、独立审查、原版 R9、受保护 main CI、必要部署均完成，且实际试点证明无需求遗漏；只有此时才可把本方案标记为“已实施”。

### 11.1 拷问后主要优化（相对初始草案）

- **从“每次提交全量”改为“开发受限增量、正式候选全量”**，明确需要修改现有提交路径，不能只改文档。
- **从“新增需求账本”改为“复用 TaskStore + 设计范围双向校验”**，避免重复状态和额外维护。
- **从“所有任务 done 即完成”改为“所有批准 REQ 有证据地 ACCEPTED”**，堵住未建 Task、取消 Task、旧 SHA 三类假完成。
- **从“每 Lane 最终 R9”改为“优先按完整交付切片集成后 R9”**，降低并行场景重复测试。
- **从“全量一次即可”改为“每个精确冻结候选一次，树变更需重验；现有机械 carryover 例外”**，保证证据不漂移。
- **从“测试全绿即可”改为“架构可维护性 + 真实验收 + 受保护 CI + 部署身份核对”**，避免质量被单一测试数字替代。
