今天（2026 年 10 月 10 日）想聊一个话题：AI Agent 的竞争，正在从"谁的模型更聪明"转向"谁能让模型长期、稳定、可审计地干活"。 最近两周，arXiv 上关于 Agent 记忆、Agent Harness（Agent 运行外壳）、自我进化的论文密集发布。我把这些论文和 GitHub 上的一个中文开源项目放在一起看，发现它们指向同一个方向。

一、先看学术前沿：Agent 的三个新共识

1. 记忆不是"存起来"，而是"按需激活"

近两周 arXiv 上 5 篇 Agent 记忆与演进论文的时间线


10 月 8 日，Kairui Hu 等人在 arXiv 发表《Embodied Turing Machines》（arXiv:2610.12369）。他们提出一个有点反直觉的观点：目前很多机器人策略把大模型（VLM/VLA）放在决策回路里，每一步都问一次大模型。他们认为更好的做法是——让代码去测量和跟踪状态，决策完全写成代码，大模型根本不进回路。

这个工作给出的三个优势很值得琢磨：状态显式可存、执行可控且能从失败中灵活恢复、不同任务可以共享同一个"能力库"从而持续积累。最终在 RoboDojo 的 42 个双臂任务上，不带模型的代码库达到了 70.24% 的成功率。

这和 Agent 软件领域的走向是同一个逻辑：记忆如果只是平铺的向量数据库，事件之间的关系和状态更新是隐形的；结构化成图，检索更准，但构建成本高，还会在长历史里引入大量无关关系。

同一天，Yichen Liu 等人的《Event-Centric Memory with Query-Aware Graph Augmentation》（arXiv:2610.11920，QGMem）给出了折中方案：把长对话历史转成"以事件为索引的原子记忆单元"，保留每一段独立经验；再把相关单元合并成动态记忆轨迹，保留状态演进和当前状态。查询到来时，混合检索召回候选，再用"查询感知重排"把最相关的单元激活为一份紧凑的工作记忆，最后组织成局部图编码成图 token 一起喂给大模型。论文称在六个基准上，检索、多跳证据组合、冲突消解、超长对话推理都有稳定提升。

翻译成人话：让 AI 记住的方式，正在从"把所有历史塞进去"转向"保留经历、合并轨迹、按问题现场组装工作记忆"。

2. 检索到的记忆，未必"可以用"

10 月 5 日一篇被 NeurIPS 2026 "Who Verifies the Agents?" Workshop 接收的论文《The Right Memory in the Wrong Context: Verifying Retrieval Admissibility in Long-Term Agent Memory》（arXiv:2610.07309，作者 Zi Wang 等，代码在
github.com/ziwang11112/right-memory-wrong-context）提出了一个很尖锐的问题：答案对不对、召回率高不高，并不能证明这条记忆路由是"合规"的。一条路由可能因为漏掉了必需证据而看起来安全，一个正确答案也可能来自不该暴露的提示。

他们提出的验证框架给每个"记忆-查询"组合打三种状态：可采信、不可采信、未决。对 RHELM 和 MemOps 两个公开长时记忆基准的冻结排名做 top-20 重分析（覆盖 3767 个查询）后，锚点召回从 0.432 提升到 0.533，80% 召回可行性从 0.237 提升到 0.311。

记忆可采性验证：重分析前后锚点召回与 80% 召回可行性对比


3. "承认不知道"正在被量化评估

10 月 8 日《Accurate but Not Humble: Evaluating Epistemic Humility in LLM Agents under Knowledge Conflict》（arXiv:2610.12360）专门评估：当检索到的证据和 Agent 的先验信念冲突时，它是会修正答案、承认不确定，还是固执地错下去。传统的 Agent 评测只看任务成功率，看不出这一层。

同日发表的《Do LLMs Learn from Rewards in Context?》（arXiv:2610.11152）则反思了"上下文强化学习"这个说法：Agent 在推理时靠积累上下文经验来变好，到底是不是真的"从上下文中学到了奖励"。

4. MCP 被尝试用于"规则注入"

10 月 7 日 Pedro Farinha 的《Applying Security by Design at the Point of Execution》（arXiv:2610.10659）做了一组对照实验：通过 MCP server 在代码生成时把受治理的安全需求交给模型。在 DualGauge 的 59 个 Python 任务上，全部安全测试通过的比例从 44.1% 升到 78.0%；在 BaxBench 的 28 个后端场景中，功能正确解里无成功攻击的比例从 65% 升到 86%。

结论的适用范围需要读者留意。论文列出的局限中，最关键的两条是：其一，联合"安全且功能正确"指标没有显著提升，因为更严格的代码在某些从未声明固定值的任务上会失败；其二，也是更硬的一条——所有实验只用了 1 个模型，每个任务只生成 1 次。论文还给出了 Oracle Security Reminder（85%）作为参照上界。所以这更接近一个有希望的单点实验，而不是"MCP 已成为标准管道"的定论。

MCP 规则注入实验：DualGauge 与 BaxBench 两个基准的通过率对比

二、回到工程：llm-first-loop 在做什么

上面这些论文里反复出现的关键词——记忆组织、工作记忆激活、经验可采性、Harness 设计、演进审计——在一个中文开源项目里被同时工程化了。

llm-first-loop（简称 LFL） 是一个 Apache-2.0 协议开源的 Agent 运行时框架（GitHub: deyi2026/llm-first-loop，0.x 阶段，仍在快速迭代中）。它自己给的核心循环是五个阶段：消息进 → 理解 → 行动 → 真诚回答 → 记住。

LFL 核心循环五阶段：消息进、理解、行动、真诚回答、记住


先摆事实。截至 2026 年 10 月 10 日：版本 0.6.27，Python 3.13+，代码库 398 个 Python 源文件（不含 __init__.py，统计口径 find src -name '.py' ! -name '__init__.py'）、约 16.2 万行（find src -name '.py' ! -name '__init__.py' -exec cat {} + | wc -l），804 个测试文件（find tests -name 'test_*.py'）。仅 10 月 4 日到 10 日这一周，就有 171 次非合并提交（git log --no-merges --since=2026-10-04 --until=2026-10-11 --oneline | wc -l）。

LFL 最有辨识度的设计，是它对"程序"和"大模型"分工的重新划线。

设计一：程序最小化，但硬边界不让

README 的表述是：大模型是核心，所有动作围绕大模型展开；程序是辅助大模型使用（及时反馈、如实反馈），不是约束大模型使用。

它把判断类的事尽量交还给模型和文档规则（RULE-AI 体系），而程序只死守六类东西：AI 无法自行可靠完成的真实执行/持久化、协议与授权、灾难性安全、物理资源、崩溃恢复，以及不可重复副作用边界。

这解释了为什么 LFL 会在测试数上花大力气——804 个测试文件对应的核心诉求是"程序故障时如实告诉 AI，别让它悄悄降级"。


程序与模型的分工：判断交还模型，六类硬边界程序不让

设计二：让 Agent 能自我审视和自我修正

LFL 提供了一组"自省工具"，让模型能查询自己的运行状态（architecture_status），并在出错时自主调用修正工具（adjust_strategy、retry_tool、refresh_config）。

演进闭环的设计尤其值得看：submit_evolution（提建议）→ 人工审阅 → 按权限分级执行 → 全链路审计。EVOLVE_LOCAL_EXEC 有三档：0=仅建议、1=白名单局部执行、2=全面执行。

这里有个细节很能说明它的性格：执行动作、验证、回滚由 AI 自主完成，但程序不会代 AI 下"已验证通过"的结论——验证结果如实标注 unverified，由 AI 自己负责复核。

设计三：记忆做成可检索、可溯源、多层的

LFL 的记忆体系包括：会话记忆、归档检索（search_archive 找回被压缩的上下文）、统一记录检索（search_records）、语义摘要、语义向量检索（EMBEDDING_PROVIDER）、独立记忆提取，以及 Evidence 系统——结论需要挂来源和采集时间才能被检索。

对照前文的 QGMem 论文"按需激活工作记忆"，LFL 走的是另一条工程路径：不追求记忆结构的绝对最优，而是让每条记忆的来源、时间、scope 都可以被独立核验。

它甚至把"证据按 owner scope 隔离"做到了对外暴露的边界上：在 MCP 只读导出时，证据面默认禁用，必须显式指定 --evidence-owner 才能访问。

设计四：Learning Plane——失败自动变成候选方法

这是我觉得最能体现"AI 优先"思路的设计。LEARNING_PLANE_ENABLED=1（默认开启）时，会话结束后写入 durable 队列，后台消费执行 ReflectionRun，产出的候选方法写入方法库，并带上运行时推导的 provenance（真实 episode ref + learning job ref）。

机制触发很朴素：单次运行轮数 ≥6、工具调用 ≥6、失败 ≥2、重复调用 ≥2、出现停滞——满足就触发一次隔离的自我蒸馏，每次入队至多产生 1 次后台模型调用。默认 METHOD_REFLECTION_MODE=auto，可以设为 off 彻底关闭。

更关键的是防自证设计：方法资格判定的 verdict（
pass/fail/mixed/insufficient）判定权在模型手里，但程序只证明 episode 身份，且 qualification episode ≠ source episode——不让一条经验自己给自己打分。

设计五：把安全边界做进运行时，而不是做进提示词

这部分我建议读者重点看，因为它是踩过坑才有的设计：

  • web_fetch SSRF 内网拦截：默认开启，拦截私网/环回/链路本地/保留段地址，IP 字面量和 DNS 解析双路径都查；重定向逐跳校验（手动循环上限 5 跳，每跳重新校验）；DNS rebinding 收窄（curl 用 --resolve 钉住已校验 IP，httpx 连接后复核实际对端 IP，命中即丢弃）。

这里有个必须如实转述的局限——项目自己在 README 里标注了：httpx 通道的 GET 在复核对端 IP 时请求已经发出，只能防数据回读，更强隔离要走 curl 钉扎通道。也就是说，DNS 防护在两条通道上强度并不一致。

  • 上下文预算预警：占用率 ≥80% 时注入一次预警，但"压缩还是收尾"的决策归 AI，程序不自动压缩。
  • 孤儿 tool_calls 回执：流式客户端中断时自动写"已取消"回执，避免严格 function calling API 报 400。
  • browser 工具的硬隔离：只读感知和变更操作分成两个工具，browser_operate 是单派发 mutation，不做 fuzzy 匹配、不重试、不替 AI 判断"任务是否完成"。

三、横向对比：LFL 和主流方案的分工

需要说清楚的是，LFL 不是要替代所有东西，它和主流方案的分工是不同的：

抽象层次

编排优先，追求快速搭出业务流

运行时优先，程序与模型分工是核心命题

记忆

通常是向量库 + 摘要

多层记忆 + Evidence 溯源 + 方法库生命周期

演进

多为人工改 prompt / 改配置

模型可提交演进建议，人工审阅后分级执行

失败处理

常有静默降级或重试掩盖

工具回执如实标注 [状态: xxx]，错误完整透传

安全

多在应用层

内核层硬执行（SSRF、重定向逐跳、DNS 钉扎*）

对外集成

主要面向自身生态

MCP 只读导出，让外部宿主复用其能力

* DNS 钉扎仅在 curl 通道成立，httpx 通道的请求发出时已无法撤回，详见前文对应条目。

LFL 最有辨识度的地方，是"诚实的失败"和"可核验的结论"这两件事被写进了底层设计。 工具失败了就说失败，没验证就说 unverified，样本不够就标"样本不足"。这种"反自我表扬"的设计，在当前行业的评测实践里（对照前文 arXiv:2610.12360 那篇专门评估"认知谦逊"的论文）恰好是对症的。

四、未来应用方向

基于现有能力，我觉得几个方向值得期待：

长期陪伴型助手。 有了分层记忆 + Evidence 溯源 + 方法库，助手有机会跨月记住用户的偏好和纠正，并让这些记忆保持可核验。这对有长期上下文的场景（写作、编程教学、健康管理）是有价值的。

可审计的自动化。 EVOLVE_LOCAL_EXEC 的三档权限 + 全链路审计 + verify_result 如实标注，意味着企业可以把一部分自主权交给 Agent，同时保留完整的追责链。对金融、医疗辅助这类需要留痕的场景，这套组合能更容易地向合规方说明"它做了什么、依据是什么"——但能否通过具体审查取决于监管口径，本文不做判断。

多端一致的 Agent。 LFL 已经支持 CLI / Web / 飞书桥三端接入，配置 FEISHU_OWNER_OPEN_ID 后两端共享同一会话——在飞书里说的话，可以在 Web 端接着聊同一个上下文。

生态共建的经验与方法共享。 export-serve-mcp 把经验库、方法库、证据 ledger、能力目录以 MCP 协议导出，供外部 Agent 宿主（如 Claude Desktop）复用。需要说明的是，该能力目前在 main 分支的 Unreleased 区，尚未随 0.6.27 正式发布，读者按已发布版本安装会找不到该子命令。配合 arXiv 10 月 7 日那篇"MCP 作为规则注入管道"的实验结果看，这个方向确实在被探索——但那是单模型、单次生成的实验，还谈不上"标准"。

五、上手

# 1. 安装（uv 一键，lockfile 精确可复现）
uv sync --frozen --extra dev

# 2. 配置密钥（默认 deepseek-flash，不设 LLM_MODEL 也能跑）
export LLM_API_KEY=sk-xxx
export LLM_BASE_URL=https://api.deepseek.com/v1

# 3. 最小闭环
python -m llm_loop.cli "请读取 data/notes.txt 并总结内容"

# 4. 交互模式
python -m llm_loop.cli --interactive

项目是 Apache-2.0 协议，要求 Python ≥ 3.13。

结语

回看过去两周的这些研究，有一条线索相当清楚：Agent 系统的下一个战场不在参数量，而在记忆的组织方式、失败的可信度、以及系统能否诚实地描述自己的能力边界。

llm-first-loop 只是一个 0.6.x 版本、约 16 万行代码的开源项目，它给出的答案是"程序最小化 + 规则驱动 + AI 自主演进"，并且用测试和文档规则把这句话落到了实处。

至于这套路线能不能走通，市场会给出答案。欢迎在评论区聊聊你更看好哪条技术路线——是让大模型进决策回路，还是让代码接管决策？
