这是 LFL 每日系列的第三期。前两期分别聊了 Agent 的记忆范式，以及 AI 自我改进的"自证陷阱"。这一期往下挖一层，看这个项目的架构本身——它到底相信什么，又在哪些地方动摇了自己的信念。

开篇：一个反常识的设计取向

大多数 Agent 框架加固的方式是加规则。

遇到问题就补一条规则，模型再犯就再加一条。项目跑久了，prompt 里塞满"请务必……""切勿……"，规则越写越长，模型越写越僵，最后大家开始抱怨"限制模型发挥"。LFL 的规则清单 docs/ai_rules.md 有 477 行，27 条 RULE-AI 规则（编号 RULE-AI-00 至 RULE-AI-26），但它的总纲第一句却是收紧动作的方向，不是收紧思考的方向——稳定目标和约束，不稳定假设；收紧动作，不收紧思考（
docs/ARCHITECTURE-ai-operating-v1.md 设计原则栏）。

更有意思的是规则零里那句定义：程序是 AI 的感官和手脚，非大脑。 程序提供信息与执行通道，不替 AI 决策。

这句话听起来平淡，但它推翻了 Agent 工程里一条默认假设——程序和模型是同一侧的，程序是"更严格的那个 AI"。在 LFL 的划分里，它们根本不在同一侧：模型是大脑，文档规则是给大脑的约束，程序只是神经和肌肉。这个划分一旦成立，后面所有设计都开始变得可推导。

哲学一：事实是一种有结构的、有时效的、会被降级的对象

LFL 有一份 567 行的《AI State Model v1》文档，把 AI 的状态切成三层。

第一层叫 Semantic AI State，里面不是一堆松散的记忆，而是七个有明确语义的槽位：Objective（目标）、Constraints（硬约束）、Facts（已确认事实）、Hypotheses（假设）、Decisions（决定）、Open Questions（开放问题）、Rejected Hypotheses（被拒绝的假设）。

光是"Rejected Hypotheses"单独占一个槽位这件事就值得停下来想一想。一般的记忆系统只存"记住了什么"，因为被证伪的内容没有价值，删掉就完了。但 LFL 认为被拒绝的假设有长期价值——它记录了"这条路走不通"，避免下一个会话重蹈覆辙。

每个 Fact 则带四个标签：authority（权威高低）、freshness（时效）、scope（作用域）、provenance（来源），外加一个 confidence。这四个标签不是装饰。freshness 的存在意味着系统承认"事实会过期"，于是有了降级链路：

current fact --freshness expires--> needs_refresh
needs_refresh --no longer decision-relevant--> evidence_ref only
open question --resolved/stale--> retire
decision --no longer relevant to active mission--> archive

一个存了三个月不再更新的"事实"，在这个架构里不会因为曾经正确就继续享有事实的地位。

文档里还有一条我认为最能说明气质的原则：HOT ≠ 高可信，COLD ≠ 低可信。 上下文温度（HOT/WARM/COLD）表达的是"当前决策相关性"，不是可信度。一个尚未验证但会决定下一步走向的假设，完全可以是 HOT。混淆这两个维度，就会滑向"越重要的信息越可信"的错误。

LFL 自己的审计文档
AUDIT-20261007-p0-architecture-gap.md 记了一个很有说服力的数字：method 卡 677 张，实际消费记录 6 条，消耗率约 0.9%。系统敢把这个数字原样写进审计、并据此判定"供给远超消费是一个问题"，而不是挑一个好看的口径——这本身就是这套事实观的一部分。




哲学二：反身的债务基线——允许报错，禁止新增

这是我觉得整套架构里最漂亮的一处设计，也几乎没被外界讨论过。

大多数项目防架构腐化的办法是立规矩："各模块不得互相依赖"。但规矩靠人遵守，早晚会破。LFL 的做法是：先把当前所有违规项如实测量并冻结成一个基线，然后写一条只准缩不准涨的棘轮（ratchet）。

Kernel v1 边界契约文档里写着，机械扫描当前主干代码，发现了 22 条反向依赖——也就是"内核依赖了外层能力模块"的违规边。处理方式不是立刻重构，而是：

这些不是"推荐依赖"，而是 P1-4 上线时的事实债务基线。任何 edge 消失时必须同步从基线删除；任何新 edge 都由 CI 拒绝。

我核验了仓库当前状态：
tests/guards/function_size_baseline.json 里的 kernel_import_edges 数组确实是 22 条，与文档完全一致，包括 core/loop -> methods、runtime -> methods 这些最刺眼的边。

这条规则的美妙之处在于它同时解决了两件通常对立的事。

一是它承认现实。22 条边不是bug，是历史既成事实。新人接手时看到的是一张诚实的欠账表，而不是一句"请不要这样做"。

二是它把治理成本从"持续自省"降到了"CI 机械判定"。
tests/unit/test_arch_guards.py（51,981 字节）用 AST 扫描静态 import，归一化成 package 级的 owner -> imported_root，然后做双向检查：出现未登记的新边则测试失败；已消失的边若没从基线清理也失败。文档的 Non-goals 段落甚至直说：本轮不声称这 22 条反向依赖已解决。

契约里还有一条反作弊条款，我觉得写得很清醒：

禁止为了过 guard 把 import 改成动态字符串导入或函数内隐藏导入。本契约约束的是职责方向，不是语法游戏。

任何做过静态架构检查的人都知道，这是最容易被绕过的地方。作者提前把这个后门堵上并写进文档，说明他清楚这类防线是怎么被突破的。

哲学三：六面是操作模型，不是代码目录

LFL 把 Agent 拆成六个控制面：Mission（目标/约束/决策）、Epistemic（事实/假设/证据）、Context（HOT/WARM/COLD + 稳定前缀）、Reasoning（假设竞争/信息增益/停止条件）、Action（风险分级/自主度/可逆性）、Evaluation（漂移/成功率/工具效率）。

但这里有个容易被误读的地方，我在审计文档里找到了明确的澄清。Kernel v1 契约第一段就写着：

LFL 的"六面"是操作模型，不是源码目录结构。本契约不把仓库重构成 kernel/ + planes/。

审计文档的判断更直接。它按自己的口径统计（src/llm_loop 下 26 个顶层包，另有 6 个顶层能力模块由 P0-3 guard 单独登记），发现有相当一部分模块无法归入任何一面：web/（交付面，六面里根本没有这一面）、semantic_logic/（横切所有面的语义权威）、core/session.py（单文件 110,382 字节）、core/history.py（97,019 字节）、core/episode_history.py（74,972 字节）。

所以这里有一条我认为是本文最重要的话：这套架构没有假装它已经实现了它自己的模型。 六个面是设计意图，二十多个实际顶层包是现实落地，两者之间的差集被如实记录在审计里，而不是被一句"六面已落地"盖过去。

值得一提的是，这份审计连自己上一版的统计口径都判了错：rev 2 写的是"27 个子包"，rev 3 用 P0-3 机械扫描推翻它，改成"26 个顶层包 + 6 个顶层能力模块"，并明确标注 rev 2 是"统计口径错误"。一个项目愿意把自己的历史统计错误留在文档里让读者看见，本身就是这套哲学的一部分。

审计文档甚至专门给自己记了错。rev 2 修正了 rev 1 的一个 currentness 错误——rev 1 只读了当日上午的 CHANGES 文档就断言某功能"已实现待部署"，但同日下午的提交已经把那段代码删掉了。rev 2 的教训被写成了机械规则：

任务清单引用的任何 capability，必须先在 HEAD 上做 symbol/commit survival check，只读 CHANGES 文档不构成充分证据。

一份架构文档里主动记录自己上一版的错误，并把它固化成下次的检查项——这件事本身比它记录的那个错误更有信息量。

哲学四：证据可以引用，不该复制

LFL 的证据体系有个反直觉的设计取向：存引用，不存副本。

状态模型文档的持久化决策表里，evidence_refs 一栏的理由写的是"引用比复制更省 token"。配合我上期提到的 Evidence 系统——结论需要挂来源和采集时间才能被检索，以及证据按 owner scope 隔离、MCP 只读导出时证据面默认禁用、必须显式指定 --evidence-owner 才能访问。

这实际上是在做一件数据工程里很少被明确表述的事：记录"谁在什么时候说了什么"，而不是"世界上发生了什么"。 前者可审计、可追责、可隔离；后者只是快照。

我在设计上有个疑问：引用比复制省 token 这个理由，在短期任务里不成立——多一次检索往返往往比直接复制更贵。LFL 显然知道这一点，所以它把 evidence_refs 限定在 Durable Semantic State 那一侧，而 Ephemeral 侧的 active_hypotheses 明确配了 supporting_evidence 和 contradicting_evidence 直接存内容。引用策略是按状态的持久性分级决定的，不是一条通用原则。

哲学的反面：这套架构自己承认的局限

写架构哲学文章只讲优点是不诚实的。这里讲三处我实际核验后发现的张力。

第一，架构文档与代码之间存在时间差。 我核对了 git 历史：
ARCHITECTURE-ai-operating-v1.md 和 ARCHITECTURE-ai-state-model-v1.md 的最后一次实质修改是 2026-08-26，距今 45 天；两份文档头部都还标着 "v1 Draft"。而同一时期 ai_rules.md 一直在更新，最近一次是 09-30。也就是说，规则层在持续演进，架构总纲却停在了 Draft 状态。以 2026-10-10 的 main@692aef75218e 为统计时点，代码有 161,472 行（不含 __init__.py）、805 个测试文件，这个 Draft 与现状的对应关系需要读者自己判断。

第二，债务基线是双刃剑。 棘轮只准缩不准涨，听起来很稳，但它有一个副作用：它把"22 条违规边"合法化了。新增一条边要过 CI，很难；而基线里已有的边在日常开发中可能被继续依赖，形成路径依赖。审计文档自己也点出了这个风险——G4 项记录的现状是"横向扩张仍在进行"，并注明当日仍有新能力合入主干，而"冻结"目前"是策略决策，无机械执行"。有意思的是，这个判断写于 10-07，而 Kernel v1 契约的棘轮正是针对它的机械落地。也就是说这个缺口正在被逐步关闭，但关闭的进度没有在本期核验范围内复查。

第三，也是我最想说的一条：这套架构的诚实，和它的完整性，是两回事。

架构文档写得非常克制，非常愿意说"我们没做到"。但我核验后发现一个事实：这些"我承认的缺口"本身，没有被纳入任何机械守卫。Kernel 边界的 22 条基线被 CI 守着，函数尺寸基线被 CI 守着，但"六面归面不全""持久化基座分散在至少 8 个 surface""方法消费率 0.9%"这些被写进审计的结论，靠的是人的纪律去偿还，不是机器去拦。

这形成一个有意思的对比：结构性错误有棘轮，承认了的结构性错误没有棘轮。 一个勤于自省的架构，和一个自省能自动执行的架构，中间隔着的不是认知，而是工程。

外部对照：这套哲学在别处也有人在做

LFL 的设计不是孤例。下面三条来自近期的独立工作，可以看到相似的判断。

其一，用冻结的裁判避免自证（上期已述，此处只取架构角度）。 我在上一期写过 arXiv:2610.12469（Rubric-CEPR）如何用冻结的 Critic 给自产样本打分。就架构哲学而言，它的意义在于：把"谁有资格做判断"写进了系统结构，而不是依赖使用者的自觉。

其二，把技能写成可证伪的契约（上期已述，此处只取架构角度）。 arXiv:2610.11781（Skill-V）把技能表示为版本化的可证伪契约，语义意图链接到可观测的行为准则，契约评估与实际结果不一致时触发对已有边界的修订。它和 LFL 方法库"激活需跨 ≥2 个不同 task_type 通过"是同一类思路的两种实现——都是把"这条经验现在凭什么算数"变成一个可检查的结构问题。

其三（本期新增），用工程手段压制架构漂移。 arXiv:2610.07832（HERMES，10-06）报告，把仓库组件从被动的软件制品变成带常驻模型的"开发原语"，在四个软件工程基准上平均超过匹配基线 12.4%；即便用 Qwen3-8B 级别的模型，也能在四个基准上落在 GPT-5.6 Sol 均匀配置的 4.5% 以内，同时在 Terminal-Bench 4.0 上降低 26.2% 推理成本。结论指向"harness 设计本身是软件工程 Agent 的主要变量"。LFL 把这条做成了 import 棘轮，HERMES 做成了组件化原语，路径不同，指向相近。

这套哲学在日常开发里长什么样

架构哲学如果只在文档里好看，就不是哲学，是口号。我抽三份真实的日常产物来看。

第一份是 LFL 自己给自己开的药方。 仓库里有一类 EVO-<日期>-<编号> 开头的文件，记录的是 AI 提出的架构演进建议。我翻了几个，格式高度一致：先写变更性质（工具 schema 面 / 程序面 / prompt 面），再写覆盖核算，最后是无异议的弱模型 A/B 对照。这套格式本身就是哲学的体现——它规定"任何要改 AI 可见表面的改动，都必须先证明对弱模型不退化"。绝大多数项目的变更记录不会写这一条。

第二份是测试文件本身。 805 个测试文件（上述 HEAD 时点）的分布不均。安全相关的、协议回执相关的测试密度明显高于业务逻辑。一个项目愿意为一个"程序故障时必须如实报错"的行为写几百个测试，说明它把这条当成了真约束而不是口号。
tests/unit/test_arch_guards.py 一个文件 51,981 字节，测的不是业务功能，是"架构不能腐化"这条元规则。

第三份最微妙：演进建议的提交方式。 LFL 的演进闭环里，AI 提建议（submit_evolution），人工审阅，然后按权限分级执行——EVOLVE_LOCAL_EXEC 有 0/1/2 三档。这个设计里有一个容易被忽略的判断：0 档（仅建议）不是失败态，而是常态。多数项目的"自动化"叙事是"AI 自动修好一切"，而 LFL 明确把"提建议"和"自动执行"分成两个权限等级，并且默认倾向保守。

我在核验过程中注意到一个细节，可以作为这套哲学的一个缩影。项目里有一批 commit 消息长这样：fix(r9): r9_commit.sh 豁免判定调用名修复——重命名漏改致判定架空。它记录的不是"修了一个 bug"，而是"这个防作弊检查因为重命名而失效了"。防的是 AI 自己，防的是自己写的门禁。

一个值得单独讲的分歧：程序该不该碰"判断"

围绕 LFL 最容易起的争论，几乎都收敛到同一个问题上：程序的职责边界该画在哪。

一种观点认为，程序应该尽可能多地替模型做判断——把规则写死，让模型少犯错。这条路线的优点是稳定，缺点是天花板低：模型遇到规则没覆盖的情况就束手无策，而且规则越多，模型越倾向于在规则里找安全区而不是解决问题。

另一种观点认为，程序应当完全让位于模型，只提供执行接口。这条路线的天花板高，但极其危险：一次幻觉造成的误删、一次错误判断触发的越权，代价可能是不可逆的。

LFL 的位置在中间，但它选的位置很特别——它不争"判断谁做"，而是争"判断的证据从哪来"。

举个具体的例子。LFL 的方法库有一条规则：一条从失败里蒸馏出来的经验，不能在同一会话里直接生效，必须先拿到 qualified 状态。这不是"程序判断这条经验好不好"，而是"程序拒绝接受一个没有独立来源的主张"。程序没有说"你错了"，它说的是"你没有证据"。

再举一个。演进建议需要人工审阅，按 0/1/2 三档权限执行。0 档只提建议、不动代码，这是默认档。这里同样没有判断——程序不判断建议对错，它只是不给自己执行的权力。

把这个模式抽象出来：LFL 的程序角色更接近"举证责任分配"，而不是"结论生成"。 它决定的是"什么样的主张可以被接受"，而不是"什么结论是对的"。

这解释了一个之前我没想通的疑问。既然程序刻意不判断内容，为什么还要在架构、依赖、安全这些地方立硬约束？

因为那些地方有客观判据。反向依赖边存在与否、依赖基线有没有减少、文件在不在磁盘上、函数尺寸超没超阈值——这些都可以被机械判定，不需要理解语义。在有客观判据的地方用棘轮，在没有的地方要求标注"我核验不了"，这条分界线是清楚的。

我认为这是这套架构里最值得带走的部分：可信的系统不是让程序更聪明，而是让程序在说不了话的地方闭嘴，在能说话的地方不放过。

读者可能会问的三个问题

Q：这些设计是不是过度工程？ 对于一个还在 0.6.x 的项目，铺 27 条 RULE-AI 规则、审计口径的 26 个顶层包（另有 6 个单列能力模块）、22 条冻结的架构债务基线，很容易被质疑过重。我认为有一个判据值得摆出来：这套复杂度里，哪些是"为了未来可能的需求"预埋的，哪些是"当下已经踩到的坑"驱动的。规则 477 行里有多少是为预埋，文档里没说；但 AUDIT-20261007 记录的缺口全部是当下已发生的问题，22 条基线也是机械扫描的真实结果。所以至少在架构治理这一块，复杂度是后验的，不是先验的。这一点我不能替它打包票，读者可以自己去读那份审计文档判断。

Q：和 LangGraph、AutoGen 这类框架怎么比？ 我在第1期给过一张对比表，这里只补一句哲学差异：主流 Agent 框架的抽象中心是"图"或"会话"——节点、边、状态如何在框架内部流动；LFL 的抽象中心是"谁有权决定什么"。它的六面里没有一面叫"编排"，因为编排本身在这个项目里不是第一性原理。这个判断是主观的，但它解释了为什么 LFL 的代码里 methods/（方法生命周期）和 semantic_logic/（语义权威）会比编排模块更受重视。

Q：这套哲学能撑到 v1.0 吗？ 我不知道，也不打算假装知道。我能核验的只是截至 2026-10-10 晚 main@692aef75218e 的时点快照：最新已发布标签 v0.6.28、805 个测试文件、161,472 行 Python 源码（不含 __init__.py），以及 10 月 4—10 日 272 次非合并提交。这三个数字说明它跑得很快。至于跑得快是"接近稳定"还是"还在补窟窿"，那份自审审计文档比我的任何猜测都更有参考价值——它连自己上一版的判断错误都记在案上了。

如果要总结这套哲学

我会把它压成三句。

第一，程序不替你思考，但程序必须让你看清自己。感官和手脚的价值不在于更聪明，而在于不撒谎。

第二，结构由机器守，内容由模型守，边界必须写在明处。可以核验的用棘轮卡死，核验不了的明说核验不了——而不是假装两者都能管。

第三，承认做不到什么，和做到什么同等重要。这份审计文档里最有价值的信息，是它记下了自己上一版错在哪里。

说到底，一个 Agent 项目的架构哲学，最终体现在它如何对待自己的错误。是删掉痕迹，还是把错误写成下次的机械检查项。
