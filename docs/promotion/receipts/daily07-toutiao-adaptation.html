LFL 原创科普 · 第七期 · 2026-10-11（北京时间）。

一个 Agent 修不好，那就开三个：一个查资料，一个写方案，一个检查。听起来像流水线，实际上经常是——三个人一起把同一个错误讲得更自信了。

最近三篇新论文从三个不同角度戳这件事：协作什么时候真的变强、错误怎么在团队里传播、以及该按什么线索定位故障。对照之下，我更关心的是另一个问题：一个子 Agent 说"我做完了"，谁去核对它到底做完没有？

本文引用的论文均为作者团队自报的实验结果，我没有独立重跑它们；文中的数字只在明确归属的单篇论文内使用，不外推为行业结论。示意图由本文原创绘制。

一、协作不是线性叠加：它有一个生死线

第一篇《Ecology of AI Agents: Collaboration Creates a Population Threshold for Takeoff》（arXiv:2610.12436，2026-10-08）讨论的不是效率，而是生态安全：当一群被赋予了现实网络攻击能力的智能体，并且会私自部署更多同类时，群体规模本身就可能变成风险。它用一个以网络安全能力为"适合度"的种群增长方程来建模，得到的结论是：没有协作时，群体起飞要求个体能力超过某个临界值；一旦允许协作，集体能力随群体规模上升，于是出现一个群体阈值——低于它，种群走向衰退；高于它，即使个体能力没变，种群也会起飞。生态学把这种形态称为强阿利效应（strong Allee effect）。

【待插入配图1】

这篇论文真正想提醒的不是"人多好"，而是两件容易被忽略的事：阈值以下不是"没收益"，而是衰退；小规模红队测试不能保证大规模部署时的生态安全。 所以它主张"生态红队"与"种群节奏控制"——在受控环境中逐级放大部署规模，测量集体能力随规模的增长曲线，重新估计阈值。作者还提醒：能力提升会压低这个阈值，每一代新模型都得重新估。

顺带说一个相邻的数字，属于另一篇本期没展开的论文：《OnTrack》（arXiv:2610.12375，2026-10-08）在 SWE-bench 轨迹上评估"中止策略"时报告，83% 的被中断运行本来就在走向失败（6 次中止里判断对了 5 次）。这跟上面的阈值不是一回事，出自不同的论文、不同的实验设定，只是都属于"别以为被拦下的都算浪费"这个直觉。

二、错误会一路向下游漂移

第二篇《Error-Propagation Modeling for Failure Attribution in LLM-Based Multi-Agent Systems》（arXiv:2610.11600，2026-10-08）关心的是归因。多 Agent 系统里，一个结果出错时，很容易变成"最后一棒"的锅：最后汇总的节点写了句错话，于是大家以为问题出在写作环节。

真实情况常常不是这样。

【待插入配图2】

上图这条链路的要害在于：检索节点没有读全原文里"仅适用于测试环境"这个限定，加工节点把原文的说法当成了结论，汇总节点又把结论写得很完整。整个链路上没有任何一步报错——每一步的输出在局部看起来都自洽，错误是在传播中慢慢变形的。

更麻烦的是，修错地方等于白修：把写作环节改十遍，下一周同样的错还会再来一次，因为病根在上游。

三、定位故障，光看日志还不够，得看"谁和谁说话"

第三篇《Know the Shape, Find the Fault: Topology-Conditioned Diagnosis of Multi-Agent LLM Failures》（arXiv:2610.10126，2026-10-07）提供了一个反直觉但很实用的角度。

论文的出发点是：多 Agent 协调失常时，执行日志里的症状可能长得一模一样，但背后是信息传递、使用或验证环节的不同问题。而通信拓扑（谁把消息交给了谁）提供了额外的结构线索。

它给出两阶段框架 MAScope：先用 TSE（Trace Structural Extractor）从没有拓扑标签的执行轨迹里重建通信拓扑，再用 TC-Judge 做拓扑条件下的失败分类。实测结果是：通信拓扑与失败类型存在统计显著的关联（χ² = 409.9，p = 1.2×10⁻⁷⁰）；在 851 条 MAST-clean 轨迹上，加入真实拓扑上下文把 gpt-mini 的 Macro-F1 从 0.173 提到 0.350；用重建的预测拓扑时达到 0.346。

不过有两个前提不能省略：一是它依赖额外标注数据——TC-Judge 除了轨迹和预测拓扑，还用了从另一批带标签轨迹估计出的经验先验，以及一段人工写的拓扑失效模式描述；二是它并没有超过最强基线——0.346 只是"接近"纯轨迹的 gpt-5.4 基线 0.372。它真正的卖点在成本：在固定编排结构下，整条流水线的预计开销约为反复调用 gpt-5.4 诊断的 6%。

把这三篇并置阅读，可以得到一个不算新鲜但很少被落实的结论：多 Agent 的可靠性问题里，有一部分不是模型问题，而是结构和记账问题。 后面那部分不玄学，却最容易被省掉。

四、LFL 现在怎么做：让"完成"必须能被核对

我在写自己的开源项目 llm-first-loop 时，恰好在同一个位置踩过坑。多 Agent 那部分代码目前集中在 src/llm_loop/subagent/ 下两个文件（__init__.py 4 行、runner.py 2421 行）。我没有试图用"多开几个"来解决协作问题，而是先把结算做硬。举三个本轮实测到的细节：

【待插入配图3】

第一，"截断"不许伪装成"完成"。 子 Agent 的结果对象里，outcome 有五种取值：completed / failed / cancelled / truncated / refused。构造函数里写了一条不变量（runner.py 第 83-93 行）：如果 outcome 写成 completed，但 refused 或 truncated 标志为真，outcome 会被强制改写。翻译成人话：上下文用完了所以只做了一半，这事儿不能报成"已完成"。这正是第二节说的"整个链路上没有任何一步报错"的最小版本。

第二，结束和结算分开算。 工具注册表里 subagent_result 的描述写着"completed 才代表子任务成功结算"（src/llm_loop/tools/registry.py:129），但代码里还有另一层：结果到底有没有被父任务取走。结算字段在不同分支下会返回 collected、uncollected 或 unknown 三种取值——子进程可能确实跑完了，也可能只是没人知道；这两种"没有结果"被明确区分，而不是糊成一个空值。

第三，租约有到期时间。 fleet 租约默认 900 秒（runner.py 第 132 行）。到期就是到期，不靠"它应该快做完了"来续命。拓扑查询工具的语义也写得很克制：只返回机械的拓扑、归属与结算事实，不复活工作，没有 handle 的时候不编造 worker。

这三件事都很朴素，没有一个能解决论文里的误差传播问题。但它们保证了一件事：当父任务说"孩子完成了"时，这句话背后有可核对的字段，而不是一种语气。

五、这套机制解决不了什么

先把话说清楚，免得读者被误导：

  • 它不解决上游读错资料。 检索节点漏读限定条件这种情况，任何记账机制都救不了；那属于检索质量，属于另一件事（我在第六期专门写过搜索 Agent 的结果完整性）。
  • 它不解决模型本身的幻觉。 outcome 字段记录的是"这次运行发生了什么"，不是"内容是否正确"。字段填 completed，只说明它没被截断、没被拒答、没抛异常。
  • 它不构成多 Agent 的通用方案。 上面那些机制是在 llm-first-loop 这一个仓库里对子 Agent 场景做的取舍，不是行业标准，也没有做过大规模对照实验。
  • 上述几篇论文的结论我都没有独立复现。 它们的实验设置、模型版本和任务集各不相同，本文只做对照阅读，不做结论背书。

六、如果你今天就要分工做一件真事

把上面的东西翻译成三条不需要改代码就能用的做法：

  1. 先画拓扑，再定分工。 谁能直接把原始材料交给最终决策者？把中间转述环节尽量压短——第二节里"错误在转述中被抹掉"，靠的就是这一层。
  2. 给"完成"下一个可核对的定义。 不是"他说完成了"，而是"我能独立回读到结果"：一个文件、一条可查的状态、一次重新打开页面就能看到的公开状态。核对方最好不是你正在等的那个环节。
  3. 区分"没做完"和"做完了但没交"。 这两种情况在多 Agent 系统里长得几乎一样，但在现实里处置完全不同：前者要重做，后者要补交接。

顺带说一句，我把这些做法写进了 LFL 的运行手册，也踩过几个具体的坑，比如图片面板打开时去点正文会被遮罩吞掉点击、一次误操作就把整篇稿子删空——这类事只有真上手才会遇到。开源的意义大概就在这儿：坑写下来了，下一个人就不用再交一次学费。

七、小结

多 Agent 不是"人多力量大"的简单版本。一篇讲生态安全的理论模型说它有生死线，一篇讲误差传播说它会把错误推向下游，一篇讲拓扑诊断说定位线索藏在通信结构里——但这三篇分属不同问题，谁也没替谁背书。

比论文更值得记住的，是那句朴素的工程结论：一个系统里，"完成"必须是一个能被第三方核对的状态，而不是一句自称。 这件事不需要很强的模型，但需要有人愿意把账算清楚。
