# 方法卡：给下一个模型的提示物

方法卡不是准入条件，也不是格式作业。它只回答一个问题：**下次遇到同类问题，读到它能不能更快做对。**
答不上来，就先别写。

## 写之前先想三件事

1. 什么时候该想起它？写进 `description`。检索回执里 `summary` 就是它的前 120 字，`description` 最多 500——第一句写场景和人话，别写背景。
2. 读到之后具体做什么，或者去哪里看？
3. 怎么知道做对了？

三句话能说清，就写三句话。说不清，再展开。

`name` 用一句能读的短标题，不要 kebab-case 机器 ID——`id` 程序会生成。代码注释里记着一组对照：近 7 天方法卡深读率 10.5%，经验是 53%；差距主要就在 name 是机器 ID、summary 没信息。

## 三种形态，随便挑，也可以混

**提醒型**——最容易写，也最常被低估。
> 对外发表前，先核对 `review_admission` 回执里的 SHA 与 P0/P1，再发。

**索引型**——指向维护中的资产，不复制。
> 发布前：读 `docs/ai_rules.md` 规则二十八 → 按 `skills/article-review-gate` 起审查 → 先核对回执里的 SHA 与 P0/P1，再发。

**规程型**——只有步骤确实不显然时才需要。
> 1. 只读失败的那一处；2. 改最小面；3. 重跑同一条检查；4. 先复现失败再改，改完用回执说话。

没有哪种更高级。六节结构（`## Trigger` … `## Counterexamples`）仍然可用，但它现在只是可选排版，不再是写入门槛。

## 唯一的硬要求：能落地

- `name`、`description` 非空；`body` 至少有一行非标题内容。
- `description` 或 `body` 里要有一句可执行的当前性验证动作（"先核对…/先跑…/复现一次/跑 pytest"）；单独出现「验证」「核对」一词也算数。这是卡在环境变化后还能被信任的原因，也是经验池的同一道底线。
- 只给结论不给出处，等于把未来的自己坑一次。

## 别让它变成干扰项

- 卡片可能被自动注入，预算上限 3 张卡、1050 字；写长了，挤掉的是别人，也更容易没人读完。
- 规则、skill、脚本已经写过的，给路径，不要抄。抄一份就多一份会过期的副本。
- 删掉"很重要""务必注意"这类词，留下动作和判据。
- 一张卡只解决一类问题；攒成手册就该拆，或者直接去改文档。

## 它会自己长

- **来源**：`source_episode_refs` / `evidence_refs`，能追溯的卡才值得信。
- **验证**：`record_qualification` 记 pass/fail；`status` 只是质量标注，不挡检索，也不挡使用。
- **过期**：路径型断言写进 `freshness_refs`，文件变了会报 `changed`，不自动降级。
- **修正**：内容变了用 `save_candidate(parent_ref=旧卡)` 写新版；旧卡确实错了、且有独立证据，才 invalidate。读到卡发现它在误导你，改它，比记住"这卡不准"有用。
- **不强制记账**：RULE-AI-29 已撤销强制 `record_use`。读了、用了、没写，不影响任何事。

## 一句话

卡的价值在"让你下次少走一步弯路"，不在它长得像一张卡。

## 写入校验与检索语义

- 写入除内容非空外，还要求 `description` 或 `body` 里出现一次可核对话号：命令 / 工具名 /「复现」/「验证」/「核对」/「先…确认」之一；只写结论、不写怎么核对的卡会被拒。
- 检索是词法 + 语义融合；结果里的 `status` 会展示（candidate / active / invalidated …）。`invalidated` 表示前提已被证伪，看到不要照做；`retired` 不进检索。
- 查卡用问题里的判别性关键词（2~4 字），拿到 `method:<id>` 后再精确水合正文。
