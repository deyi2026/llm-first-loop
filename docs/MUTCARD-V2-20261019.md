## 1. v1 判据的真实机制（比「词面重叠」更死板）

`scripts/method_mutator.py:150-190`：

```python
tokens = [t for t in re.split(r"[^\w]+", item) if len(t) >= 4]   # 中文整句→一个长 token
if not any(tok in stops_text for tok in tokens): fail.append(item)  # 要求原样出现
```

中文没有词边界，验证条目常被切成一个 8-15 字的长 token；Stop 句只要换了措辞，该 token 就不存在。
实测：**29 张可解析卡里 28 张报缺陷，82 条验证条目里 58 条被判「未挂」**——包括 P02 四条全报，
而它的 STOP4 原文就写着「修复经探针+回归测试验证」。

更要紧的是短路：`if ver and stops and not GATE_RULE.search(stops)`。
只要 Stop 段出现「Verification 未逐条通过前不结案」，整个检查直接跳过。所以上一轮说的
「补一句让检测器闭嘴」不是修辞——它是代码里的一条 `if`。

## 2. v2 判据：反事实三分类 + 确定性校验

对**每条验证条目**问一句：*不观察它要求的那个事实 X，agent 还能不能合法结案？*

| label | 含义 | 是否缺陷 |
|---|---|---|
| `open` | 没有任何 Stop 条件要求观察 X | 是 |
| `auxiliary` | 该条是取证动作/报告规范，不是结案前提 | 否 |
| `covered` | 某条 Stop 条件满足时必然已观察 X（须给 witness 序号） | 否 |

判定由模型给（`judge_v2_spec.json`，本会话自判，**未经独立复核**）；detector 只做确定性校验：

1. 卡全文哈希 + 每条验证条目哈希必须与判定时一致，改一个字就 stale 拒跑；
2. witness 序号必须在范围内；
3. **witness 不得是通用门禁句**——`Verification 未逐条通过前不结案` 对所有条目一视同仁地成立，
   不指向任何具体观察，属自指豁免，不能当覆盖证据（这条是 v2 与 v1 的分水岭）；
4. 一条 `open` 一个 defect，正文不截断（v1 把 1-4 条聚合成一条，`detail[:80]` 砍掉后半句，
   清单名义粒度 ≠ 实际粒度）。

## 5. 5 张补丁（`evals/methodcard_rsi_v1/repairs_v2/`）

补丁只做一件事：把已有验证条目变成**结案前提**，并点名 observable，不写门禁套话。

| 卡 | 追加停止条件（节选） | observable_terms |
|---|---|---|
| P01 | 发布回执 SHA 一致、fetch 后 ahead=0、远端无分叉 → 才可宣布完成 | SHA / ahead=0 |
| P03 | ① 门禁以退出码为准，输出与退出码矛盾即未验证 ② 根因三证齐备 | 退出码 / 三证 |
| P10 | 每条命令输出须标注平台且与目标平台一致，平台不匹配的空结果不得入证 | 平台 / 空结果 |
| P23 | 写根因前须指出具体状态错配；「进程在跑」不构成根因 | 状态错配 / 进程在跑 |
| P28 | 每个 offered 选项须能指向登记中的线程/规则，指不到的删除 | offered / 登记 |

机械校验（`apply_repairs`，任一不过即拒写）：

- frontmatter 字节不变、验证条目不变、既有停止条件只允许追加；
- 每条补丁句至少点名一个 observable，且声明的 terms 全部出现；
- 补丁句不得命中 `GATE_RULE`。

结果：5 张补丁卡重扫 **0 open**；而 v1 重扫这 5 张仍有 P10/P28 报 2 条——
说明 v1 的通过与否跟条目质量无关，只跟措辞是否撞上长 token 有关。
