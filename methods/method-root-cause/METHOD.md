# Root Cause Analysis

目标不是尽快产生 patch，而是建立一条足以被反驳、最终又被证据支持的因果链。

## 开始前先回答

1. 现象第一次出现在哪个可观察边界？请求构造、wire、provider、runtime、模型行为、工具结果、验证脚本，还是 UI？
2. 最近有哪些变量真正改变过？哪些变量有证据证明没有变？
3. 当前“原因”是事实还是解释？怎样设计一个结果可能推翻它的实验？
4. 能否保留一个真实 baseline，避免修复过程中失去对照？

## 默认路径

1. **冻结 baseline**：记录当前失败输入、输出、环境、commit/working state 和关键指标。
2. **缩小边界**：找第一个与预期分叉的可观察位置，而不是从最终报错倒推全部原因。
3. **列候选假设**：优先写成可以被一次实验否定的形式。
4. **排序实验，不排序语义真理**：选择最便宜、区分度最高的实验先做，但不要把启发式排序当成根因裁决。
5. **一次改变一个关键变量**：其余模型、prompt、工具面、数据、runtime 尽量锁定。
6. **根据结果更新假设**：旧假设被否定后换假设，不给它不断追加补丁条件。
7. **定位肇因后再修**：先增加能复现事故的回归验证，再做最小机制修复。
8. **修复后回到真实 candidate**：确认最终工作树/提交候选而非实验副本通过。

## 常见边界分类

先区分问题可能属于：

- **数据/状态**：输入、历史、缓存、持久化状态变化；
- **协议/表示**：消息顺序、schema、截断、projection、serialization；
- **runtime/provider**：模型版本、参数、进程、环境、依赖；
- **模型行为**：相同可见输入下的决策差异；
- **工具/执行**：真实副作用或工具输出不符合契约；
- **验证方式**：测试命令、统计口径、管道退出码、错误实验隔离造成假红/假绿。

不要在尚未排除前四类时，过早把问题归结为“模型习惯”或“模型就是这样”。

## 实验设计要求

一个有价值的实验应回答：

- 它改变了哪个变量？
- 哪两种结果分别支持/反驳什么？
- 是否真的触发被研究的机制？
- 是否存在 cache、session、数据目录、模型 residency 等跨实验泄漏？

若实验无法改变当前信念，它通常不是下一步最优动作。

## 停止条件

可以停止根因探索并进入修复，当且仅当：

- 已找到与故障边界一致的机制；
- 有单变量或等价强度证据支持因果关系；
- 替代解释已经被关键实验削弱或排除；
- 修复可以针对机制而不是表象。

若证据只能说明“相关”，就明确保留不确定性，不包装成确定根因。

## 验证

修复后至少检查：

1. 原始复现由失败转为通过；
2. 机制级回归测试存在；
3. 邻接行为未被破坏；
4. 生产 runtime/最终 candidate 与实验环境的差异已说明；
5. 改善不依赖同时改变的第二变量。

## 反模式

- 看到异常文本立刻 patch；
- 一次改五项配置，成功后归因其中一项；
- 不保存 baseline，修到最后无法比较；
- 测试没有触发被测机制却宣称验证成功；
- 把另一 provider/runtime 的结论直接当当前 parity；
- 连续换参数试到成功，再事后编因果解释；
- 先把问题归因为“模型习惯”，而没有排查程序和 prompt 可见面的变化。

## 方法边界

紧急安全止血可以先做最小隔离，但止血不等于根因已经完成。硬安全边界仍由程序负责；语义原因和修复策略由模型基于证据判断。

## 可沉淀内容

事故本身及具体根因进入 Experience；跨多个事故都成立的诊断顺序才升级为 Method；稳定可自动化的采样/验证步骤进入脚本或 Skill。
