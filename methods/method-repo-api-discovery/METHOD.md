# Repository / API Discovery

先建立当前代码树的真实 API 契约，再调用或修改。不要把运行时报错当作 API 探索器。

## 开始前先回答

1. 当前真正未知的是名称、所在模块、签名、返回值、状态生命周期，还是调用约束？
2. 哪个来源最接近真值：定义、类型、测试、调用点、文档，还是运行时 schema？
3. 代码库是否正被并行修改，使旧行号、旧 grep、旧记忆可能已经失效？
4. 是否能在不装完整 runtime 的情况下先验证纯解析/构造层？

## 默认路径

1. **定位定义**：全项目搜索准确符号、相近符号和相关模块；不要先猜 import。
2. **读契约**：查看真实签名、类型、docstring/注释、返回值和相邻实现。
3. **看调用形态**：枚举当前 callsites；多行调用要读完整片段，不能只看 grep 单行。
4. **看测试**：若调用语义仍不清楚，优先读覆盖该 API 的测试或 fixture，确认实际期望。
5. **最小验证**：可用纯函数、小对象或窄测试验证时，先做最小实验，再启动完整 runtime。
6. **执行/修改**：只有契约清楚后才调用、编辑或扩展。

## 证据分支

- **符号不存在** → 不继续猜大小写/别名；搜索邻近概念、registry 或导出面。
- **签名与记忆不同** → 当前代码定义优先，历史经验仅作线索。
- **返回值结构不明确** → 查类型、实现和测试，不通过连续运行猜 tuple/dict/object。
- **调用点很多** → 在签名变更前建立当前 callsite 清单；修改后重新枚举一次。
- **并行工作树有漂移** → 以当前 tree 内容为准，不使用早先保存的行号直接 patch。
- **文档与代码冲突** → 先确认版本/commit；对当前运行行为，代码和真实 runtime evidence 优先，记录文档漂移。

## 修改 API 时

签名或语义变更后：

1. 再次全项目反查定义和 callsites；
2. 检查多行/动态注册/间接调用，避免单行 grep 漏项；
3. 跑直接邻接测试；
4. 若生产 `src` 发生实质变化，最终还要跑项目规定的权威 gate，不能只凭定向测试宣布完成。

## 停止探索的条件

当名称、签名、返回结构和本次任务涉及的调用语义已经由当前代码/测试证实时，停止继续“多看一些 API”。不要为了完整理解整个仓库而扩大任务。

## 验证

区分以下事实：

- “能 import”不等于“调用契约正确”；
- “小测试通过”不等于“所有 callsite 已迁移”；
- “当前 working tree 通过”不等于“staged/committed candidate 通过”；
- “文档这么写”不等于“当前 runtime 就是该版本”。

## 反模式

- 凭记忆猜类名、函数名或 provider API；
- ImportError 后换另一个名字继续试；
- TypeError 后逐个删/加参数来猜签名；
- 只看搜索结果行号，不读完整定义/调用；
- 依据几小时前的 grep 结果修改并行活跃文件；
- 用完整服务启动替代可以一秒完成的纯函数/静态契约检查。

## 方法边界

本方法不要求每次调用内部函数都先做全仓搜索。只有在契约未知、版本可能漂移或改动影响面不清楚时加载；一旦事实充分，直接行动。
