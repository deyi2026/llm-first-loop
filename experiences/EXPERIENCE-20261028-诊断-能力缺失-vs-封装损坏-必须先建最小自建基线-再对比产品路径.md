## 场景
要判断"框架/API 到底支不支持某能力"（本例：Chrome 能否在 Runtime 挂死时 handle dialog），产品路径反复失败，需要区分"能力不存在"与"我方封装弄坏了"。

## 反例（上一轮踩的坑）
先跑产品工具路径 → 它在超时里 `_drop_session()` → 再去直连 CDP 查，得到 `No dialog is showing` → 误判"Chrome 不支持/被抑制/延迟显示"。**取证对象在取证前已被自己的代码破坏**，证据全假，且看起来非常"实"（错误码是 Chrome 亲口给的）。

## 正确顺序
1. **先建最小自建基线**：`/json/new` 自建 target、自写最小 CDP 客户端（不经产品封装）、关键命令 fire-and-forget、跑完即 close。得到"框架原生能力"的纯基线。
2. 基线绿 → 问题必在我方封装：再用二分法剥离（本例对照 L1/L2/L3/L7-L9：超时不断连 vs 断连 vs 多连接断一条）。
3. 只在剥离清楚后才回产品路径做最终复验。

## 关键分离实验设计
- 把"现象"拆成可独立操纵的变量：超时 / 断连 / 连接条数 / 前台可见性 / 用户手势。
- 每个变量单改一条，其余不变；死亡样例（L2：断掉唯一连接 → dialog 永久丢失）比成功样例更能定位根因。
- 结论要能说出"哪一步之后不可逆"，而不是只描述现象。

## 本次结论（可迁移的判据）
- 「超时」与「连接丢失」是两种语义，任何"超时即判丢连并 drop 会话"的封装都会把一次慢响应升级成不可逆资源损失。
- 有状态资源（dialog/session/tab 句柄）的存活往往绑定在"最后一条控制连接"上，断连前必须先检查"断了之后还能不能救回来"。

## 适用边界
适用于：CDP/WebDriver/远程调试、需保活的长连接、任何"封装层自带超时+清理"的系统。
不适用于：无状态一次性请求（重试即恢复）的场景，那里超时重试反而是对的。
