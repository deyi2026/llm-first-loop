排查方法论（本次 8 条 evidence 闭环）：
1. 用户报障"反复 1210 + 新文案"→ 新文案出现证明 honesty.py 已加载（进程代码新）；
2. 主区事件日志 grep err1210.recovery 计数=4，但 4 条全是 tool 回执文本误命中（内容含关键词），非 action 事件 → recovery 从未触发；
3. 进程日志 grep "放弃降级/注入登记" 零命中 → 连 recovery 内部的 INFO 都没有 → 未进入流程（而非流程内失败）；
4. 三层排查：开关(env ERR1210_RECOVERY)→开；代码(diff 主区/镜像=0)→全；接线(engine mixin L146/L735)→全；
5. 结论只剩门禁条件不满足：全天 run.compact=0（会话压缩走 context.compressed 497 次），_last_history_compacted 主信号 False；辅助信号（相邻请求骤降≥30%且≥8条）因仅成功轮更新 count，三连败后 prev 陈旧 → 死锁式失效。
修复（commit 1f3ef39，镜像区 main）：门禁移除（任意 1210 均尝试降级，strip 无登记自动跳过→aggregate 兜底）；attempted 键 compact seq→run seq（_err1210_run_begin 挂 engine run 入口，对齐 _reset_overflow_state 先例，每 run 至多一次防循环）；compact_first 降级为快照真实判定；两个失败分支 break 前也更新 count。
教训：(1) 恢复机制"零日志零 action"≠没坏，可能是入口门禁静默 return——排查时先确认流程是否进入，再查流程内失败；(2) 触发条件绑定单一信号源（compact 事件）时，实际触发形态（消息级压缩/注入叠加）可能走别的路径——信号源要覆盖全部实际形态；(3) "仅成功轮更新"类数据源在连续失败场景自锁——观测数据源必须全量如实。
