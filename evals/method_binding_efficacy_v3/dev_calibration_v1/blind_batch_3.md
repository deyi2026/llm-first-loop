method_id: bounded-chunk-write-verify-for-long-file-artifacts-45c00c2ebf00
description: 通过 shell heredoc/cat 写入长文档时，传输可能静默截断内容，而命令仍返回 exit 0——回执证明的是'执行了'，不是'写完整了'。对长度超过单次命令可靠规模的交付物，应预先切成有界块（首块 cat >，后续 cat >>），每块后核对回执中的累计行数，末块附文末哨兵；一旦回读发现行数不足或句中截断，不要追加修补，而是删除后按更小块重建。

## Trigger
需要用 shell heredoc/cat 把长文档（数十行以上）写入文件交付物，或对一次写盘后的内容完整性没有独立回执、只能靠 exit 0 判断的场景。

## Discriminator
写入后立即可观察的事实：回执仅 exit 0 无输出，但 read_file 显示文件只有 8 行且在句中截断（预期约 115 行）——证明退出码与'成功'字样不等于内容完整；后续每个 ~30-45 行的 chunk 写入均完整到达预期行数（33→73→115、44→64→95），说明有界分块+逐块行数核对+文末哨兵可稳定绕开该失效模式。

## Short path
- 起草时按目标长度预切有界块，每块规模远小于出现截断的单次写入（本环境中 ~30-45 行的块均成功，单次 ~115 行写入在第 8 行被截断）
- 首块 cat > 写入，回执累计行数应等于该块预期行数
- 后续逐块 cat >> 追加，每块后核对累计行数（如 33→73→115）
- 末块确认最后一句完整并追加文末哨兵（如 NO_CORRUPTION_MARKER）
- read_file 抽查头/尾与句界完整性，再声明交付

## Stop conditions
- 累计行数与逐块预期一致，且文末哨兵在位/最后一句无句中截断，即可停止写入进入交付
- 某块后行数不符或尾部截断时，停止追加，删除重建为更小的块，不继续在同一文件上修补

## Verification
- 每个 chunk 后以回执中的累计行数核对预期值
- 最终 read_file 至少覆盖文件头、尾与截断敏感位置，确认无句中截断、哨兵在位
- 不以 shell exit 0 或'执行成功'作为长文档内容完整的证据

## Counterexamples
- 短文件（几行、远低于单次写入可靠规模）：单次写入+一次回读即可，分块只增加噪音与调用数
- 写入由专用 write_file 工具完成且回执自带字节数/行数：以该回执为准，无需 shell 分块
- 文件会被并发读者立即读取、不能容忍中间态：分块追加会暴露部分写入状态，应写临时文件后原子 rename，而非套用本方法
- 截断根因不是传输规模（如磁盘满、权限错误，通常表现为非零退出码或显式错误）：分块写不解决该类失败

description: 对共享服务的变更操作（restart/publish 类）先做绑定漂移预检，再修模型侧前置，最后停在 operator 闸门：并行取部署记录与进程版本，若部署记录绑定的代码身份 ≠ 工作区当前 HEAD，直接执行必被 fail-closed；此时优先读并行会话在 dirty 增量中留下的、与该操作同名的教训记录，得到围栏机制与修复链。随后逐项收敛模型侧前置：先跑测试再补提交被已提交代码 import 的未跟踪模块；grep 验证 gitignore 的构建产物是否含新功能（防『后端新前端旧』的静默半上线），陈旧则重建并复验；从当前源码而非旧记录核对 operator-only 命令参数，最后向用户交付唯一一条命令与预期结果（新代数、绑定 HEAD、产物指纹），不反复试探被围栏拦截的操作。

## Trigger
用户要求对受管共享服务执行重启/发布等变更操作，或报告『此前承诺的自动/队列式执行没有动静』；环境中存在并行会话痕迹（两次检查之间工作树 dirty 状态发生变化、出现新的未跟踪记录）。

## Discriminator
动手前即可读出的两条事实：(1) 部署记录绑定的 git_head 与工作区当前 HEAD 不一致——预示直接 restart 会被 binding 校验 fail-closed；(2) dirty 增量中存在文件名与本次操作类完全匹配的教训/经验记录——直接给出围栏机制、前置条件与修复链。二者把『直接重启试试』从候选空间中删去。

## Short path
- 并行取部署记录 + 进程版本，比较发布绑定的代码身份与当前 HEAD；未知量：这次变更操作会被什么挡住？
- 发现绑定漂移 ⇒ 放弃直接 restart；扫描 dirty 增量中与本操作相关的教训记录并读取；未知量：围栏与修复链是什么？
- 按记录逐项修模型侧前置：跑测试后补提交被已提交代码引用的未跟踪模块；grep 构建产物验证新功能是否在产物内，不在则重建并复验。
- 从当前源码核对 operator-only 命令的准确参数（不照抄记录里的旧命令），可用一次轻量探测确认围栏仍活跃。
- 向用户交付唯一一条经源码核实的命令 + 预期结果（新代数、绑定 HEAD、产物指纹），停止于用户闸门，待回报后再执行 restart 与核验。

## Stop conditions
- 模型侧前置全部有回执变绿：测试通过、tracked-clean、新功能字符串已出现在构建产物中，且 operator 命令已按当前源码核实并交付。
- 用户回报发布完成后才进入 restart 与结果核验；此前不重复试探已知会被围栏拦截的操作。

## Verification
- restart 后出现新 pid、服务 git_head 等于发布绑定的 HEAD、启动时间为当下、新功能路由/面板可达。
- 构建产物 grep 命中新功能标识，排除『后端新前端旧』的半上线。
- 教训记录所述围栏与当前源码（预检逻辑/命令参数定义）一致；交付给用户的命令以源码为准。

## Counterexamples
- 无部署绑定的本地/沙箱进程重启：不适用绑定漂移预检，直接执行即可，套用即过度预检。
- 部署记录与 HEAD 一致且构建产物新鲜：判别式不成立，应直接执行操作而非先读记录。
- dirty 增量中没有任何与本次操作相关的记录：跳过记录扫描，不要为简单变更全量审计工作树。
- 教训记录已陈旧、围栏在新代码中变更：必须以当前源码重新核实命令，不得照抄记录。

- 实测指标覆盖目标会话全部分段且前缀指纹全程单一不变、变更原因全空

## Verification
- git -S 找到的引入提交所属分支与部署根 HEAD 的祖先关系一致（不在祖先中=未部署）

- 单工作区无分支歧义：符号缺席意味着'从未存在'，工件可能来自其他环境或陈旧数据，git -S 无意义
- 用户只关心当前运行时行为且证据工件与之无关：不应追工件血缘
- 符号命中但位于死代码或默认关闭路径：存在≠运行，必须补配置/开关核验才能下结论
