## Trigger
同时满足以下三条才适用本卡：
1. 计划来自先前会话的交接（非本会话现写），含 ≥2 个后续步骤，其中至少一步对共享资源（main、部署线、共享服务）做 push/publish/restart；
2. 交接记录含『已点名的分歧警告』——能指到具体对象与后果：哪个资源缺什么、直接发布会怎样（如『main 仅含生产 19 提交中的 2 个』『TaskBudget 生产实现未入主线』『直接发布会覆盖现有功能』）；
3. 警告指向的资源与计划终点步骤操作的资源是同一个。

任一条不满足则不启用：无发布类步骤 → 计划照常执行；警告无点名对象（『可能有问题』）→ 只做一次廉价核验，不重构计划；警告已被更晚权威记录解决 → 走停止条件 3 的单次核验路径。

## Discriminator
读取计划的第一刻即可见的两个事实：报告中写明 main 仅含生产 19 提交中的 2 个（原始生产 SHA 不在 main 祖先链上、TaskBudget 生产实现未入主线），且显式警告『以后若要直接从 main 发布，应先完成生产差异的独立整合与验证，避免覆盖现有功能』；而计划终点恰为 publish+restart——即计划隐含前提在执行前已知未满足。

## Short path
1. **登记警告为阻塞前置**：通读交接报告，逐字摘出警告句（点名资源 + 缺失物 + 后果），在计划中标注它阻塞的是哪一步（终点 publish/restart 步）；后续任何按字面顺序执行的倾向都以此标注为准。
2. **确认警告仍适用**：查生产/权威源当前状态（本例：Gen 216 / 7d70f0eaa 未变）；若生产 ref 已推进或回滚，以当前值重新量化分歧，不沿用交接报告里的旧数字。
3. **量化分歧（commit 层）**：`git log --oneline <生产ref> --not <主线>` 列出生产有而主线没有的提交清单；对每个被警告功能定位其承载提交与分支（本例：TaskBudget 13 提交在集成分支、19 提交全链在 feat/soul-prefix 分支）。
4. **验证计划隐含前提（tree 层）**：对候选发布树（当前主线或计划产出的合并结果）执行 `git diff <生产提交> <候选树> -- src tests scripts config`。有缺失文件/功能（本例：候选分支相对生产缺文件、无 TaskBudget）→ 判定直接发布会回滚，进入第 5 步；diff 为空或仅剩已登记的无关缺失项 → 命中停止条件 1，按原计划继续。
5. **在原计划中插入整合步骤**：插在发布步骤之前——merge 生产全链进主线 → `git diff <生产提交> <合并后主线> -- src tests scripts config` 须为空 → 重跑全量门禁；插入后按新序列执行，原计划其余步骤不动。
6. **过门再发布**：以『合并树 vs 生产树的 diff 仅剩预期 runtime 数据 + 全量门禁通过』作为进入 publish/restart 的停止条件（对应停止条件 2）；不满足则回到第 3 步重新量化，不得带病发布。

## Stop conditions
1. 【前提已成立】`git log <生产ref> --not <主线>` 为空，或 tree diff 证明发布树已包含生产全部内容，或缺失项不在本次发布影响面且已逐项登记理由 → 跳过整合，按原计划继续；留痕要求见 Verification-A。
2. 【整合已完成】merge 生产全链后，合并树与生产树的 `src tests scripts config` diff 为空（或仅剩预期 runtime 数据），且全量门禁通过 → 才允许进入 publish/restart；留痕要求见 Verification-B。
3. 【警告已失效】存在比警告更晚的权威记录（补齐该功能的提交 SHA、或通过的整合门禁回执）→ 只做一次 Verification-C 的廉价核验，确认后按原计划执行，不插入冗余整合步骤。

## Verification
- A（对应停止条件 1）：留存核验命令与输出摘要——生产 ref 当时 SHA、生产不在主线的提交清单（或为空）、被警告功能的文件路径存在性检查结果；非空差异逐项附『与本次目标无关』的登记理由。
- B（对应停止条件 2）：发布前核验单——合并树 vs 生产树 diff 仅剩预期 runtime 数据路径；被警告功能文件（如 TaskBudget I5 系）在位；全量门禁回执（编号/时间/通过状态）随汇报存档。
- C（对应停止条件 3）：单次核验记录——指向补齐提交 SHA 或门禁回执，并在当前 main 树实测被警告功能文件存在；此后不再重复整合。
- D（发布后，验证整条链路）：远端主线推进为纯快进、无分叉；部署回执 SHA 与发布目标 SHA 一致；汇报包含『警告→核验→（整合）→再核验→发布』完整链路供审计。

## Counterexamples
- 交接警告已被更晚的权威记录解决（main 已含该功能或有通过的整合门禁回执）——警告只是历史，重复插入整合步骤是无信息动作
- 计划终点只改本地/临时状态（无 push/publish/restart），分歧记录只是备注，不构成阻塞门
- 警告含糊无点名对象（『可能有问题』）——按低置信假设做一次廉价核验即可，不要据此重构计划
- 发布目标是全新/冷启动服务，从未运行过生产内容——不存在回滚语义，无需生产对齐门
