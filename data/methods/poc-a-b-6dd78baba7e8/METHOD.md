# 冻结件 PoC 验证法

## 适用场景
验证"某工具/能力/提示是否真的带来收益"的对照实验，尤其防止：跑完看结果再定标准（后验合理化）、fixture 判定被悄悄改动、负例不被测试。

## 六步流程
1. **预写死边界**：实验开始前写死通过/失败判定标准与 judge 脚本；指标口径、样本量、结论边界（哪些情况算"预期外，照报"）一并预写。
2. **冻结件**：fixture、协议、判定器、任务卡全部 sha256 冻结（FREEZE.json），运行期只读；改动需显式重冻+留版本。
3. **判定器自测**：判定器必须先过正例（应通过）+ 对抗负例（错误必须被拒绝：错改、作弊、伪造、漏报）双向用例，才允许上岗。
4. **A/B 对照**：控制组/实验组同一 fixture 集、同判定器，只变一个变量；PoC 规模可 1 任务×2 配置先 pilot 验管线，再全量。
5. **审计链四态**：演进/裁决类动作走 submitted→reviewing→executing→verified/executed 四态落盘，回执路径即 ID，事后可重放。
6. **诚实报告**：预期外结果（含"无收益"）照实入报告；单例不放大成结论。

## 产出物清单（每步对应）
- PROTOCOL 文档（预写边界） / FREEZE.json（冻结清单） / selftest.sh（判定器正负例自测，含"错误必须被拒绝"项） / harness+任务卡 A/B（对照执行） / judge 回执+审计记录（四态） / 最终报告（含诚实结论节）。

## 已验证范围
smx shell 域 PoC 全流程走通：selftest 18/18（含 13 个负例全被拒绝）、12 run 全 judge=true、审计链 EVO-20260912-10818cb5 四态落盘、产出诚实结论（"可回验性有、效率收益无"）。

## 边界/不适用
- 不适用于纯探索性任务（无预知成功标准时强行预写边界会造假标准）。
- 判定器本身的能力上限决定实验有效上限：判定器测不出的作弊维度，本方法不覆盖。
