## Trigger
聚合诊断脚本中某检查项返回友好阴性提示，且该阴性将驱动下一步行动：协议栈分层二分、根因断言、或判定『修复未生效』；脚本自身使用了 || echo 兜底、错误流重定向或不透传逐项退出码，使阴性来源不可审计

## Discriminator
回执中找不到该检查项自身的退出码与 stderr，阴性无法区分『仪器执行了但没找到』与『仪器本身不存在(127)』；且同机已出现过姊妹诊断 CLI 缺失证据(如 wl-paste 报『没有那个文件或目录』)——『仪器缺席』是活跃假设，一次 command -v 或去掉重定向裸跑即可裁决

## Short path
- 拿到决策级阴性且探针脚本吞掉了退出码/stderr → 第一未知量改为『仪器是否真的执行过』：command -v <tool> 或去掉重定向裸跑一次
- 若 127/未找到命令：既往同类阴性全部作废，不作为二分数据点或『修复无效』证据；改查故障同层的权威只读属性替代(如 udevadm info 看 LIBINPUT_IGNORE_DEVICE 标签，无需依赖缺失的次级 CLI)
- 若仪器存在且真实输出为空：阴性有效，才允许用于分层二分或下结论
- 修复后的验证选在与根因被证实同一层的确证点(该属性已消失/该文件已改)，不依赖未验证过的次级工具输出
- 确需缺失仪器再补装(非 tty 会话 sudo 需 -S 从 stdin 读凭证)，装完重跑探针闭环

## Stop conditions
- command -v 确认仪器存在且裸跑真实为空 → 阴性有效，停止仪器审查，回到诊断主线
- 权威层属性已直接给出答案(关键标签已存在/已消失) → 无需为确认而补装次级工具即可结案
- 缺失的工具本身就是用户问题的答案(『为什么 X 用不了』) → 127 即结论，不是探针伪影

## Verification
- 对每个决策级阴性回执：能在其中定位到该项自身退出码或未抑制的 stderr；找不到则补一次裸跑再采信
- 修复后验证点与根因被证实的层一致(同一文件/同一属性位)，而不是仅在下游现象层观察

## Counterexamples
- 单用途直跑命令、stderr 可见、退出码真实(如 grep 无匹配 exit 1)：阴性可信，不必为每个阴性都加验证轮
- 阳性结果(工具找到了目标)：仪器显然执行过，无需验证
- 用户问的就是某工具为何不可用：『未找到命令』是发现本身而非干扰，直接据此作答
