## Trigger
任务可改写为少数具名未知量（如『某机制的写入侧归属』『某组件的回执构造点』），且一次定向内容搜索的命中列表中已出现该机制的所有权位置（含目标字面量的写入/变更调用行、与目标符号同名的 def/class、声明落盘责任的模块 docstring）

## Discriminator
命中分类判据：所有权命中 = 写入调用点含目标产物字面量（如把目标 jsonl 文件名作为写入参数的行）、目标符号的定义点、声明『本模块负责落盘 X』的 docstring；提及命中 = registry/工具描述文本、配置清单、读取侧路径、纯字符串引用。本集在第二次搜索时即出现『模块 docstring 声明审计落盘两个目标文件 + 写入行』的所有权命中，当时就足以把『所有可能的审计写入方』缩为『先读这一个文件』；同理执行器定位时已出现『文件名=工具名 + 回执头构造行号』的命中，无需再探测 subprocess 内部 API 或 grep class 清单。

## Short path
- 把任务改写成 1-2 个具名未知量（写入侧归属、执行器回执构造点），每个未知量只做一次定向搜索
- 对命中分类：若单一文件集中了所有权命中（写入调用点/定义点/所有权 docstring），下一步直接 read_file 该文件命中行附近，不再横向枚举同类写入方或搜兄弟产物
- 读完所有者后，对新拿到的符号（如 record_exception）做一次调用点搜索，建立『谁调用/谁不调用』的差距事实——该差距通常就是设计决策的判据（本集：工具回执故障完全不进台账）
- 定位组件执行器时，接受『文件名=组件名 + 回执构造行』的命中直接读该文件；跳过对 stdlib/内部 API 名的探测性搜索和无差别的 class 清单 grep
- 仅当读到的所有者与搜索推断矛盾（docstring 过时、代码已迁移）时，才回到宽枚举；差距事实+修改落点确认后停止发现，进入实现、单测与真实落盘验证

## Stop conditions
- 具名未知量已由权威代码证据回答（所有者文件已读 + 关键符号调用点已清点）→ 停止发现，进入实现
- 读到的所有者不含活跃写入路径（命中为过时 docstring 或已迁移代码）→ 此刻才扩大为同类写入方枚举
- 任务交付物本身就是全量清单（审计所有写入方/调用方）→ 枚举即目标，不适用提前收窄

## Verification
- 每条设计论断都能溯源到已读的具体 file:line 代码，而非 registry 描述或文档字符串
- 机制类改动以真实落盘实测 + 单测验证生效，不只依赖源码推断
- 重复搜索仅在某次读取与搜索推断矛盾时进行，且必须换用不同判别维度（如按定义符号而非文件名）

## Counterexamples
- 交付物就是全量 census（如安全审计要求列出所有写审计文件的点）：停在第一个所有者会漏计，完整枚举才是正确路径
- 仓库是运行服务的 mirror 且版本已分叉（HEAD 与线上 generation 不一致）：源码读取回答『代码怎么写』但不回答『线上跑什么』，须以运行时证据（真实 jsonl 内容/服务版本）仲裁
- 全部顶级命中都是提及类（registry 描述、文档、测试引用）而无所有权命中：没有可读的所有者，宽发现才是正确下一步
