## Trigger
用户请求预设某开源/可下载对象存在并要求围绕它执行（部署/集成/复现），而初步检索结果一致呈现与预设相反的形态：仅托管API、仅第三方测评壳、无任何权重发布痕迹。

## Discriminator
两个独立措辞框架的查询返回一致的词汇分布：全部是 API Key/console/托管endpoint/按token计价，零 weights/download/huggingface/self-host 词汇；唯一代码仓库被描述为『介绍与实测』类壳项目；随后换词查询返回与首轮完全相同的 ranked 结果列表——这是该搜索通道已饱和的机械信号，更多措辞变体不产生新信息，剩余未知量只能由 primary source（官方页、候选仓库本体）回答。

## Short path
- 把第一未知量定义为『可本地部署的开源X是否存在』，而不是部署步骤或硬件匹配；硬件/目录检查只作为并行背景事实。
- 一次含官方词汇的检索（『X open weights huggingface download self-host』类）+一次不同框架的复核检索，读结果词汇分布而非只看排名。
- 若两轮一致仅托管、且换词后结果列表不再变化 → 停止换词搜索，直接抓取两个primary source：官方models/docs页（权重是否开放、有无自托管选项）与唯一『开源』候选仓库README（是模型本体还是调托管API的壳）。
- 两者证实前提为假 → 输出：不存在结论 + 每条断言可指回原始信源的证据表 + 真实相邻选项（官方托管入口需何key / 明确标注『非X』的本地开源替代），向用户提问后停止，不执行字面意义的部署。
- 仅当某选项依赖本机状态时做一次定向本地检查（如凭据键名是否存在，只查名不读值）。

## Stop conditions
- 官方权威页与唯一开源候选本体均已直接抓取核验，其性质（闭源托管 / 壳项目）明确。
- 换词查询返回与先前相同或高度重叠的结果列表（通道饱和），即终止该通道的一切变体查询。
- 已向用户呈现前提为假的证据与真实选项，进入等待用户决策状态。

## Verification
- 结论中每个关键断言可指回一条已抓取的primary source（官方docs/models页原文、候选仓库README原文），而非仅搜索摘要。
- 复查全部检索结果中是否存在被忽略的含权重/下载/自托管词汇的条目。
- 负存在断言附检索日期；目标有版本演进时（如1.13→1.14），确认结论按版本号/日期限定，不受alias漂移影响。

## Counterexamples
- 换词查询返回了实质不同的新结果列表或新信源 → 通道未饱和，继续检索合理，不应过早锁定『不存在』结论。
- 厂商确实发布了开源权重（结果中出现HF仓库/权重下载链接）→ 前提为真，直接进入正常部署流程，本方法不适用。
- 目标名词常见或多义（多个无关同名项目并存）→ 必须先消歧再谈存在性，结果列表重合可能只反映搜索引擎对歧义词的固化，plateau信号不可靠。
- 任务对象已知存在（用户给出确切仓库/路径）→ 存在性检查是纯开销，直接进入部署/集成。
