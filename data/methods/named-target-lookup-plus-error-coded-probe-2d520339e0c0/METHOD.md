## Trigger
用户请求文本已显式点名目标资源/厂商（如某 API/模型名），且最终结论取决于两类未知量：一是可定位的窄事实（key/配置是否存在），二是多个互斥失败模式中哪个成立（需一次真实探针区分）

## Discriminator
请求文本中的厂商名 + 配置命名约定（<厂商>_API_KEY 存放于 .env 等规范化配置文件）——把『找 key』从全目录/全文件枚举缩为一条 grep；官方文档中的错误码表把『解读失败』缩为有限个已定义分支（401/1004=坏key，402/1008=余额，400/2013=套餐级限制）

## Short path
- 用厂商名 grep 规范化配置文件，定位目标 key 行号（未知量：是否存在/在哪）
- sed 该行邻近小窗（掩码显示），确认 key 前缀长度及有无 BASE_URL 覆盖（未知量：直连还是代理）
- 拉官方文档取得精确端点、最小 payload 和错误码表（未知量：不猜参数如何发、如何解读任意报错）
- 发送恰好一次最小成本请求，读 HTTP 状态+错误码（未知量：真实失败模式）
- 将错误码对照文档表选定结论分支并停止；可选：把已验证事实沉淀为 experience 复用

## Stop conditions
- grep 未命中目标厂商 key → 才扩大到更广配置扫描或直接问用户，而非继续倾倒枚举
- 返回错误码已在文档表中有明确语义，且用户的二选一/多选一问题已被权威来源回答
- 探针会产生真实费用或副作用且用户未明确授权实测 → 不发送，转静态验证

## Verification
- grep 命中行号与上下文窗内容一致：key 名、前缀/长度、无 BASE_URL 覆盖
- 请求的端点与每个参数逐项来自官方文档当前版本，无凭直觉补的字段
- 最终结论可追溯到真实的 HTTP 状态码+错误码，且该码存在于文档错误表
- 用错误语义做了互斥三分：密钥无效(401) vs 余额不足(402/1008) vs 套餐不支持(400/2013)，只保留一个分支

## Counterexamples
- 用户未点名厂商（『随便拿一个能用的视频 key 测』）→ 无法定向 grep，宽扫配置文件才是正确动作
- key 可能存放在规范位置之外（shell profile、secret manager、CI 变量）→ 单点 grep 会漏，必须先扩围确认位置
- 探针请求本身会创建计费任务或写生产数据且用户未授权实测 → 应改静态验证或先请求授权
- 文档不可得或与真实运行版本不一致、错误码在表外 → 单次探针无法定论，需最小变差地迭代探测
