## Trigger
用户要求查找一个以标识符命名的资源（仓库/插件/包），对结构化权威索引的精确查询返回明确的 0 结果回执（逐源 0 命中），未知量是正确标识符本身

## Discriminator
回执的失败语义是机械 exact-0（所有源 0 条）而非超时/权限错误 → 候选空间从『资源是否存在』收敛为『标识符字符串变体』；且该索引的搜索端点接受松弛/前缀查询，返回条目自带 name+description+topics，可在单次响应内同时完成拼写相近性与语义意图双重验证

## Short path
- 读 0 结果回执，把未知量定为『正确标识符是什么』而非『资源是否存在』
- 在同一索引发起一次最小松弛查询（截断到高区分度前缀/丢弃最可疑 token），不切换到泛化 web 渠道
- 在返回列表中按双重验证筛选唯一候选：name 与用户串为小编辑距离 + description/topics 覆盖用户语义关键词
- 验证通过后沿同一 API 读取该候选的权威详情（元数据、README），回答用户
- 答案与索引引用一致即停止，不再发任何确认性搜索

## Stop conditions
- 索引松弛查询返回的候选通过 name 相近 + 语义描述双验证 → 转入详情读取
- 已从该候选的权威 API 端点取得用户所需事实且与索引引用交叉一致 → 停止
- 同索引内 1-2 次松弛后仍 0 命中 → 如实报告未找到或可能私有/改名，不猜测拼接名称

## Verification
- 最终结果的 URL 由结构化索引 API 直接返回，而非网页搜索摘要转述
- 候选 name 与用户原串仅小编辑差异，且 description/topics 覆盖用户意图关键词
- 轨迹中不存在『索引已确认候选之后』的额外确认性搜索调用

## Counterexamples
- 0 结果语义不可用时（失败原因是超时/限流/鉴权错误），不能推断拼错，应先修复查询本身
- 用户输入是自然语言描述而非标识符（如『能接某桌面 App 的 DSH 插件』）→ 泛化搜索本就是正确第一渠道，不适用本方法
- 同索引松弛后仍 0 结果且无近似候选 → 资源可能确实不存在或为私有，继续换词枚举正是本方法禁止的扩散
- 返回多个名称近邻候选且描述不可区分（如大量同名/分叉仓库）→ 双重验证失败，必须逐候选读取详情消歧，不能凭排名第一自动接受
