## Trigger
即将执行不可逆/面向公众的发布动作（文章、帖子、部署、群发），内容经过会重编码的渲染或转换管道，且未确认存在可靠的发布后编辑/删除回退入口

## Discriminator
同一 episode 早期已有机械证据表明渲染器非标准重编码：粘贴/格式探针显示加粗与行内代码在截图中可见但 DOM 计数 strong/code=0（被转为 span style），'标题'生成自定义 block 而非 h 标签——由此在发布前即可推断基于 innerText 或标签计数的抽查校验对该平台天然有盲区，会假通过

## Short path
- 发布前从源文构建全量清单：全部实义行（≥12 字）+ 结构元素（图片文件名、数量、顺序）
- 用规范化提取（textContent 全文 + img src 列表）从编辑器/渲染结果抽取实际内容
- 无损对照：逐行前缀命中要求 0 缺失；图片数==源文数、src 互不相同、顺序与正文引用一一对应
- 任一缺失或重复 → 停止发布，修复生成/上传逻辑后重跑对照
- 0 缺失 → 执行发布，再对公开 URL 重新抓取并重复同一对照，通过后才报成功

## Stop conditions
- 无损对照 0 缺失且图片核对通过 → 允许执行发布
- 已发布 URL 的重新对照也 0 缺失 → 停止复核，如实报告
- 对照发现截断/缺失/重复 → 停止发布动作，先修复管道
- 平台对必需内容做无法规避的有损转换 → 换通道，不强发

## Verification
- 对渲染/编辑器内容跑全量行对照（全部实义行逐条命中），禁止只查少数锚点
- img 数量与源文一致、src 唯一、顺序与正文引用一一对应
- 发布后用公开 URL 重新抓取并重复同一对照，验证发布管道本身无截断/重复
- 结果报告中区分'已无损验证'与'未验证/需人工处理'项

## Counterexamples
- 字节保真传输（cp、带 checksum 的上传、git push）：哈希/校验和已足够，行级 diff 是浪费
- 内容极短（几行）：直接目视核对比构建全量验证器更省
- 有损本身是需求（如为纯文本渠道剥 HTML）：应对照转换后规范而非源文逐行比
- 平台确认提供无损编辑/回滚入口时，验证可降级为抽查+发布后复核，因错误可低成本撤回
