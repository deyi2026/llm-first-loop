## Trigger
续跑/执行类指令（如『按建议执行』）到达，但任务状态存档缺失（task state not found、无活动 goal），而『建议』锚定在持久文档的任务清单中、对应改动落在 git 管理的仓库里

## Discriminator
git status 显示已跟踪文件零改动（仅剩无关 untracked），同时检索/证据里已有清单点名文件的近期修复线索（edit 回执、修复分支名、近期提交号）。干净树 + 近期编辑痕迹 ⇒ 编辑已落入提交而非丢失：把『恢复全部上下文』塌缩成『对该文件读 git log --stat，比对提交文件集与条目预期文件集』

## Short path
- 定位『建议』原文（报告 §/任务表），为每个条目列出预期触碰的文件集——第一未知量是每条目的完成态，不是全局上下文
- 逐条目裁决：有编辑回执且 tracked 树干净 ⇒ 已提交；有回执且树脏 ⇒ 在途未提交；无回执且 log 无踪 ⇒ 未开工
- 已提交条目：对该文件读 git log --stat，提交文件集与条目预期精确一致 ⇒ 标记完成并跳过，不重复提交
- 只对未开工条目进入实现；在途条目接续其 diff；全部条目三态裁决完毕即停，不再补读环境上下文

## Stop conditions
- 清单上每个条目都已被 ledger/回执证据裁决为三态之一，且已提交条目的文件集核对通过
- 发现 tracked 树脏且改动非本会话所写 ⇒ 停止套用，先转入未归属改动裁决

## Verification
- 提交 --stat 的文件集与任务条目声明文件集逐一匹配，多一个少一个都要能解释
- 本会话未对已裁决『已完成』的条目产生新的同主题提交（防重复工作）

## Counterexamples
- 工作树存在本会话之外的未提交已跟踪改动（并发会话在途工作）：『干净树』前提不成立，须先裁决改动归属，再谈条目完成态
- 建议对应的动作不产生仓库提交（发文、外部系统调用等）：git 账本无从裁决完成态，须查平台侧权威回执而非本方法
- 同主题历史提交密集且文件集高度交叠：仅凭文件集匹配会误判，须比对 diff 内容与条目验收点后才标完成
