## Trigger
用户提问中已明确给出官方URL/厂商域名/平台名，而真正未知量是『某订阅/会员能否及如何使用某接口』（鉴权、额度、计费归属）这类厂商语义问题

## Discriminator
用户消息本身（time 0即可见）已包含确切厂商域名与官方文档URL；此类问题可分解为『接口鉴权模型』+『计费/套餐覆盖』两个子问题，均由厂商自家文档、错误码表、套餐页权威定义。辅以早期信号：连续搜索返回完全离题结果集（漫画、Yandex、Windows帮助），证明专有套餐名未被全网索引

## Short path
- 抓取用户已给出的官方文档URL；未知量：接口鉴权模型与计费语义→从错误码表（余额不足/按量付费提示）确定该接口扣什么
- 在同一官方域名内经文档站索引或站内导航定位pricing/套餐页；未知量：该订阅档是否覆盖此接口费用（禁止凭空猜测兄弟URL）
- 套餐页公开不可达（404/登录墙）时接受边界：报告已验证事实+显式标注未核验项，并给出用户侧一步核实法（最小请求实测或控制台自查）
- 仅当第一方完全无该信息才做全网搜索；且连续1~2次离题结果集即停止换词重搜

## Stop conditions
- 鉴权与计费归属两个子问题均已有官方页面文本支撑，即停止发现
- 官方套餐页确认不可公开访问后，不再猜测URL变体、不再第3次以后换词重搜，如实报告证据边界

## Verification
- 最终每条计费/鉴权断言可回指到已抓取的官方页面原文（如错误码表、按量购买说明）
- 未从官方核到的套餐权益被显式标注为未核验，并附带最小验证方法（最小请求看task_id还是1008）

## Counterexamples
- 任务是跨厂商横向比价（哪家Token Plan更值）：第三方聚合站才是正确首站，逐个厂商官网反而绕远
- 目标是SEO良好的大众产品（如Claude Pro）：首轮全网搜索即可命中官方与可靠信息，先搜合理不亏
- 信息只存在于登录后控制台且文档站对匿名访问关闭：全网搜索/社区帖是仅存公开渠道，可以使用，但出现离题结果后应立即收束而非继续换词六七次
