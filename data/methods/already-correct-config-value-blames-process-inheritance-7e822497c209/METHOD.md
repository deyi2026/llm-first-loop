## Trigger
会话/进程的实际行为与声明配置矛盾（配置说约束已关闭、行为上约束仍生效），而『改配置／加白名单／重启／换路径』多路修复候选尚未裁决时

## Discriminator
配置项当前值已经是期望值：一次定点读取即可证明。这把『配置层是约束来源』整支候选排除，剩下唯一机制是进程族谱继承（父进程的 seatbelt／环境属性随 exec 传给后代），修复动作也随之从配置编辑收窄为『从干净父级重生』

## Short path
- 对约束对应的配置项做一次定点读取（不做任何修改），确认现值
- 现值=期望 ⇒ 排除配置层，判定约束来自进程继承；未知量收窄为『新进程应从哪个上下文派生』
- 用 --help／最小调用验证权威拉起通道的真实入口与子命令语法，让用户在沙箱外的终端执行重启，使新进程从干净父级派生、断掉继承链
- 若存在守护进程并发拉起的风险，确认互斥锁与权威通道优先级后再放行命令
- 给出一条最小 no-op 探针命令，供重生后的新会话验证约束特征错误已消失

## Stop conditions
- 配置现值与期望不符 ⇒ 分流到修配置，本方法不再适用
- 已确认配置无责、交出从干净父级重生的命令与事后探针即停止，不再枚举其他修复候选

## Verification
- 新会话运行最小探针（如 sandbox-exec -p '(allow default)' echo）：约束特征错误（sandbox_apply: Operation not permitted / exit 71）消失即继承链已断
- 重启回执的 authority/authoritative 字段指向权威通道，且与守护通道的互斥锁不冲突，无双通道抢资源

## Counterexamples
- 读到的配置文件并非运行时实际加载的那份（多处 .env 或优先级覆盖）：『配置已对』是假象，重生也不会改变行为，须先确认真实加载路径
- 约束由每次工具调用时的外层包装重新施加、与进程族谱无关：换父进程无效，应改调用方式或包装层
- 配置值确实错误（与期望不符）：直接修配置即可，不必绕道重启断链
