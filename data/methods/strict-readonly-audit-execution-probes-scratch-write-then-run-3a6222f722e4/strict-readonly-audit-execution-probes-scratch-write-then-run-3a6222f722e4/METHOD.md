## Trigger
带硬工具预算的严格只读/零写入审查任务中，某个具名未知量无法从已读回执静态结算，必须运行一段判定/扫描逻辑（真实状态闭包检查、篡改夹具复现、验收谓词实测）才能拿到结论。

## Discriminator
当时已可见的三事实同时成立：任务书明文『严格只读、仓库零修改、工具次数上限』；每次回执横幅声明沙箱对解释器直连 here-doc 有灾难级硬阻断且审计树受写保护；该未知量需跨多文件/夹具运行逻辑而非单文件直读。三者成立 ⇒ 首选『落盘再执行』姿势而不是解释器管道——被拦一次即消耗一个预算槽位，直接变成最终裁决里不得不披露的未读区间。

## Short path
- 先给未知量命名（例：门禁闭包在真实受保护分支字节上是否 PASS；某种变体输入是否被漏放）
- 查已有回执覆盖账：能静态结算就不执行——执行是预算内的选择，不是默认动作
- 确需执行 ⇒ 把最小探针 cat 落盘到审计树外临时目录，以 stub client 读受信任侧字节、导入受信任函数，绝不向被审仓库写任何字节
- 用隔离解释器一次执行，取 stdout 的确定性判定行（形如 KEY: PASS/HOLD）作为独立取证写入裁决，并与发起方口头声明分开标注
- 若仍触发硬阻断：不变换措辞/姿势重试，直接采用阻断回执自带的等价姿势一次完成

## Stop conditions
- 探针 stdout 已给出该命名未知量的确定性判定，且双向齐全：合法受保护状态 ⇒ 不误拦（防自锁/全仓 HOLD），构造的漏放输入 ⇒ 确实 HOLD
- 覆盖账显示静态可结算 ⇒ 跳过执行
- 探针需要受保护动作（push/全量测试等）⇒ 不提权，降级为明示覆盖缺口后收口

## Verification
- 执行前后 git status 均 clean：探针零字节写入被审仓库
- 探针判定行确实映射到裁决文本中对应的那条命名未知量，而非泛化诊断输出
- 门禁类验证双向齐全：既证明不误拦真实当前状态，也证明对对抗输入确实拦截

## Counterexamples
- 未知量可从已水合回执静态推导（单文件正则一眼可读、关键断言行已在手上）⇒ 纯静态确认，不应执行
- 验证要求真实运行被审候选代码本体且有副作用（非 stub 导入受信任函数）⇒ 零写入审计中不做，改为披露
- 沙箱禁写临时目录且无指定缓存目录 ⇒ 放弃执行路径，静态推理并明示覆盖缺口
- 子目标只是可放弃的只读确认、事实已可从既有证据导出 ⇒ 先按『被拦能力是否必要』裁决放弃，再谈执行姿势
