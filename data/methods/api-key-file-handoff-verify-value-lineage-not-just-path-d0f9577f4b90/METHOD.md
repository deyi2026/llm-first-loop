## Trigger
用户请求给出存放 API key/密钥的文件路径以便自己手工修改，且上下文存在失败报告（鉴权/无效 key 类报错）和正在运行的消费方服务

## Discriminator
权威文件中该键的当前值特征（尾号/长度，脱敏）与失败报错里出现的值特征是否一致：一致→文件即运行真值，改后常规加载即可；不一致→运行进程持旧值（env 继承/快照），只改文件不生效。辅助判别：同目录存在 .swp 交换残留或密集带日期 .bak，提示上次编辑未正常收尾

## Short path
- 从消费方/registry 配置的键间接引用（api_key_env=某键名）钉死权威文件与具体行——未知量：值真正存在哪份文件，一次性排除备份/样例/交换副本
- 读取该键当前值特征（尾号、长度，脱敏展示）并与失败报告中的值特征比对——未知量：报错的消费方读的是不是这份文件的当前内容
- 一致→交付路径+行号即可；不一致→同路径交付，但附加生效条件：完全重启服务（必要时从干净 shell 启动），否则改动不会被拾取
- 扫描同目录编辑隐患（swap 文件、备份时间线），警示随路径一并交付后停止；待用户改完以重启+最小真实调用收尾验证

## Stop conditions
- 权威文件与目标行已由消费方配置的间接引用证实，而非仅凭文件名相似
- 值一致性已判定，并按判定给出对应生效条件（改后即生效 vs 需完全重启）
- 编辑隐患（swap/备份冲突）已披露或确认不存在

## Verification
- 消费方配置（如 providers.json）的键间接引用字段确实指向所交付文件中的键名
- 用户改完后：完全重启服务并做一次最小真实调用（本集为 DeepSeek 直连）确认恢复

## Counterexamples
- 失败报告中不含任何可比对的值特征（无尾号/长度）→ 无法判定 lineage，不要断言『进程持旧值』，直接建议改后重启+实测
- 用户只是问路径、无失败背景（如新环境初始化）→ 跳过一致性诊断，直接交付路径与样板行
- 服务有已证实的热重载/SIGHUP 机制且即时生效 → 不必断言必须完全重启
- 消费方每请求即时读文件仍出现不一致 → 问题在多副本配置根，应转向活进程元数据（cwd/env/lsof）定位真实配置根，而非继续比对文件
