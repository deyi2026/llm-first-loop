## Trigger
续跑任务的既定卡点是『长驻宿主重启后才能加载新提交的门/校验代码』，用户指令重启并要求给出重启命令，而进程表显示旧宿主 pid 已被替换

## Discriminator
旧 pid 死亡 ≠ 新规则已加载：判定当前宿主新旧的最小权威探针是门本身的最小调用，其拒绝理由若命中只有旧规则才会产生的签名（如按旧豁免清单拒绝本应豁免的未跟踪目录），即证明当前宿主仍跑旧代码；重启命令以仓库内重启脚本的 usage/注释头为权威（含 tty、不可守护等约束）

## Short path
- 读续跑快照，拆出两个未知量：重启是否仍必要（宿主可能已被换过）？重启命令的权威形式与约束？
- 最小代价调用门（或比对新宿主启动时间 vs 提交时间）：命中旧规则签名 ⇒ 当前宿主仍旧 ⇒ 重启必要成立；签名消失则重启不再必要
- 读仓库内重启脚本的 usage/注释头，取出确切命令与运维约束（交互式需 tty、无守护自动拉起 ⇒ 必须交由用户在新终端执行）
- 交付：命令 + 重启后验证探针（同一门调用应转为受理）+ 条件化兜底（重启后仍同错才查宿主 import 根/旧安装副本），兜底不预先探测
- 停止：命令已交付且验证与回退路径已定义

## Stop conditions
- 门的最小调用不再命中旧规则签名（新规则已加载），重启判定撤销
- 带约束的重启命令已交付用户，且重启后的验证探针与同错回退分支已定义

## Verification
- 重启后用同一门调用复探：旧签名消失或受理即证宿主已加载新规则
- 若重启后仍命中同一旧签名，则启动 import 根核查（宿主可能从旧安装副本而非本仓库 editable 加载）

## Counterexamples
- 门调用昂贵或有副作用（真跑评审、消耗预算）：改用宿主进程启动时间 vs 改动提交时间判定，不做行为探针
- 拒绝理由在旧/新规则下相同（无区分力）：行为探针失效，须直接查宿主 import 根或日志
- 仓库没有重启脚本文档：从入口点与进程表重构命令才是正当路径
- 宿主是外部部署服务而非本会话长驻进程：其行为反映部署版本，与本地重启无关
- 用户明示『直接重启不要验证』且重启幂等便宜：跳过探针直接执行
