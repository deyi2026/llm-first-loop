## Trigger
报告或上游建议断言新知识卡/drop-in 数据文件需重启服务或专门刷入机制才生效（或要为此排期一次被阻塞的重启），而当前可核验手段只有源码；尤其当目标部署在另一台主机另一版本，本地只有同项目的代理源码

## Discriminator
消费端检索入口方法体内是否逐次枚举磁盘：search/list 每次调用 self._dir.glob/iterdir ⇒ 现扫即生效；枚举或索引构建发生在构造/装配期 ⇒ 启动固化。被点名的 flush/刷入脚本则按其调用点（如 AGENTS 的 push 前置闸）区分仓库侧 git 工具与运行态通路

## Short path
- 把报告主张分两类：机制类（脚本职责、加载语义）可用代理源码裁决；事实类（宿主现场状态、当前计数）只能由宿主端动作回答，不冒充核验
- 先核被点名的机制：按文件名定位脚本并读调用方/使用文档，确认它是仓库侧批量工具还是运行态通路
- 沿 config 键 → 装配点 → store 检索实现定位数据消费点，判定枚举发生在每次调用内还是构造期
- 若逐次现扫：宿主建议改写为复制文件 + 用既有列表/检索端点复核计数，动作即验证；重启方案降级为记账价值，不再受 fail-closed 重启阻塞
- 显式标注本地核验所据 head/版本与目标版本差异；宿主执行后计数未涨 ⇒ 判为版本行为分歧，回退重启/换绑定路线

## Stop conditions
- 加载语义已由检索实现直读证明，且宿主建议自带计数验证与失败回退分支
- 代理源码与目标版本差异过大、定位不到同一消费路径时，停止代理裁决，改让宿主跑一次最小探针

## Verification
- 最终建议是否分别标注『本地核验版本』与『目标版本』，且未把代理环境查询当作对目标现场的核验
- 宿主动作执行后用既有列表端点复核计数：+N 即机制成立；未涨即触发回退分支并升级为版本问题

## Counterexamples
- 消费端是启动期构建的内存索引/嵌入缓存：源目录文件再多检索也不走磁盘，重启仍必需
- 目录绑定本身在进程启动时由 env/配置解析固化：向已绑定目录加文件不需重启，改绑定目录仍需重启——两种语义要分开判
- 问题是事实类（宿主上开关是否打开、当前计数）时，代理源码给不出答案
- 代理源码与目标版本分居该机制引入前后：先对版本/changelog 再采信结论
- 宿主本身可达时直接在宿主核验，不必走代理源码
