## Trigger
用户以一两个词的模糊说法要求调研『如何接入外部平台 X』，需要平台当前的官方能力与约束来做选型；仓库内已有另一平台的同类实现可当语义锚点。判别信号：通用搜索一次回执即出现『长中文关键词链→词典/工商类无关结果，但命中#1就是平台官方域名』的垃圾签名。

## Discriminator
第一次搜索回执里当时已存在两条事实：(1) 命中#1 即目标平台官方站点——权威文档入口已经到手；(2) 其余结果全是查询词的字典/工商/泛站页面——搜索通道对该查询形态已退化。二者同时成立即可判定：继续换措辞搜索无信息增益，下一步应直取官方文档中心。

## Short path
- 仓库内锚定语义：枚举 src 模块 + 定位最近似参照（如 feishu 桥）与既有同名但异义的链路（如 mp.weixin 发布），确定『接入』指哪类能力；
- 最多一次 web 搜索，目的仅是拿官方开发者文档域名（已知则跳过）；出现垃圾签名立即停，不再发第二个长关键词查询；
- 直取官方文档中心索引/概述页，读文档树得到能力地图，把模糊目标分叉成互斥能力问题（双向通道/单向推送/内容发布/非官方自动化）；
- 对每个分叉取具体文档页验证协议事实（端点、回调/长连接、限制、互斥约束）；
- 与仓库参照实现逐项比对移植面（模块结构、推送、注册工具），未核项显式标注，输出分叉选型报告。

## Stop conditions
- 每个能力分叉都取得官方文档页裁决，或被显式标注为未核项；
- 不再对同一通用搜索通道重复长中文关键词查询（垃圾签名已出现即视为该通道对该问题干涸）。

## Verification
- 最终报告中每条能力/约束事实都能指回具体官方文档 URL（如 developer.*.qq.com/document/path/...）；
- 仓库侧移植结论（可平移/需新建/已有）与所选路径的协议事实一致；
- 模糊需求的每个合理解读都出现在分叉清单中，未被默认单一解读吞并。

## Counterexamples
- 问的是社区经验或风险（如『wechaty 封号概率』『某库口碑』）：官方文档对此沉默，web/论坛检索才是正确权威面，不应套用『直取官方文档』；
- 问的是第三方库当前 API 形态：权威是该库的已安装副本或仓库，不是平台文档中心；
- 平台无公开开发者文档（封闭/私有 API）时，文档树路线死路，应退到示例代码、SDK 源码或商务通道；
- 问题已是单一明确未知量（如『某 endpoint 的参数表』）时，无需先分叉，直接取目标文档页即可。
