## Trigger
守护类测试（计数/棘轮/风格守卫）失败并给出数值型差值（如 63→64）；你按单一候选原因完成修复且写入已被回执确认；复测返回与修复前逐字相同的失败消息

## Discriminator
失败 traceback 此前已展示守护的确定性测量逻辑且可本地导入复算（本例 _count_fn_imports(_read_source(rel)) 在单测输出中可见），同时编辑回执证明修复已生效——『唯一超标项已移除』这一假设被不变的测量值当场证伪。这两条当时已可见的事实足以把下一步从『再跑一次测试/再看一遍 diff』缩为『复算计数器并 diff 项清单』

## Short path
- 读失败消息，明确未知量：哪个/哪些被计数项造成 基线→实测 的差值
- 用守护自己的测量函数分别对基线版本（git show <base>:file）与当前工作树求值，diff 两份被计数项清单，枚举全部新增项并与差值数字对账
- 逐项按守护规则修复；涉及 import 上提时先 grep 依赖模块顶层 import 排除循环依赖
- 用单个守护测试（本地秒级）验证归零，再跑直接相关测试
- 守护转绿后才启动一次全量回归；等待期间不重复采样同一聚合信号

## Stop conditions
- 枚举项清单的净差与失败消息数值完全对账，且单个守护测试本地通过
- 守护不可本地复算（远端 CI/编译型/非确定性检查）→ 停用本方法，改用提交二分定位
- 首次针对性修复即使守护立即转绿 → 无需枚举步骤，直接进入收尾验证

## Verification
- 复跑该单个守护测试确认差值消失（秒级，代替全量套件做迭代验证）
- 用计数脚本复核实测值 ≤ 基线且数字与失败消息一致
- 全量回归只在守护通过后执行一次，确认无次生破坏

## Counterexamples
- flaky/时序/网络类失败：没有稳定可复算的本地计数器，重跑本身就是正确下一步
- 守护逻辑不可本地导入（远端服务、闭源 linter、编译期检查）：无法复算项清单，应退回 commit 二分
- 失败消息已直接指明唯一具体项且首次修复即转绿：直接修复+单测即最短路径，枚举是多余开销
- 修复本身会系统性改变度量口径（如删除整个被计数文件、需重定基线）：差值对账逻辑失效
