## Trigger
用户对账式困惑：'我已经做过 Y（勾选/审批/提交），为什么还要我做人工 X'——尤其上一轮表述可能误导用户去找不存在的按钮，需要解释真实义务并纠正错误说法

## Discriminator
当时已可见的三条事实：(1) 用户已做动作有落档记录（accepted + human_exec_override）；(2) 特性命名测试 docstring 已写明该动作只放行边界门禁、级别门禁不放水（level 0 仍仅建议）；(3) 配置文件带日期注释显示档位已降回 0。三者交叉即可把'哪里还有人工步骤/按钮'缩成'授权已封顶，只需验证残余状态是否惰性'

## Short path
- 核用户已做动作是否落档（审计/状态记录）→ 未知量：动作确实生效，不是用户记错
- 按特性名（如 exec_override）搜测试/状态机定义，读出该动作的准确授权语义与剩余门禁 → 未知量：它授权了什么、没授权什么
- 读生效配置档位（带日期决策注释的 env）→ 未知量：为何没有自动流转
- 交叉 2+3：若授权已被档位封顶，残余至多是台账 → 搜该状态是否进入 hint/待办聚合 → 未知量：系统是否真的在要求用户做事
- 仅当聚合显示确有需求时，搜完成函数 caller 定位唯一入口与暴露面（web/CLI）→ 未知量：用户能从哪里做
- 以证据回答'无需操作'或给出唯一精确入口，并纠正上轮错误表述，停止

## Stop conditions
- 落档 + 授权语义 + 档位 + 残余状态惰性四点均有权威回执支撑 → 立即成稿，不再枚举文档/界面或做补读
- 聚合显示残余状态确有催办 → 定位到唯一入口后即停
- 记录显示用户动作未落档 → 前提失效，转入真实入口定位任务

## Verification
- 回答中每个'不需要/只放行 X'断言可指回三源之一：特性测试 docstring、待办聚合代码、caller 搜索回执
- '无需操作'结论必须有聚合逻辑的直接证据（该状态不产生提示/待办），不得仅凭推断

## Counterexamples
- 审计记录显示用户动作并未落档（失败或被拒）→ 前提不成立，应帮用户定位真实 UI 入口，本方法不适用
- 残余状态会进入待办/催办聚合 → 存在真实义务，必须找到并给出入口，不能答'惰性'
- 测试/注释与运行版本脱节（陈旧测试）→ 授权语义须以实时状态记录复核，不能只信测试文本
