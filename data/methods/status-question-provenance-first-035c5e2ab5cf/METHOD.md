## Trigger
用户询问某能力/功能是否完成、生效或已在收集数据，且环境提供部署代次、精确 git head、worktree/演进分支等状态元数据

## Discriminator
部署回执已给出精确运行 head 和基于 worktree 的 code_root——即变更状态真相在提交/分支包含关系里，不在源码枚举里；且问句是状态判定而非代码内部行为

## Short path
- 取运行态回执，锁定运行线（generation + git head）
- 列演进分支/worktree，定位与问题相关的最新提交（实现提交 + 设计/文档提交）
- 读权威工件（设计文档/提交说明）取得分层与阶段结论，回答'设计成什么样、分几步'
- 核对实现提交是否包含于运行 head，判定'是否已生效'
- 读生产数据账本的行数与写入来源，判定'是否已在真实收集'
- 四态（已编码/已合入/已部署/已在统计）齐备即作答并给剩余工作依赖序，不再枚举源码内部

## Stop conditions
- 实现提交与运行 head 的包含关系已判定，且权威工件已覆盖用户各子问
- 生产数据现状（真实行数、开发期 vs 生产来源）已从账本核验
- 不为已被权威工件回答的子问继续做实现层枚举

## Verification
- 最终答案中每条状态断言可溯源到：运行回执、提交包含关系检查、或权威文档原文
- 账本计数已区分开发期写入与生产写入
- 结论明确区分'已编码/已合入/已部署/已在统计'四态，未混同

## Counterexamples
- 问句是代码内部行为（如'哪段代码把指引写进失败回执'）时，定向 grep 源码就是最短路径，本方法不适用
- 无部署/版本元数据的一次性环境里没有 head 或分支包含关系可核，只能直接读工件
- 用户只要设计观点或建议而非事实状态时，无需先做 provenance 核验
