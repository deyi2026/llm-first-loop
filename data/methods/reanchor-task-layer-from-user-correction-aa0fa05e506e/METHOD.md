## Trigger
用户对上一轮行动发出任务层纠错（『你搞错了/不是X是Y』），且纠正文本同时出现：(a) 仅在某一层有语义的动词——『同时启动』『启动前先退出』对会话配置无意义、只对进程/服务生命周期成立；(b) 明确作用域标记——点名排除某第三方工具、指定自有目录/仓库。典型背景：上一轮把服务生命周期问题误当会话配置处理并已执行了错误动作。

## Discriminator
纠正消息措辞与上一动作回执的冲突点在收到纠正当时即可观察：上一轮把『切换/启动大模型』执行成了会话模型切换，而『同时启动』『先退出原来的』这类词只对进程/服务层成立；加上用户明确排除某工具并给出自有根目录路径，候选空间可立即从『会话配置/第三方工具/自有运行时/全仓搜索』缩为『自有运行时的服务启停与切换管理』，无需任何额外探索。

## Short path
- 收到纠正先做层判定：提取生命周期动词+排除项+指定路径，确定目标层=自有本地推理服务的启停/切换管理；不在旧层做任何新动作
- 若上一轮已在错误层留下副作用（如会话模型被切走），先执行最小回滚切回默认，再开始探索
- 从用户指定的根目录做按修改时间排序的列表，用 mtime 对齐用户『刚试过就坏』的时间点选最近变更子树，不做全仓递归枚举
- 读该子树声明的单一运维入口（README/运维指南/入口 CLI 的 help），头注标明 ARCHIVED 或 Do NOT run 的一次性脚本只作背景不深入
- 用声明入口的只读命令（status/help/dry-run）做健康检查；若入口执行报 shell 级 Permission denied，回看此前列表已显示的文件属性（无执行位+带 shebang+mtime 与故障时间吻合）定位机制→chmod 修复→验证→git update-index 持久化防 checkout 复发
- 回答用户原始问题时区分事实来源：服务本身健康（日志/状态）、管理面损坏（权限）、架构约束（单端口/内存预算导致不能并发）三者分别给证据

## Stop conditions
- 层判定完成且错误层副作用已回滚
- 用户所需事实已由声明入口的只读命令与配置文件交叉验证（能否并发=架构证据、切换语义=入口 dry-run、故障根因=已修复并验证）
- 修复类动作已验证生效且权限位已写入 git index

## Verification
- 入口 CLI status 恢复正常输出且服务 endpoint 状态 UP
- 切换命令 dry-run 展示正确的先退出旧实例再启动新实例的计划，且全程不动线上在跑服务
- git index 中入口脚本权限位为 100755
- 『不能同时运行』结论同时有单端口配置与实测内存余量两类证据支撑，而非仅凭推测

## Counterexamples
- 纠正只修正事实细节而不改层（如『端口是 8901 不是 8902』）：无需回滚或换层，直接应用新事实继续原路径
- 对话语境中『切换模型』确实指会话层（『这轮聊天换个大模型答』）：不能机械把生命周期词映射到服务层，须结合上下文判层
- 纠正措辞含糊、既无生命周期动词也无路径/排除标记：应先问一个二选一澄清问题（会话层还是服务层），而不是猜层后行动
- 管理入口失败原因是服务自身崩溃而非入口权限：回滚到服务日志/进程诊断分支，mode 位检查不适用
