## Trigger
用户要求为某项目做测评/评测/实施计划，且目标以缩写或项目代号指称；当前 cwd 仓库与 docs/records 检索回执已足以确认所指项目，但尚未读过该项目任何权威文档，正准备发起目录或源码树级别的宽枚举。

## Discriminator
进入宽枚举前已同时存在三个事实：cwd 仓库名与用户缩写词干匹配；docs 检索 miss 回执列出了项目最近权威文档索引；records 命中均为该项目的评测类历史记录。这三点已把『计划的事实基础在哪』从『整个仓库都可能 relevant』缩到『README → 子系统 SoT 文档 → 最新运行产物』一条可逐步验证的链，宽枚举在当时不解决任何明确未知量。

## Short path
- 解析缩写所指：cwd 仓库名/检索回执与用户短名做词干匹配；未知量=目标项目身份，命中即停，不做全盘枚举。
- 读 README 头部：拿定位行与能力声明（通常直接点名内置子系统如评测体系）；未知量=项目声称有什么、权威文档入口在哪。
- 沿 README/顶层目录名直达子系统 SoT 文档（如 eval 类 README）：读取既有纪律、版本锁、环境事实、目录图、关联 Goal；未知量=已有资产与规则边界。
- 读最新一次运行的 RUNBOOK/顶层汇总 json，并对关键目录做存在性与空置检查（空 baselines/rules、缺失 heldout 目录本身就是载荷事实）；未知量=基线现状与失败归因——headline 分数未归因前不可直接引用。
- 仅当链条答不出某具体未知量（如某套件内部协议）时，才对该子树做有界枚举（名单级/maxdepth）。
- 成稿：每条硬事实挂一条本 run 回执；未实测的成本/可达性显式标注并附冒烟步骤；不可自查项（费用、选型）列为用户决策点。

## Stop conditions
- 计划依赖的现状事实（基线分数+失败归因、资产清单、纪律规则、空缺项）全部有本 run 回执或权威文档佐证。
- 剩余未知量属用户决策（费用档位、外部基准选型取舍）→ 以决策点形式交还，不再继续自查。

## Verification
- 抽查成稿中每条『硬事实』能否在所引回执/文件中逐字找到，找不到即降级为待验证。
- 空置/缺失类断言用当次 ls/find 回执复核，不凭记忆或训练先验。
- 引用任何分数前核对是否带失败归因口径（如未归因错误占比、flaky 清单），否则标记为不可用基线并禁止进入能力比较。

## Counterexamples
- 仓库无 README/SoT 文档（纯代码堆）→ 权威链断裂，全量枚举成为合理起点，本方法不适用。
- 缩写指的是外部产品/服务而非 cwd 项目 → 应走外部权威源盘点（canonical host 枚举），仓内文档链无效。
- 任务是修改代码或排查缺陷而非撰写计划 → 源码树阅读是正当必要动作，本方法的『延后枚举』会帮倒忙。
- 全新项目无任何历史运行 → 运行产物步骤坍缩，只剩资产盘点与纪律起草，链条缩短但不改变取向。
