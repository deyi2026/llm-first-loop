## Trigger
用户报告某远程控制/守护进程型服务『还是连不上』，且用户级重启已失败过；机器上有该应用的 root 域 daemon 对（主服务+helper）和服务日志。

## Discriminator
当时即可见的判别事实：(a) daemon 进程启动于数天前而其 plist 当天刚被修改 ⇒ 进程陈旧、与新版二进制不一致，重启有明确靶子；(b) 服务日志按连接分阶段记录——密码校验通过、注册 online，但卡在 connect p2p 且无后续 ⇒ 故障在传输/建连阶段而非服务死亡；(c) lsof/ifconfig：连接源地址为 198.18.0.1 且默认路由指向 utun ⇒ TUN 代理拦截流量。任一条都把『很多可能原因』缩到一个属主组件或一个环境因素。

## Short path
- 列出该应用 root 域 daemon 的 plist 修改时间与进程启动时间；未知量：陈旧进程是否为属主（老 PID+新 plist ⇒ 重启候选）
- kickstart 陈旧的 root 域 daemon（用户被锁在外面时的廉价首选动作）；未知量：失效连接状态是否被清掉
- tail 服务自身日志；未知量：入站连接卡在哪个阶段（认证过+注册 online+P2P 无后续 ⇒ 传输阶段）
- 对环境拦截者做一次性核查：源 IP 异常网段+默认路由是否走 utun；未知量：是否 TUN 代理破坏 P2P；是则建议手动关闭增强模式或重试
- 持续看日志直到此前卡住的阶段走通（P2P_CONNECTED/会话建立）即停止；次要线索（代理进程身份、API 自动化探测）推迟到用户提出需求再查

## Stop conditions
- 日志显示入站会话已越过此前卡住的阶段完整建立（或用户确认远程可见桌面）
- 日志中完全没有入站连接尝试 ⇒ 问题在客户端/凭据/上游可达性，停止服务端动作
- 日志不可读/不存在 ⇒ 退回『重启一次+查厂商文档』，不要无证据继续排查

## Verification
- 成功信号是服务日志中越过卡点的阶段推进（如 P2P_CONNECTED error 0、desktop 会话注册成功），而非退出码 0 或新 PID
- 用同阶段前后对照归因：修复前连接尝试卡在 P2P（19:54:31/55），修复后同类尝试走通（19:58:42），才能把成功归于该动作

## Counterexamples
- 日志显示认证阶段失败（密码被拒/账号问题）：重启 daemon 无效，应修凭据/账号
- 日志已显示会话能正常建立 ⇒ 故障在发起连接的客户端一侧，不要动服务端 daemon
- 无服务日志或日志二进制不可读：分期分诊不可行，退回重启+厂商文档，不要卡在找日志上
- 虽有 TUN/保留网段异常，但该应用端点在分流规则中被显式直连/排除 ⇒ 不要把 P2P 失败归因于代理
