## Trigger
某个依赖 monkeypatch env/config 重定向写入或读取路径的测试，单独运行该文件为绿，但在更全的运行序中失败或表现为'什么都没写'，且全量失败数超过已知预期基线。

## Discriminator
失败 traceback 此刻已经显示：受害者测试使用 monkeypatch fixture、断言重定向后的输出为空（如 rows == []），且单文件运行为绿——即覆盖机制只在完整顺序下失效。这把未知量收窄为'生产侧解析链中是否有缓存状态遮蔽覆盖'，而不是'哪些测试碰了这个 env 变量名'（真正的污染源往往根本不引用该变量）。

## Short path
- 将全量失败清单与预期基线做差集，把新增失败按共享机制（同一 fixture/env 重定向）分组，确定一个共同未知量：覆盖为何在完整顺序下失效。
- 直接读生产模块的解析/开关函数（路径解析、启用判断），查找模块级缓存全局变量——它一旦被绑定就遮蔽 env 覆盖。
- 只 grep 该缓存 setter（如 configure()）的调用方，命名污染执行路径（如构建 runtime 的 factory 测试），而不是枚举所有引用 env 变量名的测试。
- 若处于合并/集成上下文，用 git show <各父提交>:文件 判定该 setter 行属于哪一方，决定这是谁的债、该改测试还是改生产语义。
- 按测试隔离债修复：加 autouse fixture 逐例把模块全局重置回未绑定态，不改动生产的优先级语义。
- 用有序的'污染源文件 + 受害者文件'两元素运行验证，再跑一次全量，期望失败数回落到事先归因过的基线。

## Stop conditions
- 有序两元素运行在修复前能复现失败、修复后为绿——根因闭环，停止诊断。
- 生产解析链显示无任何缓存状态（每次调用都纯读 env/config）——放弃本假设，转向并行度、tmp 目录冲突或枚举其他测试的方向。
- 失败在干净的单文件运行中也能复现——这不是顺序依赖，本方法不适用。

## Verification
- 修复前：按'污染源在前、受害者在后'的顺序运行能复现失败；修复后同样顺序为绿。
- 全量套件的 FAILED 数量回落到事先归因的基线（仅剩已知与本次改动无关的环境伪影失败）。
- 修复提交的 diff 只触及测试隔离（fixture），未改动生产代码的优先级/绑定语义。

## Counterexamples
- 模块每次调用都现读 env/config、无缓存——空输出症状来自并行执行、临时目录冲突或受害者自身泄漏状态，此时枚举兄弟测试或用随机顺序复现才是正确下一步。
- 反向污染：受害者测试自己绑定了全局、导致后续测试挂——重置应放在污染源头（或用 finalizer），而不是在后来的文件里加 autouse 重置。
- 绑定优先于 env 是文档化的运行时要求（如 factory 必须钉死 audit 目录）——把生产改成'env 永远赢'会回归预期语义，只有测试侧隔离是安全修法。
