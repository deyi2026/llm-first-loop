## Trigger
准备修改单一权威文件中一个具名区域（函数/命名段落/含独特字面构造的区块），且动手前需确认既有测试、预检或契约测试是否锚定该区域的行为或字面值

## Discriminator
刚读取的改动区域本身就提供唯一锚点 token：具名函数名（如 _start_web）或区域内独特构造（如 `for _ in $(seq 1 30)`、特定端点/日志字符串）。任何锚定该区域的测试必然在其内容中引用这些 token 才能定位断言目标；因此主题级文件名关键词（restart 等 18 条命中）绝大多数是噪声，而未在区域中实际出现过的猜测字符串必然落空

## Short path
- 读取改动区域，固化当前事实：循环/预算构造、判定条件、区域内真实存在的字符串（这一步同时产出锚点 token 集合）
- 用区域锚点 token（函数名优先，其次独特构造）对测试目录做内容检索，直接得到锚定该区域的测试清单（如 6 条命中）
- 只读取命中断言中与被改值相关的部分（如对 _start_web 体的 split 断言），确认没有任何断言引用将被修改的值/构造
- 确认无锚定冲突后进入编辑；若锚点检索为空或命中断言引用了概念而非 token，才放宽到文件名/主题关键词枚举

## Stop conditions
- 锚点命中的相关断言已逐条读取，且没有任何断言引用将被修改的值或构造：搜索结束，进入编辑与门禁
- 某断言精确锚定被改值（如硬编码循环次数）：把该测试纳入同一次改动后再进独立审查与全量门禁
- 锚点内容检索返回空：说明该区域可能无测试锚定或改动超出区域语义，此时才做一轮宽检索兜底

## Verification
- 全量门禁中该文件相关测试无意外失败，即证明锚点命中集覆盖了真实锚定集
- 若全量出现锚点检索未覆盖的失败，证伪本次『局部改动』判断，下次对该类改动应叠加宽检索

## Counterexamples
- 横切面改动（重命名共享 flag、改 CLI/环境变量契约）：测试可能引用概念或消费点而不引用函数名，锚点检索漏检，必须配合宽检索或按消费点反查
- 目标文件无具名区域、无独特 token（纯配置/数据文件）：不存在锚点 token，此方法退化为普通文件名检索或直接跑套件
- 锚点 token 过于常见（main/start）：内容检索噪声淹没信号，应换区域内更独特的 token 或加路径限定后再检索
