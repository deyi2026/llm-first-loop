## Trigger
在浏览器自动化或发布流程中，某个非幂等的状态变更动作（上传/提交/写入）预期的事件或回执没有出现，正准备重执行整段动作流时。

## Discriminator
状态变更调用本身已成功执行（如 CDP setFileInputFiles 已完成、无错误回执），且落点状态可直接检查（渲染后 DOM 中产物可见、可计数）——『事件未触发』只是表现层信号，不是失败证据；调用层错误回执才是真失败。该 DOM 状态在当时即可检查（事后发现图早已渲染），knowledge-at-time 成立。

## Short path
- 先明确未知量：状态变更是否已落盘/渲染？
- 直接检查落点状态（DOM 查询/渲染产物计数），此步之前禁止重执行
- 若已落盘：把事件未触发归因为 UI 接管怪癖，继续后续流程（如点确认），不重传
- 若确实未落盘：诊断事件处理一次，之后最多做一次输入有实质变化的诊断性重试
- 发布完成后按验收做锚点存在性与产物计数校验

## Stop conditions
- 渲染产物计数等于意图数量 → 视为成功，继续后续流程，禁止重传
- 状态不可检查且一次诊断重试后仍无法判定 → 停止并如实上报，不继续盲重试
- 存在调用层错误回执 → 按真失败处理：先修原因再重试，不适用『先查状态』分支

## Verification
- 最终页面渲染产物计数与意图一致（如 5==5，不出现需事后删除的重复产物）
- 发布锚点存在性校验通过，且无重复条目

## Counterexamples
- 状态变更调用本身返回错误/超时回执 → 效果确实未落盘，修因后重试才是正确路径，不要浪费步骤去查状态
- 动作是幂等只读（导航、查询、读文件）→ 直接重试即可，无需状态检查仪式
- 落点状态完全不可检查（无稳定选择器/环境限制）→ 本方法前提不成立，改用替代验证信号或接受一次有界重试
