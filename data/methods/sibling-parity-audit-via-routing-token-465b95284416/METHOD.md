## Trigger
用户断言或怀疑两个并行子系统被差别对待（一方多出门槛、惩罚性权重、可见性过滤或使用前置流程），需要核实真实分支并产出差异清单；且仓库中存在整仓快照/发布镜像目录会污染全库搜索。

## Discriminator
代码以显式开关区分二者（kind == "method" / method_store if kind==... else experience_store / method_ref vs experience_ref）；搜索该 token 的命中是分歧分支的闭合集合（本集 8 条全部在活代码）。同时首轮搜索回执已显示 .releases/* 为整仓快照镜像（同一命中重复约10份），全库搜索必须排除这些目录。

## Short path
- 把未知量定义为'枚举两子系统处理分歧的全部代码点'，而不是'找某一方的门槛'——后者会命中测试/config/快照噪音
- 搜索共用路由 token（kind == "x"、x_store/y_store、x_ref/y_ref），仅限活代码目录、排除快照镜像 → 得到闭合的分歧点清单（本集收敛到 4-5 处）
- 逐处并排读两臂实现（检索函数对、排序权重、状态可见性过滤、promotion/settlement 前置），产出差异对照表
- 对每个疑似门槛用真实存量分布验证是否实际起作用：统计状态直方图（1124/1157 皆为 candidate → 状态阶梯对现有卡是惰性的），据此修正或证伪上一轮的因果断言
- 按用户裁决标准（只保留保护卡完整性的门，不保留限制使用的门）做最小拆除；每撤掉一个兜底性权重后重查它此前遮蔽的真缺陷（描述命中权重>正文权重的检索错误）
- 跑针对性测试子集 + 改动前后代表性查询对比，报告差异表、被证伪的旧判断、遗留需用户裁决项

## Stop conditions
- 路由 token 搜索在活代码命中数收敛且每处双臂已并读 → 分歧枚举完成，不再做泛名词或全库搜索
- 每个门槛都已对照存量分布判定'代码存在但是否实际起作用'，不再凭代码存在直接下结论
- 拆除兜底权重后其遮蔽的真实缺陷已复查（无新退化），即停止追查

## Verification
- 确认 token 命中清单覆盖最终报告引用的全部门槛位置（排序权重、可见性过滤、promotion 前置、工具文案）——无遗漏则枚举闭合
- 撤除兜底权重后用代表性查询对比改动前后 top5，确认正文相关卡上位且无新退化
- 直方图证据与旧断言显式对照，报告中明写哪条上一轮结论被证伪及证据

## Counterexamples
- 两个子系统不共享路由 token（独立服务/独立代码库）→ token 搜索零命中，应改用接口/schema 对比或契约文档 diff
- 任务是单子系统行为调试而非对称性审计（'为什么 A 排序错了'）→ 直接枚举该子系统，无需姊妹臂对照
- 差异主要由数据/内容驱动而非代码分支 → 分支点审计找不到，应比较存储 schema 与存量内容
- 仓库无快照镜像目录 → 无需目录裁剪；若镜像无法在工具层排除且已知活文件路径，宁可直接读活文件而非反复全库搜索
- 存量分布均匀或为空 → '对照分布证伪门槛'一步不提供信息，只能依据代码与设计意图判断
