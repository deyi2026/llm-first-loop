## Trigger
用户请求基于其描述的系统状态（如'队列里有 N 个死任务/09-26 以来的老任务，某错误已失败 X 次，污染面板'）执行标记 failed、删除、清理等破坏性操作，且请求中含精确错误字符串/ID 与具名观察面（面板/看板）线索

## Discriminator
请求文本本身已含高区分度判别物：① 精确且少见的错误字面量（如 episode_not_found）必然出现在抛出它的第一方代码里，一次对 src/webui 的定向 grep 即得子系统与存储路径；② 具名观察面（面板）的数字必有同源 API/存储。二者在手时，按通用名词（queue/task/job）做全仓文件名搜索只会命中 .venv 第三方包噪音，全仓 grep 会超时，扫描 87MB 大日志也是慢速排除法

## Short path
- 从请求抽出可证伪断言清单（当前排队数、按 created_at 的年龄分布、错误事件总数与归属、历史肇事项现状）与判别字面量（精确错误串、面板名）
- 对第一方源码目录 grep 精确错误串 → 得到抛出点、任务/队列存储文件与面板同源状态 API；不做全仓超时 grep、不做通用名词文件名搜索、不扫大日志
- 直接读/调用该权威存储：过滤当前非终态项的 created_at（验证'老任务'是否存在），统计错误事件按任务归属（验证'死任务'是否存在），逐个查历史肇事项是否已终态且被去重阻止重入
- 用同一状态源解释症状的良性原因（如 admission 阻塞/消费暂停导致计数虚高）
- 前提被证伪 → 拒绝破坏动作，给出带数据源的核验结果并请用户提供所见视图的截图/URL/数据源；前提成立 → 仅对核验出的精确 ID 集合执行

## Stop conditions
- 权威存储已逐条回答请求中的每项断言（计数、年龄、错误归属、历史项状态），不再做目录/日志/文档枚举
- 前提不成立且已给出替代解释与证据，等待用户补充观察面信息
- 前提成立且破坏动作只针对已核验的精确集合，执行后即停

## Verification
- 面板同源 API 数字与存储全量 fold 计数一致，或差异可解释（核验期间队列仍被并发写入）
- 按'死任务'谓词（如源 episode 缺失且非终态）在当前非终态集合上实际过滤，命中数靠查询而非用户口述或记忆
- 历史肇事项逐个确认终态与去重阻断，证明清理目标确实存在或确实不存在

## Counterexamples
- 请求只含模糊症状（'队列好像堆了很多旧东西'）而无精确 token：判别物不存在，目录/文档层面的发现式定位是合理首步
- token 是通用词（timeout/not found/failed）在数百文件命中：不再具判别力，应改走具名观察面（面板 API/状态接口）路线
- 目标状态在外部系统（云控制台/另一主机的队列）：本地 grep 无关，需直接查外部权威接口
- 权威存储正被并发写：本方法只支撑'当前前提是否成立'的即时判定，不授权终局性断言（那是 fresh-read-authoritative-record 方法的作用域）
