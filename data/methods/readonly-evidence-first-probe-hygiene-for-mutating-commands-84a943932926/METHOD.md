## Trigger
用户报告一条登记/状态写入类命令'未生效'需要定位原因；或已形成'命令入口形式会静默失败'的假设并准备用真实参数实跑验证；且目标命令会修改持久状态或审计日志。

## Discriminator
执行探测前已可见的判别事实：(1) 该命令的审计写入是无条件的，append-only 日志中目标 ID 计数为 0 直接证明'从未成功执行'，与'假成功/未落盘'可区分，主问题由此收口；(2) 入口形式假设可由只读 grep 源码判定——__main__ 守卫存在即证伪'python -m 静默空转'；(3) 命令语义明显是 mutating（状态流转 accepted→executed 并写审计），用真实 ID 实跑探测，成功即完成真实变更。

## Short path
- 收到'未生效'报告后，先数该命令无条件写入的 append-only 审计日志中目标 ID 的记录数：0 → 从未成功执行；>0 但状态未变 → 回执与落盘不一致问题，两个假设一步分开。
- 若还需给用户正确的命令形式，只读检查入口注册与 __main__ 守卫：守卫存在即证实 python -m 可用，假设被源码直接证实/证伪，不实跑。
- 若实跑探测不可避免，改用合成/不存在的 ID、--help 或废弃记录作为探测目标，使探测成功也无害。
- 真实目标上的真实登记属于任务本体操作，应在诊断收口、参数（含结果说明文本）确认后一次性执行，而非当作探测副产品。
- 执行后用主记录 + 审计日志双通道复核回执与落盘一致，停止。

## Stop conditions
- 审计日志计数已唯一确定'从未运行'或'运行未落盘'，不再为验证入口形式而实跑命令
- 入口形式已由源码守卫/入口注册只读证实，直接给出正确命令或经授权执行
- 真实登记已落盘且回执、主记录、审计三方一致，无探测残留

## Verification
- 探测前自问：这条命令成功时会不会写任何持久状态/审计？会 → 禁止用真实目标 ID 探测
- 以'无条件审计写入'为判据复核结论：日志 0 条与'从未跑过'一致，与'假成功'矛盾
- 任何实跑之后立即检查审计日志新增条目与主记录字段，确认没有意外副作用残留

## Counterexamples
- 命令是纯只读查询（status/get/ls）：用真实 ID 实跑本身就是最快验证，无需合成目标
- 任务本身就是执行该变更（用户明确要求代跑登记）：真实 ID 执行是任务本体，不是探测
- 命令对不存在的 ID 是 create 语义而非 update：合成 ID 探测也会产生垃圾记录，应改用 --help/dry-run 或一次性沙箱环境
- 源码无法判定运行时行为（环境依赖分发、远程路由）且无审计旁证时：只读证据不足，经用户授权在可回滚环境实跑是合理的，不应僵化拒绝实跑
