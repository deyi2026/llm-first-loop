## Trigger
用户询问某个已知配置/模型注册表条目是否缺字段、缺能力、需要修复；权威 live 文件位置已知（如上一轮已确认/修改过），或可通过定向 find 定位；仓库中同时存在大量归档副本（备份文件、eval 结果快照），宽搜索会被陈旧副本噪声淹没。

## Discriminator
任务开始时已存在两个事实：(1) 上轮上下文已确认 live 注册表路径（助手自己引用'上一轮我改的就是它'），问题只针对该文件的'现行定义'，其他副本均非权威；(2) 首次宽搜索的输出本身即显示命中集中在 evals/*/results 与 .bak 备份——归档副本只会复制旧状态。这两点可把'全仓库都可能有答案'缩为'一个 live 文件 + 兄弟条目基线 + 代码消费点'。

## Short path
- 直接读已知路径的 live 注册表并打印全部 provider 结构；未知量：目标条目现行定义是什么、与兄弟条目差在哪（若记忆路径失效，用定向 find 重定位，而非宽内容搜索）
- 将目标条目与同注册表兄弟条目逐字段 diff，得到候选缺口清单；对全局统一出现的字段（如 fail-open 默认值）用一次 parser 代码 grep 排除为'非缺口'
- grep 候选缺失字段的代码消费点（选择逻辑/兜底链），确定缺标志的实际影响面与验证路径
- 读 client 实际 payload 构造代码，复刻真实请求形状（避免测试契约与生产不符）
- 用一个脚本对每个候选缺口产生决定性 live 信号：明确拒绝错误码（如 text-only 报错）=无缺口且缺标志是正确状态；200+图像 token 计量差=真实缺口；顺带同场验证流式/tools 契约
- 感知类结论（如'模型说图片全白'）用独立工具交叉验证排除幻觉；确认后才修改注册表，并重跑 parser/消费路径验证修复生效

## Stop conditions
- 目标条目与兄弟条目的每一处字段差异都已归入三类之一：统一默认值（有 parser 代码证据）/ 决定性 live 信号已分类 / 已记录 note，无未分类差异
- 若做了修复：parser 重读返回预期值，且下游消费路径（如模型选择）产生预期变化
- 所有涉及模型感知输出的结论至少完成一次独立交叉验证
- '无缺口'与'有缺口'结论均附决定性信号，而非仅凭字段缺失推断

## Verification
- 缺口/无缺口结论各有一个决定性 live 信号：明确能力拒绝错误码，或成功响应+token 计量差（图像输入 vs 纯文本基线）
- 被排除的候选缺口有 parser 源码证据（默认值 fail-open、零路由权重）
- 修复后从 live 文件（而非 eval 归档副本）重新解析验证，并确认消费路径行为变化
- 感知输出与独立识别工具结果一致

## Counterexamples
- 权威 live 文件位置完全未知且无明确 data/运行时目录，此时定向 find 或受限搜索是必要的第一步，本方法不适用
- 问题本身是'全仓库谁引用了该配置'（迁移影响面分析），宽搜索才是正确工具，直奔 live 文件会漏答案
- 注册表内没有可作字段规范基线的兄弟条目（单条目注册表），diff 失去基准，应改用官方文档/规格对照
- 环境禁止 live 探测（离线、破坏性写操作、成本敏感），只能依赖静态契约与文档，此时'字段缺失'不能作为缺口证据
- 条目差异源于版本演化而非缺口（旧名路由到新模型），需按迁移语义处理而非补字段
