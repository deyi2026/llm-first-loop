## Trigger
执行类工具在重启/换通道后全线失败，且最小 no-op 命令同样失败（命令从未真正运行），而剩余必做步骤是必须真实发生的动作（运行门禁、git push、部署生效），任何只读回执都无法替代其效果。

## Discriminator
纯读 no-op 命令（pwd/echo/--version）也在通道初始化阶段失败，stderr 指向 profile 应用/沙箱装配而非命令本身；检索到的同族经验卡（写侧 EPERM、workdir 绑定写权限）成立前提是通道已成功启动——前提不满足即整类排除；若仓库文档/测试已把该失败原文记录为结构性（嵌套沙箱必然 exit 71），则通道内不存在参数级解法，唯一问题是把执行路由给谁。

## Short path
- 用最小 no-op 把失败分类为通道级而非命令级（命令未执行即失败）
- 用错误原文做一次仓库内容搜索：若项目已把该失败记录为环境必然，接受分类为结构性死亡，不再试 shell/argv/后台/隔离等通道变体
- 把剩余步骤二分为『可由只读回执或宿主侧通道（裸 git 冻结、审查子进程）完成』与『必须真实执行』
- 对必须真实执行的步骤：原样交付审查通过的那几条命令给用户，前置一步推前竞态核对（如 ls-remote 确认远端 tip 仍等于回执值，否则停下），后置收口核对（如推送后远端 tip 应为该 commit）
- 完成声明止步于已验证事实，执行缺口如实标注『我做不到』+根因与证据引用；环境缺陷走上报通道；用户贴回输出后用只读工具核验与预期一致再继续

## Stop conditions
- 结构性死亡已被项目权威文档/测试证实，且已停止通道变体重试
- 剩余步骤已全部二分，人工执行指令（含前后核对）已交付用户
- 用户回贴输出并经只读核验与预期一致

## Verification
- 核对用户回贴输出与预期一致（如远端 tip 变为推送 commit），用只读工具交叉验证，不重启死通道重试
- 自查最终答复中不存在『宣称已执行但实际未执行』的条目；不可达步骤均附根因与证据引用

## Counterexamples
- no-op 命令成功、仅写操作或特定命令失败 → 属命令级/写权限类问题，适用 workdir、补丁交付等既有经验，不套本卡
- 剩余步骤可由宿主侧只读通道（裸 git 冻结产物、审查子进程、回执定点查询）完成 → 先穷尽非执行通道，不急于委托人工
- 失败原因未知且仓库无该失败模式的记录 → 先按 env-dead-channel-noop-probe 分类并搜索签名，确认为结构性后再进入委托流程
