## Trigger
需要复核、事实核查或采纳一份第三方分析/状态报告，且报告含时效性运行态断言：进程/服务存在性（常表述为『未发现/未监听』）、『最近一次活动于时间T』、定时任务启用状态，而报告的观察时刻早于当前时刻。

## Discriminator
报告所述组件隐含的持久状态工件（state 文件、运行报告 jsonl、日志）带有新于报告观察时刻的写入时间戳——仅此一条即证明存在活写者，无需依赖进程表命中；同时『进程名关键词 grep 未命中』本身是弱探针：守护进程命令行可能是解释器模块启动形式（如 python -m app.runtime.launch web），完全不含搜索关键词，而监听 socket 才是存在性强探针。

## Short path
- 把报告断言清单分两类：稳定类（commit/版本/文件内容，可抽检）与时效类（存活/最近活动/开关状态，必须逐条重验），并为每条先指认权威事实源。
- 时效类先读持久状态工件：最新时间戳新于报告观察时刻 ⇒ 判『报告过期、存在活写者』，处置窗口从『正式发行前』提前到『现在』。
- 用绑定面定位写者：按监听端口查进程表取 PID，不依赖关键词 grep。
- 按 PID 拉全命令行/启动时间/cwd 绑定身份；核对状态工件最近一次运行是否落入该进程存活窗口，完成归属。
- 全部时效断言重定价后再逐条判定『属实/错误/过期』并重排优先级；运行态结论各自引用进程+端口+状态工件三重证据收尾。

## Stop conditions
- 每条时效断言都有权威再验证：状态工件时间戳、或 端口→PID→命令行 三重证据完整；
- 判定覆盖报告关键条目，稳定类抽检无矛盾（出现矛盾即升级为全量重验）；
- 每条运行态结论可溯源后停止探测，不再追加确认性读取。

## Verification
- 进程启动时间 ≤ 状态工件最新写入时间戳，且端口 LISTEN 的 PID 与该进程一致；
- 『过期』判定有可比时间戳对支撑：报告观察时刻 vs 状态工件最新时刻；
- 负向存在判定必须注明经哪种强探针（监听端口/全量进程表）未命中，而非仅关键词 grep。

## Counterexamples
- 断言关于静态内容（版本号、commit、代码逻辑、文档段落）——无需端口/进程探测，按名称级粒度匹配检查即可；
- 组件为一次性 CLI、无持久状态且无固定端口——状态工件与端口探针均不适用，退化为全量进程表加产物 mtime 推理；
- 状态工件时间戳不新于报告观察时刻、且目标端口确实无人监听——负向存在成立，可直接采纳并停止。
