## Trigger
用户下『重启/杀掉/重部署 X』这类状态变更指令，X 是常驻服务，且可观察的生命周期信号（last exit 非零、runs 次数高、日志有报错）初看像故障征兆

## Discriminator
动手前三个可立即读取的事实：(1) 同一域的服务清单里是否列有该服务的 watchdog/守护者（守护者存在则 exit code 必须先归因）；(2) 守护者动作日志最近条目是否显示『几分钟前刚执行过重启』；(3) 权威就绪端点（如 /ready 返回 readyConnections>0）是否证明目标状态当前已成立

## Short path
- 读目标服务的 launchctl/systemd 状态；未知量：是否在运行、近期生命周期如何。同时注意同列表是否出现 watchdog 类同级服务
- 若守护者存在，读守护者动作日志；未知量：非零 exit 和最近一次重启由谁触发、发生在多久前
- 探测权威就绪/健康端点；未知量：用户要的目标状态（服务健康可用）现在是否已成立
- 目标状态已成立且守护者刚重启过 → 不执行指令，输出归因证据链（守护日志时间戳 + 就绪返回值），并把真正的根因信号（如边缘侧握手失败）单列为独立排查项
- 若用户澄清目的是验证启动链路/清计数/强制换配置 → 指令本身就是目标，照做并验证恢复

## Stop conditions
- 就绪端点证明目标状态成立、且守护者日志显示近期已重启 → 停止，不执行，回报证据等用户裁决
- 归因后确认症状源自外部/上游（如边缘 TLS 握手失败）而非本地进程 → 转入根因排查，重启不再是对策
- 用户确认目的就是重启本身（测试链路、清计数）→ 执行后验证就绪恢复即停

## Verification
- 非零 exit code 在守护者日志中有时间戳对齐的 SIGKILL/重启记录，归因闭环
- 拒绝执行重启时，引用就绪端点返回值 + 最近一次守护重启时间作为证据
- 若最终执行了重启，验证就绪端点恢复且连接重新注册完成才算结束

## Counterexamples
- 域内没有任何 watchdog/守护者：非零 exit 大概率是真崩溃，重启合理且应附带崩溃诊断
- 就绪端点失败或连接数为 0：即使守护者刚重启过，说明重启未生效，应升级为根因排查而不是再重启一次
- 用户明确说目的是验证 plist/启动链路或清 runs 计数：指令即目标，直接执行，无需归因劝阻
