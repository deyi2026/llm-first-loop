## Trigger
需要诊断某个以唯一标识符给出的工具/组件为何卡死或超时；且在调查开始或进行中，可观察到另一个不同工具（尤其同属只读/同执行池）也发生超时

## Discriminator
两条当时即可见、无需未来知识的事实：(1) 目标以唯一符号名给出，一次全文 grep 即可取得全部注册/委托点，目录枚举不缩小任何未知量；(2) 第一步工具回执显示另一个同类只读工具也在现场超时——两工具共超时而非目标独有，把候选空间从'该工具自身实现缺陷'缩到'共享只读执行资源被环境事件拖慢'，前提由后续读码确认实现无阻塞原语

## Short path
- 对目标标识符直接全库内容检索，一次取得注册/定义/委托点；解决未知量'实现在哪'，跳过目录层级枚举与位置预设
- 沿命中文件中的显式委托说明（docstring/注释'实现委托至 X'）逐跳读到实际执行函数；解决未知量'入口到实现的链路'
- 审查执行热路径与全部回调的阻塞原语（锁/join/无超时 IO/子进程）；解决未知量'实现自身能否造成长阻塞'
- 若实现为内存操作+fail-open 且存在同窗共超时的同类工具：转向环境证据——查工具的执行分组（同池/同线程组）、事件流中的超时实例、进程重启与版本变更时间线；解决未知量'阻塞来自哪一层'
- 三向排除验证：独立进程计时组件本身、探测服务进程存活与响应、运行一个非同池工具对照；解决未知量'共享资源饱和假设是否成立'
- 窗口结束后重试原工具，恢复正常即确证暂态自愈；输出根因结论并停止，不做代码或配置变更

## Stop conditions
- 实现热路径发现真实阻塞原语（锁竞争、无超时外部等待、无界循环）→ 放弃环境分支，转入实现修复
- 同池工具同窗超时 + 独立计时远小于超时阈值 + 事后重试恢复 + 时间线存在对齐的环境事件（重启/大量 IO）→ 根因闭环，停止
- 全程仅目标工具超时、同池其它工具全部正常 → 共因假设被证伪，停止环境取证，聚焦该工具实现与配置

## Verification
- 根因结论需同时满足：隔离计时组件远快于超时阈值、服务进程探测正常、非同池工具正常、同池工具同窗共超时、窗口后重试恢复
- 核对委托链每一跳的注释与实际 import/调用一致，确保审查的是真正被执行的实现而非同名旧版本
- 时间线交叉核对：超时窗口须落在环境事件窗口之内，避免把先后关系当因果

## Counterexamples
- 只有目标工具超时、同池其它工具全部正常 → 不适用环境分支，应继续查实现内死锁/缺超时外部调用/无界循环
- 标识符是高频常见词（如 status/run），全文检索命中数百处 → 符号锚定失效，应先读注册表或文档取得唯一限定再检索
- 用户要求修复或防复发而非仅定位 → '暂态已自愈'不是终点，须继续给出超时上限、池容量等对策
- 环境无 shell/权限，无法独立进程计时或探测服务 → 三向排除不可行，只能依赖重试与时间线推断，结论应降级为'疑似'而非定论
