## Trigger
对 Web 编辑器/表单的合成输入（CDP Input 事件、粘贴、按键输入）改变了 DOM，但应用程序自身的指示器（字数计数器、提交/发布按钮的启用状态、保存状态）从未反应，导致对替代输入方法进行越来越多的枚举尝试。

## Discriminator
在故障发生时可观察到两点：(1) 刚刚阅读的经过验证的脚本暴露了一个激活步骤（Page.bringToFront，文档字符串 'verified to receive input events'），作为其经过验证的输入路径的强制性先决条件，但失败的运行跳过了它；(2) 应用指示器冻结而 DOM 继续变化，这是一种模式，表明应用程序正在丢弃未聚焦/未激活的事件，而不是输入编码不受支持。

## Short path
- 在首次输入尝试之前，将经过验证的方案的前置条件步骤（激活/聚焦）枚举为契约的一部分：bringToFront + 在目标字段进行真实点击，而不仅仅是输入命令本身。
- 运行一次决定性的微测试：输入一个字符；比较 DOM 长度与应用自身的计数器。
- 如果 DOM 变化而计数器冻结，则将其归类为激活/聚焦缺陷：运行 bringToFront + 真实点击，然后重新测试。
- 仅在指示器反应后，才评估输入方法质量（粘贴是否保留了 h2/列表/图片；哪些标签被剔除）。

## Stop conditions
- 恢复激活后，应用计数器增加且发布/提交按钮启用 — 停止诊断输入传递问题。
- 指示器有反应但内容格式降级 — 切换问题：这是输入编码限制，需记录降级并继续，不要进行更多聚焦试验。

## Verification
- 在激活 + 真实点击后，输入一个小样本，并确认计数器 > 0 且发布按钮已启用。
- 在正确的聚焦下重新运行最初“失败”的方法（粘贴），并在选择较慢的按键路径之前确认它在应用模型中注册（计数器与内容长度匹配）。

## Counterexamples
- 计数器增加但格式错误（例如，粘贴剔除了 <b>/<strong> 但保留了 h2）：聚焦没问题；修复方法是更改输入编码并接受/记录降级，而不是激活。
- 即使在激活 + 真实点击后 DOM 也从不变化：目标是错误的（错误的选择器或屏幕外的坐标，例如 rect y=-3842）— 修复方法是滚动到视野内并重新定位，而不是聚焦。
- 无头浏览器或始终聚焦的上下文，没有激活概念：此方法不适用；直接进行编码/选择器检查。
