## Trigger
用户给出状态断言（如"已经批了"）且需要核实系统记录的真实状态与后续处置；或任务问题形如"某条目现在处于什么状态、由谁处置、下一步按什么规则走"。

## Discriminator
摩擦起点之前已可见两条事实：(1) 前两次 search 回执已展示记录分类学——执行状态存放在按条目 ID 键控、带 status/executor/verify_result 字段的结构化记录类中（10 条示例可证），即状态问题的答案形态是"该 ID 的状态记录"而非叙事关键词命中；(2) 助手开局自述目标就是"程序层的实际状态"，环境有专门的状态端点（返回 pending/executing 计数器）。这两点当时就足以把候选动作从"枚举所有日志源换关键词试"缩为"查状态计数器 + 按 ID 取状态记录"。

## Short path
- 把未知量显式写成状态问题：是否已批准离队？是否已自动执行？先查程序状态端点计数器一次拿全。
- 计数器给出数量后（如 0 待审、2 执行中），按精确 ID 逐条定位状态记录：两条命中 executing、第三条缺失即为第三条的状态证据。
- 对已定位的 ID 完整读取状态记录（含 note/boundary 字段），取得处置指令：执行主体是谁、经哪些工具落地、如何自验、以及第三条是否被边界拦截留人工。
- 严格按记录内指令执行与验证（修正工具落地、执行前后状态对比），不为推断机制做环境考古。
- 登记完成状态并在 note 如实写明限制（如运行态需重启生效）；当计数器与逐 ID 记录交叉一致时停止。

## Stop conditions
- 状态端点计数器已回答两个未知量，且逐 ID 全量记录已读、处置指令明确——停止发现，进入执行。
- 逐 ID 记录状态与计数器一致且与用户断言闭合时，不再追加任何目录/版本库考古。
- 只有当目标 ID 在状态源中确无记录时，才扩大到跨通道发现或回问用户，不以全库枚举替代。

## Verification
- 最终处置动作与状态记录内 note 的指令逐条对应（执行工具、验证方式、登记路径、边界条款）。
- 计数器与逐 ID 记录交叉一致（如 executing 计数 = executing 状态记录条数）。
- 区分"记录状态"与"运行态生效"：对常驻服务需额外运行时验证，并在登记/答复中如实说明限制。

## Counterexamples
- 未知量是内容而非状态（某默认值是多少、代码如何实现）：状态端点和状态记录不包含答案，直接读源码/文档才是正确路径。
- 状态记录显示 executed 但产物是未重启的常驻服务：记录状态≠运行态生效（本 episode 结尾即为此情形），仍需运行时验证，不能只信状态记录。
- 目标条目在状态源中无任何记录且批准发生在系统外通道：此时关键词搜索/跨通道发现才是必要的，方法不适用。
