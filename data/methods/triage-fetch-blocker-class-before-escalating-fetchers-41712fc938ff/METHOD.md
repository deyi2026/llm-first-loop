## Trigger
目标 URL 抓取失败（超时/403/仅返回壳），且已同时拥有至少两个通道的结果：直连（curl/web_fetch）与能执行 JS 的渲染代理

## Discriminator
渲染代理已通过反爬并执行 JS、返回 HTTP 200，但正文语义是"Log in or sign up"登录墙而非目标内容或空壳——这证明渲染与封锁均已解决，剩余阻碍是鉴权；该事实在首次读取代理正文时即已出现，无需更强抓取器再验证

## Short path
- 并行发起直连与渲染代理各一次抓取；未知量：内容是否匿名可达
- 读取渲染代理返回的正文（不只看状态码）；未知量：阻碍属于传输拦截/渲染缺失/鉴权中的哪一类
- 若正文为登录墙：判定鉴权门禁，不再升级任何匿名抓取器（无头浏览器同为匿名，必得同样登录墙）
- 若 URL 形态非标准命名空间（如带特殊前缀），做一次标准形态变体对照，区分'受限分享格式'与'ID 无公开版本'
- 停止抓取升级，向用户给出需其授权的选项：重生成公开链接 / 粘贴内容 / 授权本地登录态会话

## Stop conditions
- 能执行 JS 的匿名通道返回 200 且正文即目标内容 → 抓取已成功，进入分析
- 能执行 JS 的匿名通道返回登录墙，且另一独立通道（如直连 403）一致失败 → 鉴权门禁确认，停止抓取升级
- 两通道均返回无登录 UI 的空加载壳 → 转向数据加载/provenance 分析，而非鉴权或封锁路径

## Verification
- 至少两个独立匿名通道交叉验证（直连状态码 + 渲染代理正文）；单通道登录墙不足以定性
- 确认渲染代理确实执行了 JS（返回渲染后正文而非原始壳），否则登录墙可能是未渲染假象
- URL 变体对照：标准形态返回不同的通用页面（如首页壳），支持'受限链接格式'结论

## Counterexamples
- 直连 403 但渲染代理返回完整目标内容 → 阻碍是 bot/TLS 指纹封锁，升级更强抓取器正是正确动作，不得套用此方法提前停止
- 登录墙仅对数据中心 IP 出现、住宅 IP 的真实浏览器可见内容（IP 级门禁）→ 各通道结果会不一致，应先做一次本地匿名通道对照再定性
- 渲染 200 但正文是无登录 UI 的纯加载壳 → 属异步数据加载问题，应沿网络请求/provenance 追内容，而非下鉴权结论
