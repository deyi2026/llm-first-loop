## Trigger
接到跨阶段遗留事项/待办清单，要逐项设计处置方案，且清单生成后仓库已有后续交付提交（部分问题可能已被后续 phase 顺手修复或加固）

## Discriminator
清单项断言的问题是否仍复现于当前 HEAD：相关路径的 git log 是否出现显式点名该修复的后续提交，且当前代码/测试中存在对应加固痕迹（如『PhaseX 加固』类注释、已收敛的 helper、放大的时序余量）；双通道一致 → 该项前提被证伪，应关闭而非再设计

## Short path
- 把每个清单项拆成『断言的问题 + 相关源码/测试路径 + 仍存在的可观察证据』，明确未知量=该项前提在当前 HEAD 是否成立
- 逐项先跑 git log --oneline -- <相关路径> 并 grep 当前代码中的加固标记/helper/注释，用证据证伪或确认前提，再谈方案
- 后续提交显式点名修复且代码痕迹与之一致 → 关闭该项，记录 commit id 与加固证据，不为它产出任何设计或代码（再改造可能有害）
- 前提仍成立（问题调用点仍在、无加固提交、无覆盖测试）→ 该项才进入方案设计、拷问与代码审查子 agent 门

## Stop conditions
- 每个清单项都完成二值判定：『前提仍成立待处置（附 HEAD 上问题仍存在的具体证据）』或『已被后续交付解决，关闭（附 commit 证据）』
- 不为已关闭项起草任何再改造方案；双通道证据矛盾（提交声称修复但代码无痕迹）时标记待人工核，不得直接关闭

## Verification
- 关闭结论必须有双通道一致证据：提交记录显式点名该问题的修复 + 当前代码/测试中的加固痕迹与提交内容吻合
- 保留项必须能指出当前 HEAD 上问题仍存在的具体位置（裸调用点、脆弱断言、缺失测试），否则不得保留

## Counterexamples
- 清单项是新增能力或纯待办，不携带『某问题仍存在』的可证伪前提 → 直接进入设计，无需前提检查
- 仓库无可用提交历史，或提交信息从不描述修复内容 → 前提检查退化为只读当前代码，不得凭『可能已修』猜测关闭
- 当前 HEAD 上问题证据仍直接可见（失败测试、裸调用点）→ 前提成立必须保留处置，不得因历史提交存在而误关
