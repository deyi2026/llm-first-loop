## Trigger
上一任务/链路刚结束（用户询问下一步、状态或收尾建议），环境提供权威状态聚合工具（活动 goal 检查、最近事件流、待办/故障/恢复计数器、VCS 工作区状态），且问题本身不要求产出新内容。

## Discriminator
进入枚举前已知两个事实：goal 检查返回无活动目标；证据列表显示最近证据全部来自刚结束任务的验证命令（如台账路径 grep）。这两点把“下一步”缩小为两个一跳可得的未知量——系统级待办计数是否全零、工作区是否有未提交项。原始证据内容对答案无增量；重读快照或搜历史记录属于对已闭合结论的重复验证。

## Short path
- 查活动 goal/task → 无活动目标则“下一步”不是继续任务，转状态盘点；有活动目标则直接建议继续它
- 读最近事件流（一次、覆盖闭合时刻）→ 找带声明校验的闭合声明；无声明或校验失败才需要回原始证据核查
- 查待办/审核/故障/恢复计数器 → 全零即系统侧无事可做
- 查工作区 VCS 状态（如 git status）→ 捕获未提交改动与未跟踪文件，作为唯一可能的遗留事实
- 按计数器与 VCS 状态给优先级建议（先闭合未提交改动，再清点未跟踪），停止一切发现类调用并征求确认

## Stop conditions
- 无活动目标 + 上一链路闭合声明已验证 + 计数器全零 + 工作区状态已捕获：停止所有枚举/检索/快照重读，直接输出建议
- 每条建议均可追溯到某个计数器数值或 VCS 状态的具体行，不依赖任何未读的原始证据内容

## Verification
- 删除式复查：若去掉所有原始证据快照读取与历史记录搜索，最终结论是否仍完整成立——应成立
- 声称“已闭合”须有闭合声明+全零计数支撑；声称“有遗留”须指向非零计数或具体 VCS 状态行
- 闭合声明必须带声明校验（declaration/honesty check）通过，否则视为未闭合

## Counterexamples
- 计数器非零（存在待执行/待审/故障/恢复项）→ 下一步应针对该具体项做窄检索，聚合器只给方向不给细节，本方法不适用
- 事件流中无闭合声明或声明校验为 False → 不能凭快照枚举宣布闭合，必须回台账/原始证据核实后再谈下一步
- 聚合器已知会滞后（外部执行者手动登记、缓存未刷新）→ 需用原始台账/状态文件交叉验证，不能只信计数器
- 用户的“下一步”指某具体项目的规划或内容产出（非会话状态）→ 状态聚合器回答不了，应做领域检索
