## Trigger
用户/上游要求给出下一步、提交或交付建议；git status 显示未提交改动；本会话没有产生这些改动的任何写入回执（多会话/多代理共享检出树环境下尤其常见）

## Discriminator
改动文件 mtime 晚于本会话最近一次对工作树的观察时点，且本会话无对应写入动作；diff 内容与仓内另一权威文档（评审报告/任务书）点名的修复项逐条吻合 → 改动来自并发写入者，归属未裁决且写入者可能仍在活动

## Short path
- git status/diff 出现 M 改动而本会话无写入回执 → 把『改动归谁、能否处置』列为第一阻断未知量，不默认可并入建议提交
- ls -l 取改动文件 mtime 与本会话最后观察比较；diff 对照仓内评审/任务文档的处方清单，推断写入者身份与完成度（未知量：谁写的、写完没有）
- 只读验证：用项目权威解释器（如 .venv/bin/python）跑受影响文件的测试，确认改动质量，验证过程不产生新写入（未知量：改动是否可信）
- 按意图分桶 diff：语义修复 / 纯格式化 / 与任务无关；建议格式化与无关改动单独提交或排除，不混进修复提交
- 把归属裁决（收编进分支 / 仅验证不提交 / 独立 worktree 重做）与推送授权作为显式选项交给用户；归属未定前不给吸收式提交指令

## Stop conditions
- 归属已由用户裁决，或全部改动存在本会话写入回执
- 已交付带选项的建议；不再对同一组无主改动重复枚举仓库环境状态

## Verification
- mtime 证据链成立（晚于本会话最后观察时点）且 diff 与权威文档处方一一对应
- 受影响测试在项目权威解释器下通过，验证过程未新增工作树写入

## Counterexamples
- 单会话独占检出树且所有改动都有本会话回执 → 无归属问题，直接按原计划推进
- 改动是 mtime 远早于任务开始的陈年脏文件 → 处置是询问 stash/clean，不是并发写入者推断
- 用户明确说明改动是本人手动所写 → 只做质量验证与意图分桶，不必做归属裁决
