## Trigger
需要判定某条记录/写入（来自上一步或上一会话）是否已持久化，且一次 search/索引查询未命中，正准备据此得出『未落库、需重存』类缺席结论。

## Discriminator
当时已知的三件事足以阻止误判：① 事件流/回执显示 23:42:43 的写入调用确已执行（存在正向写入证据）；② search_records 是记录库之上的派生索引，未命中只刻画索引态、不刻画存储态；③ 写入落点介质可枚举（experiences/ 目录 + git status 未跟踪清单已在手）。正向写入证据 × 索引未命中构成冲突，必须在介质层裁决，而非直接采信索引判缺席。

## Short path
- 从事件流/工具回执确认：写入调用是否执行过、写入方的落点介质是什么（哪个目录/存储）
- 对该介质做一次直接探查（ls 目标目录或 git status 未跟踪清单）；未知量：记录是否真的在介质上
- 介质命中→判定已落库；只处置实际缺陷（如命名违规则重命名），绝不重存
- 介质确实缺失且无成功写入回执→缺席成立，才执行重存
- 检索索引只用于发现/定位，永不作为缺席判据

## Stop conditions
- 写入介质上确认记录存在（文件在盘/存储列表可见）→ 停止，不做重复写入
- 介质确认缺失、且事件流中无成功写入回执 → 缺席成立，重存后停止

## Verification
- 任何『未落库/需重存』结论必须引用介质层证据（目录列表/git status/存储查询），不得只引用索引未命中
- 若存在写入回执而索引未命中，必须先按『索引滞后/漏索引』解释并完成介质探查后，才允许改动写入状态

## Counterexamples
- 记录库本身是索引型主存储（写入即入索引、无文件对应物）：索引查询就是在查介质，未命中加一次直查即可判缺席
- 事件流显示写入调用从未执行或在落盘前已失败（无写入回执）：缺席由 trace 直接支撑，无需介质探查即可重存
- 写入方落点介质不可枚举且无任何回执：只能给出带不确定性标注的『疑似缺席』，不得宣称确定性缺席
