## Trigger
用户要求核实某工作流/队列的当前状态（如'应该没有待审了吧'），且上下文中已有具体对象 ID；或记录索引对唯一 ID 查询返回空后，正面临'继续换关键词检索 / 全量内容扫描 / 直查数据文件'的分支选择。

## Discriminator
唯一 ID 在记录索引中命中为空——若该对象类被索引，唯一 ID 几乎必中，故未命中是'索引不覆盖'的强证明，继续在同一索引换词重试是浪费。同时所求未知量是状态字段的取值：状态存于结构化账本中，按字段过滤既快又准；而对大 JSONL 的内容 grep 会被超时回执证伪（回执明确是执行超时而非无结果）。

## Short path
- 用唯一 ID 对记录索引做一次探测（未知量：索引是否覆盖该对象？）；命中为空即终止索引侧查询，不再换关键词变体
- 由未命中判定索引不覆盖 → 列出已知状态/审计目录的文件名（未知量：哪个文件是权威账本？），只取目录元数据，不做递归内容扫描
- 读账本并按状态字段过滤统计（未知量：是否存在待审/非终态/已批未执行项？），一次得出状态分布与残留明细
- 对用户点名的具体 ID 交叉核对执行登记日志（未知量：是否卡在 accepted-未执行）
- 状态分布与点名 ID 的状态均已由账本验证后停止，汇报结论；不做审批目录等旁支宽枚举，除非主账本无法解释现象

## Stop conditions
- 全量状态分布计数与所有点名对象的状态字段均已在权威账本中读到
- 账本过滤显示无非终态残留，且与执行登记一致——用户所问事实已被单一权威来源验证

## Verification
- 点名对象 ID 在账本中的 status 字段与执行日志登记相互一致
- 结论来自字段精确过滤（如 status in {proposed, accepted, executing}），而非内容关键词匹配
- 若报告'队列干净'，确认过滤覆盖了全量记录数（如 136 条全量统计），而非只看了尾部若干条

## Counterexamples
- 问题是内容语义检索（'哪里讨论过X'、'相关记录有哪些'）而非状态字段查询 → 关键词/内容搜索仍是正解，本方法不适用
- 索引用唯一 ID 直接命中 → 使用命中结果即可，无需另寻账本文件
- 系统布局完全陌生、无任何已知状态目录 → 浅层列出数据根目录是合理首步；本方法只反对两件事：索引未命中后的同源重试、对大文件的全量内容 grep
- 账本是分散的多文件且无统一状态字段 → 单文件字段过滤不成立，需先确认 schema 再过滤
