## Trigger
缺陷报告/事故单/提案全文已点名工具名+参数名（常附可疑维度如『解析基准不对』『未约束解析基准』），需定位根因并动手修复时。

## Discriminator
报告原文是否已具名 tool+parameter+可疑维度；若是，则站点代码『consult 哪个基准』这一条读数即可把假设空间二分：基准传播断（上游没设/设错）vs 消费者旁路（站点按进程 cwd 校验、把相对串原样下发而从不读权威基准）。后一情形下走完整上游链是纯绕路。

## Short path
- 从报告具名站点出发，定向检索/直读该工具对该参数的解析+校验+下发段（一次动作）
- 记下该段 consult 的基准：进程 cwd / 环境默认 / 权威 context var / workspace base
- 若站点从不读权威基准→消费者旁路成立：只做一次定点确认权威基准在报告场景确实被设置（找 set 点，不读整条机制链）
- 修复=消费点改用权威基准解析（相对路径归一），回执回显解析后的绝对基准使越界即时可见；补一条锁缺陷本体的双向断言测试（落在正确根 且 不落在进程 cwd）
- 仅当站点代码正确使用权威基准仍失败，才转入上游传播链追踪

## Stop conditions
- 站点被证实不 consult 权威基准，且上游 set 点存在→根因闭合，停止溯源，进入修复与测试
- 报告未具名工具+参数（只有用户级症状）→本方法不适用，先复现或走机制链定位

## Verification
- 新增测试必须在旧代码上失败（锁缺陷本体）、新代码上通过
- 修复后回执回显解析后的绝对 workdir，越界在回执层可直接发现

## Counterexamples
- 报告只给用户级症状（『文件出现在错误位置』），未具名工具/参数：无法锚定站点，先复现再定位
- 具名站点只是薄封装，真正解析在委托目标里：读站点只见委托边，沿边一跳即可，仍不需枚举足迹
- 缺陷依赖运行时状态或竞态（如 spawn 时序）：静态站点读无法判别，需运行时复现
- 权威基准本身在报告场景就设错：消费者旁路假设为伪，站点锚定会误导，必须上游修复
