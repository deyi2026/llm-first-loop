## Trigger
用户实测反证了'重启后会生效'的预测：某配置变更只对部分实体可见（'只有 X 生效，其他都没有'），且变更来自最近一轮刚落盘的编辑（通常存在带时间戳的备份文件）

## Discriminator
可见子集是否精确等于某个历史文件状态：若带时间戳备份里恰好只有 X 带新值，说明渲染机制与字段本身正确、运行进程加载的是旧快照；该事实在任务首轮（用户报告本身+上轮编辑上下文）即可获得，能把候选空间从'字段/文件/渲染链全部排查'缩小为'加载时刻 vs 写入时刻'两个时间戳的比较

## Short path
- 由部分可见性提出时间线假设（加载的是旧快照）；未知量1=变更是否完整在盘、何时落盘 → stat/ls 配置目录，读当前文件与带时间戳备份，对比内容并记录 mtime；若备份内容恰等于用户可见子集即强证实
- 未知量2=运行进程加载哪个文件、何时加载 → 一次限定在 src/ 的搜索确认加载路径（如 {data_dir}/xx.local.json），并查运行进程 pid/start_time
- 比较时间线：进程启动早于修复落盘 → 根因闭环（旧进程持有修复前快照），不再重推渲染/解析链；若进程启动晚于最后写入 → 时间线假设证伪，才转向字段名/渲染链核查
- 触发重启并留存真实回执（action_id）；回执若声明两阶段等待（先等会话结束再等空闲）则不轮询、立即收尾
- 写明验证条件：新进程 start_time 必须晚于配置最后 mtime，且回执为终态成功，之后用户刷新确认可见子集扩大到所有应生效实体

## Stop conditions
- 时间线证明运行进程加载的就是最新状态（start_time 晚于配置最后写入）→ 时间线假设被证伪，停止本方法，转向字段/文件/渲染链核查
- 重启回执终态成功且新进程 start_time > 配置最后 mtime → 根因与修复均已验证，等用户界面确认即可，不再做多余复核

## Verification
- 对比带时间戳备份的内容与用户报告的可见子集：两者一致即证明'可见状态 = 某历史快照'，而非机制错误
- 重启回执（action_id）真实存在于服务/部署状态记录；新 pid 的 started_at 晚于配置文件最后修改时间
- 用户刷新后可见子集扩大到所有应生效实体；对仍不生效的实体必须能给出独立解释（如该实体本无档位机制）

## Counterexamples
- 零可见（没有任何实体显示新值）：不能推断时间切片，应先核查是否改错字段/文件/渲染链，时间线比较无判别力
- 系统按请求热加载配置（无进程级快照语义）：进程启动时间与加载时刻无关，应查缓存 TTL 或每请求加载逻辑
- 可见值并非来自被编辑的文件（如来自 provider 端默认值或另一配置源）：需先验证可见值的真实来源，否则时间线比较会误导
