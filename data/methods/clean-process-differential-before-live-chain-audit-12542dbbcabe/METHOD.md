## Trigger
对新部署或重启后的功能做验收时，目标功能在 live 进程上零可观察产物；且已从实现/测试确认输出触发条件（如：特定 kind + 命中 method 的 query 才产尾注），并已用满足条件的输入复测仍无产物——"条件不满足"已被排除。

## Discriminator
该行为可在隔离环境中复现：本地仓库可运行、存在可直跑的正例路径（单测或直接调用同一代码路径）。这个当时已知事实把假设空间一分为二——代码/数据缺陷 vs live 进程构建时的内存态——成本仅一次受控运行；而对 live 链路只能逐环节排除，代价是数十次调用（本集最终自述为"全链盲查"）。触发条件矩阵与本地可运行副本在缺陷信号出现时均已到手。

## Short path
- 把各服务 restart 回执（已逐一 succeeded）当作存活证据，直接以新功能自身的端到端探针作为功能检查，不全量翻读 audit/evidence 转储。
- 首次探针未命中时，读一次实现/测试提取精确触发矩阵，再用满足条件的输入复测。
- 缺陷信号确认（触发条件满足、live 无产物）后：立即在同一触发条件下跑一次干净进程复现——正例单测或直接调用 searcher/渲染路径。
- 按差分结果分支：复现有产物 ⇒ 代码/数据正常，归因 live 进程内存态；把静默 fail-open 分支升级为日志/配置投影使下次一行可诊，再重建重启。复现无产物 ⇒ 此时才逐环节审计代码/数据链。
- 差分已裁决后停止枚举剩余"以防万一"候选（env、pyc、竞态、会话状态）；把剩余精力投入修复+一行可诊断性。

## Stop conditions
- 一次干净进程同触发条件运行已裁决分支归属（代码/数据 vs live 进程状态），不再对获胜分支之外的链路环节做排除。
- 修复+重建后 live 进程复跑同一触发条件：缺失产物出现，且原先静默的分支现可产出日志/配置信号。

## Verification
- 干净进程复现必须满足从实现提取的精确触发矩阵（同 kind、同 query 类、同开关状态），不能用近似输入。
- 显式记录差分对（live：缺失；干净进程：有/无），结论必须同时引用两侧证据。
- 修复后复验：在重启后的 live 进程上重跑同一触发条件，确认产物与新诊断日志同时出现。

## Counterexamples
- 缺失产物依赖 fresh 进程无法触及的 live-only 状态（真实会话、pid 绑定、外部服务）——干净复现通过不能排除代码，应改为排查 live 专属路径。
- 触发条件无法在隔离环境满足（依赖生产数据/密钥），或实现/测试未暴露触发矩阵——此时先做有针对性的链路检查。
- live 进程实际运行哪个 build 本身未确认——先确认运行版本再做差分，否则对比无意义（陈旧进程会使结论失效）。
- 多个未知变更同时上线、无冻结基线——属根因分析场景（冻结 baseline、单变量实验），不套用本方法的快速差分。
