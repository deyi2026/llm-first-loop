## Trigger
用户以因果断言为前提问'如何修改'（'X 的 API 更新了，我如何修改'），且首轮 grep 该名字的命中全部落在带日期的快照/镜像目录（同一文件跨多个镜像根重复出现）、活跃配置/源码文件类型零命中。

## Discriminator
首轮搜索回执的路径形态本身已是答案：命中全在 cache-<date>/<mirror>/、deploy-<date>/ 等冻结快照且跨镜像重复出现，说明字符串只存在于历史记录，生效位置必在运行时注册表/服务而非工作区文件；随后 live 探测中，同一服务上多个语义无关的不同模型返回完全相同的账号/凭据级错误码，把候选根因从'接口格式变化'一步缩到'上游账号层'。

## Short path
- grep 一次后先读回执的路径形态而非逐条追内容：命中全为带日期快照/镜像副本即停止换 pattern 再枚举（后续变体只会命中哈希片段、注释等噪声），把未知量切换为'该名字运行时挂在哪个 provider/服务'。
- 查询 live 模型注册表/catalog，拿到唯一挂载点（provider、base_url、端口），并意识到列表存在不等于可用。
- 沿挂载点的部署/经验文档给出的验证链，对真实端点做最小探测：目标模型一次真实 chat 请求 + 同服务 1-2 个兄弟模型各一次。
- 读错误体分级：兄弟模型同码的账号/凭据级错误 ⇒ 用户前提被证伪，输出账号层处置（申诉/换凭据/替代 provider）并请用户提供其看到的变更原文；仅目标模型独报参数/格式 4xx ⇒ 才进入'改哪层代码'的定位。
- 根因层级被 live 证据裁决即停止；未证实需要时不提出任何代码修改。

## Stop conditions
- live 端到端错误码已裁决根因层级（账号/凭据级 vs 接口契约级），且已回应用户前提的真伪
- 运行时注册表证明该名字不在任何生效 provider 上 ⇒ '如何修改'问题本身不成立，先向用户要出处
- 用户提供了具体变更公告或新报错 ⇒ 前提被外部证据固定，转入按公告映射修改层，不再需要兄弟模型对照证伪

## Verification
- 对照结论必须来自真实出网请求的错误体，而非 /v1/models 列表 200；有条件时回查服务端日志确认请求确实到了上游
- 否定用户前提时附可复现的请求与错误码，并保留'公告可能存在但未搜到'的反向余地
- 最终建议清单里不包含任何未经证实需要的代码改动项

## Counterexamples
- grep 命中就在活跃源码/配置文件里且正是要改的目标 ⇒ 直接读文件定位修改点，不必绕行运行时注册表
- 用户附上官方变更公告原文或具体新报错 ⇒ 前提已固定，直接按公告改，无需证伪
- 仅目标模型返回列出合法取值的参数校验 4xx ⇒ 是接口契约变化，走修改路线，账号层假设不成立
- 真实请求有副作用/高费用/不可重放 ⇒ 不得为诊断乱打 live 请求，改用日志与文档证据
