## Trigger
用户问某机制『是否一直在用/还生效吗』，且以功能而非确切组件名指代目标；首个 status/健康检查返回了一个类别匹配但角色未声明的组件

## Discriminator
首个状态输出中组件的声明角色字段与用户命名功能是否一致。本例：status 已显示 local_runtime 的角色仅为 observer/admission_authority（准入观察），知识层 semantic_* 开关也未把打分归到该 runtime，而用户命名功能是『打分』——类别撞名当场可见，足以把调查目标从『追 lfrt 打分痕迹』改为『找打分功能的真正生产者』

## Short path
- 从用户问句提取命名功能谓词（给规则/经验/方法打分）；用已到手的 status 做角色匹配：local runtime 角色字段只含 observer/admission → 该组件降级为易混淆同类项，不作调查目标（未知量：谁是打分功能的实现者）
- 以功能的生产者/产物锚点定向搜代码与配置：scorer、打分、管线目录名、输出 jsonl、审计事件名、独立端口 → 定位真正打分管线与模型端点（避免通用词 qualification/打分的撞名宽搜）
- 读该管线定义确认触发机制（如结算钩子、committed>0、幂等 fail-open），明确『什么算在用』
- 用权威产物核连续性：输出文件条目时间戳、审计事件成败记录、端点健康；发现断点则用『机制入库时间 vs 承载进程启动时间』交叉归因（旧代码进程），而非假设钩子故障
- 一次性核实易混淆组件的边界声明（如只读观察边界的模块 docstring），在答案中做同类项区分；断点补齐后停止

## Stop conditions
- 目标功能的实现组件、触发机制、当前活性、最近一次实际活动时间戳、断点及其原因均由权威来源（代码定义面、产物文件、审计日志、端点状态）核实
- 同类易混淆组件的角色边界已用一处权威声明核实，可在答案中一句话区分

## Verification
- 最终认定的生产者（管线/端口/模型）能在代码定义面找到对应实现，而非仅凭关键词或记忆命中
- 活性结论附带最近一次实际活动的时间戳证据（产物条目时间或审计事件时间）
- 断点归因有时间线交叉验证：机制入库提交时间、承载进程启动时间、漏处理事件时间三者互洽

## Counterexamples
- 状态输出的角色标签已包含用户命名功能（如问『准入观察是否在用』而组件声明就是 admission/observer）→ 直接采用该组件，只核最近活动，无需转向功能搜索
- 系统中同类组件只有一个，类别匹配大概率就是正确目标 → 角色门控是多余开销，直接核活性即可
- 用户以确切组件名提问（『lfrt 有没有被打分调用』）→ 追该组件的使用痕迹本身就是任务，即使角色标签不符也应先查标签是否过时而非换目标
