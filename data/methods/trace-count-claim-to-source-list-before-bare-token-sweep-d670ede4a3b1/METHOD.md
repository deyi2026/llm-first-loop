## Trigger
任务范围来自某状态/收口/总结文档的一句『N 条 X 待处理』，但该句未逐条列出；同时 X 也是项目里广泛使用的优先级或分类标签（如 P0/P1/P2、严重度分级），裸词全文搜索会命中大量与目标无关的优先级标注

## Discriminator
状态文档只给条数不给逐条清单，说明数字是从审查/裁决文档派生的二手主张；且检索回执里『P2-N』式编号命中与大量优先级列标注混杂——编号 ID 模式指向 finding 本体，裸词命中 taxonomy 噪音，二者在回执里可机械区分，看到即可换用编号模式收窄

## Short path
- 先读定义待办的那份状态/收口文档，确认它是『条数主张』而非逐条清单；未知量：这 N 条到底是什么？
- 改用编号 ID 模式（如 'P2-'）做作用域受限 grep，而非裸词全文 search；未知量：原始枚举分布在哪几份文档、各自编到几号？
- 只读命中文档的对应章节（有界区间），把各出处枚举相加；未知量：是否存在加总恰为 N 的单一清单？
- 对不上即停止对齐尝试：按出处重建分类对照表（已闭环/部分满足/延期/不做/未对账），把条数出入（如 8 条主张 vs 12 行重建）写进交付物第一段
- 表中每条代码态主张在部署副本/真实工件上核对，全部条目有处置即停

## Stop conditions
- 每个出处枚举出的条目都有明确处置（闭环/部分/延期/不做/未对账），且条数出入已作为发现显式披露
- 或溯源即命中单一权威 N 条清单——此时直接按清单逐项处置，不再重建

## Verification
- 『不存在单一清单』是否定性结论：须先完整枚举文档目录（ls 全量）确认覆盖，不得基于截断搜索回执下结论
- 重建表每行的代码态主张须核对在部署副本/目标工件（如 .releases 快照）上，而非工作树或记忆
- 条数出入的来源与口径在交付物中逐字写明，读者可独立复算

## Counterexamples
- 状态文档自身已逐条列明 N 项：清单就在手上，直接逐项处置，无需溯源重建
- X 不是项目级 taxonomy 标签、词形唯一：裸词搜索即精准且更省，无需编号模式
- 条数来自机器维护的注册表/任务跟踪器：注册表本身就是权威清单，读它而不是 grep 文档
- 条数被显式标注为估算（『约 N 条』）：出入不构成需更正的发现，只作背景说明
