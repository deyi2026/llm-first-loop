## Trigger
需要重验此前轮次对某代码库的断言/引用位置，且仓库存在 .releases 类快照重复树（每个源文件被复制 N 份），或宽泛内容检索已经超时/命中被重复树淹没

## Discriminator
待核断言文本在动手前就已包含精确锚点：具体文件路径 + 特征符号（常量名、raise 错误字符串等）——这足以把'全库发现式搜索'缩成'按内容定位工作副本单文件'一步；首次文件名检索回执中 .releases/ 占 19/19 条命中，进一步证实重复树是纯噪声

## Short path
- 从待核断言中直接提取锚点：文件路径 + 特征符号（常量名/错误字符串），不新起发现式宽检索
- 用 文件名+特征内容 的窄检索（或直接 read_file 已知路径）取得工作副本行号；命中若落在 .releases/ 等快照树则视为噪声丢弃
- 读命中处上下文，判定当前逻辑是否仍支持原断言
- 若不一致：git log -- <file> 查最近提交时间与主题，区分'断言后代码被改'与'断言本来就错'，避免误撤回或误坚持
- 对阈值/判定类结论，import 真实函数跑最小边界探针（篡改比例扫描、极端输入），不凭读码下结论
- 把每条旧断言分类为 仍成立/已被修复/成因未证，附证据后停止

## Stop conditions
- 所有待核断言均已按当前 HEAD 验证并三分类（仍成立/已被修复/证据不足）
- 工作副本命中行的符号与断言引用一一对应，且 git log 显示断言之后无相关改动
- 建议中引用的每个数值均来自实测探针输出而非推断

## Verification
- 命中行所属路径不在快照/镜像目录（如 .releases/）内，是权威工作树
- 行号与符号名同原断言逐一对应，排除同名巧合
- git log 提交时间戳与原断言产生时间的先后关系明确可判
- 最终建议引用的阈值/比例与探针实际输出一致

## Counterexamples
- 原断言只有模糊描述（如'browser 模块某处有个限制'），无可提取的特征符号——此时宽检索/目录枚举是必要步骤，不能套用锚点缩窄
- 任务是找某符号的全部调用点或用法面（usage discovery），宽搜索本身就是目的，缩到单文件会漏命中
- 断言针对的是某个具体 release 快照而非工作树，此时 .releases/<hash> 才是权威目标，排除快照树反而取到错值
- 仓库无重复树且检索本就瞬时完成，宽窄路径成本无差异，该方法不产生收益
