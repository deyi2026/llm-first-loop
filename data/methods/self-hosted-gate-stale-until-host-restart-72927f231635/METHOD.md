## Trigger
在本会话内刚（经子代理）把某门/检查的实现代码改动提交进工作树与 HEAD，该实现位于承载本会话的长驻宿主进程自身包/工具目录内（宿主工具清单含此门），现准备在本会话内调用该门以验证新行为是否生效。

## Discriminator
实现宿属与时间线：该门实现路径属于宿主进程自己的 import 树（与 tool scope 同源，首次 grep 的路径即可判定），且宿主进程存活早于本次改动——本会话自己刚做的提交必然晚于进程启动，长驻进程执行的是已 import 的旧模块，磁盘/HEAD 状态对它无效。旁证：全新解释器的测试全绿而会话内调用仍按改动前旧规则拒绝，这一分歧本身就是 stale 签名。

## Short path
- 改动落地并独立复审通过后，调用该门前先解未知量：这次调用将执行哪个版本的实现（进程内存还是磁盘）？
- 判定宿属：实现路径是否在宿主自身包内 + 宿主进程启动时间 vs 改动 commit 时间（本会话自己刚提交 ⇒ 进程必然早于改动）
- 若宿主早于改动：不要用该调用裁决新代码；直接向用户申请重启宿主（或明知旧行为、仅作留证），并明示重启即生效
- 重启后同一调用应按新行为放行/给出新语义，再继续既定验证序列（准入门→全量测试→收口登记）

## Stop conditions
- 已确认实现宿主进程在改动之后启动，或回执证明该调用已执行新行为，才用调用结果裁决代码
- 证明该门每次调用另起子进程从磁盘 import、或读取调用时数据 ⇒ 无需重启，直接调用

## Verification
- 调用前比对：宿主 pid 启动时间 < 改动 commit mtime ⇒ 进程内为旧实现
- 分歧测试：fresh 解释器 pytest 全绿 + 会话内工具按旧拒绝码拒绝 = stale 签名，而非代码未落地
- 重启后同一调用以新行为通过，且结果语义来自新规则而非旧规则

## Counterexamples
- 门每次调用 spawn 新进程从磁盘 import（调用行为已与工作树一致）→ 不需重启
- 改动的是调用时读取的配置/数据文件而非被 import 的模块代码 → 生效不依赖重启
- 拒绝原因是新代码自身缺陷（fresh 测试也红）→ 不能归因进程 stale，应回实现修复
- 门由外部服务的另一份独立检出执行 → 重启本会话宿主无效，需定位真正承载该逻辑的进程
