## Trigger
单向棘轮/债务基线/allowlist 类闸门测试失败（断言文案为『新增/扩大，需显式审查 baseline』或等价），且近期功能性提交触碰过被审计维度；此时第一未知量不是『怎么让测试变绿』，而是『这是该修代码的回归，还是设计内未登记的新债』。

## Discriminator
读闸门测试源码即可得到两个动手前已知的事实：①测试 docstring/断言已声明政策（删除/迁移永远允许，新增需显式审查基线更新），并 import 仓库自带的审计/盘点工具；②基线 fixture 中已存在被点名模块的历史条目。二者合起来意味着：差量可机械计算、登记有先例可抄，修复路径在读测试文件那一步就已确定，无需对代码做宽搜索或反复换 grep 参数。

## Short path
- 读失败的闸门测试源码，提取政策声明与审计工具入口（测试文件自己 import 了它）——解决未知量：这是哪类红、按什么规则修
- 用该审计工具对当前代码全仓盘点并与基线 diff，得到签名级精确差量（覆盖全仓而非只看断言点名的模块，防漏登别处）
- git blame 差量行 + log 基线文件最近提交：确认新债来源提交与最近一次登记提交（后者即格式先例）
- 逐条裁决差量签名：存在语义匹配的已登记 helper → 迁移消债；核对 helper 真实契约（返回形状/副作用）确认不合 → 才走显式登记
- 照先例格式落地登记：只加新签名 + 同步计数 + 审查理由块（注明语义必要性与来源提交），冻结的 baseline_context 字段一字不动
- 验证闭环：新基线对当前树重放全部棘轮断言；再注入探针新访问确认加宽后的闸门仍红（证明是登记而非拆除）

## Stop conditions
- 全部棘轮断言（计数、边界类断言、冻结字段保护）在新基线下对当前代码通过
- 注入的探针新债仍被闸门拦截
- 每条新签名要么已实际迁移、要么有『迁移不可行』的具体契约级理由并写入审查块

## Verification
- 单独重跑该闸门测试文件全绿
- 探针注入后闸门仍失败（拦截有效），移除探针后恢复绿
- 冻结字段与既有保护测试逐字节比对相等
- 审计工具输出的分类计数与更新后基线计数一致

## Counterexamples
- 红是真实回归（如明明有 config resolver 可用却新增直读密钥）→ 修代码，禁止用登记掩盖
- 存在语义匹配的已登记 helper（返回形状、副作用都吻合）→ 必须迁移，显式登记是例外路径而非默认
- 仓库没有配套审计工具、基线是自动生成的 lint 快照 → 本路径不适用，需先建立人工审查流程再谈加宽
- 失败源于审计工具自身 bug（别名误判、误报）→ 修工具并回归验证，而不是改基线迁就错误输出
