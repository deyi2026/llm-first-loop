## Trigger
用户以"X 没重启成功？/修复没生效？"追问上一轮干预结果；上轮 evidence 中存在持久化改动的写入成功回执，同时验证回执失败或缺失（如控制面 API 返回鉴权错误），action trace 中找不到任何重启/激活命令

## Discriminator
当时已在场的组合事实：上轮最近回执为"写盘成功 + 验证鉴权失败"、全量 trace 无重启/激活命令、现场进程启动时间早于改动落盘时间、权威日志 mtime 早于用户报障时刻——这四个可观察事实足以把开放的"失败原因"空间缩成"干预从未激活"与"失败事件从未到达"两个可二值判定的未知量

## Short path
- list_evidence 后只 hydrate 上轮最后几条回执，确认实际发生过什么：有无重启/激活命令、改动的验证回执是成功还是失败
- 一次现场探测：目标进程/服务实例的启动时间对比改动落盘时间，判定"目标是否重载过"（回答用户字面问题）
- 一次时效探测：权威日志 ls -lt + tail，用 mtime 对比用户测试/报障时刻，判定"失败事件是否到达本机"
- 把因果链逐环标注为已验证或假设（写入→加载→事件到达→症状复现），向用户明说哪一环尚未验证
- 下一步选择恰好一个能让激活问题变得无关的可证伪开关实验（如整体退出疑似干扰层），而不是在未验证加载状态的配置上再叠一层修改

## Stop conditions
- 用户的事实性问题已用 provenance 回答（如"根本没有重启发生过，上轮只改了配置文件且未验证加载"）
- 上轮干预的激活状态与事件到达状态均已被明确标注为已验证或未验证
- 后续方案是恰好一个单变量实验，而不是继续枚举日志关键词或宽泛探测

## Verification
- 全量 action trace 中确实不存在被默认发生的重启/激活命令
- 权威日志 mtime 与用户失败尝试时刻的时间差已核对（事件是否到达）
- 提议的实验只切换一个变量，且切换前后各采集一次同源日志作对照

## Counterexamples
- 上轮验证回执已确认改动生效而问题依旧 → 跳过激活层，直接进入新假设与单变量实验（method-root-cause 场景），不要重复验激活
- 纯状态询问（"服务在跑吗"）且无历史副作用 → 一次现场探测即可，无需回溯 provenance
- 改动介质被目标进程自动 watch/reload → 激活近乎必然，不值得花轮次复验，直接检查事件到达与症状复现
- 失败事件已确认到达且干预已确认生效 → 两个二值事实均闭合，本方法不再提供信息，应转入根因分析
