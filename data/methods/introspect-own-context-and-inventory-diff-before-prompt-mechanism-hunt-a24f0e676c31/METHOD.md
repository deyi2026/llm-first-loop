## Trigger
用户对你自己的运行上下文提出加载状态假设或质问（“是不是没一开始加载必要规则？只加载了迷你版/精简版？”），点名或暗指某个候选来源工件；本质是知识层归因问句，需要机械事实裁决“实际加载了什么、来自哪个载体、是设计还是故障”。

## Discriminator
动手检索前已在场的两份一手证据：自己上下文中实际可见的规则引用/指针清单（标题、编号、“完整真值源：…需要时读取”句）直接回答“加载了什么”；被点名候选工件的头部自我角色声明（如“已重分类为 playbook、普通 run 零 prompt 注入”+守护测试名）及其条目清单。两组清单做集合差，双向互不包含（它有我没有、我有它没有）即可证伪“加载的就是它”。

## Short path
- 枚举自己上下文实际在场的引用/指针（零工具调用），先回答“加载了什么”这一未知量。
- 读被点名候选工件（如 lite 版）头部角色声明与条目清单，与在场清单做集合差：互不包含即证伪用户二选一，实际载体是第三种（更薄索引）。
- 读权威 SoT 头部的注入策略语句与守护测试名，把“没全文注入”分类为设计使然或疑似故障。
- 若质问背后挂着上一轮失败，才按已见规则 ID 定点读其“适用范围”段：区分“没加载”与“在场但管辖域外”，得出真因。
- 四个未知量（在场清单/注入源/设计意图/适用域）各有一个一手证据即停，不进入 builder/env/runtime 机制考古。

## Stop conditions
- 在场清单、注入源裁决、设计意图分类（如涉及上一轮失败再加适用域裁决）各自有一手证据闭合即停。
- 仅当出现与头部声明矛盾的硬事实（定向 grep 结果与声明不符、捕获的请求 prompt 与声明冲突），或问的是其他进程/未来 run 的加载时，才转入机制层检索。

## Verification
- 在场清单与一份外部捕获（wire log/冒烟请求记录中的完整 system prompt）核对一致，而非仅凭记忆自报。
- 判“第三载体”须满足集合差双向非空：候选有而我没有、我有而候选没有。
- 设计/故障分类锚定到守护测试名或显式策略语句原文，不是“看起来像故意的”。

## Counterexamples
- 问的是其他进程、子代理或未来 run 会加载什么，内省不可用，机制层检索本身就是正路。
- 被点名工件没有自我角色声明（纯数据文件、生成产物），头部法失效，须查消费方代码。
- 用户的任务就是搞清“谁在哪构建注入”（机制即目标），机制考古是任务本体而非摩擦。
- 运行时对模型隐藏 system prompt，在场清单无法内省，应直接找请求捕获/wire log 作为真值。
