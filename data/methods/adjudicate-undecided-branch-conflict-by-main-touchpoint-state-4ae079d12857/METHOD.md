## Trigger
分支合并/收口裁决任务：登记文档或提交信息（如『方向未定，不全量 cherry-pick』）显式标注某 src 改动与 main 现行演进的冲突方向未裁决，需逐子项判定取分支方向、取 main 方向还是不采纳留痕。

## Discriminator
裁决前已可见的三条事实：①标注本身点名冲突对端是『main 现行演进』——参考系是 main 当前态而非分支历史；②分支线提交清单里若已出现『断言同步 main 现行文案』类提交（如 6e807fc3e 式），说明该线已自行向 main 适配；③main 在冲突触点的就地注释/守卫测试通常已写下决策与理由（如『反向 import 会构成运行时环，校验由调用方执行』）。这三条足以把『重放两线 30+ 笔提交』缩成『每个触点一次 main 现行态读取』。

## Short path
- 从登记文档/提交说明提取『方向未定』子项及其触点清单（文件+函数），并列出分支线全部提交主题备查。
- 对每个触点直接读 main 现行实现与就地注释（只读探测命令用分号串联，避免 grep 未命中 exit 1 截断整链输出），判定方向是否已被 main 采纳并演进。
- 若触点注释显示方向已定：核对分支线后部是否有测试断言同步 main 文案的提交作尾随确认；有则该子项裁决『取 main（演进后语义，如整批校验取代逐条 continue）』，分支对应改动留痕不合并。
- 若 main 侧无守卫棘轮锁定该改动、且其为纯位置重构/零行为收益：判『不采纳留痕』，记录被什么取代。
- 若触点无任何决策编码：退回行为级对比或独立审查裁决，不臆断 main 默认正确。
- 全部子项各有 main 侧可核验证据后停止裁决，进入单线整合过闸。

## Stop conditions
- 每个『方向未定』子项都有一处 main 侧证据（就地注释+现行实现、守卫棘轮的有/无、或分支线断言同步提交）支撑明确裁决。
- 裁决结果与整合线测试断言的现行文案/语义互相印证，无文案漂移。

## Verification
- 整合后测试断言与 main 现行文案一致（无『返回类型异常』vs『条目类型异常』式漂移）。
- 每个不采纳项在台账留痕『被什么取代/为何不采纳』并引用具体 main 证据。
- 被采纳方向以 main 演进后版本语义为准，而非分支原始实现。

## Counterexamples
- main 在触点无注释、无守卫测试、代码不含任何决策痕迹 → 触点读取不产出方向，须行为对比或独立审查。
- 冲突对象是 main 尚不存在的新能力（无触点可读）→ 方法不适用，按价值与治理授权裁决。
- 治理记录显式指定分支线为接管方向（main 为待弃旧线）→ 以 main 现行态为参考系会反向误裁。
- 就地注释与现行实现/测试相矛盾（注释过时）→ 以实现+测试断言为准，注释只作线索不作结论。
