## Trigger
用户提出跨系统能力对比/借鉴类问题（'A 能否借鉴 B'、'B 有什么是 A 没有的'、'B 有什么可取'），且两侧系统的第一手工件（B 的运行状态/配置，A 的源码/文档）本地可读——通常一次只读 ls/grep 即可确认可读性。特征信号：问题隐含'B 缺 A 补'的未经检验前提。

## Discriminator
两点当时已可见：(1) 问题前提在开工前无法区分'BOT 有 LFL 没有的'与'LFL 已有等价物'，而两侧功能名称/角色相似（都有子代理、指令、权限、移交记录）不构成能力等同——等同必须比机制强度（建议性消息传递 vs 验收门/CAS 强制）；(2) B 的能力真值就在本地可读工件里（state/config 及其注释），A 的能力真值在可 grep 的源码里——两侧都存在一手证据源，对比不必靠描述或印象完成。开工初期即可用这两个事实把'自由发挥借鉴建议'缩成'逐项查证的对照映射'。

## Short path
- 拆未知量：把'能否借鉴'拆成 B 的逐项能力清单——直接读 B 的运行工件与配置注释，不靠记忆或转述。
- 对每项 B 能力，在 A 的源码/文档做一次针对性检索，确认是否存在等价机制，并比较约束强度（建议性 vs 验收门/CAS 等强制机制）。
- 三分分类：A 已有等价或更强→拒绝并给 A 侧证据；A 真缺→列为可借鉴项并按'纯增量 vs 需改运行时结构'排序；A 反而更强→标注反向结论，不做动作。
- 以对照表交付，每一格挂证据引用；所有 B 侧条目分类完毕即停，不再扩展枚举。

## Stop conditions
- B 侧每个枚举出的能力项都有带证据引用的三分分类（已有等价/真缺/反向），对照表完整即停。
- B 侧主工件不可读（无权限/不存在）→ 放弃对等映射，转为带明确不确定性标注的二手描述，不出假装完整的对照表。

## Verification
- 每条'A 已有 X'必须引用 A 侧符号/文件；每条'该抄 X'必须引用 B 侧工件原文（含配置注释中的踩坑记录），不接受仅名称匹配。
- 等同判定必须比较机制强度而非概念名：'B 用消息传递移交'与'A 用验收门+CAS 落盘'不可判为同一能力。

## Counterexamples
- B 的工件不可访问、只有 README 或二手转述 → 不能套用，对等映射会变成虚构，只能出带不确定性标注的推断。
- 问题不是对比而是'在 A 中复刻 B 的确切行为' → 目标是保真而非查重，'已有等价即拒绝'的规则不适用。
- A 侧对应能力只存在于未合并分支或计划文档 → 应分类为'在途'而非'已有'，直接判重复建设会误杀真实缺口。
- 问题只是'A 有没有 X'的单点查询 → 一次定向检索即可，整套对照方法是过度流程。
