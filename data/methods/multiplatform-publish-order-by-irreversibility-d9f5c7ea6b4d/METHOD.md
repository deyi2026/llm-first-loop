# 多平台发布的顺序决策：把不可逆的放在最后

## Trigger
同一篇定稿需要在 ≥2 个平台发表（今日头条 + 知乎 / 小红书 / 公众号等），且各平台的登录态、编辑器、校验手段不完全一致时使用。
单一平台场景不需要本方法。

## Discriminator
按**「发布后能否自助修改」**排序，而不是按平台流量或阅读量排序。
判别问句：**这个平台发布之后，我能改吗？**
- 能改（存在编辑入口）→ 风险低，可先发。
- 不能改（只能删或重发）→ 风险高，**必须最后发**。

本卡来源：知乎实测 `/edit/{id}` 重定向、草稿箱 404、文章页无编辑按钮 —— 发布即不可回滚；而今日头条有草稿与编辑路径。

## Short path
1. 先核各平台登录态（用真实页面直接观察，不用配置枚举推断——见 method:decisive-gate-probe-over-channel-enumeration）。
2. 把「可自助编辑」的平台排前，「不可回滚」的平台排后。
3. 在**第一个平台**上把完整链路跑通并校验通过：富文本注入 → 图片上传 → 发布 → 无损全量对照（见 method:irreversible-action-lossless-reconciliation）。第一次发布就是流程演练场。
4. 链路在首个平台验证过后，再对后续平台执行同一套校验（源侧行是共享的，同一套缺失计数脚本可直接复用）。
5. 后续平台若在同一会话卡在登录态，不要原地轮询等待——先推进不依赖它的产出（配图、审阅、上手文档），把阻塞事实报给用户。

## Stop conditions
- 某个平台卡在登录态 → **停止对该平台的尝试**，不要伪造发布、不要尝试代持凭据。改为推进非门控产出，并明确告知用户需要人工介入（扫码/授权）。
- 首个平台发布后校验未通过 → **不要继续往后续平台发**。同一份有缺陷的正文发到第二个平台，等于把缺陷复制一份，并且让排查范围翻倍。
- 已连续两个平台各自失败 → 停止发布动作，回到注入时序与度量层排查（见配套卡的 Stop conditions）。

## Verification
每个平台发布后独立跑一次缺失计数脚本，`missing=0` 才登记该平台完成。
本卡实证：头条先发（pgc_id=7694948729350111759，审核中）→ 链路问题在头条暴露并修掉 → 知乎复用同一套校验，首版因度量层失效被拦下、改无损对照后重发通过。

## Counterexamples
- 按「流量最大的先发」排序——阅读量与可回滚性是两个独立轴，混在一起会先在高风险平台上试错。
- 把不可回滚平台当首发，用它做「流程演练」——演练本应在损失最小的平台上做。
- 因为知乎没登录就放弃当日全部产出——登录态只是**后期门控**，写作、配图、审阅、上手文档都不依赖它，应照常推进。
- 已经发出去发现有缺陷时，反复尝试在原平台修补——本卡来源案例中该平台根本没有编辑入口，修补路径不存在，正确动作是改度量后从源重发。
