## Trigger
服务/进程被判'死亡'的唯一依据是单一坐标未命中或过期的进程快照，且即将据此执行恢复动作（restart/拉起）或把该判定固化进自动健康检查；环境中可见并发管理面（launchd KeepAlive、service job、另一控制面）或坐标可漂移（端口被挤占、新启动进程模式、pid 文件失配）

## Discriminator
拦截回执或系统清单已显式指出存在一个尚未查询的权威控制面（如 'must use service_control; generic shell restart is not authoritative'），且'死亡'证据时间戳早于当前动作、坐标单一（一个端口/一个 pid 文件/一个锚定正则）；或手上已有经 ps/lsof 验证存活的参照进程，可用于一票否决待部署的匹配器

## Short path
- 恢复动作前先做一次即时宽观察：列服务端口族 LISTEN 套接字 + 全参数进程 grep（未知量：目标此刻是否在任何坐标上存活）
- 若在非预期坐标发现存活（端口漂移/新进程模式/pid 文件陈旧）→ 放弃恢复，转入归因'判定面为何未命中'并对齐健康检查坐标（未知量：判定面与部署面为何分裂）
- 确需生命周期动作 → 只走权威控制面，不用通用 shell restart（未知量：谁有权变更共享服务状态）
- 把新匹配器写入自动健康检查前，先用一行命令对已知存活参照进程验证命中，再对停机实例/错误端口验证不命中——语法检查（bash -n）不能替代此步（未知量：该平台原语在两端是否都判对）
- 健康检查对存活实例实测零误报、通知路径实际触发一次后收口

## Stop conditions
- 存活/死亡已由动作时刻的直接宽观察确认（非缓存或单坐标否定）
- 新健康检查对已知存活参照进程实测命中，且对停机/错端口场景实测翻转不命中
- 所有恢复动作均经权威控制面执行，日志中无假阴性 detect_fail 引发的重复拉起与'端口已被占用'冲突

## Verification
- 对已验证存活的 pid 运行健康检查匹配器，必须返回健康
- 停掉一次性可牺牲实例（或探测错误端口）确认检查翻转为不健康
- 复查 guard/重启日志：不存在因看漏存活实例而触发的二次拉起与端口冲突记录

## Counterexamples
- 刚刚已通过权威控制面 status 取得新鲜状态 → 无需再宽观察，直接据其行动
- 密封单管理面环境（容器固定端口、配置保证无漂移、无并发管理器）→ 单坐标否定足以判死
- 待判定的未知量不是进程存活（如配置正确性、数据一致性）→ 该方法不适用
- 匹配器是对平台无行为分歧的标准接口查询（如 HTTP status 对已知端口）且端口坐标刚被确认 → 无需参照进程预验
