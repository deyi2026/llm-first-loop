## Trigger
收到操作员/用户回执（含对象 ID、声称的新状态、『AI 会话不会自动收到本操作，请核实后继续』类可见性声明），需程序化核实外部控制面状态变更后再继续执行任务。

## Discriminator
回执中的『AI 会话不会自动收到本操作』声明（进入核实前已可见）：它事先声明该操作不会出现在会话自动可见的事件/证据流中，而事件流条目是本会话 action_trace（自观测通道）——因此状态未知量的权威载体只能是以对象 ID 索引的登记簿记录，宽拉事件流在结构上就无法回答该未知量。

## Short path
- 解析回执：对象 ID、声称的新状态、以及『会话不会自动收到本操作』的可见性声明
- 据该声明排除会话自观测通道（事件流/证据流），直接按 ID+记录类型查询登记簿状态记录（本集：第二次 search_records 命中 evolution_exec EVO-20261009-0ffcaad8 ai executing unverified）
- 对照登记簿状态与回执：一致→核实闭合，进入执行；不一致→以登记簿为准并上报操作员
- 执行前提核查沿已读文件的显式引用边逐个进行（如被读文件头部点名的红灯测试文件），不预先宽拉任何全量通道

## Stop conditions
- 按 ID 查到的登记簿状态记录与回执一致（或不一致已上报待裁决），状态未知量闭合，停止核实类查询并转入执行

## Verification
- 核实所用证据是登记簿记录类型（含对象 ID 与状态的记录，如 evolution_exec），而非会话事件条目
- 若过程发生了宽通道拉取，检查其是否实际回答了状态未知量；未回答（如事件流仅返回自身 action_trace）即标记为可消除绕行并在下次避免

## Counterexamples
- 待确认的是『本会话/本工作区此前发生过哪些动作』时，事件流正是权威通道，应直接查它
- 按 ID 查登记簿失败、无记录、或记录与回执矛盾需要旁证时，才扩大到事件流/证据库等交叉验证
- 部署形态中审批通知本就注入会话事件流的系统，事件流即权威来源，本方法不适用
- 回执未含对象 ID 或未声明可见性时，先向用户要 ID/入口，而不是猜通道
