## Trigger
在有副作用的第三方平台发布/编辑流（公众号、专栏等）中，某阻塞性子步骤需要 UI 自动化，且已有多条相互独立的交互通道先后尝试同一目标

## Discriminator
不同弹窗/面板都能打开渲染，但各自的最终 commit 控件（确定/使用/确认）以不同方式失败——同一阶段跨控件失败指向共享层门而非单控件 bug；另：若首条通道已给出结构性原因（如『正文图包在 section 里，平台选择器不识别』），那是数据形状问题，应先修形状而不是换通道

## Short path
- 进入平台编辑器前或之初，一次廉价预检账号级提交资格（实名/资质/权限状态）——第一未知量是『这个账号到底能不能 commit』，不是『哪个控件怎么点』
- 首条通道失败且给出结构性原因（选择器列表空因图片被 section 包裹）→ 修数据形状（工具栏原生插一张图）后重试同一条通道，而不是立刻换通道
- 第二条独立通道也在 commit 环节失败 → 假设从『控件自动化 bug』切换为『共享门』：核验账号资质＋重载页面/新会话各一次
- 共享门被权威证据确认（如控制台显示未实名）→ 停止一切控件级枚举；把精确的最小手动步骤（选封面→补声明→发表→取线上 URL 回读）交人工，STATUS 如实记录未发布与阻塞原因

## Stop conditions
- 任一通道 commit 成功且线上终态（URL/发表记录）回读验证通过 → 收口
- 账号级硬门被权威回执确认（控制台资质状态、平台报错）→ 停止控件工作并升级人工
- 已向用户给出最小手动步骤且阻塞原因已落 STATUS → 本会话不再尝试新 UI 通道

## Verification
- 升级前，阻塞原因必须有账号级/共享层的权威回执（控制台资质页、平台显式报错），不能只凭多次控件失败推断
- 若声称已发布：必须取线上 URL/发表记录回读核验标题、图、正文；编辑器内『已保存』字样不算发布

## Counterexamples
- 只有一条通道失败且原因明确是数据形状问题（图片被 section 包裹致选择器为空）→ 修形状即可，不应触发共享门升级
- 某次 confirm 偶发无响应（异步延迟）而其他通道正常 → 有界重试/受控探测即可，不是账号门
- 自有系统/本地流程没有账号层与第三方门 → 共享门假设不成立，应走常规根因分析
- commit 成功但内容有误 → 属验收/校对问题，与本方法无关
