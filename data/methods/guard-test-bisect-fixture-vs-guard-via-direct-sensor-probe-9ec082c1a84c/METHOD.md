## Trigger
自写守卫/防护检查（占用检查、文件锁、权限门、过滤规则）的测试出现意外通过或意外失败，需要定位是守卫 bug 还是测试桩未产生可感知属性

## Discriminator
守卫感知哪个通道是已知事实（如 pgrep -f 匹配进程 cmdline），桩的构造方式是否让标记进入该通道也是已知事实（shell 会把注释从 argv 剥离、bash -c 可能被 exec 优化）。用守卫同款传感器命令对桩独立探测一次：命中+守卫漏→守卫缺陷；未命中→桩无效，先修桩

## Short path
- 明确守卫的感知通道（cmdline/打开文件/锁文件/时间戳）及其内部使用的具体探测命令
- 构造测试桩时让标记以该通道的真实形式存在：路径作为进程真实 argv 参数（而非 shell 注释）、真实持有文件句柄或真实创建锁文件
- 守卫未触发时，先用守卫同款传感器命令独立探测桩（如 pgrep -f <路径>），二分定位桩 vs 守卫
- 传感器命中而守卫漏→查守卫自身命令构造（引号/转义/路径规范化）；传感器未命中→修桩重测，不动守卫
- 双向验证：正例（占用→跳过）与负例（无占用→放行），再测正路径与硬保护路径（is_protected 直测），最后清理测试残留

## Stop conditions
- 桩经传感器直测命中且守卫正确触发，或确认守卫缺陷并最小修复后双向重测通过
- 真实生产占用者的进程形态（如 Chrome 实际 argv 形态）无法用桩模拟时，标注该分支未验证，不用硬凑的桩冒充覆盖
- 纯进程内单测（刺激直接以参数传入）不存在通道错配，直接调试代码即可

## Verification
- 用 ps 独立查看桩进程 cmdline，确认包含守卫所查的标记
- 守卫触发与放行两个方向均有实测记录，而非只测一边
- 正路径执行后结论性数据与硬保护路径完好（如 worker-result.json 保留、data/runtime 被拒）

## Counterexamples
- 守卫感知通道是文件锁/lsof 而非 cmdline 时，argv 标记桩通道错配，测不出任何问题；桩必须匹配守卫实际查询的通道
- 传感器直测已命中而守卫仍漏——此时确为守卫 bug（引号/转义问题），继续换桩只会浪费时间
- 生产占用者以相对路径或已解析符号链接形式携带路径时，桩需模仿真实形态，否则测的是桩而非守卫
- 纯函数单测中刺激直接传入，无外部通道可言，该二分不适用
