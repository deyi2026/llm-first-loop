## Trigger
多批次 gated 项目（设计文档含逐批次闸门表与偏差登记）被问『下一步建议』，且上轮结论或登记行把多个条目 ID 捆绑在同一阻塞原因下；或存在『已合入+部署+测试绿但目标环境从未跑过』的批次

## Discriminator
合并行（如『B-4/B-5 未实施：闸门未满足 X』）与逐条闸门表并存：逐条表为每个 ID 单独定义闸门条件，把实时状态回执逐 ID 对照各自的闸门，通常能发现合并原因只闸其中一部分，另一部分的闸是别的条件甚至已满足

## Short path
- 实时探测当前状态面（status/权限回执），把『为什么没真实数据』缩到单一具体卡点（区分授权类别/锁屏/环境缺失）
- 直读权威逐条闸门表（而非摘要行/偏差登记），把每个未实施或被卡 ID 映射到它自己的闸门条件
- 用实时状态对照各闸门 → 分流：真被卡 / 闸门已满足或卡点不同（可立即开工或换前置）
- 把『已合入+部署+测试绿但从未真实环境验证』的批次列为最高优先：真实风险在验证缺口，不在剩余功能数
- 上轮遗留的『留给用户定』事项先查仓库策略面（.gitignore/README 注释、同类文件跟踪计数）再定性：策略已定的按机械动作处理
- 汇报先逐条纠正上轮错误归因（引行号/回执字段），再给可并行的建议顺序

## Stop conditions
- 每个 ID 的闸门条件都已与实时状态对照并归类（真卡/可动/数据依赖）
- 建议顺序中每条都注明依据（行号/回执字段/仓库策略行），且卡点已排除的条目标为可并行

## Verification
- 纠正后的归因能被逐条闸门表原行文逐字支撑（引用具体行号）
- 实时回执字段与闸门条件同名对应，不拿文档里的陈旧状态冒充当前状态
- 『机械动作』的定性有策略面原文支撑（如 .gitignore 的 ! 规则与已有同类文件被跟踪的计数）

## Counterexamples
- 摘要行与逐条表一致（每行单 ID，或各 ID 确实共享同一闸门条件）→ 无需拆分，直接沿用摘要结论
- 单批次项目只有一道闸门 → 无捆绑可拆，直接对照唯一闸门
- 闸门条件依赖 live probe 也测不到的运行时状态 → 不得断言『闸门已满足』，保持未实测并把它本身列为前置动作
