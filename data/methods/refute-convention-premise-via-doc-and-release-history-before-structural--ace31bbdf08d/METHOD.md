## Trigger
继承（自己上一轮或第三方报告）的多步建议中，存在对持久工件做结构搬移/规范化/形态对齐的条目，且其执行以『现状不合规范』这一未经验证的前提为真。

## Discriminator
该工件是否存在成文流程约定（发布/流程文档对目标结构的明文要求）与跨版本历史先例（近几个 release 的同工件实际形态）：两者一致表明现状即既定惯例 → 前提被证伪；文档要求与现状确实不符 → 前提成立。两次只读操作即可在动手前完成判别，不需要先做任何编辑。

## Short path
- 把该条目改写成隐含事实断言（『现状 X 违反规范 Y』），把『前提是否为真』当作该条目的第一个未知量，而不是默认建议为真
- 一次读取声明规范 Y 的成文文档，确认其对目标结构的实际要求
- 一次查看该工件近几个版本的历史形态（版本历史/上一版内容），确认现状是否为既定惯例
- 前提证伪 → 不执行结构搬移，仅修有独立证据的缺陷（如把误挂条目拆出独立小节，正文逐字不动、不合并版本段）
- 前提证实（文档确实要求另一形态）→ 才执行规范化，并跑该工件的一致性检查
- 在交付报告置顶更正该条目结论，把『是否修改规范本身』交回计划所有者

## Stop conditions
- 惯例前提真伪已由成文文档 + 跨版本历史裁定，且本轮唯一被执行的改动是有独立证据的缺陷修复
- 条目属纯程序性动作（无事实前提）时跳过此前置，直接执行

## Verification
- 跑该工件对应的一致性/契约测试，确认修改不破坏成文流程
- diff 复核：未被惯例保护的段落零搬移、未合并任何版本段，仅拆分/修复目标缺陷
- 与前一版本同位置形态比对，确认结构连续性而非引入新不一致

## Counterexamples
- 工件无成文规范且历史形态本身漂移不定 → 惯例前提不可判定，应按目标形态执行并请 owner 拍板，而非以此为由拒绝改动
- 建议针对的是行为缺陷（断言失败、bug）而非结构形态 → 直接验证行为证据，不必查惯例
- 成文文档已过时、近期版本已实际切换到新形态 → 文档与历史冲突时以最新历史为准并上报文档过期，不能机械照文档执行
- 建议是本轮刚生成且已附完整证据链 → 前提已被满足，重测属无信息重复
