## Trigger
需要实测某个守卫/准入闸对危险输入形态的分类行为是否已按预期生效，且探针载荷需经 shell 送入解释器或生产函数；同一工具链还存在与被测守卫相互独立的执行层灾难性硬阻断（如 execute_command 的 E6）。

## Discriminator
发探针前已可见两条事实：① 被测守卫源码注释把『载荷直通解释器』（cat <<EOF | bash 类）标为典型灾难形态——探针投递若用同形状，等于自己递给兄弟守卫拦；② 被测守卫自己的单测全部以字符串字面量进程内调分类函数、从不拉起 shell——这既证明进程内直调是既定测试姿势，也意味着不需要用危险 shell 形态投递。

## Short path
- 读修复 diff + 新增测试断言形态，得到应拦/应放行矩阵（未知量：本次改动到底改了哪些分类条件）
- grep 单测 import 确认直接引生产模块（无桩），按预检回执指定的 venv 解释器跑单测层
- 探针载荷改用安全投递姿势：写 /tmp 落盘脚本 + python -I 执行，受保护动词等危险字面量运行时拼接构造，不以 here-doc 直通解释器形态发任何命令
- 版本钉扎（git rev-parse HEAD）等工作树核对单独成条，绝不与危险形态探针捆绑——硬阻断会整条没收
- 直接调生产分类函数逐条打印矩阵结果，与断言矩阵逐项比对后停止

## Stop conditions
- 矩阵逐项与修复意图一致：应拦全 BLOCKED、应放行全 exempt
- 实测代码版本已单独钉扎（HEAD==修复提交）且生产模块直连无桩
- 剩余差异确认属另一套守卫（如 E6）的行为且不在本次被测范围内，如实记边界而非继续试探

## Verification
- 单测层结果、生产函数直调矩阵层结果、独立 rev-parse 版本钉扎三者互相印证
- 被拦回执按规则/标签归属到执行层守卫，与被测守卫的行为证据严格分开陈述
- 落盘脚本不含完整危险字面量（运行时拼接），落盘文件本身不触发数据面守卫

## Counterexamples
- 被测守卫的危险形态与投递机制无关（纯函数收字符串字面量，如路径穿越检测）：无需特殊投递姿势，一次进程内调用即可
- 任务本就是验证执行层硬阻断自身是否工作：触发拦截即实验目的，应预期被拦并预先规划等价姿势重发，而非回避
- 回执已显式信任该形态（白名单调用者/豁免通道）：改姿势只会徒增一轮往返
