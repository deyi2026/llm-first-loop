## Trigger
多会话共享仓库中，用户已裁定等待并行会话收口后再执行共享门禁/部署，你进入等待-轮询循环，每周期需回答两个未知量：它收口了吗？它还活着吗？

## Discriminator
上一周期回执已给出的锚点输出（HEAD 哈希、未提交项计数、blocker 错误数）与本周期廉价探针完全一致 → 被监控工作树输入未变 → 确定性检查重跑必然复现同一结果，可跳过；会话工件 mtime 新鲜但无测试/检查进程 → 并行方处于推理阶段，是"慢"而非"死"。

## Short path
- 开局把裁定翻译成可判停的收敛判据（HEAD 推进，或 blocker 计数→0，或工作区大幅缩减）并落盘监控协议与后续动作链（准入→全量→部署）
- 每周期：bounded wait + 仅廉价锚点探针（git log -1、未提交计数、blocker 文件 mtime），一次回答"收口了吗"
- 锚点与上周期完全一致 → 跳过确定性检查重跑；仅当 blocker 相关文件的 mtime/diff 或计数变化时，才按文件限定作用域重跑该检查（同时规避执行超时上限）
- 收敛锚点连续多周期停滞 → 才加测活跃度（会话 JSON mtime、pgrep 测试/检查进程），判定"慢而活 vs 僵死"，据此决定继续等、升级报告或提请代修授权（不擅碰并行方未提交改动）
- 判据满足 → 立即执行预注册动作链，无需再向用户确认

## Stop conditions
- 收敛判据满足（HEAD 推进或 blocker 清零）→ 退出轮询，复跑一次门禁确认真绿后进入部署链
- 活跃度证据消失（会话工件长时间无更新且无相关进程）→ 停止无限等待，升级报告并给出代修变体供用户裁决
- 到达约定报告点或用户改变裁定 → 输出周期状态报告（起点 vs 现在的锚点对照表）

## Verification
- 重跑确定性检查前核对 blocker 文件 mtime/diff 是否真的变化，未变则不跑
- "活跃"结论必须落在可观察工件（会话文件落盘时间、进程表）上，不得凭"应该还在修"推断
- 判据满足后先复验门禁真绿（而非沿用旧计数），再触发部署

## Counterexamples
- 检查本身非确定性（flaky 测试、依赖网络或外部服务状态）→ 输入未变也须按周期重跑，输入门控失效
- 无廉价输入变化信号（非 VCS 目录、拿不到 mtime/diff）→ 只能按时间表重跑，本方法退化为普通轮询
- 并行方工作只体现在远端/提交状态而非本地工作区 → HEAD 即唯一锚点，本地 mtime 门控无意义
- blocker 属于自己批次而非并行方 → 不应进入等待轮询，直接修复
