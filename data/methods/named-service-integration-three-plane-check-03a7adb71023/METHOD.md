## Trigger
用户询问具体命名的外部服务 X『能否接入/接上/打通』本系统（工具链/Agent 框架）来使用其资源，需要给出可行性结论与接入方式；本地仓库/配置可读。

## Discriminator
一次以服务名 X 为关键词的仓库级搜索命中即同时给出：集成模块或 spec 的路径、X_ 前缀 env 配置模板（默认开关、fail-open、所需凭证）。该命中当时就足以把『能不能接』缩为三个独立未知量：代码是否真落地、当前环境是否启用、X 侧端点/协议前置是否满足；且 tasks/spec 勾选框未勾选这一事实不能当实现状态证据。

## Short path
- 以服务名 X 做一次仓库级关键词定位（避免拼长复合查询或先枚举目录）；未知量：X 集成的 locus 与形态。
- 直接 stat/列出集成模块目录与工具注册文件验证『实现已落地』，不信 spec 勾选状态；未知量：代码是否真实存在。
- 读实际运行配置（真实 .env / 运行时工具面板）而非模板默认值；未知量：当前环境是否启用。
- 若『接入』存在多义（执行器平面 vs 模型源平面），逐一检查对应扩展点结构（如 provider 注册表是否可加自定义源）；未知量：各解释的结构可行性。
- 对 X 侧外部前置（如是否暴露 OpenAI 兼容端点）无本地证据时，显式标注未验证并给确认方法，不替用户下结论。

## Stop conditions
- 实现存在、当前启用两平面各有直接证据；外部前置要么有来源要么显式 unverified
- 用户每种合理解释都有可执行步骤或明确否定理由
- 不再按文件类型（spec/README/eval/docs）继续扫源找『再确认几个』

## Verification
- 『已实现』断言对应真实代码路径/工具注册文件存在
- 『未启用/已启用』断言对应实际配置文件或运行时状态，而非 .example 模板默认值
- 凡涉及外部服务行为的断言，无本地证据即标注未验证

## Counterexamples
- 用户在排障（『X 接了但不工作/报错』）→ 走根因分析方法，不做接入可行性三平面检查
- X 在仓库零命中且问题开放式（『我还能接什么』）→ 需要 broad discovery 枚举而非此梯子
- 目标系统是黑盒（无本地仓库/配置可读）→ 前两平面无本地证据，方法退化为外部文档查证
- 系统无独立运行时配置、模板即真值（如纯静态配置）→ 跳过启用平面，避免重复验证
