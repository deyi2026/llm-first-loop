## Trigger
验收/核验任务同时包含服务端可查事实与用户屏幕上才能观察的结果（渲染、交互、视觉行为），且测试消息的位置与效果属于用户已知信息；或打算跨多个 store 搜索一条用户刚发出的消息。

## Discriminator
两个当时可见的事实：(1) 当前入站用户消息本身已含测试特征标记（如 $PWD + 未闭合 ```bash 围栏）→ 当前对话即最可能的测试载体；(2) 验收标准是'流式渲染是否正常'，这是用户屏幕上的结果，服务端任何 jsonl 都无法回答，只能由用户一句话确认。二者在任务开始时即已存在。

## Short path
- 把验收项逐条分类：服务端可验证（审计行落盘/建议状态/usage.jsonl 存在性）vs 用户感知（KaTeX 渲染效果）
- 服务端项：一次读取已解析出的权威数据目录对应日志（evolution_review_log + 建议/exec 记录），同时确认落盘、状态、零起点，到此收口
- 用户感知项：检查当前入站消息是否已含测试标记；本集含 $PWD + 未闭合围栏 → 当前消息即测试载体
- 直接向用户提一个封闭问题：'这条消息在面板上渲染正常吗？若发在别的会话请告知是哪个'，然后停止——位置与效果均是用户私有事实
- 任何对标记的 grep 检索仅作为用户回答'发在别处'后的第二跳，且限定用户指名的 store

## Stop conditions
- 权威数据目录单次读取已确认全部服务端可验证项（落盘、decision、status、usage.jsonl 零起点）
- 用户感知项已转化为对用户的一个明确问题（答案归属用户），且上下文内无相反证据
- 存在性类检查（文件是否存在）一次完成，不重复确认

## Verification
- 审计/状态事实必须来自 resolved 权威数据目录的日志本身，而非旧目录、缓存或转述
- 任何 grep '命中'须确认所在文件是外部输入而非自己的 checkpoint/goal/笔记（自指命中=计划文本回声，不是到达证据）
- 渲染类结论最终以用户单句确认为准，绝不从服务端日志推断渲染正确
- 扫描其他会话 store 仅在用户指名渠道后进行，且回报 0 命中即停，不扩大窗口

## Counterexamples
- 落盘本身就是交付物（如本集验证 EVO_REVIEW_WEB 审计行写入）：服务端单次读取是正确路径，不应改成问用户
- 标记是常见字符串（如 'bash'）：上下文内命中无判别力，需更独特标记或用户声明位置后才能定位
- 用户不可用且必须证明消息到达（数据完整性审计）：有界 store 搜索是必要的，方法退化为'限定时间窗+用户曾指名的渠道'
- 纯前端交互测试且无文本标记：'上下文内查标记'步骤不适用，应直接走用户确认分支
