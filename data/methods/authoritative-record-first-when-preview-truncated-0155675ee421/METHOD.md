## Trigger
用户以唯一记录 ID 引用某条变更记录，声明其已被带外批准（accepted/approved），并要求核实状态后忠实继续执行；records 搜索命中确认记录存在，但内容预览在机制/建议章节之前可见地截断。

## Discriminator
首次 records 命中时已并存两个事实：状态为 accepted（执行义务成立），且预览在机制/建议章节前被截断（root-cause 段中途断句）；同时记录带唯一 ID、存在持久审计台账文件保存完整条目。这把候选空间从'自行推断规格+全库探索注入机制'缩为'按 ID 取台账全文，然后只读规格点名的机制'。

## Short path
- records 按 ID 检索：确认 accepted；观察预览在机制章节前截断这一事实
- 从持久审计台账按记录 ID 取单条完整条目（定位台账路径一次、解析该条），解决未知量'到底要实现什么'——含注入条件、幂等、条数/字数上限、护栏
- 把规格显式点名的复用目标（程序附录通道标签、未确认 failed 扫描函数、verify_acknowledge 入口）当作唯一需要打开的工件清单
- 沿导出符号消费边找同构先例：grep 单一事实源模块的导出符号（如 render_program_appendix/REFERENCE_LABEL 的 importers），而不是猜测术语变体（method_pool 等无据搜索）
- 镜像先例模块的保证实现扩展（层级、幂等、硬上限、fail-open），随既有套件补针对性测试
- 在同一台账登记执行结果，全部规格要求映射到代码且测试通过即停，不做无关子系统探索

## Stop conditions
- 已从台账取得全文，且每条规格要求（通道、注入条件、幂等、硬上限、护栏）都映射到具体代码改动
- 规格点名的工件全部定位并读取完毕，不再进行猜测式宽搜索或重复同一 records 查询
- 针对性测试与全量回归通过、行为与既有先例模块一致、执行结果已登记

## Verification
- 任何设计决策前，解析出的台账条目 ID 与状态与审批回执一致
- 实现恰好复用规格点名的通道/入口，并遵守其声明的幂等与硬上限规则
- 新路径单测通过、既有套件无回归、先例模块的机械保证（状态层、fail-open、闭合即停）未被破坏

## Counterexamples
- 索引预览已包含完整规格（未截断）：跳过台账取全文，直接沿点名工件走
- 不存在按 ID 持久化的记录存储（搜索索引是唯一来源）：by-ID 台账路径不可用，应改进检索查询或向调用方索取全文，而不是重复相同的搜索期待不同截断
- 任务是开放式探索（找同类先例、评估可行性）而非忠实执行一条已批准记录：宽泛代码搜索是合理手段，不应套用本方法
- 规格要求全新机制且无既有复用目标：消费边跟随找不到先例，应转入全新设计而非强行类比
