## Trigger
用户授权执行一个上轮已规划好的受闸动作（git push / merge / knowledge flush 等），而开局第一条只读状态核对显示仓库已越过该计划的成立前提：本地 HEAD 不等于上轮记录的提交、工作树干净、无待入库或待推送内容。

## Discriminator
开局只读命令的三事实同时成立：HEAD ≠ 上轮记录 SHA + 工作树干净 + 待办资产为零。三者同时成立即证明间隙内有外部写者完成过一轮完整收尾（写、提交、推送），『执行』分支应被剪除，只剩两个未知量：『动作是否确已完成』与『实际所做的与授权是否一致』。此时重执行或沿用上轮结论推演都是错分支。

## Short path
- 开局只读核对（HEAD/status/远端配置）；未知量：世界是否仍在授权时的前提状态？
- 发现 HEAD 漂移且树干净 → 只查两 SHA 之间的提交范围（git log 旧..新 + 每提交 --stat）；未知量：间隙内谁写了什么？
- 直查权威远端（对已钉死的权威 remote 执行 ls-remote 目标分支）；未知量：被授权动作是否已被完成？
- 远端 SHA == 本地 HEAD → 动作已完成，剪掉执行分支，转入审计：逐个间隙提交与授权文本对账（多做了什么/少做了什么/改写了什么）。
- 核对凭据链：用回执文件自述字段（scope、candidate_sha、失效条款、时间窗）对照实际被推的最终树，判定前置审查是否仍有效，不引用签发时点旧树。
- 把差异清单 + 有序补救选项（补事后回执/接受现状/恢复被删内容）上报用户分叉决策；未获新授权不做任何写操作。

## Stop conditions
- 权威远端直查确认目标分支 SHA 与本地 HEAD 逐字一致 → 不再触发任何执行/写动作
- 间隙内每个提交都已与授权范围逐项对账、且凭据链有效性已按其自述失效条款判定 → 停止发现，转入上报

## Verification
- ls-remote 返回的远端分支 SHA 与本地 HEAD 逐字一致（不能只看本地 refs/remotes 缓存）
- 间隙内每个提交的文件清单/内容都已与用户授权原文逐项比对，差异被显式枚举而非概述
- 凭据失效判定只使用凭据文件自身声明的作用域与失效条款对照实际交付树（如 patch-scope 自述『签发后改动即失效』+ 交付树含签发后 5 个新提交 ⇒ 失效），不借签发时点的旧状态背书

## Counterexamples
- 开局核对显示 HEAD 与预期一致且确有待推提交 → 授权仍有效，直接走正常执行分支，不需要此审计流程
- 单写者仓库、无并行会话机制 → HEAD 漂移更可能是自己上一轮未记账，应先查自身历史而非假设外部写者并审计他人
- 授权动作与仓库状态无耦合（纯文档编辑、外部 API 调用）→ 前提漂移不影响执行，直接做
- 凭据是整树绑定且声明 revalidated_on_use 的类型 → 不能仅凭『签发后有新提交』判失效，须按凭据自身重验语义重新判定
