## Trigger
用户把一个配置项或模型行为标注（如 reasoning_control=always_on_effort）当作疑似原因，询问它是否造成某个运行中 agent 会话的行为症状（不收敛、一直跑、过度探索）。

## Discriminator
配置 dump 与模型注册目录上是否同时可见：(a) 该旋钮的真实语义标注（档位协议 vs 开关）；(b) 一个共享同一旋钮标注与同一全局档位、却正常收敛的对照（如当前会话模型同协议同 effort=max 却几轮收敛）。(b) 一旦存在，『旋钮本身导致症状』的单因假设即被反例否证。

## Short path
- 读运行配置 dump + 模型注册目录，一次闭合两个未知量：旋钮到底是什么、是否存在同配置正常对照
- 对照存在时，把问题从『是不是它造成的』改写为『它在多层归因中处于哪一层』（放大器/直接机制/预算上限）
- 按会话 id 定点过滤事件流，取稳定性判定、单轮耗时、上下文预算与门控事件，归类症状：报错循环/死循环/慢速长跑
- 对遥测中唯一不透明的事件 token（如 compaction_gate.*）做一次定点源码核对，防止把观测配置误读为故障
- 输出分层归因 + 最便宜的可控验证实验（降档复跑对比）+ 预算收紧建议

## Stop conditions
- 旋钮语义已核实、症状类别已由该会话自身遥测刻画、单因假设已被对照证实或否证，即停止取证
- 用户实际只想改配置（行动请求）而非要归因时，立即转配置 override 定位路径，不再继续因果取证

## Verification
- 对照样本确实与嫌疑会话共享同一旋钮标注与同一生效档位，而非仅名字相似
- 症状结论与目标会话自己的遥测一致（如前缀稳定追加=非死循环、无报错=非故障循环）
- 归因未把放大器说成唯一主因，且附带可执行的降档验证方案而非纯推测

## Counterexamples
- 注册面不存在共享该旋钮的对照模型（唯一样本）时，对照反证不可用，应改为降档 A/B 复跑实测归因
- 遥测显示报错/熔断/前缀断裂等故障态时，先按故障层归因（错误类别→配置解析 vs 事件记录），不适用分层放大器框架
- 用户只要求『把这个默认值改掉』时，直接走配置 override 面定位，无需因果取证
