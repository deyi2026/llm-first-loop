## Trigger
用户引用页面/公告措辞质疑此前实测结论，需要在当前 shell 重新探测外部服务真实状态；此前测试曾成功（如 429/200，说明凭据当时有效），而当前进程的凭据/环境前置条件尚未验证即执行了重测。

## Discriminator
同一 auth 类错误（401"令牌已过期或验证不正确"）在同一 run 中同时出现在目标端点和无关的对照端点上，且此前 429 证明该 key 数小时前认证有效：权限/配额类错误是模型或端点专属的，两端同错指向凭据层（shell 未加载 key），对"套餐是否放开"这一目标问题零证据。

## Short path
- 重测前先用一条命令确认/加载探测前置条件（检查 $GLM_API_KEY，未设则从已知配置 .env 加载），保证与原测试环境同构
- 单次成对探测：同一凭据同一命令下，目标模型 + 已知可用的同端点对照模型各打一发
- 按层分类结果：对照 200 且目标返回权限专属错误码（如"套餐暂未开放"类业务码）⇒ 目标问题已被权威回答；两端点同报 auth 错 ⇒ harness 层，修好环境重测，该结果不计入目标证据
- 抓官方文档原文（非搜索摘要缓存）核对口径，读全句含括号限定语，确认"全面放开"措辞的覆盖范围并与实测互证
- 实测与文档一致即停止，答复中同时给出结论与中间 auth 错误的 harness 归因，避免留下表面矛盾的数据点

## Stop conditions
- 同一凭据下对照模型返回 200 且目标模型返回权限专属错误码——目标状态已被直接回答
- 实测结果与官方文档原文（含括号限定）一致，用户引用的措辞歧义已解释
- 修复 harness 后两端点仍 401——问题已转为"key 是否真失效"，应换路径（控制台/校验接口）而非继续枚举本地配置

## Verification
- 同一 run 内对照探测成功，排除凭据与网络层因素
- 目标错误码为权限/配额类业务码而非 auth 类，错误文案与"未开放"语义一致
- 文档原文引用与 API 实测可互相印证，最终答复中显式折扣此前 harness 层的 401 数据点

## Counterexamples
- 目标问题本身就是"key 是否失效"：此时 401 是直接目标证据而非 harness 噪声，不应先验地归因为环境未加载
- 没有此前成功探测的 baseline（从未有过 200/429）：401 无法归因"前置条件丢失"，很可能真是 key 失效，应先验证 key 本身
- 对照端点与目标共享同一认证/配额池而非独立对照：两端同错不能完成分层，需换真正独立的对照（另一 provider 或健康检查端点）
- 文档原文已直接、无歧义地回答问题且用户未要求实测：直接引用原文即可，无需发起 API 探测
