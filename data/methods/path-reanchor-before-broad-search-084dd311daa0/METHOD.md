## Trigger
read_file 失败回执为明确的持久 not-exist（非超时/权限等瞬时错误），失败路径尾部包含用户目录型组件（如 Downloads/），而当前锚点不是用户主目录，且精确文件名已知。

## Discriminator
回执类型为已登记的持久 not-exist（排除瞬时故障）＋ 路径尾部含 Downloads 等用户目录组件 ＋ 精确文件名已知。这三个当时已可见的事实把『全仓/内容搜索定位文件』缩成『同一尾部换 1~2 个锚点重试』。用户目录型组件出现在项目工作区路径下，本身就指示锚点错误而非文件不存在。

## Short path
- 确认回执类型：持久 not-exist 而非瞬时错误（瞬时错误应重试原路径）。
- 解析失败路径：识别用户目录型组件与已知精确文件名，形成『尾部不变、仅换锚点』假设。
- 用完全相同的路径尾部在最可能的替代锚点（用户主目录）做一次 read 重试。
- 若换锚仍 not-exist，至多再试一个锚点（cwd 或上级目录），然后停止锚点枚举。
- 两次换锚均失败后才执行工具建议的 search_files（优先按文件名 pattern 而非内容关键词，避免噪声命中）或向用户求证路径。
- 读取成功且内容与任务引用的标识（版本号/章节号）匹配后，立即返回原任务，不做进一步定位搜索。

## Stop conditions
- 换锚读取成功且内容与任务引用的标识匹配 → 停止定位，回到原任务。
- 锚点重试已达 2 次仍 not-exist → 放弃锚点假设，转 search/求证分支。
- 回执指示瞬时错误、权限或 IO 问题 → 本方法不适用，按错误类型处理。

## Verification
- 成功读取的文件内容包含任务所引用的标识（如文档版本号、被引用的章节号）。
- 未在换锚重试之前发起宽内容搜索（检查 action 顺序）。
- 对同一目标的锚点重试不超过 2 次，失败后确实切换到 search/求证分支而非继续枚举。

## Counterexamples
- 文件确实不存在或已被重命名（用户记忆有误）：两次换锚失败后必须停止并求证，继续枚举锚点即是新的发散。
- 失败路径完全位于项目内部（如 src/foo.py），不含用户目录组件：应直接在工作区内按文件名搜索，换主目录锚毫无意义。
- 项目内部恰好存在同名业务目录（如 data/Downloads）且目标确实应在其中：not-exist 的原因是文件名而非锚点，锚点重试会误导方向。
- 工具回执已明确给出替代路径或与锚点无关的具体恢复动作：优先按回执指示行动，而非套用换锚假设。
