## Trigger
需要对一项用户级/本机部署（systemd --user、路径在用户家目录、服务监听本机端口）核验数据或状态是否生效；或核验通道已返回 401/403 等鉴权类失败时

## Discriminator
被核验部署的全部已知事实都在本机：unit 是 --user、文件落在 ~/.local、且上下文中已出现该服务自身的本机端口地址；公共域名不属于这个实例，在它上面取到的任何结果都无法回答本机问题。首个 401 的性质是入口要求鉴权而非瞬时故障——UA 轮换与同主机换相邻路径都不可能产生凭据。

## Short path
- 先明确本次核验的未知量属于哪个部署实例：本机这套服务，还是公共托管实例
- 选择属于该实例的读数通道：直接请求本机端点一次，或给用户一条本机 probe 命令并等待其输出
- 从该实例自身读数得到明确结论（新卡可检索/状态生效）后即停，不再叠加其他验证通道
- 任一通道首个 401/403：将该通道标记为不可用并切换通道，不在同通道上换 UA 或换相邻端点重试

## Stop conditions
- 被核验实例自身的读数（本机端点响应，或用户贴回的本机命令输出）已给出明确判定
- 某通道出现鉴权类失败（401/403 且响应表明要求凭据）——该通道判定为不可用，停止在其上重试

## Verification
- 最终判据必须来自被部署实例自身的读数面：本机 API 响应、本机目录清单或用户在本机执行的命令输出
- 确认没有把公共站点或其他实例的响应误当作本机部署生效的证据

## Counterexamples
- 被核验对象本身就是公共托管实例（SaaS/线上服务）：公共端点才是正确通道，401 应转为寻找或申请凭据，而不是转本机
- 401 明确由 WAF 的 UA 指纹规则引起（响应头/正文点名 UA 限制）：换 UA 重试一次是合理的，与缺凭据的 401 性质不同
- 核验目标只是文件落位且 cp -v 回执已逐条成功、加载机制已核：直接以回执加目录清单收口即可，无需再打任何 API
