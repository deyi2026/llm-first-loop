## Trigger
需要报告某个已产生的长任务结果（后台 job 输出/长命令产物），但其句柄（job_id、输出位置）不在当前上下文，只能靠事件流/Evidence 检索找回时。

## Discriminator
本会话当时已可见的关键事实：检索返回的唯一命中是本次查询自身的 action_trace 回执——说明该索引的内容类是“我自己的动作痕迹”而非任务运行时输出，继续换 query/scope 只会再枚举自己的痕迹；同时已知套件规模远超前台 60s 上限、且重跑命令若以 tail -N 类截断 sink 收尾，用户关心的结论行（汇总统计）必然丢失。这两条当时已知事实共同把候选动作从“多通道挖掘+事后补数”缩成“立即重跑+一次自答式捕获”。

## Short path
- 【未知：句柄能否从记录恢复】先做一次 session 事件流/Evidence 检索；命中若仅为自身查询回执，通道判死（至多再给一个不同 scope 的变体），停止换词重查
- 【未知：用什么事实替代丢失结果】判定向前重建：在当前代码上重跑，直接生成新鲜权威回执，而不是继续在不可能命中的通道里枚举
- 【未知：实现落点/测试范围】用已有 provenance（近期命令痕迹 + git status/worktree 列表各一次）确认在哪个工作区跑，不做全目录枚举
- 【未知：跑多久/怎么收】规模已知超前台上限 ⇒ 首发即后台 job；命令自设计为输出全量落盘（重定向/tee 或 junitxml）并保真末尾汇总行，不用 tail -N 类截断 sink 收尾
- 【未知：结果与精确数字】轮询到 done，从持久化捕获读 exit code + 汇总行；两者交叉一致即作答
- 【可选未知：陈旧失败缓存是否构成矛盾】一条 stat/mtime 核对；缓存时间早于本次 run 且本次全绿 ⇒ 判为残迹并注明，仅当用户要求数字级澄清才安排重放

## Stop conditions
- 检索命中只包含自身动作/查询的回执痕迹 ⇒ 立即停止该通道的参数变体，转入重建
- 权威回执到手（exit code + 末尾汇总统计相互一致）⇒ 立即作答，不再追加收集式运行（如 --co）或重复确认
- 缓存 mtime 早于本次 run 且本次 exit=0 ⇒ 残迹判定成立，停止追查

## Verification
- 最终结论必须取自持久化捕获（文件/回执），而不是会被行数上限截断的轮询窗口
- exit code 与汇总行交叉一致（如 exit=0 且汇总无 failed/error）才宣布全绿
- 任何关于缓存/残迹的结论必须附 mtime 与本次 run 起止时间的先后关系作为证据

## Counterexamples
- 检索结果包含非自身的运行时记录（例如真实的 job 启动/完成事件，只是缺目标这一条）⇒ 通道有料，此时按时间窗/事件类型做精确检索优先于重跑，不应套用本方法
- 用户需要的是那次特定运行的原始现场（不可复现的失败、一次性外部结果、重跑有副作用）⇒ 必须恢复原句柄或原始产物，禁止用重跑替代
- 命令没有“已知很长”的证据（可能秒回）⇒ 先前台探测一次即可，不必一律后台+落盘，避免为小命令引入簿记开销
