## Trigger
用户询问被检系统某功能『是否已被实际使用/启用』，且工作区即该系统源码仓库，含归档快照副本目录与依赖虚拟环境等会污染宽泛搜索的噪声树，需要区分『已实现』与『已启用』两个不同未知量。

## Discriminator
功能的装配/注册模块（可由测试文件的 import 行一次定位）的 docstring 或代码会显式枚举该功能全部配置/启用层次；而按功能名做的宽泛文件搜索结果被 fixtures、快照哈希副本和 site-packages 主导——这类结果对『是否启用』这一未知量不提供信息，二者对比即可判定应走哪条路。

## Short path
- 把『有没有用上』拆为两个未知量：实现完备度、运行时启用状态；先缩小启用状态。
- 用一次定向查找定位装配/注册模块（如由测试 import 行指向的模块），读其层次/入口列表——它就是权威检查表。
- 逐层查实况：相关环境变量是否存在、扩展 store 或 list 命令、effective 配置函数实跑输出、当前会话工具表是否含该功能注册名。
- 启用结论定下后，再调查实现完备度（模块规模、测试文件数、git 历史、一次冒烟运行），用于完善建议部分。
- 若结论依赖代码行为，先回显实际加载的模块路径并与工作区副本 diff，确认未被归档快照/发布副本误导。

## Stop conditions
- 装配代码枚举出的全部启用层次都已用直接证据判定为空或非空（不得以『搜索没命中』当作未启用的证据）
- 实现完备度主张有测试/冒烟支撑；凡引用工作区代码下结论的，均已确认实际加载的 import site

## Verification
- 至少两个独立权威来源结论一致（如 effective 配置函数实跑输出、当前会话工具表、环境变量/store 实查）
- 『未启用』结论须对照装配代码枚举的层次清单逐项核销，而非凭印象或单一路径推断
- 引用工作区代码下结论前，diff 实际加载副本与工作区副本是否一致

## Counterexamples
- 用户问『X 是怎么实现的/代码库支不支持 X』——源码检索是主路径，运行时启用检查不适用
- 目标系统未在运行且无配置产物可查——启用状态只能静态查配置文件/store，不应硬造运行时探针
- 功能只有单一众所周知的配置入口——直接读它即可，定位装配代码反成绕路
- 问的是第三方库在本项目内的使用情况——正确做法是排除 venv/归档目录后的内容搜索，而非运行时启用检查
