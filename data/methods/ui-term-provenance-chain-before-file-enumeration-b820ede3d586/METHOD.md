## Trigger
用户报告某本地应用 UI 元素（列表/条目/面板）的状态问题（从哪来、为何这么多、能否删/改），且该应用的前端源码、后端源码和运行时数据文件都在当前仓库或本机可访问。

## Discriminator
在扩散发生前已存在的事实：仓库根一次 ls 已暴露前端目录、后端 src、数据目录的布局；且用户可见的元素名词（如'工作区'）必然出现在渲染它的前端组件与 API client 里。因此对前端 src 的一次定向 grep 就能同时命中组件与后端 endpoint，把搜索空间从'所有文件'缩成一条 component→API→route→存储 的链，无需枚举 dist 资产、字体等无关文件。

## Short path
- 一次 ls 确认仓库布局：前端目录、后端 src、数据目录（未知量：代码与数据各在哪）。
- 用用户可见名词 grep 前端 src，定位渲染组件与 API 调用，拿到具体 endpoint（未知量：这个 UI 列表的数据从哪来）。
- 用 endpoint 字符串 grep 后端，定位 route 与 store；读 store 头部注释/实现，拿到存储文件路径与操作语义，如'删除=注销不删数据、当前项不可删'（未知量：删了会发生什么、是否安全）。
- 直接读权威数据文件（注册表/状态 JSON），统计总数并按路径特征分类真实条目 vs 测试/临时遗留（未知量：哪些是无用的）。
- 经权威 API（或确认语义后的存储操作）对非当前项执行清理，回执/重读数据文件验证数量变化，并告知 UI 如何刷新（未知量：结果是否生效、用户如何看到）。
- 若清理入口在 UI 缺失（后端有接口前端没接），在结论中说明，并停止探索。

## Stop conditions
- 操作语义已从后端 route/store 代码确认，且条目清单已从权威数据文件确认，即停止代码探索。
- 变更已通过 API 回执或重读数据文件验证数量变化，不再追加确认性枚举。
- 一旦开始枚举与该名词无关的目录（构建产物、字体、无关模块），说明已偏离，应退回溯源链。

## Verification
- 对用户的行为学结论（如'注销不删数据'）必须能在后端代码中指出对应实现，而非猜测。
- 数量与分类统计来自权威数据文件本身的解析结果，而非 UI 截图或截断输出。
- 执行变更后重新读取数据文件或调用列表 API，确认数量与预期一致。
- 确认保留项包含当前激活项（受'当前项不可删'约束）。

## Counterexamples
- 运行中的服务不是本仓库代码（部署版本不一致）时，源码结论必须对照运行实例/真实 schema 验证，不能直接套用。
- UI 文案经 i18n 或与代码标识符不同名，grep 可见名词会落空；应改为查网络请求或组件树，而非继续换词枚举。
- 列表纯存于客户端（localStorage/IndexedDB）无后端时，链在第二步就断，应直接检查客户端存储。
- 若用户目标本来就是某个已知文件/路径的操作，直接处理该 artifact 即可，无需走 UI 溯源链。
