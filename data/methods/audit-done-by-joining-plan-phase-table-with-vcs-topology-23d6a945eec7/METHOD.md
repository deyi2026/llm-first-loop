## Trigger
用户追问某条多阶段/分期工程『是否完全做完、还剩哪些没做』，且检索回执或记录中已出现该工作的冻结计划文档（含分期表或冻结阶段顺序）。

## Discriminator
摩擦发生前已可见：①首次检索回执已给出冻结计划文档的确切 ID 与冻结阶段顺序（P0→…→P2/P3 类分期）；②git log 已显示按阶段命名的工作包提交。这已把『做完与否』从开放问题缩成有限 join：计划表每个工作包 × 集成分支归属 × 未合并计数 × 全库未开工检查；后续对同一记录库的换词重查不缩小任何未知量。

## Short path
- 从检索回执逐字取计划文档 ID 并读其工作包/分期表，得到封闭的完成判据清单（不凭记忆重构文件名）
- 在集成分支上按阶段标记把每个工作包映射到提交（git log --grep / branch --contains）
- 对相关工作分支做 rev-list --count main..b，确认无未合并半成品
- git log --all --grep 检查未上线阶段是否在任何分支存在
- 输出逐包状态表，区分『已交付』与『验收条件已核验』，每包状态确定即停

## Stop conditions
- 计划表内每个工作包都已获得确定状态（已合并/进行中/未开始）
- 各包状态由拓扑证据（归属提交、未合并计数）支撑，而非进度性记录断言

## Verification
- 分期表工作包数与拓扑检查覆盖数一致，无遗漏阶段
- 结论带分支/commit 指针作快照表述；未逐条核验的退出条件如实标注为未核验

## Counterexamples
- 无冻结计划/范围文档：没有封闭判据清单可 join，应先向用户或 tracker 确定范围，不套用
- 单一交付物任务（一个 PR/一次提交）：直接查该 PR/提交状态即可，分期×拓扑属过度流程
- 用户问的是验收/质量（退出条件、测试是否真通过）：git 拓扑不能证明验收矩阵逐条 PASS，需另取测试证据
- 计划文档已被新决策取代或明显过期：须先确认最新范围基线再 join
