# 多平台发布的顺序决策：把不可逆的放在最后

## Trigger
同一篇定稿需要在 ≥2 个平台发表（今日头条 + 知乎 / 小红书 / 公众号等），且各平台的登录态、编辑器、校验手段不完全一致时使用。
单一平台场景不需要本方法。

## Discriminator
按**「发布后能否自助修改」**排序，而不是按平台流量或阅读量排序。
判别问句：**这个平台发布之后，我能改吗？**
- 能改（存在编辑入口）→ 风险低，可先发。
- 不能改（只能删或重发）→ 风险高，**必须最后发**。

⚠️ 判别「能否改」必须用平台**实际提供的编辑路由**实测，不能凭一次 404/重定向就判不可回滚。
父卡原始观察用 `/edit/{id}` 探测知乎得到重定向、草稿箱 404、文章页无编辑按钮，遂判「知乎不可回滚」。
2026-10-12 用正确路由 `/p/{id}/edit` 实测：已发布文章可编辑并「更新」成功（回执 `receipts/20261012-daily10-submit.json` tail_fix_round 节）。
URL 形式猜错会直接翻转不可逆性判断。当前已实证：知乎与头条都有可用编辑入口。

## Short path
1. 先核各平台登录态（用真实页面直接观察，不用配置枚举推断——见 method:decisive-gate-probe-over-channel-enumeration）。
2. 把「可自助编辑」的平台排前，「不可回滚」的平台排后。判别「可编辑」时先查平台真实编辑路由（如知乎 `/p/{id}/edit`），不要猜 URL 形式。
3. 在**第一个平台**上把完整链路跑通并校验通过：富文本注入 → 图片上传 → 发布 → 无损全量对照。第一次发布就是流程演练场。
4. 链路在首个平台验证过后，再对后续平台执行同一套校验（源侧行是共享的，同一套缺失计数脚本可直接复用）。
5. 后续平台若在同一会话卡在登录态，不要原地轮询等待——先推进不依赖它的产出（配图、审阅、上手文档），把阻塞事实报给用户。
6. 发布后发现的文字级缺陷，走各平台编辑页修正并 grep 复核（见 method:patch-apply-verify-by-content-diff），不要重发新帖。

## Stop conditions
- 某个平台卡在登录态 → **停止对该平台的尝试**，不要伪造发布、不要尝试代持凭据。改为推进非门控产出，并明确告知用户需要人工介入。
- 首个平台发布后校验未通过 → **不要继续往后续平台发**。同一份有缺陷的正文发到第二个平台，等于把缺陷复制一份，并且让排查范围翻倍。
- 已连续两个平台各自失败 → 停止发布动作，回到注入时序与度量层排查。

## Verification
每个平台发布后独立跑一次缺失计数脚本，`missing=0` 才登记该平台完成。
父卡实证：头条先发（pgc_id=7694948729350111759，审核中）→ 链路问题在头条暴露并修掉 → 知乎复用同一套校验，首版因度量层失效被拦下、改无损对照后重发通过。
2026-10-12 补充：尾注缺陷在两平台均已发布后才发现，走编辑页修正成功，验证了「先发可编辑平台」的价值——若先发的是真不可回滚平台，该缺陷只能靠删帖重发。

## Counterexamples
- 用猜测的 URL 形式（如 `/edit/{id}`）探测编辑入口得到 404，就判平台不可回滚——必须查平台真实路由。
- 平台存在编辑入口但需要额外权限/审核（修改后重回审核队列）：仍算「可编辑」，但应把「修改会重回审核」作为排序权重的一部分，不必因此改排最后。
- 单平台发布无排序问题，本卡不适用。
