## Trigger
交付或交接报告声称某动作（push/合并/发布/清理）被一组外部实体阻塞，并给出『等对方收口、等静默窗口』类建议，需要核验该阻塞说法成立性与完备性；或自己在写下『被别人挡住、只能等』这类结论之前。

## Discriminator
报告对阻塞集合做了完备性断言（『被 A、B 两条拦住』），而系统存在权威持久账本可一次枚举全部非终态项；且报告方自身历史（checkpoint、回执、reflog）中已出现同族资源 id 多于其交代的数量（多条 lane id、中途变更过的方案）——这是漏报自己残留的先行信号。注意：队列/槽位工具返回空不等于无阻塞，必须先分清闸读的是账本还是队列视图。

## Short path
- 把阻塞句拆成两个未知量：点名项是否真处于非终态？集合是否完备？
- 直读权威账本，按状态过滤非终态项，与声称集合做差分（一次读取同时闭合两个未知量）
- 对多出的每项做属主归因：owner session/goal id 是否就是交付方自己
- 对自己名下项判定是否已被取代（其 head 是否为当前主线的祖先、产物是否已被合并结果覆盖）→ 归类为可自行清理的残留
- 结论按『自己可清 vs 需他人』分区：前者立即处置、不等静默窗口；后者才等待或请授权

## Stop conditions
- 账本中每个非终态项都已归因并归入自清/等他人两区，与声称集合的差异全部有解释
- 报告方历史中不再有未交代的同族资源 id

## Verification
- 处置自己残留后重读账本，确认该项退出非终态集合
- 确认阻塞闸真实读取面与所清账本一致（清错面不解除阻塞）

## Counterexamples
- 报告只点名单一阻塞项并附该项自身回执（非集合完备性断言）→ 只核该项状态即可，无需全量枚举
- 阻塞资源无单一权威账本（分布式锁/外部服务状态）→ 枚举法退化为逐项探测
- 核验者对自清同样无授权（跨会话写被拒）→ 枚举仍值得做，但只能修正报告与建议，不能动手
- 闸实际读取队列/槽位视图而非账本 → 清账本残留不解除阻塞，须先确认闸的读取面
