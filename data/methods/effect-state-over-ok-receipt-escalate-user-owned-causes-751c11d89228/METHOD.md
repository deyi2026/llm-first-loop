## Trigger
工具回执返回 ok/成功，但下游可观察状态（计数器/DOM 元素数/落库量）与之矛盾；且该步骤存在历史成功回执（同样本地输入此前成功过）。

## Discriminator
「ok 回执 vs 效果状态为 0」的矛盾 + 历史成功基线，二者共同排除本地文件/路径/格式类原因：残余原因是会话/凭据/限流等状态化环境侧因素，带内证据不可区分，且唯一判别动作（如刷新登录态）位于用户自有资源上、超出自身 effect 权限。

## Short path
- 读下游可观察状态（上传计数/目标 DOM 计数）而非工具回执，确认为真值判据，确认效果确实失败
- 对照历史成功回执做基线 diff：相同输入此前成功 → 排除本地文件/路径/格式；不重验输入，不重复回执已 ok 的同一注入
- 枚举残余原因（会话过期/限流/需重登），承认带内不可区分：不猜测具体原因，不换措辞暴力重试
- 定位唯一判别动作及其归属：若需触碰用户自有资源（登录态/凭据），升级为结构化决策请求——现状事实 + 2~3 个选项 + 单一推荐 + 明确不代决的边界
- 对经此路径仍不满足的硬门（如独立复审），在回执中把决策降级为附条件并如实写明未满足项；放行/降标仅由用户明确签收生效
- 用户完成判别动作后重跑同一脚本，以效果状态变化（计数从 0 到目标值）为停止判据，而非回执

## Stop conditions
- 下游效果状态从 0 变为目标值（如上传计数/DOM img > 0），且与历史成功回执形态一致
- 或用户明确选择降级路径（无图发布/暂停），并接受如实披露的未满足项
- 所有未满足的硬门已在回执中如实记录为附条件，且被用户明确接受或搁置——不存在未披露的自行降标

## Verification
- 重跑后检查下游可观察状态（计数/DOM），不把工具回执当成功证据
- 核对回执如实记录审稿独立性状态与附条件决策依据
- 确认全程没有未经授权触碰用户自有状态（浏览器登录/凭据）

## Counterexamples
- 回执 ok 且下游状态也显示成功 → 无阻塞，直接进入下一步，不追查
- 无历史成功基线（该步骤从未成功过）→ 本地输入原因仍然存活，必须先与成功样例或规范做 diff，而不是直接跳到会话侧原因
- 嫌疑变量在自身权限内（可带内重新认证、可改请求头重试）→ 应用单变量实验自行区分（method-root-cause 场景），无需升级给用户
- 失败面给出了明确错误码/响应体 → 原因空间已被收窄，直接读错定位，不需要枚举不可区分的原因集
