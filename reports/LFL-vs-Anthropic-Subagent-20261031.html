摘要：五条判断

结论先行：LFL 与文章主张同源，但在四个具体位置上有实质差异；其中三处是 LFL 主动选择的工程取舍，一处是尚未补齐的短板。

#判断依据与含义
1 形态上高度一致
一致		 LFL 就是"单一 Agent + 主循环"：核心循环 core/loop/engine.py（2939 行）+ runner/lifecycle，README 明示"不是 Agent 框架：无 planner / router / SOP 阶段机"。代码中不存在意图分类器或规划器类。文章批评的"编排框架式多 Agent"，LFL 从设计上就没有采纳。
2 保留编排工具，但无角色 Agent
方向一致		 LFL 有 11 个编排面工具（spawn_subagent、workflow_run、fix_loop、dsh_task 等），但没有任何"研究员/写手/审稿人"式的角色化子代理；子代理按需创建、默认并行上限 3（RULE-AI-25 第 4 条）。这与文章"不要硬编码角色与交接边界"一致，差异在于工具颗粒度偏多（见 T5）。
3 审查闸是"保留并强化"，不是"照单全收"
部分一致		 RULE-AI-28 保留独立审查子代理，但加了四道约束：异模型（GLM-5.3）、只读上下文、冻结真实产物 SHA、通过后签发一次性资格。这比文章的"少数场景可保留"更进一步，但本质仍是 AI 审 AI，同构偏见只被削弱、未被消除（T2）。
4 工具全量在场，是有意的弱模型取舍
取向差异		 文章主张工具定义超过 30–50 个后应改为"元数据 + 按需搜索"。LFL 反其道：84 个工具全部在场，注册表注释写明"这不是路由表"。理由是目标部署为本地弱模型——候选集一旦收缩，弱模型不会去"搜"，只会绕路或误判，而详细契约能直接降低错选与错参。代价是前缀体积与选择噪声，且该取舍的收益目前只有案例级实践、没有冻结 A/B（见 4.7.1）。强模型部署下应重新评估（P0-1 已改为条件化）。
5 压缩治理比文章建议更工程化
超越		 文章说"该做的是压缩上下文，把它当主 Agent 的新任务"。LFL 不仅在主循环内压缩，还配了压缩恢复门：零丢失归档 + 不可变 manifest（sha256）+ 强制五问回执 + 重放防护。压缩从"有损操作"变成"可审计、可回溯的事件"。
一句话总评　文章主张"把能力还给主循环"，LFL 在实践中走得更远——它没有只做减法，而是把过去由编排层承担的职责（校验、压缩、事实留存、授权）下沉成了主循环内的机制与规则。唯一被文章点中、而 LFL 明确反向选择的是工具界面：84 个工具全量在场、不做检索式发现。这是针对本地弱模型的刻意取舍（详见 4.7.1），不是遗漏；它的有效期与"运行弱模型"这一前提绑定，换成强模型时需要重新评估。

1　分析对象、材料与方法

1.1　文章侧材料的性质与局限

本次取得的材料是今日头条上的一篇中文转述，标题为《别学 subagent 了，很可能要凉了。》，文中自述依据 Anthropic 工程博客《Building agents: When to fold subagents into your main agent loop》，并配有一张"根据官方迁移动图中文重绘"的三栏对照图（Main Loop with tools / Main Loop with tool search / Subagent）。

三点必须说明：其一，我没有读到英文原文，本报告对文章观点的引用全部来自这篇转述的归纳；其二，文中"工具定义超过 30–50 个之后工具选择会变差"这类数字，在转述中未给出实验条件、模型版本与度量方式，属于转述中的断言，本报告把它当作"待验证的经验阈值"，不当作已证结论；其三，标题带有传播性夸张（"很可能要凉了"），但正文的迁移建议是具体的，因此分析对象取其操作性主张，不取其情绪化标题。

1.2　LFL 侧事实的取得方式

LFL 的所有架构断言都来自当前工作树的直接读取，而非记忆或推测。取证方式有四类：

  • 定位式读取：README.md、docs/ai_rules.md（35 条 RULE-AI）、src/llm_loop/core/loop/*.py、src/llm_loop/tools/registry.py、src/llm_loop/config.py、src/llm_loop/core/compaction_contract.py、src/llm_loop/core/loop/engine_services/compaction_gate.py。
  • 反向定位：用 grep 搜索不存在的结构（如 class *Router、intent_classif、class *Planner），以"未命中"作为"LFL 没有该机制"的证据。这类否定性证据单独使用时不可靠，因此只用于印证 README 与设计文档中的正向声明。
  • 运行时快照：以 get_tool_schema('*') 列出的工具目录作为"当前会话可见工具"的事实源；以 registry.py 中 _COMPACT_TOOL_DESCRIPTIONS 的顶层键数（84）作为"内置工具 compact 契约覆盖数"。
  • 默认值读取：config.py 中的字段默认值与 env_bool 兜底值，用于判断题述的"默认开启"是否成立（例如 tool_schema_lazy）。

C4上下文收集型子代理造成信息损失：核心问题会被当细节滤掉，主 Agent 只拿到二手信息子代理回传摘要在下游决策中与原始材料等价（关键信息召回率无差异）；或主 Agent 事后回查原文的成本可忽略。
C5并行只在上下文互不相交时成立；调研型任务的并行收益小、合并成本高调研型并行任务在合并阶段的返工成本低于串行执行节省的时间。

C7三问判据：产物能否纯丢弃？上下文分支是否互不相交？是否确实并行？存在大量不满足三问却仍从子代理获益的稳定任务类型。
转述中未出现、但对 LFL 最相关的一点：文章讨论的是"要不要用子代理"，而 LFL 的实际问题已经推进到"子代理的产物如何不丢真、不失真地回到主循环"。这是两个不同层级的问题：前者是结构选择，后者是信息保真。LFL 用 Evidence 引用机制回答了后者的一半（见 4.4 与 T4）。

4.1　架构形态：单循环而非编排框架

文章主张（C1）：单一 Agent 加主循环，比"给 LLM 套一个显式 workflow 的编排框架"更接近 LLM 的真实工作方式；多 Agent 编排有同类问题。

LFL 事实：README 的原话是"AI 优先的 Agent 运行时 Harness，而不是 Agent 框架：没有 planner、没有 router、没有 SOP 阶段机、没有 Prompt 模板阶段机。单主循环就是唯一决策主体。"代码侧的印证是：核心循环 engine.py 2939 行承载全部决策推进，core/loop/ 下的 build / runner / lifecycle / events 都是循环的支撑件，而不是"阶段"。全库检索不到 Router、Planner、intent classifier 类。

一致　这不是"部分相似"，而是同一设计哲学的两处独立表述。LFL 的规则体系里还有一条对应的元规则：程序只提供工具与运行环境，不替模型制定任务策略或完成裁决（系统提示的 llm-first-loop 段）。文章说"路由本质上是工具选择，应该交给模型"，LFL 说"程序不替 AI 决策"——同一件事，一个从 Agent 结构说，一个从程序职责说。

一个容易被忽略的差别　文章批评的"框架"指的是编排结构（角色、阶段、交接）；LFL 里虽然也有大量"框架性"设施（工具契约、规则、证据层、任务图），但它们的职责是地面设施——保证事实可核、动作可审、越权可拦，而不是替模型决定下一步做什么。这个区分很重要：前者会侵蚀模型判断，后者只约束模型的行为边界。

4.2　角色分工与路由

文章主张（C2）：Coordinator + 专业 Agent + 交接的写法看似合理，实则把"该由模型做的路由决策"硬编码成了结构；早期工具选择本身就是路由，硬编码子 Agent 反而制造了交接边界。

LFL 事实：LFL 没有任何角色化子代理——没有"研究员""写手""审稿人"这类预置角色。子代理的出现只有三种触发：显式并行派发（spawn_subagent / workflow_run）、修复循环（fix_loop）、独立审查（review_admission）。spawn_subagent 的 compact 描述第一句就是"非阻塞启动隔离子代理并返回 child_id；父代理可继续当前 run"——它的定位是并行执行单元，不是角色。子代理的模型、工具、上下文由调用方显式声明，没有任何"按角色加载预设"的机制。

一致　但这里有一个必须说清的转移：文章说"路由就是工具选择"，那么当工具数量达到 84 个时，路由的压力并没有消失，只是从结构层转移到了工具选择层。LFL 保留全量候选、只压缩单条定义的体积，是有意的弱模型取舍（见 4.7.1）；代价是候选集大小不变，噪声靠"名字可判别 + 描述带机械事实"来压，而不是靠隐藏。

4.3　构建者—验收者

文章主张（C3）：这是少数仍值得保留的子代理模式，但前提是"自我确认的风险真实存在且危害大"（代码、对外内容）；而且"AI 审 AI"存在同构偏见——同一个模型审自己或同族模型审自己，容易得出同向的错误结论。

LFL 事实：RULE-AI-28 规定的三类动作（全量测试、git push、文章发表）必须经过独立审查子代理，且约束是四层：

  • 异模型：审查者固定为 GLM-5.3，与被审会话的模型不同厂；
  • 只读上下文：审查者不继承执行者的对话历史，只看冻结的产物；
  • 冻结产物：以真实产物的 SHA 为审查目标，"正文 PASS / 旧回执 / 不同目标均不能放行"；
  • 一次性资格：通过后在内存中签发一次性资格，不能复用、不能跨目标。

部分一致　LFL 的做法可以理解为对文章顾虑的逐条回应：异模型回应"同构"，只读上下文回应"被执行者的叙述带偏"，冻结 SHA 回应"审的不是要发的东西"，一次性资格回应"回执复用"。四条加起来，把"AI 审 AI"从"同族模型互相点头"改造成了"两个不相干的模型对同一份冻结产物各自表态"。

但残余风险没有消除：异模型不等于异构偏见。两个模型可能共享同一批训练语料、同一种"看起来很完备"的审美偏好，对同一类缺陷同时失明。审查者读到的仍然是被审者产出的文本，如果产物在结构上完整、在措辞上自信，审查者被说服的概率并不低。LFL 目前没有对"审查者自身的漏判率"做度量，也没有在 RULE-AI-28 中为不可逆动作保留人类终审的强制档位（review_admission 之外的人工确认是场景性的，不是规则性的）。这是 T2 的内容。

与文章的一处实质分歧　文章倾向于"尽量不要 AI 审 AI"；LFL 的选择是"保留，但把审查条件收紧到可审计"。这不是谁对谁错：在没有人可以随时在场的运行环境里，"有约束的机器审查"优于"无审查"；但在有人在场的场景里，把人排除在终审之外是浪费。合理的做法是分档——把"人类终审"作为不可逆动作的一个可选档位显式化，而不是默认省略。

4.4　上下文收集型子代理

文章主张（C4）：让子代理去读文档、再把摘要交回来，会造成信息损失——子代理压缩时会把"它认为不重要"的东西滤掉，而核心问题常常被当成不重要的细节；主 Agent 拿到的是二手信息，后续多轮再传更低效。

LFL 事实：RULE-AI-25 把回传方式写成了硬纪律："中间产物的正文不进入编排者上下文。编排者的注意力预算是全局资源，回传默认只携带：结论（一句话）、stable evidence_ref / artifact ref、可选短摘要（≤200 字符）。正文消费走引用+分页。"机制侧的三件套是：Evidence 持久化（evidence://v1/... 稳定引用）、分页投影（read_evidence 每次最多 4000 字符，带 next_start）、摘要绑定（source_synopsis 绑定源 SHA，摘要不可与源版本脱钩）。

部分一致　这里需要把两种"损失"分开看，否则会误判：

损失类型文章批评的LFL 的机制与效果
传输损失
回传时被压缩掉的信息		 子代理写摘要 → 主 Agent 只看到摘要 已被消除。回传的是 ref，不是摘要；主 Agent 需要时可分页水合原文，甚至逐字回读。source_synopsis 还把摘要与源 SHA 绑定，摘要无法悄悄过期。
采集损失
根本没被存下来的信息		 子代理判断"什么重要"，判断错就永久丢失 未被解决。Evidence 只保证"存下来的可精确回查"，不保证"该存的都存了"。如果子代理读文档时把一段关键限定当噪音略过，主 Agent 事后无论怎么水合都找不到它。

本报告自身就是一个可用的观察样本：文章正文先经 web_fetch 落为 evidence，再由我按 4000 字符分页读取（原文约 1.1 万字符，读了 3 页）；如果我当时只让某个子代理"总结一下这篇文章"，那么"三问判据""反模式"这些段落是否会被保留，就取决于它的判断，而我现在无法复核它漏了什么——因为漏掉的东西不会进 evidence。传输损失可以靠机制解决，采集损失只能靠采集时的纪律。

4.5　并行

文章主张（C5）：并行的成立条件是上下文互不相交；代码类任务可以并行，调研类任务并行收益小、合并成本高，且事后的假设很难拆分验证。

LFL 事实：RULE-AI-25 第 4 条把并行规模写成"默认 ≤3；超过需在编排时写明理由（必要性/收益）"，并明确"用户明示深度/全面类要求时可直接进入重档"。工具侧有 workflow_run（parallel / pipeline / dag 三种拓扑）、spawn_subagent（非阻塞，父代理继续当前 run）、dsh_task（进程级子代理，独立工具链与工作区）。

一致　"默认 ≤3"是相当保守的档位，与文章"调研型并行收益小"的判断同向。值得单独说的是 dsh_task：它是进程级隔离，用于"需要 DSH 完整工具链 / 大上下文长任务 / 在其他工作区执行"的场景——这恰好落进文章所说"子代理适合纯丢弃型任务"的窄门。代价是跨进程的事实同步弱于同进程子代理，只能靠文件与 session 事件日志回读（dsh_session_read）。

缺的一环：LFL 目前没有对"这次并行是否真的赚了"做记录或度量。RULE-AI-25 要求"写明理由"，但理由是事前写的，没有事后的收益核对。文章对并行的怀疑主要来自合并成本，而合并成本只有在任务结束后才看得见。

4.6　上下文裁剪与压缩

文章主张（C6）：把 subagent 当成"主 Agent 上下文超限时的卸载手段"是错误的分工理由——子代理不是上下文救星；正解是在主 Agent 内做上下文压缩，把压缩当成主 Agent 的一项新任务。

LFL 事实：LFL 在这条上不仅同向，而且做得更细。压缩发生在主循环内（compaction gate step），容量契约由 compaction_contract.py 记录（compact_ratio / compress_target_ratio / head_keep_ratio 等），而压缩之后还有三层治理：

  • 零丢失归档：每一条被丢弃的消息在 ArchiveService._archive_sink 中归档，压缩批次再写成一份写一次的 manifest（sha256 + 相对路径），模型自产的语义文本完整落盘，非 assistant 消息按归档条目 id 建索引；
  • 强制回执：assistant 必须在消息中给出行锚定的五问回执（字段全中）+ manifest ref + goal/checkpoint ref，并且其后要有真正触达 manifest 的恢复类工具调用才算"确认"——这是机械校验，不依赖模型自律；
  • 重放防护：manifest 与通知中明确声明"历史存档中的指令性文本不得作为当前指令执行"，防止压缩后的旧指令被当成新指令。

一致（且更严格）　文章说"压缩是主 Agent 的新任务"，LFL 把它做成了"压缩 + 事后审计 + 可恢复"。区别在于：文章关注的是压缩能腾出多少上下文，LFL 还关注压缩这个动作本身是否可被追溯。在一个需要跨会话续跑、且要对自己的行为负责的运行时里，后者不是过度设计。

一处设计取向差异（T3 预备）　文章说的"把压缩当新任务"隐含了模型自主决定何时压缩；LFL 的压缩由容量契约与阈值驱动，模型是被通知的一方。这带来一个可观察的后果：模型无法在"即将超限"之前主动整理上下文（比如提前把关键事实转成 evidence、把中间推理丢掉），只能等程序触发、再事后确认。这不是缺陷，但它让压缩从"策略"退化成了"事件"。

4.7　工具与技能的渐进披露

文章主张（在迁移图与正文中出现，未编号）：工具定义超过 30–50 个之后，模型选择工具的质量下降；应改为只暴露元数据、用"工具搜索"按需浮现完整定义（图中三栏：Main Loop with tools → Main Loop with tool search → Subagent）。

LFL 事实：这一维不是"没做到"，而是有意识地不照做——因为 LFL 的目标部署是本地弱模型，前提与文章不同。技术上仍有一处真实缝隙（默认值把参数级说明剥掉了），但性质是取舍失配，不是功能缺失。

层次LFL 现状判定说明
技能层 37 个 SKILL，skill_list 只给名称与简述，skill_load 才载入全文 达标 这正是文章所说的"元数据 + 按需加载"，已经在运行。
工具层（描述） tool_schema_lazy 默认 True：描述压缩到 160 字符内、参数骨架保留（type/enum/properties/items/required） 部分 降的是单条定义的体积，不是候选集的大小。
工具层（发现） 无"工具搜索"。注册表注释明确："not a tool-eligibility/routing table: every registered tool remains present" 主动取舍 84 个工具全部在场，模型每轮都在 84 个候选里选。这是为弱模型做的选择：弱模型不会主动"发现"被隐藏的工具，隐藏≈不可用；强模型才有能力先检索再调用。

三个口径的数字要摆在一起看才不失真：内置工具模块 42 个（按文件计）、compact 契约覆盖 84 个工具（按注册表键计）、运行时目录 80 余项（含 MCP 与插件，按会话实时列举）。无论用哪个口径，都越过了文章给出的 30–50 阈值，倍率在 1.7–2.8 之间。

为什么 LFL 没做工具搜索？ 两个理由叠加。第一是模型前提：目标部署是本地弱模型，它不会主动去"发现"一个没出现在清单里的工具，隐藏就等于不可用，所以宁可全给、每条写短。第二是路由禁令：注册表注释写明，一旦按"是否需要这个工具"裁剪投递清单，程序就在替模型做路由——这正是 4.2 里文章与 LFL 共同反对的事。LFL 选择的是"全都在场，但每条更短"，文章主张的是"只让相关的在场"。这是同一目标（降低选择噪声）下的两条路径：

路径机制代价
LFL 现状全量投递 + 描述压缩候选集恒定 84；前缀体积受控；无漏投风险；不引入路由判断
文章主张元数据目录 + 工具搜索候选集按需收缩；但"搜什么"本身是一次模型判断，检索失败就变成"看不见工具"

两条路径不是非必即彼的取舍，而是由部署前提决定的选择：对能自行检索的强模型，"少而精"是减压；对不会主动发现的弱模型，"少"就是"没有"。下面把这层前提单独摊开。

4.7.1　模型能力前提：为什么"少而精"对弱模型是反向风险

文章与 LFL 的结论相反，根源不在架构，而在假设的模型不同：文章面向前沿强模型（能先读元数据、再决定搜索什么）；LFL 的运行配置里有 cognilocal 本地端点（ornith-35B-A3B、qwen3.8-flash-next），默认对齐的是弱模型。同一个界面，对这两种模型是两种风险。

LFL 仓库里能支撑这个取舍的记录有三条：

  • 失败形态是"没路标就乱试"，不是"候选太多"：docs/context_health_review_2026-08-31.md 记录 9B 级量化模型把 evidence:// 直接传给 execute_command，判词是"通道完好、路标缺失"。当时的修复不是减少可见工具，而是把机械事实写进工具描述与回执、再加硬护栏。
  • LFL 承认骨架不足，并要求"回读完整 Schema"：docs/COMMON_GOVERNANCE.md 第 3 条写明 lazy/compact 只保证可执行骨架、不承载全部操作语义，"陌生工具、参数语义不清或参数/协议失败时，先读取当前完整 Schema/code/docs 后修正"。这条配套动作成立的前提，正是工具仍在目录里、可按名找到。
  • "只投一小撮工具"的做法曾经试过并被退役：docs/DESIGN-20260903-llm-agency-first-repair-optimization.md:31 记录了 PREFIX_LAYERED / CORE9 + keyword→full-schema 的分层 selector 同步退役，只保留稳定 schemas(lazy=True)——即"压缩说明文本，不改变可调用能力"。这是 LFL 自己走过的"缩小候选集"失败路径。
但同一份计划否决了另一半假设　docs/PLAN-20260925-execution-efficiency-fcr.md §P3 写得很直白："Only create weak/strong-model profiles if the frozen data proves a stable interaction. Do not assume in advance that strong models need less interface truth." 同文 §3 把"lazy schema 默认值仅由省 token 来辩护"列为被否决的优化目标；docs/ASSESS-20261008-project-audit.md:371 撤回了"直接释放约 50% 上下文"与"schema 完全无任务价值"两项承诺。也就是说：LFL 为弱模型保留详细信息，是有据的；但"强模型就可以少给"在 LFL 自己的记录里仍是未证假设。

这项对照实验设计过，还没跑：同一份计划定义了 P1A 三臂——A 现状 lazy/compact、B FCR 契约（承载性事实不按字数截断）、D 全量 schema 参考臂。对应目录 evals/execution_efficiency_fcr/ 目前只有 __pycache__，未见冻结结果。所以无论"详细更好"还是"精简更好"，现在能引用的都只有案例级实践，不是可复现的对照数据。

当前实现上还有一条缝，需要你裁决。 默认 tool_schema_lazy=True（config.py:489/:1073，启动脚本亦默认 1）会剥掉参数级说明，只留 type/enum/min/max/properties/required；compact 描述是人工精编、保留承载性事实，但每条只有一句。若"弱模型需要详细信息"是要贯彻的公理，本地部署应显式置 TOOL_SCHEMA_LAZY=0，让完整 schema 真正投递；否则实际生效的是"84 个工具全在场 + 骨架参数 + 一句精编描述"，与"加载详细的工具信息"还不是同一件事。

小结：这个取舍站得住，但要按部署前提表述，而不是当作通用优势——它的有效期与"运行的是弱模型"绑定。前提消失时（换成强模型），文章的路径重新成立。

4.8　跨轮次的事实一致性

文章主张（C4 的延伸）：子代理执行完就断开，主 Agent 后续轮次完全不知道细节；需要细节时只能重新派一个子代理，效率更低。

LFL 事实：LFL 有三层保真——Evidence（事实层，stable ref + 分页 + 摘要绑 SHA）、Task/Goal（进度层，checkpoint 四要素：发现/决策/验证/阻塞）、task_state（模型自写的目标/已核事实/未执行动作/未决问题）。跨会话还能靠 event_stream 与 list_evidence(scope=recovery) 恢复。

部分一致　LFL 保证的是事实可回查，不是推理可回查。子代理默认只回传结论与 ref，它"为什么得出这个结论"的中间判断（试过哪些路径、排除了哪些假设）不会自动留存。要拿到这些，得显式读 DSH 的 session 事件日志（dsh_session_read），而那只覆盖 DSH 子代理，不覆盖同进程的 spawn_subagent。

这正是文章那句"单 Agent 后续轮次完全不知道细节"的另一半真相：LFL 用证据层补上了"事实不知道"，但没有补上"理由不知道"。而"理由"在两类场景下是硬需求——出问题后的归因，以及判断某个旧结论是否仍然成立。

5　张力与残余风险（T1–T5）

这一章只写"对不上的地方"。五条里有三条是设计取向差异（不构成错误），两条是真实缺口（会带来可观察的代价）。每条都标明证据强度：已核＝有代码或回执；推演＝从机制推出、未实测。

T1　工具规模已越过文章阈值，LFL 反向选择全量在场——风险落在近义簇而非数量

证据强度：已核（数量）+ 推演（后果）

84 个具名工具，加上 MCP/插件后运行时目录为 80 余项。文章的经验阈值是 30–50，LFL 已知越线仍选择全量在场：这是本地弱模型前提下的主动取舍（4.7.1），因为弱模型不会去"发现"被隐藏的工具。因此真正该收敛的不是候选集数量，而是近义簇——让名字本身可判别，比让工具消失更安全。

后果是可推演的：模型在"要查什么"上不会错，但在"用哪个入口查"上容易错域——比如用 search_files 去搜已持久化的证据，或用 search_archive 去查当前会话。这类错误不会导致任务失败，但会产生一次无效调用与一次纠正，累积成可观的回合开销。本报告没有做 A/B 实测，因此这一条只作为"高置信度假设"提出，而不是结论。

T2　审查闸仍是 AI 审 AI，异构性只到"换模型"为止

证据强度：已核（机制）+ 未核（漏判率）

四道约束（异模型 / 只读 / 冻结 SHA / 一次性资格）解决的是"审查对象不对""回执可复用""被执行者叙述带偏"三类问题。没解决的是最根本的那类：两个模型可能共享同一种"看起来没问题"的判断偏好。审查者读到的是被审者写的文档，文档越是结构完整、措辞自信，审查者越可能给出 PASS——这与文章对"AI 审 AI"的担忧是同一件事，只是把"同一个模型"换成了"同一种审美"。

LFL 目前没有度量审查者的漏判率（无从度量，因为漏判只有在事后被人类发现时才可见），RULE-AI-28 也没有为不可逆动作保留强制的人类终审档位。这是设计选择，不是疏漏——但在"对外发布"这类无法撤回的动作上，缺一个"人在环上"的显式档位，代价可能很高。

T3　压缩的触发权在程序，不在模型

证据强度：已核（代码路径）+ 推演（后果）

容量契约（compact_ratio、compress_target_ratio、head_keep_ratio）由程序按预算计算，压缩时机由阈值决定，模型是被通知方，事后再用五问回执确认。文章说的"把压缩当主 Agent 的新任务"隐含了一层意思：由模型判断"现在该整理上下文了"——在即将超限之前主动把关键事实转成 evidence、把中间推理丢掉。

LFL 目前缺这一步。模型不能在"还剩 15% 预算"时主动请求压缩，只能在程序压缩后确认。后果是压缩从"策略"退化为"事件"：压缩点由预算曲线决定，而不是由任务结构决定——可能正好切在一个论证的中间。

T4　Evidence 解决传输损失，不解决采集损失

证据强度：已核（机制边界）

RULE-AI-25 让回传变成引用，主 Agent 可精确水合原文，这一步是对的。但引用机制有一个天然边界：它只能保证"存下来的可回查"，不能保证"该存的都存了"。子代理在采集阶段做的取舍（哪些段落进 evidence、哪些当噪音丢掉）不受任何机制约束，也没有事后复核的入口——因为被丢掉的东西不在任何 ref 里。

这不是 LFL 独有的问题，任何"采集—引用"架构都有。但 LFL 有独特的机会：它已经在 RULE-AI-25 里规定了回传格式，只要在该格式上再加一个字段，就能把不可见的取舍变成可见的声明。

T5　编排面工具偏多，与文章"只留一两个"的倾向相反

证据强度：已核（清单）

当前编排面工具共 11 个：spawn_subagent、agent_message、agent_followup、subagent_result、subagent_lease、subagent_topology、workflow_run、fix_loop、dsh_task、dsh_session_read、review_admission。文章的整体倾向是"只留一两个子代理原语"，LFL 保留了 11 个。

但保留的理由不是"角色分工"，而是四类互不重叠的用途：派发（spawn / workflow）、联络（message / followup）、观测（result / lease / topology）、专用编排（fix_loop / dsh_* / review_admission）。其中"观测"三项（subagent_result / subagent_lease / subagent_topology）语义高度相邻，都在回答"我的子代理现在怎么样了"，合并成一个带 action 参数的 subagent_status 是低风险收敛。

6　改进建议与验证方式

按"收益/风险"排序，每条给出可判真假的验收条件。P0 是缺口修复，P1 是风险收敛，P2 是可选优化。

P0-1　工具分层（仅限强模型部署）：常驻核心 + 可发现层，不引入任务路由

项内容
适用前提只有当会话主模型是能自行检索的强模型时成立。对当前对齐的本地弱模型，结论相反：不要做候选集收缩，应继续全量在场 + 把承载性事实写进契约（并可显式 TOOL_SCHEMA_LAZY=0）。判据不是"模型名字"，而是冻结 A/B 中该模型在"隐藏工具+可发现"下的绕路率与首调正确率是否变好。
动作在 ToolRegistry 上增加 tier 字段（core / discoverable）。schemas() 默认只投 core（建议 ≤30）；discoverable 层的工具仍全部注册、仍可调用，其完整定义经 get_tool_schema(name) 或 get_tool_schema('?关键词') 浮现。判定层级的是工具自身的稳定性/通用性，不是"当前任务需不需要它"。
为什么不违背 4.2程序不判断任务类型，只判断"这条工具属于常驻还是可发现"。路由仍由模型完成：它要先意识到"我需要一个不常见的工具"，再发起一次发现。这与文章"元数据 + 搜索"同构，但不把发现结果写死成路由表。
验收（可判真假）① 常驻层工具数 ≤30；② 现有测试全绿（schemas(lazy=True/False) 语义不变，仅默认集合变化）；③ 在同一组 20 个真实任务上做 A/B：工具误选（错域调用）次数下降 ≥30%，且任务完成率不下降；④ 前缀 token 体积下降 ≥50%；⑤ 强弱分层报告：强模型档达标即可采用，弱模型档若绕路率上升或首调正确率下降，则该部署维持全量在场，不启用分层。
风险"模型不知道某工具存在"导致绕路（用 execute_command 手搓）。缓解：可发现层在系统提示中保留一行"另有 N 个工具可按名发现"。验收项③需同时统计"绕路率"。

P0-2　近义工具收敛与命名判别化

项内容
动作五个 search_* 保留但重命名到可判别前缀（如 fs_search / evidence_search / archive_search / doc_search / record_search），或在 compact 描述首句统一加"数据域：本地文件系统 / 会话证据 / 归档 / 文档库 / 学习记录"。后者零迁移成本，优先做后者。
验收同一组任务上"错域调用"次数（调用返回可疑但非报错，如空结果后改用另一入口）下降 ≥50%；get_tool_schema('?search') 的输出能让模型在不看正文的情况下区分五者。
风险改名会破坏既有提示词与经验卡中的工具名引用。因此推荐先加描述域标签，改名作为后续独立变更单独评审。

P1-1　审查闸补"可证伪理由"，并为不可逆动作加人类终审档位

项内容
动作① 审查回执禁止裸 PASS：必须给出至少一条"我检查了什么、凭什么判断通过"的可证伪陈述，以及一条"我未能覆盖的部分"；② 为 article_publish 这类不可撤回动作增加 human_final 档位，由用户显式确认，不默认省略。
验收抽查 20 份审查回执：100% 含可证伪理由与未覆盖声明；裸 PASS 数为 0。人类终审档位在发表类动作上被触发的比例为 100%。
理由这两项都不提升"通过率"，只提升"通过的可信度"。对 T2 是对症下药，但仍是缓解——漏判率依然无法自证。

P1-2　子代理回传加"未采信但对结论有威胁的信息"字段

项内容
动作在 RULE-AI-25 的回传格式中增加一个可选字段：counter_signals——"我读到但未采信、且如果为真会改变结论"的信息，每条 ≤100 字符，附来源 ref。这正是对 T4 采集损失的直接对冲：它不保证不漏，但把"漏"变成了"声明的漏"。
验收抽查 20 次子代理回传：含该字段的比例 ≥80%；主 Agent 因该字段改变结论或追加验证的比例 ≥10%（低于此说明字段形同虚设，需重新设计）。
成本每次回传增加约 100–300 字符，仍远低于 RULE-AI-25 设定的正文禁入上限。

P1-3　观测类子代理工具合并

项内容
动作subagent_result / subagent_lease / subagent_topology 合并为 subagent_status(action=result|lease|topology, child_id=…)。三者都是只读观测，语义相邻，合并后候选集减少 2 个，且不影响任何写路径。
验收现有子代理相关测试全绿；spawn → status → followup 的典型链路调用次数不增加；迁移期内旧名保留别名（alias），别名调用计入 legacy 计数，30 天后归零再移除。

P2　可选优化

  • P2-1 让模型可以请求压缩：新增一个显式的"整理上下文"动作（或在 adjust_strategy 上开放 request_compaction），使压缩既能被阈值触发、也能被模型按任务结构触发；两者共用同一 manifest 与五问回执，避免出现两套压缩账本。
  • P2-2 并行收益的事后核对：RULE-AI-25 现在只要求事前写理由。可在编排结束后要求一行"实际收益"（并行省下的时间 / 合并返工的成本），沉淀成可检索记录，用于将来校准"≤3"这个档位。
  • P2-3 工具选择退化的可观测指标：从 tool_history 中统计三个比率——错域调用率、空结果后改投率、重复发现率。这三项是文章所说的"工具选择变差"的可观测代理，比"工具数量"更接近真实问题。
