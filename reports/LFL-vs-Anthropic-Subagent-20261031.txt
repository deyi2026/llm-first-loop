依据与含义
1
形态上高度一致
一致
LFL 就是"单一 Agent + 主循环"：核心循环
core/loop/engine.py
（2939 行）+ runner/lifecycle，README 明示"不是 Agent 框架：无 planner / router / SOP 阶段机"。代码中不存在意图分类器或规划器类。文章批评的"编排框架式多 Agent"，LFL 从设计上就没有采纳。
2
保留编排工具，但无角色 Agent
方向一致
LFL 有 11 个编排面工具（
spawn_subagent
、
workflow_run
、
fix_loop
、
dsh_task
等），但没有任何"研究员/写手/审稿人"式的角色化子代理；子代理按需创建、默认并行上限 3（RULE-AI-25 第 4 条）。这与文章"不要硬编码角色与交接边界"一致，差异在于工具颗粒度偏多（见 T5）。
3
审查闸是"保留并强化"，不是"照单全收"
部分一致
RULE-AI-28 保留独立审查子代理，但加了四道约束：异模型（GLM-5.3）、只读上下文、冻结真实产物 SHA、通过后签发一次性资格。这比文章的"少数场景可保留"更进一步，但本质仍是 AI 审 AI，同构偏见只被削弱、未被消除（T2）。
4
工具全量在场，是有意的弱模型取舍
取向差异
文章主张工具定义超过 30–50 个后应改为"元数据 + 按需搜索"。LFL 反其道：84 个工具全部在场，注册表注释写明"这不是路由表"。理由是目标部署为本地弱模型——候选集一旦收缩，弱模型不会去"搜"，只会绕路或误判，而详细契约能直接降低错选与错参。代价是前缀体积与选择噪声，且该取舍的收益目前只有案例级实践、没有冻结 A/B（见 4.7.1）。强模型部署下应重新评估（P0-1 已改为条件化）。
5
压缩治理比文章建议更工程化
超越
文章说"该做的是压缩上下文，把它当主 Agent 的新任务"。LFL 不仅在主循环内压缩，还配了压缩恢复门：零丢失归档 + 不可变 manifest（sha256）+ 强制五问回执 + 重放防护。压缩从"有损操作"变成"可审计、可回溯的事件"。
一句话总评
文章主张"把能力还给主循环"，LFL 在实践中走得更远——它没有只做减法，而是把过去由编排层承担的职责（校验、压缩、事实留存、授权）下沉成了主循环内的机制与规则。唯一被文章点中、而 LFL
明确反向选择
的是工具界面：84 个工具全量在场、不做检索式发现。这是针对本地弱模型的刻意取舍（详见 4.7.1），不是遗漏；它的有效期与"运行弱模型"这一前提绑定，换成强模型时需要重新评估。

把转述文的核心论点拆成七条可检验的命题。第三列写的是"这条主张若要被证伪，需要什么样的观测"——这样对比才不会退化成观点对观点的互相印证。
编号
主张
可证伪形式（需要什么观测才能推翻它）
C1
单一 Agent + Main Loop 应优于多 Agent 编排框架
在同质任务集上，编排框架的完成率与单位任务成本不劣于单循环，且失败模式更少。
C2
"角色分工 + 交接"型子代理失效：路由本质就是工具选择，应由模型判断而非硬编码
固定角色分工在长期运行中带来可度量的收益（交接开销被抵消），且硬编码路由的错误率低于模型自选。
C3
构建者—验收者只在"自我确认风险真实且危害大"时保留；且"AI 审 AI"存在同构偏见
同模型自审漏判率与异模型审核无显著差异；或自我确认造成的损失在多数任务中可忽略。
C4
上下文收集型子代理造成信息损失：核心问题会被当细节滤掉，主 Agent 只拿到二手信息
子代理回传摘要在下游决策中与原始材料等价（关键信息召回率无差异）；或主 Agent 事后回查原文的成本可忽略。
C5
并行只在上下文互不相交时成立；调研型任务的并行收益小、合并成本高
调研型并行任务在合并阶段的返工成本低于串行执行节省的时间。
C6
把子代理当作上下文裁剪手段是反模式；正解是在主 Agent 内压缩上下文
"上下文超限就外派"的任务在质量与一致性上不劣于"主循环内压缩后继续"。
C7
三问判据：产物能否纯丢弃？上下文分支是否互不相交？是否确实并行？
存在大量不满足三问却仍从子代理获益的稳定任务类型。
转述中未出现、但对 LFL 最相关的一点
：文章讨论的是"
要不要用子代理
"，而 LFL 的实际问题已经推进到"

4.1　架构形态：单循环而非编排框架
文章主张（C1）
：单一 Agent 加主循环，比"给 LLM 套一个显式 workflow 的编排框架"更接近 LLM 的真实工作方式；多 Agent 编排有同类问题。
LFL 事实
：README 的原话是"AI 优先的 Agent 运行时 Harness，而不是 Agent 框架：没有 planner、没有 router、没有 SOP 阶段机、没有 Prompt 模板阶段机。单主循环就是唯一决策主体。"代码侧的印证是：核心循环
engine.py
2939 行承载全部决策推进，
core/loop/
下的 build / runner / lifecycle / events 都是循环的支撑件，而不是"阶段"。全库检索不到 Router、Planner、intent classifier 类。
一致
这不是"部分相似"，而是同一设计哲学的两处独立表述。LFL 的规则体系里还有一条对应的元规则：程序只提供工具与运行环境，
不替模型制定任务策略或完成裁决
（系统提示的 llm-first-loop 段）。文章说"路由本质上是工具选择，应该交给模型"，LFL 说"程序不替 AI 决策"——同一件事，一个从 Agent 结构说，一个从程序职责说。
一个容易被忽略的差别
文章批评的"框架"指的是
编排结构
（角色、阶段、交接）；LFL 里虽然也有大量"框架性"设施（工具契约、规则、证据层、任务图），但它们的职责是
地面设施
——保证事实可核、动作可审、越权可拦，而不是替模型决定下一步做什么。这个区分很重要：前者会侵蚀模型判断，后者只约束模型的行为边界。
4.2　角色分工与路由
文章主张（C2）
：Coordinator + 专业 Agent + 交接的写法看似合理，实则把"该由模型做的路由决策"硬编码成了结构；早期工具选择本身就是路由，硬编码子 Agent 反而制造了交接边界。
LFL 事实
：LFL 没有任何角色化子代理——没有"研究员""写手""审稿人"这类预置角色。子代理的出现只有三种触发：显式并行派发（
spawn_subagent
/
workflow_run
）、修复循环（
fix_loop
）、独立审查（
review_admission
）。
spawn_subagent
的 compact 描述第一句就是"非阻塞启动隔离子代理并返回 child_id；父代理可继续当前 run"——它的定位是
并行执行单元
，不是
角色
。子代理的模型、工具、上下文由调用方显式声明，没有任何"按角色加载预设"的机制。
一致
但这里有一个必须说清的转移：文章说"路由就是工具选择"，那么当工具数量达到 84 个时，路由的压力并没有消失，只是
从结构层转移到了工具选择层
。LFL 保留全量候选、只压缩单条定义的体积，是有意的弱模型取舍（见 4.7.1）；代价是候选集大小不变，噪声靠"名字可判别 + 描述带机械事实"来压，而不是靠隐藏。
4.3　构建者—验收者
文章主张（C3）
：这是少数仍值得保留的子代理模式，但前提是"自我确认的风险真实存在且危害大"（代码、对外内容）；而且"AI 审 AI"存在同构偏见——同一个模型审自己或同族模型审自己，容易得出同向的错误结论。
LFL 事实
：RULE-AI-28 规定的三类动作（全量测试、git push、文章发表）必须经过独立审查子代理，且约束是四层：
异模型
：审查者固定为 GLM-5.3，与被审会话的模型不同厂；
只读上下文
：审查者不继承执行者的对话历史，只看冻结的产物；
冻结产物
：以真实产物的 SHA 为审查目标，"正文 PASS / 旧回执 / 不同目标均不能放行"；
一次性资格
：通过后在内存中签发一次性资格，不能复用、不能跨目标。
部分一致
LFL 的做法可以理解为对文章顾虑的逐条回应：异模型回应"同构"，只读上下文回应"被执行者的叙述带偏"，冻结 SHA 回应"审的不是要发的东西"，一次性资格回应"回执复用"。四条加起来，把"AI 审 AI"从"同族模型互相点头"改造成了"两个不相干的模型对同一份冻结产物各自表态"。
但残余风险没有消除
：异模型不等于异构偏见。两个模型可能共享同一批训练语料、同一种"看起来很完备"的审美偏好，对同一类缺陷同时失明。审查者读到的仍然是被审者产出的文本，如果产物在结构上完整、在措辞上自信，审查者被说服的概率并不低。LFL 目前没有对"审查者自身的漏判率"做度量，也没有在 RULE-AI-28 中为不可逆动作保留人类终审的强制档位（
review_admission
之外的人工确认是场景性的，不是规则性的）。这是 T2 的内容。
与文章的一处实质分歧
文章倾向于"尽量不要 AI 审 AI"；LFL 的选择是"保留，但把审查条件收紧到可审计"。这不是谁对谁错：在没有人可以随时在场的运行环境里，"有约束的机器审查"优于"无审查"；但在有人在场的场景里，把人排除在终审之外是浪费。合理的做法是分档——把"人类终审"作为不可逆动作的一个可选档位显式化，而不是默认省略。
4.4　上下文收集型子代理
文章主张（C4）
：让子代理去读文档、再把摘要交回来，会造成信息损失——子代理压缩时会把"它认为不重要"的东西滤掉，而核心问题常常被当成不重要的细节；主 Agent 拿到的是二手信息，后续多轮再传更低效。
LFL 事实
：RULE-AI-25 把回传方式写成了硬纪律："中间产物的正文不进入编排者上下文。编排者的注意力预算是全局资源，回传默认只携带：结论（一句话）、stable evidence_ref / artifact ref、可选短摘要（≤200 字符）。正文消费走引用+分页。"机制侧的三件套是：Evidence 持久化（
evidence://v1/...
稳定引用）、分页投影（
read_evidence
每次最多 4000 字符，带
next_start
）、摘要绑定（
source_synopsis
绑定源 SHA，摘要不可与源版本脱钩）。
部分一致
这里需要把两种"损失"分开看，否则会误判：
损失类型
文章批评的
LFL 的机制与效果
传输损失
回传时被压缩掉的信息
子代理写摘要 → 主 Agent 只看到摘要
已被消除
。回传的是 ref，不是摘要；主 Agent 需要时可分页水合原文，甚至逐字回读。
source_synopsis
还把摘要与源 SHA 绑定，摘要无法悄悄过期。
采集损失
根本没被存下来的信息
子代理判断"什么重要"，判断错就永久丢失
未被解决
。Evidence 只保证"存下来的可精确回查"，不保证"该存的都存了"。如果子代理读文档时把一段关键限定当噪音略过，主 Agent 事后无论怎么水合都找不到它。
本报告自身就是一个可用的观察样本：文章正文先经
web_fetch
落为 evidence，再由我按 4000 字符分页读取（原文约 1.1 万字符，读了 3 页）；如果我当时只让某个子代理"总结一下这篇文章"，那么"三问判据""反模式"这些段落是否会被保留，就取决于它的判断，而我现在无法复核它漏了什么——因为漏掉的东西不会进 evidence。传输损失可以靠机制解决，采集损失只能靠
采集时的纪律
。
4.5　并行
文章主张（C5）
：并行的成立条件是上下文互不相交；代码类任务可以并行，调研类任务并行收益小、合并成本高，且事后的假设很难拆分验证。
LFL 事实
：RULE-AI-25 第 4 条把并行规模写成"默认 ≤3；超过需在编排时写明理由（必要性/收益）"，并明确"用户明示深度/全面类要求时可直接进入重档"。工具侧有
workflow_run
（parallel / pipeline / dag 三种拓扑）、
spawn_subagent
（非阻塞，父代理继续当前 run）、
dsh_task
（进程级子代理，独立工具链与工作区）。
一致
"默认 ≤3"是相当保守的档位，与文章"调研型并行收益小"的判断同向。值得单独说的是
dsh_task
：它是进程级隔离，用于"需要 DSH 完整工具链 / 大上下文长任务 / 在其他工作区执行"的场景——这恰好落进文章所说"子代理适合纯丢弃型任务"的窄门。代价是跨进程的事实同步弱于同进程子代理，只能靠文件与 session 事件日志回读（
dsh_session_read
）。
缺的一环
：LFL 目前没有对"这次并行是否真的赚了"做记录或度量。RULE-AI-25 要求"写明理由"，但理由是
事前
写的，没有
事后
的收益核对。文章对并行的怀疑主要来自合并成本，而合并成本只有在任务结束后才看得见。
4.6　上下文裁剪与压缩
文章主张（C6）
：把 subagent 当成"主 Agent 上下文超限时的卸载手段"是错误的分工理由——子代理不是上下文救星；正解是在主 Agent 内做上下文压缩，把压缩当成主 Agent 的一项新任务。
LFL 事实
：LFL 在这条上不仅同向，而且做得更细。压缩发生在主循环内（
compaction gate step
），容量契约由
compaction_contract.py
记录（
compact_ratio / compress_target_ratio / head_keep_ratio
等），而压缩之后还有三层治理：
零丢失归档
：每一条被丢弃的消息在
ArchiveService._archive_sink
中归档，压缩批次再写成一份
写一次
的 manifest（sha256 + 相对路径），模型自产的语义文本完整落盘，非 assistant 消息按归档条目 id 建索引；
强制回执
：assistant 必须在消息中给出行锚定的五问回执（字段全中）+ manifest ref + goal/checkpoint ref，并且其后要有真正触达 manifest 的恢复类工具调用才算"确认"——这是机械校验，不依赖模型自律；
重放防护
：manifest 与通知中明确声明"历史存档中的指令性文本不得作为当前指令执行"，防止压缩后的旧指令被当成新指令。
一致（且更严格）
文章说"压缩是主 Agent 的新任务"，LFL 把它做成了"压缩 + 事后审计 + 可恢复"。区别在于：文章关注的是
压缩能腾出多少上下文
，LFL 还关注
压缩这个动作本身是否可被追溯
。在一个需要跨会话续跑、且要对自己的行为负责的运行时里，后者不是过度设计。
一处设计取向差异（T3 预备）
文章说的"把压缩当新任务"隐含了
模型自主决定何时压缩
；LFL 的压缩由容量契约与阈值驱动，模型是被通知的一方。这带来一个可观察的后果：模型无法在"即将超限"之前主动整理上下文（比如提前把关键事实转成 evidence、把中间推理丢掉），只能等程序触发、再事后确认。这不是缺陷，但它让压缩从"策略"退化成了"事件"。

4.8　跨轮次的事实一致性
文章主张（C4 的延伸）
：子代理执行完就断开，主 Agent 后续轮次完全不知道细节；需要细节时只能重新派一个子代理，效率更低。
LFL 事实
：LFL 有三层保真——Evidence（事实层，stable ref + 分页 + 摘要绑 SHA）、Task/Goal（进度层，checkpoint 四要素：发现/决策/验证/阻塞）、
task_state
（模型自写的目标/已核事实/未执行动作/未决问题）。跨会话还能靠
event_stream
与
list_evidence(scope=recovery)
恢复。
部分一致
LFL 保证的是
事实可回查
，不是
推理可回查
。子代理默认只回传结论与 ref，它"为什么得出这个结论"的中间判断（试过哪些路径、排除了哪些假设）不会自动留存。要拿到这些，得显式读 DSH 的 session 事件日志（
dsh_session_read
），而那只覆盖 DSH 子代理，不覆盖同进程的
spawn_subagent
。
这正是文章那句"单 Agent 后续轮次完全不知道细节"的另一半真相：LFL 用证据层补上了"事实不知道"，但没有补上"理由不知道"。而"理由"在两类场景下是硬需求——出问题后的归因，以及判断某个旧结论是否仍然成立。
5　张力与残余风险（T1–T5）
这一章只写"对不上的地方"。五条里有三条是设计取向差异（不构成错误），两条是真实缺口（会带来可观察的代价）。每条都标明证据强度：
已核
＝有代码或回执；
推演
＝从机制推出、未实测。
T1　工具规模已越过文章阈值，LFL 反向选择全量在场——风险落在近义簇而非数量
证据强度：已核（数量）+ 推演（后果）
84 个具名工具，加上 MCP/插件后运行时目录为 80 余项。文章的经验阈值是 30–50，LFL 已知越线仍选择全量在场：这是本地弱模型前提下的主动取舍（4.7.1），因为弱模型不会去"发现"被隐藏的工具。因此真正该收敛的不是候选集数量，而是
近义簇
——让名字本身可判别，比让工具消失更安全。
后果是可推演的：模型在"要查什么"上不会错，但在"用哪个入口查"上容易错域——比如用
search_files
去搜已持久化的证据，或用
search_archive
去查当前会话。这类错误不会导致任务失败，但会产生一次无效调用与一次纠正，累积成可观的回合开销。
本报告没有做 A/B 实测
，因此这一条只作为"高置信度假设"提出，而不是结论。
T2　审查闸仍是 AI 审 AI，异构性只到"换模型"为止
证据强度：已核（机制）+ 未核（漏判率）
四道约束（异模型 / 只读 / 冻结 SHA / 一次性资格）解决的是"审查对象不对""回执可复用""被执行者叙述带偏"三类问题。没解决的是最根本的那类：
两个模型可能共享同一种"看起来没问题"的判断偏好
。审查者读到的是被审者写的文档，文档越是结构完整、措辞自信，审查者越可能给出 PASS——这与文章对"AI 审 AI"的担忧是同一件事，只是把"同一个模型"换成了"同一种审美"。
LFL 目前没有度量审查者的漏判率（无从度量，因为漏判只有在事后被人类发现时才可见），RULE-AI-28 也没有为不可逆动作保留强制的人类终审档位。这是设计选择，不是疏漏——但在"对外发布"这类无法撤回的动作上，缺一个"人在环上"的显式档位，代价可能很高。
T3　压缩的触发权在程序，不在模型
证据强度：已核（代码路径）+ 推演（后果）
容量契约（
compact_ratio
、
compress_target_ratio
、
head_keep_ratio
）由程序按预算计算，压缩时机由阈值决定，模型是被通知方，事后再用五问回执确认。文章说的"把压缩当主 Agent 的新任务"隐含了一层意思：
由模型判断"现在该整理上下文了"
——在即将超限之前主动把关键事实转成 evidence、把中间推理丢掉。
LFL 目前缺这一步。模型不能在"还剩 15% 预算"时主动请求压缩，只能在程序压缩后确认。后果是压缩从"策略"退化为"事件"：压缩点由预算曲线决定，而不是由任务结构决定——可能正好切在一个论证的中间。
T4　Evidence 解决传输损失，不解决采集损失
证据强度：已核（机制边界）
RULE-AI-25 让回传变成引用，主 Agent 可精确水合原文，这一步是对的。但引用机制有一个天然边界：
它只能保证"存下来的可回查"，不能保证"该存的都存了"
。子代理在采集阶段做的取舍（哪些段落进 evidence、哪些当噪音丢掉）不受任何机制约束，也没有事后复核的入口——因为被丢掉的东西不在任何 ref 里。
这不是 LFL 独有的问题，任何"采集—引用"架构都有。但 LFL 有独特的机会：它已经在 RULE-AI-25 里规定了回传格式，只要在该格式上再加一个字段，就能把不可见的取舍变成可见的声明。
